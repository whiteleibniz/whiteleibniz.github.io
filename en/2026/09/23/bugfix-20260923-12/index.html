GBA Exit Logic Aligned with FC

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_12 — GBA exit logic changed to be line-by-line identical with FC (removing GBA-specific branches)

Item Content
Discovery time 2026-09-23
Fix time 2026-09-23
Module lv_pages/gba_game_page.c
Versions involved Taking over the site after bugfix_20260923_11 (front ends already separated)
Severity level Medium (no new fault; a convergent fix that “eliminates structural divergence”)
Trigger The user explicitly requested: “change the GBA one to FC’s exit logic”

1. Problem symptoms

After the front-end separation (bugfix_20260923_11), although GBA and FC each use a separate binary, the exit logic is still not the same set:
the GBA page retains an “early release” path that the FC page does not have (the exiting flag + a background reaping thread + refreshing 3 frames in a row).

This path is where problems repeatedly occurred across the three rounds of failures 09→10→11. The user judged from this that “the logic on the two sides is mixed together, making exits inexplicable”, and asked to change GBA’s exit logic directly to the FC one.

The user’s judgment is correct: the FC set is the only exit path that has been long-term verified on the real machine; none of the “improved versions” currently has a credible verification basis.

2. Scope of impact

  • lv_pages/gba_game_page.c: the exit path (gba_wait_thread / gba_exit_to_list / gba_timer_cb / state struct).
  • miniretro_gba (the front-end binary) is not touched, and the FC page is not touched (the FC page stays as-is, not a single line changed).
  • At the structural level: eliminating “artificial differences between isomorphic components” — the differences themselves are where subsequent faults hide.

3. Root cause analysis

3.1 The four differences before the fix (GBA’s extra complexity relative to FC)

# Difference FC page GBA page (before fix)
1 Waiting criterion Blocking waitpid, recognizing only “the child process really disappeared” 5ms polling, recognizing the exiting flag or the child process disappearing
2 Exit function side effects Only SIGTERM → 120ms → SIGKILL Additionally sets s_gba.exiting = true
3 Reaping fallback None (blocking necessarily gets the corpse) gba_reap_bg() independent background thread
4 Picture recovery lv_obj_invalidate() ×1 invalidate() + for(3) lv_refr_now()

3.2 Why these four differences are risks

  • Difference 1 is the same lesion behind the three rounds of hangs/black-screen hangs in 09/10/11. As long as non-hard events such as “flags” or “time caps” appear in the waiting criterion, there is a possibility of “judging a still-running game as already exited”, with the consequences fixed as two: ① hardware_keys_set_interceptor(NULL) removes the key interceptor → the exit key stops working and the game can never be exited again; ② app_runtime_set_lvgl_paused(false) lets LVGL grab back fb0 → overwriting the still-running game. The difference between the two historical versions is only “the trigger condition for the misjudgment” (time cap / flag being read); the essence is the same source.
  • Differences 3 and 4 are patches for the timing problem of difference 1. Early release means “the flag is consumed but the child process is still touching fb0”, so refreshing 3 frames in a row to grab the picture and opening a separate thread to reap become unavoidable. After changing back to the hard-event criterion, these two patches no longer have any reason to exist, and keeping them is an extra failure surface instead.
  • Structural reason: the FC page’s logic has been long-term verified on the real machine; the GBA page carries a “found only here” path. The same design intent is written differently in two places, making it easy for any future change to modify only one side — this is exactly a re-run of the kind of problem in document 11 where “the shared binary gets broken”, just shifted from “a shared artifact” to “shared semantics, separate implementations”.

3.3 The trade-off of the cost (explicitly accepted)

The only cost of the FC set is: recovering the UI requires waiting for the kernel to reclaim the evdev fd, measured at about 455ms from signal to reaping complete (of which the child process’s internal cleanup is ~34ms and the rest is the kernel’s inherent overhead). Rounds 09 and 10 are exactly the failures that occurred while trying to “save those few hundred milliseconds”.

This change explicitly chooses to bear that ~400ms in exchange for “GBA and FC behaving line-by-line identically”. Reasons:

  • A 455ms flash of black screen feels to the user like “a pause on exit”, which is acceptable;
  • Compared with “occasional freezes, the exit key failing, and only a restart recovering”, this cost is far smaller;
  • The verifiability brought by consistency > the performance gain of a few hundred milliseconds.

4. Fix

Principle: the GBA page’s exit path copies the FC page exactly, with no dedicated branches.

4.1 gba_wait_thread() changed to a blocking waitpid

Safety basis: the upstream gba_exit_to_list() guarantees that a SIGKILL is necessarily added 120ms after SIGTERM,
and SIGKILL is uncatchable ⇒ the child process necessarily ends ⇒ the blocking waitpid necessarily returns, so there is no indefinite waiting.

4.2 gba_exit_to_list() removes early release

4.3 Delete the gba_reap_bg() background reaping thread

A blocking waitpid necessarily gets the corpse, so the fallback thread has no reason to exist. Deleting it also eliminates the race space where “two pieces of code both assign child_pid“.

4.4 Remove the exiting field from the state struct

The exiting in gba_state_t and its reset in gba_launch() are both deleted, returning the field layout to alignment with fc_state_t.

4.5 gba_timer_cb() picture recovery returns to a single invalidate

4.6 Rewrite the file header comment

Change the narrative of “we are faster than FC” to “deliberately identical with FC, and explain why speed is no longer pursued“,
while leaving the two failed schemes (the SIGUSR1 handshake / time cap) in the comments as counter-examples, preventing successors from walking the same path again.

5. Verification method and results

5.1 Code consistency check (local)

  • grep -n "exiting\|reaped\|reap_bg\|lv_refr_now\|SIGUSR1\|RELEASE_SIGNAL" →
    only comment content is matched, with no code residue whatsoever;
  • gba_wait_thread() compared line by line with fc_wait_thread() → structure, criterion, recovery order, and sequential comments are all identical,
    differing only in the s_gba / s_fc prefixes and indentation.

5.2 Build and deployment (device side)

ssh_tools/gba_redeploy.py (without --mini, only deploying the page + compiling + restarting):

Check item Result
make -j2 MAKE_RC=0, error: count = 0
Binary replacement ATOMIC_OK (compiled to .tmp then mv -f, atomic)
Games running before deployment None
Processes after restart lvgl_demo ×1 + lvgl_watchdog ×1, single instance, no zombies

5.3 Real-machine functional verification (handed to the user)

  1. Desktop → GBA Games → select ROM → confirm, entering the game;
  2. Press the 买单 (pay-the-bill) key to exit → expect about half a second of black-screen flash before returning to the game list, with the exit key effective throughout;
  3. Enter the game and stay for more than 5 seconds before exiting (key point: verify there is no longer “misjudgment after running for N seconds”) → the behavior should be the same as step 2;
  4. Enter once more and play normally for a while → exit, confirming there is no residual black screen and the list remains operable;
  5. Compare with FC games: enter → exit; the behavior should match GBA’s (both are “a half-second black-screen flash”).

6. Regression risks

Risk Assessment
Exit is about 400ms slower than the previous version Explicitly accepted; this is the inevitable cost of aligning with FC, and it is the only verified timing
Whether a single invalidate is enough The FC page likewise only calls invalidate once and has long been normal; the recovery timing is now identical to FC’s, so it is judged sufficient. If “residual game picture after exit” occurs on the real machine, it means GBA’s fb cleanup differs from FC’s, and the investigation should start from fb_restore() in miniretro_gba, not by adding more refreshes
Whether a blocking waitpid waits indefinitely No: SIGKILL is uncatchable and the upstream necessarily sends it
The extreme branch of pthread_create failing In that branch (inside gba_launch), it is waitpid(pid, NULL, 0) and no kill first, which in theory blocks until the game ends on its own. The FC page has exactly the same pattern; to maintain line-by-line identity it was not changed this time; it is an extremely low-probability path, and if it needs fixing, both sides should be fixed simultaneously
FC page Not a single line changed this time

Appendix: one correction to the deployment script

gba_redeploy.py originally used ps -o pid,args | grep 'lvgl_demo' to get the PID and then kill -9.
That command runs via sh -c, and the command line of the carrying shell itself contains the string lvgl_demo →
it is matched by grep → kills itself → the SSH connection is reset (the previous deployment round was disconnected here).
It is now changed to ps -o pid,comm | awk '$2=="lvgl_demo"{print $1}': comm is the process name (without arguments),
so the carrying shell’s comm is sh and does not self-match. The miniretro series switches to $2 ~ /^miniretro/ prefix matching.
