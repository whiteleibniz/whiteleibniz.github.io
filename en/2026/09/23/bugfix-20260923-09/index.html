Stutter When Exiting a GBA Game Back to the List

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_09 — Stutter when exiting a GBA game back to the list (the kernel reclaims input device fds extremely slowly)

  • Date: 2026-09-23
  • Module: GBA game page exit path / extern/miniretro/miniretro.c / kernel input subsystem
  • Impact: The response speed of exiting a GBA game back to the list (FC page shares miniretro, theoretically equally slow but not changed this time); also includes a zombie process problem of “not reaped after a forced kill fallback”

Difference from bugfix_07: 07 fixed “the picture freezes / leaves residue after exit” (the fb stays on the flipped page).
This one fixes “the picture comes back slowly“, which still exists after 07 — pressing the 买单 (pay-the-bill) key takes about 0.35~0.4 seconds to return to the list.

1. Problem symptoms

Press the 买单 key (116) to exit the game; the picture is no longer the game picture, but the list takes about 0.35~0.4 seconds to appear, which feels like “a stutter”. User feedback: “exiting the game back to the list still stutters”.

2. Scope of impact

  • GBA game exit back to the list (fixed this time)
  • FC game exit (shares the same miniretro, theoretically equally slow; FC page unchanged, behavior unchanged)
  • Fixed along the way: a child process left unreaped after one SIGKILL fallback → became a zombie under lvgl_demo

3. Root cause analysis

Measured with 2ms-granularity sampling + segmented timing added in the miniretro exit path (ssh_tools/gba_exit_latency.py):

Reproduced device by device (miniretro is not needed; opening/closing alone reproduces it):

Device Node Driver close() time
Physical four keys /dev/input/event0 sprd-gpio-keys 39 ~ 215 ms
Another set of keys /dev/input/event1 sprd-eic-keys ~80 ms
Headset key /dev/input/event2 headset-keyboard ~80 ms

Conclusions:

  1. The child process’s internal cleanup is not the bottleneck (deinit/pan/screen clear total about 30ms).
  2. This machine’s kernel takes a fixed tens to hundreds of milliseconds to close sprd input devices. When a process exits, the kernel must close these fds, and no user-space change can avoid it — so “the child process actually disappearing” takes at least ~340ms.
  3. There are also two segments of idle waiting on the parent side:
    • the usleep(250ms) hard wait inside gba_exit_to_list();
    • gba_wait_thread() uses a blocking waitpid to wait for the child process to “actually disappear” (= after that 340ms in the kernel) before resuming LVGL.
  4. The two segments add up → about 0.35~0.4s. The stutter is not a rendering problem; it is “waiting for an unnecessary event”.

4. Fix

Core idea: UI recovery no longer waits for the child process to die; instead, the child process actively notifies the parent process at the moment “the picture has been handed back”.

miniretro side (child process)

  • The cleanup order is fixed as: core_deinit() (must be kept; mGBA persists the battery save .sav here) → fb_restore() (flip back to page 0 + clear the screen, about 35ms) → notify_parent_ui_released() → _exit(0).
  • notify_parent_ui_released(): sends SIGUSR1 to the parent process.
    It must be explicitly enabled by the parent process via the environment variable MINIRETRO_UI_RELEASE_SIGNAL before it is sent — the default action of SIGUSR1 is to terminate the process, so any caller without a handler installed (such as the FC page) would be killed upon receiving it.
  • After _exit(0), no more individual close(fd)/munmap: the kernel has to do it on exit anyway, and those 340ms are pushed to the background, not blocking the UI.

Page side (lv_pages/gba_game_page.c)

  • gba_launch(): install signal(SIGUSR1, gba_ui_release_handler) + setenv("MINIRETRO_UI_RELEASE_SIGNAL","1",1) before fork (this must happen before fork, otherwise the signal may arrive first → the default action kills the process).
  • gba_exit_to_list(): only kill(pid, SIGTERM), with no waiting at all.
  • gba_wait_thread() has two phases:
    • Phase ① waits with 5ms granularity for “SIGUSR1 received or the child process actually exiting” (≤500ms fallback); as soon as either is satisfied, call hardware_keys_set_grab(true) → remove the interceptor → app_runtime_set_lvgl_paused(false);
    • Phase ② background reaping: after a 5s timeout, SIGKILL and synchronously waitpid to reap it.
  • Keep the millisecond timing [miniretro][timing] logs for direct reference next time a regression occurs.

5. Verification method and results

① Exit latency comparison (controlled measurement)

Metric Before fix After fix
Child process internal cleanup 385 ms 37 ms
Parent process receives “picture handed back” — 40.6 ms
Child process actually disappears (kernel reclamation) 394 ms 337 ms (already unrelated to the UI)

② Handshake protocol verification (ssh_tools/gba_ui_release_test.py, a Python pseudo parent process, no physical key presses needed)

③ Whether recovery is “instantaneous”: lv_tick_inc() executes unconditionally in the main loop (main.c:635), so LVGL time keeps running during the pause, meaning the 100ms timer has long expired after recovery and the first lv_timer_handler() triggers a full-screen redraw; the main loop ticks every 10ms. That is, the recovery path has no extra waiting.

Expected feel: press 买单 → hand back the picture in 40ms → immediately redraw the list (previously 0.350.4s).

6. Regression risks

  • The child process neither notifies nor exits: after 500ms in phase ①, the UI still recovers, degrading to the old behavior without hanging; in phase ②, force-kill and reap after 5s.
  • During the child process’s exit (0.30.4s), it still holds the fds of fb0/evdev (the kernel is reclaiming them), but it no longer draws and does not affect LVGL (LVGL holds fb0 itself; yoffset is a device-level state).
  • FC page unchanged: exiting still waits for the child process to disappear (~340ms). To speed it up as well, move the three page-side changes above to fc_game_page.c (the miniretro side is ready, and the signal gate is off by default).
  • Deployment discipline (pitfall stepped on this time): extern/miniretro/build.sh is gcc ... -o miniretro, writing the target file directly. When recompiling while the user is playing, a launch action happens to exec into the half-overwritten binary → the child process hangs inside exec, startup fails, and after 2.5s it is force-killed by the fallback and left unreaped (zombie).
    The unified requirement now is: binaries must always be “compiled to *.tmp → mv -f atomic replacement”, with deployment going through ssh_tools/gba_redeploy.py.
