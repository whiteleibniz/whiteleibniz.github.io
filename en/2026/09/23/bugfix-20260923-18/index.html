GBA intermittently leaves the game picture on exit: forced page flip

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_18 — GBA intermittently leaves the game picture after exit (forced page flip)

  • Date: 2026-09-23
  • Symptom: after exiting a GBA game, the screen sometimes still shows “the game picture at the moment of exit”, and the UI does not come back; it does not always happen — the same operation sometimes returns to the game list normally, and sometimes stays frozen on the game picture.
  • Affected scope: lv_pages/gba_game_page.c (only this one file is changed; the frontend is untouched)
  • Does it affect FC: No (the FC frontend does not flip pages and has no concept of pages)
  • Relationship to document 14: document 14 treated “always hangs after exit” (adding the gba_reset_fb_page() fallback); document 18 treats the intermittency that this very fallback introduced — it carries a precondition check that should not be there.

1. Background: who draws which page

The device framebuffer has 3 virtual pages (yres_virtual = 3840 = 3 × 1280).

Who How it uses fb0
LVGL (lv_linux_fbdev) Draws only at the mmap base address = always writes page 0; yoffset is not changed after initialization, and there are zero occurrences of FBIOPAN_DISPLAY in the source
GBA frontend (miniretro_gba) Uses FBIOPAN_DISPLAY double-buffered page flipping to eliminate tearing → the foreground page alternates between pages 0/1

Inference: if the foreground page stops on page 1 at exit, whatever LVGL draws is invisible → the screen stays frozen on the game picture. Document 14 was localized on this inference, and a gba_reset_fb_page() fallback was added on the parent process side.

2. Root cause: that “harmless-looking” precondition check in the fallback

The fallback added in document 14 is implemented with a condition:

The basis for the judgment at the time was “this driver’s yoffset read-back was measured to be reliable”. The problem this round: even if that statement holds, it is not enough to support this check — because it also implicitly assumes:

“read-back yoffset == 0“ is equivalent to “the scan output is reading page 0”

yoffset is only the driver’s internal bookkeeping value (the request parameter for the next pan); it does not guarantee being equal to the page the scan output (scanner / LCDC) is currently reading. Once the two disagree:

  • The screen actually displays page 1 (the game picture);
  • The read-back yoffset is 0;
  • The check evaluates false → the entire page flip is skipped → residue.

Whether “the two agree” depends on the driver’s internal state at the moment of exit (how the previous frame was committed, which beat the SIGKILL landed on), and is independent of the code path — which explains exactly what the user said: “it does not always happen“.

In other words: document 14’s fallback turned “always hangs” into “occasionally hangs”.
It only fails when “the read-back happens to be untrustworthy”, so it looks random.

Second latent hazard: the page flip and the full-screen repaint are in two execution flows (the former in the reaping thread, the latter queued to the main thread by lv_async_call). These are two halves of the same visual transaction, and any interruption in between (the callback being swallowed, the page being destroyed first, the main loop missing that beat) leaves the intermediate state of “flipped back but not repainted” or “repainted but the foreground page is still page 1”, each of which manifests as the picture not coming back.

3. Fix (one file, 4 changes)

All in lv_pages/gba_game_page.c.

3.1 gba_reset_fb_page() — remove the check, unconditionally flip the page (core)

Key difference: GET is used only once — to obtain a complete, valid fb_var_screeninfo as the base; it never participates in the decision of “whether to flip the page”. The page-flip request is sent every time.

3.2 gba_repaint_async() — the page flip and the repaint on the same beat

Putting both things into the same main-thread callback with no operation in between → they are necessarily completed on the same beat, leaving no intermediate state.

3.3 gba_timer_cb() — a second safety net on the main-thread side

The main thread’s recovery path (the finished flag branch) also adds one page flip before the repaint. It is fine whichever of it and 3.2 runs first; the page flip is idempotent.

3.4 Frontend miniretro_gba.c — untouched

Its fb_restore() has long been “unconditionally flipping back to page 0” since document 14; what needs fixing this round is exactly the missing other half of the symmetry on the page side.

5 call sites in total (grep -c 'gba_reset_fb_page();' = 5): gba_repaint_async / gba_wait_thread / gba_timer_cb / gba_on_create / gba_on_destroy.

Why “unconditional” is safe

All call sites are after the child process has already disappeared (or right after the page is created, when there is no child process at all); there is no opponent concurrently writing fb0; FBIOPAN_DISPLAY is itself idempotent, and sending it once more when already on page 0 has zero side effects.

5. Anti-pattern record (already merged into the skill)

  • ★ “Idempotent operation + precondition check” is asking for branches. As long as the value the check depends on (here the driver read-back) has any possibility of “being inconsistent with the real state”, the check turns the zero-cost idempotent operation into “intermittently not executed“, and the symptom looks like a random failure. For idempotent operations with negligible cost: just do it, don’t ask.
  • ★ Do not put the two halves of the same visual transaction in two execution flows. “Returning the foreground page home” and “painting the new picture on” are the same thing; splitting them across two threads/two callbacks leaves an intermediate state nobody understands.
  • ★ Conclusions of the “X was measured to be reliable” type must carry the scope of the inference they support. “The read-back is reliable” ≠ “the read-back value equals the scan output”; the latter is the assumption the code actually relies on.
  • The first investigative direction for intermittent failures is the “check condition”, not “timing”: first ask “is there any way this code can choose not to act given correct input” — the payoff is far higher than suspecting a race first.

6. Leftovers

  • User’s on-device consecutive retest: multiple “enter game → 买单 exit” runs, each should return to the game list immediately.
  • Rollback point: device lv_pages/gba_game_page.c.bak_fbpan = before this change.
  • If this exit logic is ever copied to another “external program takes over fb” app (such as the video playback page), the “unconditional page flip” must be moved along with it; do not just move the name gba_reset_fb_page().
