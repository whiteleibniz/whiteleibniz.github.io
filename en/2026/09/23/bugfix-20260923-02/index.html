Failure to Clear the Focus Group on Page Exit Causes the Desktop Focus Ring to Disappear

wlb
2026-09-23
bugfix, 桌面UI

bugfix_20260923_02 — Pages do not clear the focus group on exit, causing the desktop focus ring to disappear

Symptoms: After entering any page and returning to the desktop, pressing the direction keys makes the pink focus box disappear out of nowhere, and the focus can no longer reach the target icon; restarting the application restores it. Touch clicks are unaffected.
Root cause layer: The focus group lifecycle of the LVGL page framework (lv_pm/lv_page_manager.cc) / the desktop’s custom navigation (main.c).
Fix effort: 2 files (lv_pm/lv_page_manager.cc +49, main.c +7/-1).
File name: bugfix_20260923_02_页面离场不清焦点组导致桌面焦点环消失.md
Related commit: 221fa7d
Date: 2026-09-23

Symptoms

After returning to the desktop from any non-desktop page, the desktop shows the following when direction keys are pressed:

  1. The pink focus box disappears out of nowhere — a key is pressed, but the interface gives no indication of which icon is currently selected;
  2. Continuing to press the direction keys fails to reach the desired icon (for example, wanting to go back to “Radio”, but getting stuck elsewhere or not moving at all);
  3. Repeated presses show no pattern; restarting the application (not the device) restores normal behavior, and it breaks again as soon as a page is entered and then left.

That is, on the path of “enter a page → return to the desktop”, the desktop navigation gets polluted.

This is a bug discovered along the way while investigating “Bluetooth shows connected when it is actually not connected”:
in order to do key-press verification for the Bluetooth page (enter the page → return → walk to the Bluetooth icon), we found that it could not be reached at all, and only then did we learn that the desktop focus had long been broken.

Scope of impact
Affected Key navigation on the desktop (launcher); all scenarios of “enter a page and then return”; indirectly triggered another misjudgment of “the radio page cannot be entered” in this session
Not affected Touch clicks (they do not go through the focus group); navigation within the page itself; page rendering; FM radio, Bluetooth, and other business logic

Being able to touch but not to navigate with keys is the most typical manifestation of this bug.

Root cause

Two independent defects are superimposed, each of which alone can make navigation fail.

3.1 On page exit, pages do not remove their own controls from the “common focus group”

LVGL’s default focus group is globally shared. Each page calls lv_group_add_obj(lv_group_get_default(), obj) in onCreate to attach its own controls to it, but almost nobody calls lv_group_remove_obj() on exit — only 3 files in the whole repository perform this pair of operations; all other pages are “add only, never remove”.

As a result, every time a page is entered, a batch of controls that have already been deleted along with the page, or have become invisible remains in the group, becoming “ghost focus”. Measured counts (lv_group_get_obj_count):

group_find_neighbor picks neighbors among these ghosts, so:

  • Selecting a control without user_data → the code that draws the desktop focus box cannot get the cell information → the box disappears;
  • The “neighbor relations” of the direction keys are disrupted by the ghosts → the target icon cannot be reached.

3.2 group_find_neighbor only looks at the control’s own HIDDEN, not its ancestors

In the custom navigation in main.c, the original criterion was:

However, in LVGL, hiding a panel hides the outer container, and the child controls inside do not themselves carry LV_OBJ_FLAG_HIDDEN. As a result, the volume overlay slider in its collapsed state on the status bar (parent panel 340×42, slider itself 252×14) gets selected as a legitimate candidate.

It was located by “printing the shape of the ghost object and then looking it up” (see §4.2):

Selecting it likewise yields no usable user_data → the focus box cannot be drawn.

In one sentence: ① the group contains ghosts; ② the visibility check only looks at the object itself, not its ancestors.

Diagnosis process

4.1 First confirm “who the focus actually lands on”

Add one stderr trace line to the section of code on the desktop that renders the focus box (printf is delayed by block buffering, so you must use fprintf(stderr, ...)):

  • When the fault occurs (the intermediate state where the page manager cleanup is in but ancestor awareness is not):
    [fc] focus idx=17/18 cell=0x... content=(nil) box=(nil)
    → content/box being null pointers means the current focus object has no user_data, so the desktop cannot get the information “which icon cell this focus belongs to”, and the box naturally cannot be drawn.
    idx=17/18 also corroborates this: the desktop only added 17 cells to the group, and the 17th (0-based) is not the desktop’s at all.
  • After the fix: [fc] focus idx=7/18 cell=0xb70881d4 content=0xb7088374 box=0xb7088444
    → all three pointers have values = the focus box can be drawn normally.

The denominator of idx (the total number of objects in the group) is itself a clue: print the group count at each page’s entry/exit, and you will see the number only rise and never fall (see §3.1 and §6.1) — this is the direct evidence that “the ghosts are accumulating”.

4.2 “Print out” the ghosts and then look them up

Focus tracing alone is not enough; we also need to know what the ghosts look like. Temporarily add a dump section in the page manager:

Relying on the two features size=(252,14) + parent container 340×42, we found s_volume_slider at lv_status_bar/volume_control.c:207, which counter-proves §3.2. The diagnostic trace was removed after it had served its purpose.

4.3 Ruled-out directions

Attempt Result
Suspect that the desktop computes neighbors incorrectly (left-right row-crossing issue) ❌ The desktop logic has never changed, and restarting the application restores it → it is “polluted externally”, not an algorithm error
Suspect that dangling pointers left in the group after lv_obj_clean deletes objects cause a crash ❌ There is no crash, only focus misalignment; LVGL automatically removes objects from the group when deleting them
Suspect that “the radio page was not destroyed” ❌ [pm] destroy 'radio' is printed normally and the page is indeed destroyed — but the controls are still in the group (the group and the object lifecycle are two separate things)
Fix only §3.1 (unified cleanup by the page manager) ⚠️ Mostly recovered, but the group count is still 18 (= desktop 17 cells + 1 non-desktop object) → this shows there is still one member that does not belong to the desktop, so §3.2 must be fixed as well

6.3 Not done / to be observed

  • Only the path “radio page → desktop” was covered. The other 10+ pages go through the same pm_page_destroy cleanup, so in theory one fix covers them all; however, they were not tested page by page. If anything abnormal occurs, look directly at the [pm] log line to confirm which page missed the cleanup.

Lessons learned

  1. Entry and exit into a globally shared container must be paired. The focus group is a global singleton; if pages only add and never remove, it is equivalent to dumping garbage into a common area — and the symptom appears on the victim (the desktop), not the culprit (the page), making it extremely hard to reason back from the symptom. Anything that is a “global registry” should have its lifecycle managed uniformly by the framework layer; do not count on each page being conscientious.
  2. The lifecycle must be viewed at two layers: an object being deleted ≠ being removed from the group. The page can be destroyed perfectly cleanly ([pm] destroy printed normally), yet the controls still linger in the group. When investigating this kind of problem, printing “how many elements are currently in the container” is far more effective than printing “what I deleted”.
  3. The visibility check must be ancestor-aware. LV_OBJ_FLAG_HIDDEN only describes the object itself; “can the user see this control right now” is a question along the parent chain. Any pattern in LVGL that “hides a container” steps on this pitfall.
  4. “Restarting the application fixes it” is a strong signal of “external pollution”. It shows that the fault is not in the algorithm itself, but that the runtime state has been dirtied elsewhere — the investigation direction should immediately shift from “is the computation correct” to “who touched the shared state”.
  5. Use fprintf(stderr, ...) for diagnostic traces. printf writes to files with block buffering, so logs lag badly and are easily misjudged as “the code did not execute” (the same pitfall was also stepped on while investigating the FM page).
  6. Sink “specifications” into the framework layer instead of writing them into documentation. This case originally just wrote “remember to remove” in the documentation, and nobody followed it; after moving it into pm_page_destroy, old and new pages became compliant in one shot. Conventions that can be enforced by code should not rely on conscientiousness.
