GBA Exit Hangs on a Black Screen and FC Gets Collateral Damage — Fully Separating the Frontends

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_11 — GBA exit hangs on a black screen, and FC is implicated (complete front-end separation)

Item Content
Discovery time 2026-09-23
Fix time 2026-09-23
Module extern/miniretro/* (new separated artifacts), lv_pages/gba_game_page.c
Versions involved Taking over the site after bugfix_20260923_10
Severity level High (GBA exit is unusable and it drags down the originally normal FC as well)

1. Problem symptoms

The user reported two consecutive rounds:

  1. “The exit logic still has problems, it still hangs on a black screen“;
  2. “Separate the GBA and FC miniretro; FC’s original version always worked well, but it was polluted by the GBA changes, which made FC’s miniretro not work well either, making FC unplayable, with inexplicable exits”.

Item 2 is the key judgment: the two game pages share a single front-end binary, so changing GBA is bound to affect FC. The user’s demand (physical isolation) is more correct than “keep patching the shared component”.

2. Scope of impact

  • GBA game page: black screen after exit, and the exit key stops working;
  • FC game page: collaterally affected by the changes to the same miniretro, with abnormal exits;
  • At the root-cause level: any design of “multiple pages sharing one executable front-end” is a breeding ground for this kind of cross-module pollution.

3. Root cause analysis

3.1 ★ The waiting loop sets a cap of “running for N seconds counts as exited” (the direct cause of the black-screen hang)

gba_wait_thread was originally written as “proceed once enough time has been waited”:

The game runs normally for a full 3 seconds, which satisfies the “loop finished” condition, so:

  1. hardware_keys_set_interceptor(NULL, NULL) removes the key interceptor → the 买单 (pay-the-bill) key is no longer intercepted → the game cannot be exited;
  2. app_runtime_set_lvgl_paused(false) lets LVGL resume drawing → the parent process grabs back fb0, overwriting the still-running game;
  3. The two combined = what the user sees as 「hangs on a black screen」, and only a restart can recover.

This is precisely the watershed of “FC is fine, GBA has problems”: the FC page uses a blocking while(waitpid(pid, &status, 0) < 0) {...} (no cap), so it never misjudges.
The GBA page introduced the cap to “recover the UI faster”, which instead created the bug.

3.2 UI recovery is tied to “the child process disappearing” (prolonging the black screen)

This machine’s kernel takes several hundred milliseconds to reclaim /dev/input/eventX; measured at ~455ms from signal to reaping complete,
while the picture is handed back in ~40ms. Waiting for the reaping before recovering the UI wastes 400ms — during which the screen is entirely black.

3.3 Detail issues

  • gba_timer_cb only calls lv_obj_invalidate(lv_screen_active()) once, which may be out of sync with LVGL’s recovery timing and get swallowed (the flag is consumed but the picture is not drawn back);
  • fb_restore() calls FBIOPAN_DISPLAY without checking the result: if yoffset does not really return to zero, LVGL draws on page 0 while the screen still shows page 1 → a permanent black screen, completely silent, and impossible to locate.

3.4 Structural root cause: a shared front-end

FC and GBA share extern/miniretro/miniretro. All the changes added for GBA — double-buffered page flipping, pitch addressing, 240×160 admission, audio resampling, and exit signal handling — land on this single shared artifact. FC is thus repeatedly implicated — this is the inevitable result of “change A, break B”, not any single change being written poorly.

4. Fix

4.1 ★ Complete front-end separation (the user’s scheme)

Artifact Owner Description
extern/miniretro/miniretro FC only Restored to the repository’s original version via git checkout, and never recompiled or touched by GBA changes from now on
extern/miniretro/miniretro_gba GBA only Contains double buffering / pitch / 240×160 / audio fixes / exit fixes
extern/miniretro/miniretro_gba.c GBA source
extern/miniretro/miniretro.c FC source Already restored to the original version along with the binary
extern/miniretro/build.sh — Only compiles miniretro_gba, and states at the top of the script “do not write the artifact as miniretro again”

The first-choice path of gba_find_bin() on the page side is changed to miniretro_gba, keeping miniretro as a fallback:

4.2 Four fixes to the exit logic (only on the GBA page)

  1. Remove the time cap from the waiting loop, recognizing only two real termination conditions:

  2. Add the exiting flag: recover the UI as soon as the picture is handed back, without waiting for reaping

  3. Refresh 3 frames in a row on recovery, not relying on a single invalidate:

  4. fb_restore() verifies the page-flip result: only pan when yoffset != 0, and read back to confirm after panning, logging a warning if it does not return to zero (turning “a permanent black screen with no clues at all” into something locatable).

Also add a “still my own pid” check to the waiting thread, preventing a previous round’s thread from waking up and clearing the new round’s state.

5.2 Each front-end runs on the real machine (ssh_tools/split_verify.py)

Front-end Core Picture (non-black pixel ratio) Exit code Reaping time yoffset after exit Zombies

GBA miniretro_gba mGBA 0.380 ✓ 0 (graceful exit) 575 ms 0 ✓ None
  • FC’s exit code -15 matches the expectation of “the original version has no signal handling”; its page side detects after 120ms that the process has disappeared and recovers the UI directly — this is precisely the behavior the user remembers as “FC used to work well”.
  • On the GBA side, the exiting flag lets the UI recover in ~125ms, with reaping moved to the background; yoffset returning to zero confirms there is no black-screen risk.
  • After recovery, lvgl_demo ×1 + lvgl_watchdog ×1, single instance, no leftovers.

5.3 One correction to the deployment script

gba_redeploy.py uses ps -o pid,args | grep '<name>' to get the PID to kill,
but that command’s own command line contains this string → it matches the sh -c carrying the command → kills its own SSH connection
(a ConnectionResetError was actually measured this time). It has been uniformly changed to ps -o pid,comm (the comm of the carrying shell is sh, so it is not hit by mistake); see split_miniretro_gba.py / split_verify.py.

6. Regression risks

  • miniretro has been restored to the original version: any future change needed on the FC side must be done independently, and can no longer go through the path of “recompiling miniretro” (build.sh now only produces miniretro_gba). If FC really needs to be changed, first git checkout a copy under another name (such as miniretro_fc) before changing it, keeping the three from interfering with each other.
  • The GBA side no longer has a “time cap”: the waiting thread keeps looping during the game (once every 5ms, negligible overhead).
    This is a deliberate choice — better to spin a few more times than to misjudge “already exited”.
  • Both the gba_reap_bg / onDestroy reaping paths may call waitpid on the same pid; both sides already handle ECHILD.
  • This change did not touch the rendering or audio chain, so the color, sound quality, and frame rate should not change.
