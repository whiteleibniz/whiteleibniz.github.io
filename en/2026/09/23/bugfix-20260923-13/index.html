bugfix_20260923_13 — GBA exit “hangs on a black screen”: the real culprit is the frontend clearing the screen itself on exit (not an issue with the fork form)

  • Date: 2026-09-23
  • Device: Spreadtrum SC9832A / armv7l / Alpine / 720×1280 fb0 (yres_virtual=3840, 3 pages) / 4 physical keys
  • Files involved:
    • Device extern/miniretro/miniretro.c (GBA-dedicated frontend, build artifact miniretro_gba)
    • Local ssh_tools/_tmp/miniretro.c (same source)
    • Local ssh_tools/gba_redeploy.py (deployment script; this round also removed a latent hazard that could damage FC)
  • Evidence scripts: ssh_tools/gba_black_probe.py, ssh_tools/gba_black_run.py, ssh_tools/ssh_run.py

1. Symptom

User feedback: when a GBA game exits, the screen “hangs on black”; the FC frontend uses the exact same exit method (also fork + an independent frontend process) and has “always been smooth”.

The user’s question was: “isn’t the GBA frontend also a fork-style process?” — Yes it is. GBA and FC take exactly the same fork + execl form (parent process = lvgl_demo, child process = extern/miniretro/miniretro_gba or miniretro; the frontend writes /dev/fb0 directly). Precisely because the form is identical, the question “why is one smooth and one stuck” can only be investigated in the screen content, not in the process model.

2. Scope of impact

  • Only the GBA page exit path (lv_pages/gba_game_page.c → miniretro_gba).
  • The FC page is unaffected: its frontend extern/miniretro/miniretro is the git repository original and does not catch SIGTERM; not a single line was touched this round (md5 verification in §5).

3. Root cause analysis

3.1 Measurement: what actually happens to the screen after both frontends receive SIGTERM

Stop lvgl_demo/watchdog, launch both frontends directly and run them for 3s, then send SIGTERM and sample the center region of the screen at each time point (“non-black ratio / average brightness”; fb0 has 3 virtual pages, so sampling follows the current yoffset to the currently displayed page):

3.2 Conclusion

There is only one difference: whether the frontend clears the screen on exit.

  • miniretro (FC) does not catch SIGTERM and performs no fb operations → the kernel kills it directly, so the screen stays on the game’s last frame.
  • miniretro_gba (GBA) catches SIGTERM and runs a graceful shutdown, in which fb_restore() contains the statement memset(fb_buf, 0, fb_total_bytes), which blacks out the entire virtual video memory at t=20 ms → the screen goes black instantly.

Meanwhile, the child processes of both frontends take about 1020 ms to truly disappear (the inherent overhead of the kernel’s exit_files() recycling the 5 inherited /dev/input/eventX devices one by one plus the fb0 mapping, unrelated to whether the frontend writes fb). The parent process (GBA page) currently uses a blocking waitpid and only restores the UI after reaping completes (this is the approach aligned with FC requested by the user in document 12).

So the two timelines are:

  • FC: the screen stays frozen on the game’s last frame for 0~1020 ms → the UI is restored and redrawn. What the user sees is “the picture held for a moment, very smooth”.
  • GBA (before fix): the screen is pure black for 20~1020 ms → the UI is restored. What the user sees is “hangs on a black screen”.

In one sentence: the “hang” is shared by both frontends (~1s of kernel reaping overhead, the same for FC); the “black” is unique to GBA and is caused by its own screen clearing.

3.3 Why the memset screen clear was written in the first place

The original worry was “residual game picture”: after LVGL resumes it only refreshes dirty regions, so residue would smear on the screen. But the GBA page already performs lv_obj_invalidate(lv_screen_active()) full-screen redraw when resuming, so this worry does not hold — the screen clear was a redundant action, and its cost was a full second of pure black screen.

4. Fix

4.1 fb_restore(): screen clear → cross-page freeze copy (core fix)

  • The action of panning back to page 0 is kept (yoffset not returning to zero = LVGL drawing on an invisible page = permanent black screen; this part is mandatory).
  • The screen is no longer cleared; if the foreground page is page 1 at the moment of exit, the whole of page 1 is copied to page 0, guaranteeing “screen content identical pixel by pixel to before exit” (frozen, no black flash, no frame skip).
  • The page offset uses the existing variable fb_page_bytes (= bytes of one screen), fully consistent with the rendering side’s fb_dst = fb_buf + target * fb_page_bytes; there is no out-of-bounds access.

4.2 Deployment script gba_redeploy.py: removed a latent hazard that could damage FC

The --mini branch originally hardcoded gcc ... -o miniretro.tmp ... mv -f miniretro — that is, it compiled the GBA source under the FC binary name, which would overwrite the FC original that was painstakingly restored in the previous round. This round it only produces miniretro_gba, and a guard was added: backup before compilation + cmp verification after; an error is raised as soon as the FC frontend md5 changes.

Lesson: when two artifacts of the same “name family” live in the same directory, the build script must use different target names, with the constraint hardcoded at the top of the script.

Check 1: is the screen still black on exit (both frontends run 3s each → SIGTERM → sample until the child process disappears)

  • FC: non-black 0.954 / brightness 227.4 throughout, identical to before exit (frozen).
  • GBA (after fix): non-black 1.000 / brightness 248.0 throughout, identical to before exit (frozen).
  • The black-screen window dropped from ~1s to 0.

Check 2: was the copy branch actually executed (under double buffering the foreground page alternates between 0/1)

  • yoffset was 0 in all 4 running samples (see §6 leftover item 3), but the exit log shows fb pan 回第0页 17.8ms → fb 定格最后一帧(不清屏) 33.0ms, taking 15 ms — exactly the time for copying a full 3.7 MB page, which proves the copy branch was executed.
  • No pan 失败 warnings at all.

Check 3: final state

  • lvgl_demo ×1, lvgl_watchdog ×1 (the duplicate watchdog produced during the test has been cleaned up to a single instance).
  • FC frontend md5 = a95d9171d8d8b82a52c12ac84e68aaa2, consistent with the pre-build backup.

6. Leftovers and observations (unhandled, for future reference)

  1. After exit, returning to the list still takes about 1 second: this is the inherent overhead of the blocking waitpid waiting for reaping plus kernel fd reclamation, exactly the same for FC (1015ms). If “restore the UI as soon as the picture is handed back” is ever needed, an “early release” mechanism will have to be reintroduced — but that is exactly the direction that failed twice on 09/10 (the mistakes back then: _exit(0) + a timeout loop inside a mutex + setenv cross-page pollution). Per the user’s request this round to “match FC line by line”, this optimization is not made.
  2. Kernel fd reclamation takes ~1020 ms, longer than the ~455 ms measured earlier (possibly affected by the system load at the time). It is inherent kernel behavior that the frontend cannot influence.
  3. Reading back yoffset from the driver is unreliable: even when pan actually takes effect (the copy branch was triggered, meaning g_front=1), the FBIOGET_VSCREENINFO read-back still returns 0. Therefore the “yoffset read-back verification” in fb_restore() will not raise false alarms, but it also cannot detect pan failures — it must not be used as the criterion for whether pan succeeded (the earlier memory records need to be corrected accordingly).
  4. The device rebooted once on its own during this round of testing (uptime 45 min), unrelated to this bug.
