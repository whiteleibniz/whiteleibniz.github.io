GBA Game Audio Crackles and Pops

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_06 — GBA game audio crackles and pops

  • Date: 2026-09-23
  • Module: GBA game page / extern/miniretro/miniretro.c (audio chain)
  • Impact: All GBA games (FC games are affected by the shared code as well, but FC’s audio rate happens to equal the reported value, so the problem is not exposed)

1. Problem symptoms

The game picture is normal and the sound is audible, but it is accompanied all along by crackling noise / popping, with the music and sound effects both smeared.

2. Scope of impact

  • GBA application (mgba_libretro.so + miniretro)
  • All applications that output audio via /tmp/bt_audio.fifo (FC games, the music/video page, all sharing the same resampling function)

3. Root cause analysis

Running MINIRETRO_AUDIO_DEBUG=1 miniretro mgba_libretro.so <rom> in a controlled manner on the device prints the probe, yielding hard evidence:

  • fpc=1097: the core delivers 1097 frames of audio per retro_run.
    Meanwhile av_info reports sample_rate=32768 and fps=59.73, so theoretically it should be 32768/59.73 ≈ 548 frames.
    The actual value is 2× — the core’s real audio rate is about 65536 Hz, while the reported value is only half.
  • The old code converted according to the reported value: out_per_in = 44100/32768 = 1.346,
    so each frame needs to output 1097 × 1.346 ≈ 1476 frames.
  • But the output buffer is only static int16_t buf[2048] (=1024 frames), so every frame is truncated to 1024 frames,
    i.e. about 30% of the samples are stably dropped on each callback.
  • Result: about 58,000 frames are produced per second while Bluetooth only consumes 44,100 frames, drop persists at 2~12 times per second,
    and frames are truncated on top of that — the triple superposition is the persistent crackling/popping heard.

4. Fix

Stop trusting the core’s self-reported sample_rate, and switch to adaptive resampling based on the measured rate:

  • A sliding average of the frame count per callback, s_fpc (it depends only on the core, not on this machine’s speed);
  • Measure the wall-clock frame rate s_fps_meas every 300ms;
  • in_rate = s_fpc × s_fps_meas, out_per_in = 44100 / in_rate;
  • Expand the output buffer to int16_t buf[8192], completely eliminating truncation;
  • Do not emit sound before the first measurement window produces a result (the frame counts of the first batch of callbacks at startup are extremely unstable; the measured first frame has only 82 frames, and using it to estimate the rate would compute a several-fold overproduction, flooding the fifo right at startup).

Note: you cannot convert using the “core’s nominal rate”. This machine’s CPU, even at 100%, can only reach about 56fps; if converted at the nominal 59.73fps, only 0.94 seconds of audio would be produced per second → Bluetooth would be short of 6% of the data per second → persistent underload popping.
The audio must be stretched to real time based on the measured frame rate (see section 6 for regression risks in detail).

5. Verification method and results

Metric Before fix After fix Verdict
Whether each frame’s output hits the buffer limit Consistently hits the cap (2048 int16) About 1700 int16, does not hit the cap ✅ Truncation eliminated
drop (fifo write failures per second) 2 ~ 12 0 ✅ No dropped frames
out_rate (actual output frame rate) ≈52200 (overproduction) 43000 ~ 45800 (target 44100) ✅ Aligned with Bluetooth consumption
fps 50 56 —

The probe is kept in the code, enabled with the MINIRETRO_AUDIO_DEBUG=1 environment variable, and disabled by default in production.

6. Regression risks

  • The overall pitch is about 6% too low: this machine can only run at 56fps (target 59.73fps), and after the audio is stretched to real time, the pitch shifts down accordingly.
    The picture is likewise 6% slower, so the audio and video content remain synchronized; only the tone is slightly lower. The closer the frame rate is to 60, the smaller this deviation.
  • Completely eliminating this requires raising the frame rate to 59.73fps, while rendering + emulation already saturate the CPU (measured busy_ms≈990/1000).
  • FC games share this function: FC’s fpc × fps exactly equals its reported sample rate, so the conversion result is identical to the old logic and its behavior is unchanged.
