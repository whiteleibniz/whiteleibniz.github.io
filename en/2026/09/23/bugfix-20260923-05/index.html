GBA Screen Shows Vertical Stripes / Tearing

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_05 — GBA picture shows vertical stripes / tearing (the source pitch is ignored)

Symptoms: There is a picture now, but the whole screen shows regular vertical stripes, with content misaligned horizontally, as if “torn”.
Root cause layer: The source row stride (pitch) addressing of the miniretro frame callback video_cb, plus concurrent scanning of the frame buffer.
Fix effort: extern/miniretro/miniretro.c totals +81/-13 cumulatively (including this item and the bugfix_20260923_04 black-screen fix; this item is the main part).
File name: bugfix_20260923_05_GBA画面纵向条纹撕裂.md
Related commit: (to be backfilled after commit)
Date: 2026-09-23

Symptoms

  1. GBA games can be entered (see bugfix_20260923_04), but the screen shows regular vertical stripes: the content is cut into vertical bands, with black gaps between the bands, and the whole image is misaligned horizontally and unreadable (the user describes it as “tearing-like”).
  2. Comparison: the FC game picture is completely normal, with no stripes.

Initial suspicion: is this timing tearing (missing vsync) or addressing misalignment? Both can “look like tearing”, so they must be distinguished first.

Scope of impact

  • Affected: GBA (240×160, RGB565, pitch=512).
  • Not affected: FC (fceumm, whose pitch happens to equal width×2) — linear reads are also correct, so it has always been normal.
    This change is transparent to FC.

Root cause

The video_cb in miniretro.c completely ignores the row stride given by the core:

  • FC: pitch = 256 × 2 = 512 bytes, which happens to equal width × 2 → linear reads are correct by coincidence.
  • GBA: the core log measured video_cb: 240x160 pitch=512 — that is, 256 pixels per row, while the visible width is only 240.
    A linear read skips (256-240)=16 pixels too few per row, so the misalignment accumulates row by row over 160 rows, equivalent to about 10 rows of source data,
    causing the picture to be sheared horizontally and, due to cross-row wraparound, producing regular stripes.

Hard evidence: add a one-time print in video_cb; after recompiling, the log outputs [miniretro] video_cb: 240x160 pitch=512 fmt=2 (每行像素=256) — pitch and width really are inconsistent.

Diagnosis process

  1. Detour one (critical): it was initially judged to be vsync tearing, so double-buffered page flipping was added to miniretro (the fb has yres_virtual=3840, i.e. 3 pages, using FBIOPAN_DISPLAY to switch pages).
    But the user’s feedback was “still the same, not fixed” → this shows it is not tearing at all, but data misalignment.
  2. Capture the screen to distinguish: we cannot see the device screen with our own eyes, so capture the screen on the real machine —
    the device-side python3 os.pread dumps /dev/fb0 (capturing the foreground page according to the current yoffset) → retrieve it via SFTP → decode it locally as PNG by [R,G,B,X] → open the image and look.
    One look makes it clear: it is regular vertical stripes (content misaligned, with black gaps), not tearing lines. The direction immediately shifts to addressing.
  3. Locate pitch: read the video_cb source and find (void)pitch; and the linear read; add a one-time print to confirm pitch=512 ≠ 240×2=480.
  4. Rule out double buffering as the culprit: double buffering is kept (it has no side effects and has defensive value against real tearing in the future), but adding the pitch fix is the real cure.

Solution

The video_cb in extern/miniretro/miniretro.c:

  1. All three pixel format branches are changed to fetch data row by row by stride (falling back to width*2 when pitch==0):

    XRGB8888 (pitch/4) and 0RGB1555 (pitch/2) work the same way.
    Note that the result is still 0xAARRGGBB, with the R/B byte swap done uniformly by scale_rotate90 before writing out.

  2. Keep double-buffered page flipping (g_dbuf, FBIOPAN_DISPLAY; automatic degradation to single buffering on first failure) —
    on this machine FBIO_WAITFORVSYNC returns EPERM and is unavailable, so page flipping is the only viable anti-tearing measure.

  3. Recompile: cd extern/miniretro && sh build.sh.

Verification

  • Controlled self-test: after the fix, run miniretro mgba_libretro.so <rom> standalone and capture 20 consecutive frames on the real machine:
    • the title screen (an orange-garbed character + a cyan radiating background) and the opening animation (multiple character portraits) are clear across the whole screen;
    • no vertical stripes, no tearing, no black gaps.
  • Log: 双缓冲页翻转已启用(yres_virtual=3840), video_cb: 240x160 pitch=512.
  • Device end state: 1×lvgl_demo + 1×lvgl_watchdog.sh, with no miniretro leftovers.
  • Pending user confirmation on the real machine: desktop → “GBA Games” → confirm key to start → visually confirm no stripes/tearing → exit with the 买单 (pay-the-bill) key (116).

Lessons learned

  1. “Tearing” and “stripes/misalignment” are two different diseases and must be separated first.
    • Tearing = a timing problem (the frame buffer is being modified while it is being scanned) → double buffering / page flipping / vsync.
    • Stripes = an addressing problem (the per-row stride is computed wrong) → check pitch/stride.
      Applying double buffering without distinguishing them wastes a round (this bug did exactly that, wasting one round trip).
  2. When interfacing with different libretro cores, pitch must be used; never assume pitch == width × bpp/8.
    mGBA aligns buffer rows to 256 pixels, making pitch/2 = 256 ≠ width(240).
    Linear reads are “correct by coincidence” when width happens to divide pitch evenly; switch resolution and it is exposed immediately.
  3. When you cannot see the device screen, capturing the screen on the real machine is the most cost-effective diagnostic means:
    os.pread("/dev/fb0") → SFTP → decode as PNG locally by [R,G,B,X] → look at the image with human eyes.
    Telling at a glance whether it is stripes or tearing beats a pile of log reasoning.
  4. Quantitative metrics like “proportion of non-black pixels” can only prove “there is a picture”; they cannot prove “the picture is correct”; judging “whether the picture is correct” requires human eyes.
  5. Do not treat “changed but had no effect” as noise: the user said “still the same” twice, which is precisely the strongest signal that “the root cause judgment was wrong”.
