GBA audio lags video by 1~2 seconds: located in the speaker-side buffer

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_17 · GBA audio-video latency of 1~2 seconds: located in the speaker-side buffer, no fixable point on the device side

  • Date: 2026-09-23
  • Device: Spreadtrum SC9832A / Alpine Linux / 720x1280 fb
  • App: GBA game (miniretro_gba + mgba_libretro.so) → Bluetooth A2DP (小爱音箱 / Xiaoai speaker)
  • Category: audio chain / latency budget localization
  • Conclusion: the full-chain latency on the device side is ≤0.25s, a 48x difference from the user’s measured 12s; the excess is in the Bluetooth speaker’s application-layer buffer, which is neither observable nor controllable from the device side → no code changes this round

1. Symptom

User feedback: in the GBA game, the sound lags behind the game picture, on the order of 1~2 seconds, and it is fixed (it lags by that much as soon as the game is entered, with no obvious change over long play sessions).

The “fixed” property is decisive: it rules out the “device-side backlog” class of causes (a backlog accumulates over time and grows the longer you play), and points to a fixed buffer somewhere in the chain.

2. Localization method: chain segmentation quantification (latency budget table)

Split “game audio generation → sound output” into 5 segments, quantify the latency of each segment, and find the segment whose magnitude does not add up:

# Segment Latency Basis (reproducible)
1 mGBA core internal audio buffer ~33ms libretro.c: internalAudioBufferSize = audioSamplesPerFrame * 2 (capped at 0x4000); GBA has ~1097 samples per frame → about 2 frames; and retro_run takes them out with mAudioBufferRead(buffer, ..., audioSamplesPerFrameAvg) once per frame, with no accumulation
2 Frontend miniretro_gba 0 fifo_write() is write-on-receipt, non-blocking (EAGAIN is dropped directly); resampling is stateless sample dropping (s_out_acc accumulator + direct sample copying), with no internal queue and no batching
3 /tmp/bt_audio.fifo backlog 80ms measured after the water-level loop closed: back ≈ 14000B (the original 0.21s has been squeezed to ~0.08s)
4 daemon in-flight packets ≤122ms A2DP_MEDIA_INFLIGHT_MAX=6 × 20.3ms per packet; measured inflight=0/1776, credit busy=0
5 Bluetooth air interface + speaker application-layer buffer not observable see §3
— Device-side subtotal ≤0.25s

Compare with the user’s measured 1~2 seconds: the entire difference falls on segment 5.

3. Why it was judged to be on the speaker side (and why the device side cannot measure it)

Basis for the judgment: all four segments on the device side have hard measurements totaling ≤0.25s; the “fixed” property also rules out cumulative causes. The remaining magnitude can only come from the speaker.

Why the device side cannot observe the speaker buffer (these three points are the focus of this section; do not waste effort looking again):

  1. The ACL layer’s Number-Completed(0x13) is not an application-layer consumption acknowledgment — it is returned by the Bluetooth controller and only means “the air-interface transmission is done”; the speaker putting the packet into its own buffer does not trigger any additional notification.
  2. The A2DP media channel uses L2CAP basic mode, which has no credit flow control — the sink does not tell the source “how much I still have on hand”.
  3. The daemon’s sending cadence is the device side’s absolute clock (one packet every 20.3ms), fully decoupled from the speaker’s consumption cadence; the device side can only know “how much I have sent”, not “where it has played to”.

Corroborating evidence: the daemon source comment (from the v48R22 fix) states “sink 缓冲约 2s“. That was observed in an abnormal state (pushing the stream without START), but it indirectly confirms that this speaker’s buffer depth is on the order of seconds.

4. This round’s conclusion and decision

  • No code changes on the device side. Reason: the only remaining compressible amount on the device side is about 90ms (fifo water level 60→30ms, in-flight window 6→3), which is a 5% magnitude relative to 1~2s, with negligible benefit; and tightening the Bluetooth sending window carries a historical “CP reset” risk, making the risk/benefit ratio not worth it.
  • The fifo water-level loop already landed in the previous round (squeezing the backlog from 0.21s to 0.08s) is kept; it is an effective, side-effect-free improvement.
  • The feasible improvement direction is only on the speaker side: the speaker app / speaker unit’s “low latency / game mode” switch; or swapping in a Bluetooth speaker/headphones with lower latency for a comparison.

5. Verification

  • The user has confirmed: fixed lag, on the order of 1~2 seconds → fully consistent with the “speaker fixed buffer” model.
  • Comparison experiment (recommended for the user, one step to a conclusion): connect the device to another Bluetooth headphone/speaker; if the latency changes significantly → 100% confirmed to be on the speaker side; if it is still 1~2 seconds regardless of the swap → go back and check the chain.

6. Anti-patterns and pitfalls

  • ★ Do not use “device-side buffer metrics” to explain “second-order” latency — first make a latency budget table, see which magnitude does not add up, then dig into that segment. Guessing “it must be the buffer” by intuition will keep you spinning on the device side.
  • ★ Number-Completed ≠ application-layer consumption acknowledgment (see §3.1); using it to estimate the speaker buffer is wrong.
  • ★ Pay attention to the counting method when measuring: only differencing whole-file counts is meaningful; using “fixed-prefix counts” for differencing is necessarily 0 (a pit I dug for myself; it was really stepped on this round); log rotation can also pollute the difference.
  • ★ Using FIONREAD to measure fifo backlog is trustworthy: it returns the number of readable bytes inside the pipe, independent of the number of readers; reading only FIONREAD without read will not steal the consumer’s data.
  • ★ The frontend’s design of “stretching audio to real time” is correct: the core’s output varies with the actual frame rate, and the frontend normalizes by s_fpc × s_fps_meas and always outputs at 44100 frames per second, keeping audio and video content rate in sync (at the cost of pitch dropping with the frame rate). Stop doubting this part.
