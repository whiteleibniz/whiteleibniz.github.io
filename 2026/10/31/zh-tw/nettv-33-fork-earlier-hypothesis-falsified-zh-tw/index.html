netTV 硬解（33）：把 fork 提前到 VSP 之前——假設被證偽，但「處理器零輸出」這條線索值錢

wlb
2026-10-31
VSP 硬解, 多行程, 展訊 SC9832A, 崩潰取證, 嵌入式

🌐 語言：简体中文 · 繁體中文 · English

系列第 33 篇。上一篇把並行渲染池做成了成績單（20fps → 28fps），但那次 10 分鐘回歸裡藏著一個沒解決的污點：worker 每跑約 150 秒就被 SIGSEGV 殺一次，10 分鐘 3 次。這一篇是「我以為我知道原因，結果不是」的完整記錄——以及一條比結論更值錢的線索。

1. 起因：成績單背後那個污點

回歸數據很好看：28.2fps、池渲染 13~14ms、ION 洩漏 0、行程殘留 0。但 stdout 裡躺著三行：

每代 worker 都老老實實跑了四五千幀才死，不是啟動期問題。而且死法很怪：SIGSEGV，但處理器一句話都沒留下——沒有 /tmp/nettv_segv.log，stdout 裡也沒有任何崩潰傾印。

2. 假設：fork 的時機比 fork 本身更危險

我們的並行渲染池是「常駐子行程」：啟動時 fork N 個，之後靠管道收發任務。原來的 fork 點是第一幀——那時 OMX 元件已經 init、VSP 已經打開並且正在解碼。

於是很自然的一個假設：在 VSP 正在工作的時候 fork，子行程會複製一份 VSP 的使用者態狀態（buffer 佇列、暫存器影子、廠商堆裡的上下文），父子都認為自己持有這塊硬體，狀態遲早打架，最後父行程踩到野位址。

這個假設還有一個旁證：專案裡早就定過一條鐵律——fork 出來的子行程必須把 SEGV/BUS/ILL 復位成 SIG_DFL，因為父行程的 handler 末尾是 siglongjmp(g_jb)，而 g_jb 在父行程堆疊上；子行程一旦觸發訊號，就會 longjmp 進父行程的堆疊，憑空變成「第二個解碼行程」去搶同一個 VSP。既然「子行程繼承父行程的執行上下文」這條路上已經栽過一次，那「繼承 VSP 狀態」很可能就是第二次。

3. 方案 A：把池子挪到 VSP 之前

改動本身不複雜，難的是三件必須先做好的配套：

配套 為什麼必須先做
render_cfg_init() 渲染配置（帶高 / NEON / LUT）靠 fork 繼承傳給子行程，子行程內不碰 getenv
stage_ensure() staging 必須 mmap MAP_SHARED 且先於 fork 存在，否則子行程拿到的是凍結副本（畫面錯且不報錯）
fb_init() 子行程寫的是 fb 映射出來的位址，映射必須先存在

第一項還好，它是一個已有的函式，只是從「第一幀 lazy 呼叫」改成「提前顯式呼叫」。第二項要動結構：原來 staging 是解碼迴圈裡一個 static 區域變數，第一幀才建立——只要它在那兒，池子就只能後 fork。所以把它提成檔案作用域的 g_stage + stage_ensure()，行為不變（同樣只建立一次），只是時機提前。

第三項是本機的老坑：池子 fork 得早了，之後 exec 出來的 mplayer、非同步音訊泵都會繼承管道寫端。萬一池子行程真死了，父行程的 read() 因為別的行程還捏著寫端而永遠收不到 EOF——整幀卡死，而不是應有的「回退序列」。所以四條管道全部 FD_CLOEXEC（只在 exec 時生效，對靠繼承拿 fd 的池子行程無影響）。

第一反應是「mplayer 崩了，把我們也帶走了」。但順著行程樹推一遍就發現因果是反的：

這句是結果不是原因，而且它出現在我們日誌裡只是因為 stdout 是繼承的。差點被它帶進溝裡——如果當時直接去查 mplayer，這一晚就白幹了。

順帶記一條通用經驗：排查崩潰時，先問「這條日誌是死因還是死後現象」。死後現象的特徵是它由別人的子行程印出，且和你的行程樹是同一條死亡鏈的下游。

5. 結果：假設被證偽

同一台板子、同一個源、同樣的三個 env（NETTV_RPOOL=2 + NETTV_AUDIO_ASYNC=1 + NETTV_HLSBUF=1），跑 5 分鐘：

指標 v32（基線，10 分鐘） v33（方案 A，5 分鐘）
monitor 重啟 3 次 1 次
fps_x10 265~282 282
池渲染牆鐘 14ms 13~14ms
首幀自檢 通過 通過
ION clients / 殘留 0 / 0 0 / 0
音訊丟段比 0.29 0

歸一化一下：基線是 1.5 次 / 5 分鐘，v33 是 1 次 / 5 分鐘。在只有個位數樣本的崩潰統計上，這叫「沒有變化」。方案 A 被證偽——fork 時機不是這個崩潰的原因。

（另：這一輪裡設備還發生過一次核心重啟，時間點是上一輪 v33 跑到第 2 分鐘時；第二次 5 分鐘跑沒有復現。沒有足夠樣本判定它和 v33 有關，只作為疑點記錄在筆記裡，不作為結論。）

v33 不部署。 它沒解決問題，就不該動現網——這條原則比「新版一定更好」重要。

6. 真值錢的線索：處理器一次都沒跑

方案 A 裡我塞了一個純取證的改動：sigaltstack 備一塊 64KB 替身堆疊 + SA_ONSTACK。動機是——三次 SIGSEGV 處理器零輸出，最可能的解釋是堆疊溢位：處理器沒有堆疊可跑，核心直接按預設動作殺行程，現場全丟。

結果這條路也被堵死了：加了 altstack，依舊零輸出；child.log 裡 SIGSEGV 關鍵字出現 0 次。

處理器沒跑，只剩幾種可能：

  1. 堆疊溢位（已被 altstack 排除大部分情況）；
  2. handler 自己又崩了（但它第一行就是純計算，然後才 write，沒機會）；
  3. 訊號被遮蔽——故障執行緒把 SIGSEGV 遮蔽了，核心找不到能投遞的執行緒，直接按預設動作殺整個行程。

第 3 條不是空想，這個專案裡就有先例：當年裸 clone 出來的渲染子執行緒會呼叫 rp_block_sig() 遮蔽 SIGSEGV，它一崩就是「處理器零輸出 + /tmp/nettv_segv.log 不存在」，和現在一模一樣。那次因此定下了「渲染側一律 fork、禁用裸 clone」的鐵律。

現在的區別是：我們自己的兩個會遮蔽訊號的執行緒（vsync 翻頁執行緒、檔 2 渲染子行程）預設都是關的。所以嫌疑落到了廠商庫自己建立的執行緒（libstagefright 的 ALooper / 解碼執行緒）——那是我們改不到、也擋不住的地方。

7. 下一步：把黑盒子做在共用記憶體裡

既然處理器幫不上忙，就別指望崩潰瞬間能取到什麼，改成平時一直在記：

  • worker 每幀把「目前環節 id / 幀號 / 段號」寫進已有的 g_cnt_shm（mmap MAP_SHARED，monitor 手裡也有一份）；
  • 子行程一死，monitor 直接把 shm 裡最後一組值印出來。

這套的關鍵指標是零 I/O 開銷——寫共用記憶體是幾條指令，不像 ph() 那樣每次 O_SYNC 落盤 15ms。代價是粒度粗（只到「環節」級），但足以區分「崩在廠商 DRIVE 裡」還是「崩在讀幀/渲染裡」。

另一條並行的二分線：用 NETTV_RPOOL=0 + AF=1 和 RPOOL=2 + AF=0 各跑 5 分鐘，把「渲染池」和「非同步音訊泵」這兩個新加入的元件分別排除掉。

8. 這一晚的三條方法論

  1. 證偽也要寫進筆記。假設被推翻但沒留記錄，下一輪會從頭再推一遍——這次的「fork 時機」假設，推理鏈完整、旁證充分，照樣是錯的。記下來，下次直接跳過。
  2. 先分清「死因」和「死後現象」。Parent process disappeared 看起來像 mplayer 的鍋，其實是死亡鏈的最下游。
  3. 零成本的取證升級優先做。sigaltstack 十行程式碼，把「堆疊溢位」這個假設直接判死，比任何推理都便宜。
