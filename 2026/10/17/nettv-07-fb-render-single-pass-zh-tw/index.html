netTV 硬解攻堅(七)：把 250ms/影格的渲染壓到 20ms——用幾何合成幹掉三次全解析度搬運

2026-10-17

前面幾篇把 VSP 硬解、mbinfo 假實體位址、GOP 重播這些坑都填了，畫面能出，但只有 4fps。取樣器一抓，100% CPU 全花在 fb_render 上——不是廠商函式庫死鎖，就是我們自己的 NV12→ARGB＋旋轉 90°＋縮放。這篇記錄怎麼把它從 250ms/影格 幹到 19-21ms/影格。

一、先看舊的渲染長什麼樣

VSP 解碼輸出是 NV12 1920x1088，螢幕是 720x1280 直式螢幕，所以每影格要做三件事：NV12 轉 ARGB、旋轉 90°、縮放到 720x1280。舊實作是規規矩矩的三遍法：

中間那兩個 g_argb / g_targb 各 8.3MB，合起來每影格要吞掉約 25MB 的記憶體流量（2.07M 像素 × 4B × 讀改寫好幾輪）。在 Cortex-A7 上這就是 250ms。

二、關鍵洞察：中間那一層全解析度是純浪費

盯著輸出尺寸看了一眼就明白了：最終只有 720×1280 = 921,600 個像素，中間卻按 1920×1080 = 2,073,600 個像素算了一遍。也就是說辛辛苦苦算出來的像素裡有 56% 根本不會被取樣到，直接扔了。

既然如此，為什麼不直接算出「會被用到的那 44%」？

把三個幾何變換合成一下（轉置 + 垂直翻轉 + 3/2 最近鄰取樣），可以得到一個直接映射：

推導：targb[tx][ty] = argb[1079-ty][tx]，而 fb[oy][ox] = targb[oy*3/2][ox*3/2]，代進去就出來了。注意行列角色別搞反——我第一版就把它們寫反了，畫面整體轉置、底部還多出一條空帶，抓影格比對才現形（後面細說）。

還有一個繞不開的矛盾：轉置問題裡，「按輸出行順序寫」和「按源行順序讀」不可能同時成立。按輸出行寫，源就要按列讀（步長 1920 位元組，每像素一條 cache line）；按源行讀，輸出就要按列寫。解法是分塊：把輸出按 16 行一條帶，先算進一個 band[16][720] 的暫存區，再整行 memcpy 到 framebuffer：

這樣讀側每條源行只碰 1~2 條 cache line（24 位元組視窗），寫側每輸出行是一次 2880 位元組的連續突發，兩邊都舒服了。

三個細節值得記：

  • UV 必須按偶數列取。c 可能是奇數（3/2 取樣出來的列號是 0,1,3,4,6…），NV12 裡 u/v 是交錯成對存放的，所以要用 cb = c & ~1 對齊到偶數列，再取 Cl[cb]、Cl[cb+1]。寫錯就是半邊畫面偏色。
  • 存取局部性。輸出行是順序寫的；輸入 Y 行號 r 每行只走 1~2 行、列是順序讀的，cache 友好。這比「整影格轉置」那種跳 4.3KB 寫一個 4 位元組的寫法健康得多。

順帶把兩個 8.3MB 的中間緩衝也刪了，省 16.6MB 記憶體——在只有幾百 MB 的裝置上不是小數目。

三、量化：從 4fps 到 12fps

播放器裡有 bench 自測入口（30 次渲染逐次計時），第一版（錯誤幾何、無轉置矛盾）跑出 19-21ms/影格。修正幾何、加上帶狀 staging 後，端對端實測 25 影格 / 2057ms = 12.1fps——比舊的 4fps 提了 3 倍。中途還踩了一個隱形的坑：

「看不到影片」的真正原因不在渲染，而在翻頁。 播放器一直把畫面寫進 framebuffer 的第 1/2 頁（雙緩衝），但 fb_pan() 裡是一句 return; /* no-pan 實驗 */——FBIOPAN 從來沒真正執行過，螢幕永遠停在 LVGL 桌面用的第 0 頁。也就是說：解碼、渲染、寫螢幕全都在正常工作，唯獨最後一步「把可見視窗切過去」沒做，使用者看到的就是紋風不動的桌面。修法用安全姿勢（這是之前核心崩過的血淚定案）：只信 FBIOGET_VSCREENINFO 取回的真結構體，校驗 yres_virtual >= 3840，改 yoffset 後再 ioctl(FBIOPAN_DISPLAY)。順帶給監控行程加了 fb_sys_home()——子行程被 SIGKILL 時來不及自己翻回第 0 頁，螢幕會凍在最後一影格上，監控得負責把畫面切回來。

教訓很樸素：換了幾何映射，先抓一影格 framebuffer 和已驗證的基準影格逐位元比對，再談上線。 我當時憑 bench 計時好看就當了真，結果方向是錯的——效能好和畫面對，是兩回事。

四、差點誤判：提速是不是引爆了廠商函式庫崩潰？

中間出了個插曲。剛換上新渲染跑直播源，20 秒裡 SIGSEGV 91 次、監控行程重啟 124 次。看現場日誌，崩在廠商函式庫 libstagefright_sprd_h264dec.so 處理完一影格之後，和之前定案的「OMX 輸入佇列 use-after-free」長得一模一樣。

第一反應是：渲染快了 12 倍 → 餵碼流的節奏快了 → 把廠商函式庫的競態/UAF 逼出來了。聽起來很合理，差點就這麼寫進結論。

但一次觀測不能定性。於是加了個環境變數開關 NETTV_RENDER=0 回退舊三遍法，用同一個二進位檔做 A/B：

渲染路徑 時長 SIGSEGV monitor 重啟
慢（三遍） 40s 0 6
快（單遍） 40s 0 3

快路徑不但沒崩，重啟次數還更少。那批崩潰是當時裝置/源的狀態問題（反覆 kill 之後的 ION/CMA 狀態、加上凌晨直播源乾涸），跟渲染路徑沒關係。

教訓很樸素：效能最佳化之後的第一批異常，很容易被歸因為「最佳化改了時序」。在定案之前，先做一個只切換最佳化、其它都不動的 A/B，成本很低，但能省掉一次錯誤定案。

五、順手踩到的幾個坑

  1. 裸 bionic 下 _exit 不 flush stdio。我們是 -nostdlib -Wl,--entry=main 直接進 main 的，bench 的計時、影格率心跳全打不出來——因為 _exit 直接走了，stdio 緩衝沒落盤。所有測點後面都得跟一句 fflush(0)，否則「沒有日誌」會被誤讀成「沒執行到」。

  2. 子行程日誌被監控行程重生時 O_TRUNC 截斷。監控每隔幾秒重生一次子行程，日誌每次都被清空，崩潰現場根本留不下來。改成 SIGSEGV 處理器追加寫一個獨立檔案 /tmp/nettv_segv.log，跨重啟保留。

  3. GCC 的塊分區重排 bug。加了點程式碼之後編譯器報錯：

    是 GCC 把函式切成 .part.0 之後給組譯器下了非法的 .size。建置腳本加 -fno-reorder-blocks-and-partition 解決。

  4. 單條 SSH 命令裡用 & 起背景行程不靠譜，後面的命令會被工作階段斷開截斷，連重導向檔案都沒創建。長任務一律寫成腳本上傳，再 nohup sh xxx.sh &。

  5. 子行程每輪固定停在 31 影格，不是崩潰。影格上限參數預設是 0（無限），真正原因是 load_chunk() 在 m3u8 段邊界拿不到新段（源乾涸）乾淨退出。看到「每輪影格數一樣」別急著往卡死上想。

六、現狀與下一步

渲染這一環已經不是瓶頸了（20ms）。但端對端影格率還沒提上去——因為源本身乾涸，每輪子行程只活到 31 影格，量不出真實 fps。接下來要用本機多 GOP 的 .ts 檔案源把解碼餵滿，排除源的干擾，再收拾剩下的：每輪 3MB 的 memcpy、slice 輪裡的 usleep(20ms)、以及簽名掃描。

一句話總結這類最佳化的思路：別急著給熱點函式上 NEON、上組譯，先問一句「我算的這些像素，最後有幾個真的會被看見」。很多時候把中間層砍掉，收益比指令級最佳化大一個數量級。
