展讯 SC9832A 网络电视攻坚（八）：给厂商库打补丁翻车记——我是怎么把活寄存器 ip 写坏的

前一篇把厂商库 libstagefright_sprd_h264dec.so 里那个”每 GOP 边界必踩坏链表节点”的 UAF 定性了，我兴冲冲地打了个二进制补丁：三处链表遍历加节点合法性校验。结果部署上去——一张帧都出不来了。这篇记录翻车原因（活寄存器被我当成了临时变量）和 v2 补丁的写法，顺带把 addr=0x747474 这个悬了半天的崩溃签名给结案了。

一、现象：config 阶段就崩，0 帧

补丁版二进制跑起来，子进程日志停在：

SEGV 处理器抓到的现场：

addr=0x747474（”ttt”）、pc=0x636363（”ccc”）、sp=0x706d616c（”lamp”）——三个都是 ASCII。10-17 晚上我就是被这个签名带偏的：一看全是 ASCII，就推断”我们的 NAL/环形缓冲拷贝路径有越界写，把码流数据写进了栈和堆”，然后花了一整晚审 rb_put / load_chunk_local / cfg memcpy 的长度来源，一无所获。

二、先做 A/B，别急着改代码

这次学乖了，先用环境变量把”补丁库”和”原库”切成两半各跑 40 秒：

版本 结果
补丁库（自动启用） stat_lines=0、segv=1、cfg_crash=1 —— 一张帧都没有
原库 NETTV_H264DEC_SO=/system/lib/... config 通过，出帧（27/22/4 帧一轮），但仍卡在 AU[102]（GOP 边界 116686B 大 IDR）挂死 → monitor 重启

结论一句话：补丁本身是坏的，原库的行为才是对的（能出帧，只是 GOP 边界还会挂）。0x747474 是补丁自己的产物，不是什么”流数据越界写”。之前那个”统一病根”假设作废。

教训：崩溃签名长得像”内存被数据砸烂”时，先别去审自己的拷贝路径。先 A/B 排除自己刚改动的东西——这次改动（补丁库）就在最可疑的位置，我却先假设是老代码的问题。

三、反汇编：ip 是活的，我把它当临时寄存器用了

把原始 .so 的 findCodecConfigData（0x7b80 起）相关片段扒出来（ARM 32 位，不是 Thumb）：

看到 7e1c: mov r2, ip 了吗？**ip（r12）在整个双层循环期间是恒定值——首节点**，外层每轮回边都要从它重新起步。

而我 v1 补丁为了把节点指针传进 thunk，在两个 site 都写了：

以及 site B 的 7e58: mov ip, lr。这一下子把 ip 变成了”上一次的外层节点”，下一轮 mov r2, ip 拿到的根本不是首节点，内层计数 fp、比较 cmp fp, r3 全错，最后走到某个虚调用就踩到了垃圾指针——于是 pc=0x636363、addr=0x747474。

顺带还查出 v1 第二个 bug：site C 的 thunk 里 add r4, r4, #1 紧跟 pop {r4, pc}，栈上弹回来的旧值把刚加的 1 覆盖掉，r4 永远加不上去。

四、v2 怎么写：找一段”死”的寄存器

补丁 thunk 必须借一个寄存器传参（因为 bl 会冲掉 lr），但 ip 不能用。逐条看这段循环的寄存器生命周期后发现：**r0 在 0x7e1c 到 0x7e44 之间是死的**——它上一次的定义在 7e00~7e14，下一次使用在 7e44 ldr r0,[fp,#0x24] 被重新赋值。于是：

  • site 上写 mov r0, lr（把外层节点指针塞进死寄存器 r0）；
  • thunk 里用 r0 取 next / 做合法性校验，临走用 mov lr, r0 把 lr 还原；
  • thunk 只 push {lr} … pop {pc}，不弹 r4，不碰 ip；
  • 坏节点处置：内层 site 置 r2 = r8（哨兵）让 cmp r2,r8 立即相等退出；外层 site 置 r2 = 0 让 7e60 bne 不成立退出——比 v1 的 mov lr, r8 安全，不再去解引用哨兵。
  • 干脆不碰 site C（0x83e8 兜底路径，收益低风险高）。

六、实测结果（2026-10-18 补测）

v2 补丁推到设备后跑了 75 秒，结论有点扎心但很有价值：

指标 v1 补丁 原库 v2 补丁
DRIVE empty(SPS) 崩溃 1 0 0
出帧 0 帧 正常（8.6fps） 正常（8.8fps）
SIGSEGV 1 0 0
monitor 重启 0（因为压根没帧） 每轮固定 @27 帧 每轮固定 @27 帧

三件事：

  1. v2 确实修好了 v1 的 bug —— config 阶段不再崩，说明”用 r0 代替 ip”这个修法是对的。补丁本身现在无害。
  2. 但它没治住 GOP 边界挂死 —— 原库和 v2 一样，都是每轮精确停在 27 帧。
  3. 推论很重要：当前这个 GOP 挂死不是 site A/B 那种链表 UAF 崩溃，而是”卡住不返回”的死循环形态。给指针加合法性校验，对无限循环一点用没有——我之前把这两件事当成同一件事，这是个概念错误。

所以 v2 就不上生产了（没收益还多一份改动面），保持原库。

七、下一步

放弃”加固厂商遍历”这条路，改做进程内解码器重生：在 GOP 边界检测到挂死后，不退出整个进程（保住 m3u8 下载进度和环形缓冲里的码流），只重建解码器组件本身（Loaded→Idle→Executing 重新走一遍 allocateBuffer + config）。这样既避开厂商库的累积性损坏，又不会重播上一段。

顺带记一条：设备重启后磁盘从 348M 掉到 203M 可用，/tmp 日志清理收益很小，说明还有别的长期增长源，得查一下。

八、补丁落地前的三条纪律（都是踩出来的）

  1. 洞必须在可执行映射内。10-17 首版把 thunk 写到了 0xdd18 —— 那是 .got/.data，linker 把机器码当动态表项解析，解码直接全瘫。可用区间是 .rodata 段尾的零洞 0xcdc4..0xd000（落在 LOAD1 R+X 映射内）。
  2. 改 so 前先把原始指令逐条扒出来，确认被替换的指令宽度与语义（add fp,fp,#1 这类副作用要在 thunk 里补做）。
  3. 补丁一定要能用环境变量一键回退。这次能 5 分钟定位到”补丁是坏的”，全靠 NETTV_H264DEC_SO 这个逃生门。

六、当前状态与下一步

v2 补丁（outputs/patch_h264dec_uaf_v2.py → h264dec_uaf_v2.so）已经生成并推到设备，但验收跑之前设备的 sshd 会话被耗尽了（22 端口 banner 直断，只能断电重启），实测数据下次补。

重启后的验收判据：

  • DRIVE empty(SPS) 崩溃 计数 = 0（config 不再被补丁搞崩）；
  • [STAT] 帧数能单调涨过 31（不再每轮停在同一帧数）；
  • monitor 重启明细里不再出现”卡在 AU[102] 附近”的固定模式。

如果 v2 也压不住 GOP 边界挂死，那就说明遍历加固这条路不对，得换思路：在进程内做解码器重生（保住 m3u8 进度），或者干脆按 GOP 配额只喂到边界前、用下一个 IDR 重置解码器状态。
