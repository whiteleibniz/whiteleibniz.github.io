netTV 硬解攻堅(八)：給廠商函式庫打補丁翻車記——我是怎麼把活暫存器 ip 寫壞的

wlb
2026-10-18
ARM彙編, SIGSEGV, UAF, VSP, h264dec, 二進位補丁, 展訊, 硬解

前一篇把廠商函式庫 libstagefright_sprd_h264dec.so 裡那個「每個 GOP 邊界必踩壞鏈結串列節點」的 UAF 定性了，我興沖沖地打了個二進位補丁：三處鏈結串列走訪加節點合法性校驗。結果部署上去——一張影格都出不來了。這篇記錄翻車原因（活暫存器被我當成了暫時變數）和 v2 補丁的寫法，順帶把 addr=0x747474 這個懸了半天的崩潰簽名給結案了。

一、現象：config 階段就崩，0 影格

補丁版二進位檔跑起來，子行程日誌停在：

SEGV 處理器抓到的現場：

addr=0x747474（”ttt”）、pc=0x636363（”ccc”）、sp=0x706d616c（”lamp”）——三個都是 ASCII。10-17 晚上我就是被這個簽名帶偏的：一看全是 ASCII，就推斷「我們的 NAL/環形緩衝拷貝路徑有越界寫，把碼流資料寫進了堆疊和堆積」，然後花了一整晚審 rb_put / load_chunk_local / cfg memcpy 的長度來源，一無所獲。

二、先做 A/B，別急著改程式碼

這次學乖了，先用環境變數把「補丁函式庫」和「原函式庫」切成兩半各跑 40 秒：

版本 結果
補丁函式庫（自動啟用） stat_lines=0、segv=1、cfg_crash=1 —— 一張影格都沒有
原函式庫 NETTV_H264DEC_SO=/system/lib/... config 通過，出影格（27/22/4 影格一輪），但仍卡在 AU[102]（GOP 邊界 116686B 大 IDR）卡死 → monitor 重啟

結論一句話：補丁本身是壞的，原函式庫的行為才是對的（能出影格，只是 GOP 邊界還會卡）。0x747474 是補丁自己的產物，不是什麼「流資料越界寫」。之前那個「統一病根」假設作廢。

教訓：崩潰簽名長得像「記憶體被資料砸爛」時，先別去審自己的拷貝路徑。先 A/B 排除自己剛改動的東西——這次改動（補丁函式庫）就在最可疑的位置，我卻先假設是老程式碼的問題。

三、反組譯：ip 是活的，我把它當暫時暫存器用了

把原始 .so 的 findCodecConfigData（0x7b80 起）相關片段扒出來（ARM 32 位元，不是 Thumb）：

看到 7e1c: mov r2, ip 了嗎？**ip（r12）在整個雙層迴圈期間是定值——首節點**，外層每輪回邊都要從它重新起步。

而我 v1 補丁為了把節點指標傳進 thunk，在兩個 site 都寫了：

以及 site B 的 7e58: mov ip, lr。這一下子把 ip 變成了「上一次的外層節點」，下一輪 mov r2, ip 拿到的根本不是首節點，內層計數 fp、比較 cmp fp, r3 全錯，最後走到某個虛擬呼叫就踩到了垃圾指標——於是 pc=0x636363、addr=0x747474。

順帶還查出 v1 第二個 bug：site C 的 thunk 裡 add r4, r4, #1 緊跟 pop {r4, pc}，堆疊上彈回來的舊值把剛加的 1 覆蓋掉，r4 永遠加不上去。

四、v2 怎麼寫：找一段「死」的暫存器

補丁 thunk 必須借一個暫存器傳參（因為 bl 會沖掉 lr），但 ip 不能用。逐條看這段迴圈的暫存器生命週期後發現：**r0 在 0x7e1c 到 0x7e44 之間是死的**——它上一次的定義在 7e00~7e14，下一次使用在 7e44 ldr r0,[fp,#0x24] 被重新賦值。於是：

  • site 上寫 mov r0, lr（把外層節點指標塞進死暫存器 r0）；
  • thunk 裡用 r0 取 next / 做合法性校驗，臨走用 mov lr, r0 把 lr 還原；
  • thunk 只 push {lr} … pop {pc}，不彈 r4，不碰 ip；
  • 壞節點處置：內層 site 置 r2 = r8（哨兵）讓 cmp r2,r8 立即相等退出；外層 site 置 r2 = 0 讓 7e60 bne 不成立退出——比 v1 的 mov lr, r8 安全，不再去解參照哨兵。
  • 乾脆不碰 site C（0x83e8 兜底路徑，收益低風險高）。

六、實測結果（2026-10-18 補測）

v2 補丁推到裝置後跑了 75 秒，結論有點扎心但很有價值：

指標 v1 補丁 原函式庫 v2 補丁
DRIVE empty(SPS) 崩溃 1 0 0
出影格 0 影格 正常（8.6fps） 正常（8.8fps）
SIGSEGV 1 0 0
monitor 重啟 0（因為壓根沒影格） 每輪固定 @27 影格 每輪固定 @27 影格

三件事：

  1. v2 確實修好了 v1 的 bug —— config 階段不再崩，說明「用 r0 代替 ip」這個修法是對的。補丁本身現在無害。
  2. 但它沒治住 GOP 邊界卡死 —— 原函式庫和 v2 一樣，都是每輪精確停在 27 影格。
  3. 推論很重要：目前這個 GOP 卡死不是 site A/B 那種鏈結串列 UAF 崩潰，而是「卡住不返回」的無窮迴圈形態。給指標加合法性校驗，對無限迴圈一點用都沒有——我之前把這兩件事當成同一件事，這是個概念錯誤。

所以 v2 就不上生產了（沒收益還多一份改動面），保持原函式庫。

七、下一步

放棄「加固廠商走訪」這條路，改做行程內解碼器重生：在 GOP 邊界偵測到卡死後，不退出整個行程（保住 m3u8 下載進度和環形緩衝裡的碼流），只重建解碼器元件本身（Loaded→Idle→Executing 重新走一遍 allocateBuffer + config）。這樣既避開廠商函式庫的累積性損壞，又不會重播上一段。

順帶記一條：裝置重啟後磁碟從 348M 掉到 203M 可用，/tmp 日誌清理收益很小，說明還有別的長期成長源，得查一下。

八、補丁落地前的三條紀律（都是踩出來的）

  1. 洞必須在可執行映射內。10-17 首版把 thunk 寫到了 0xdd18 —— 那是 .got/.data，linker 把機器碼當動態表項解析，解碼直接全癱。可用區間是 .rodata 段尾的零洞 0xcdc4..0xd000（落在 LOAD1 R+X 映射內）。
  2. 改 so 前先把原始指令逐條扒出來，確認被替換的指令寬度與語意（add fp,fp,#1 這類副作用要在 thunk 裡補做）。
  3. 補丁一定要能用環境變數一鍵回退。這次能 5 分鐘定位到「補丁是壞的」，全靠 NETTV_H264DEC_SO 這個逃生門。

六、當前狀態與下一步

v2 補丁（outputs/patch_h264dec_uaf_v2.py → h264dec_uaf_v2.so）已經產生並推到裝置，但驗收跑之前裝置的 sshd 工作階段被耗盡了（22 連接埠 banner 直斷，只能斷電重啟），實測資料下次補。

重啟後的驗收判準：

  • DRIVE empty(SPS) 崩溃 計數 = 0（config 不再被補丁搞崩）；
  • [STAT] 影格數能單調漲過 31（不再每輪停在同一影格數）；
  • monitor 重啟明細裡不再出現「卡在 AU[102] 附近」的固定模式。

如果 v2 也壓不住 GOP 邊界卡死，那就說明走訪加固這條路不對，得換思路：在行程內做解碼器重生（保住 m3u8 進度），或者乾脆按 GOP 配額只餵到邊界前、用下一個 IDR 重置解碼器狀態。
