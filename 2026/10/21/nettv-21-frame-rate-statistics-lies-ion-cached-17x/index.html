nettv-21：16.9fps 是假的——帧率统计口径骗了我们三个月，以及一个 17 倍的读帧提速（SC9832A 硬解排查实录）

🌐 语言：简体中文 · 繁體中文 · English

上一轮刚把”UI 点频道黑屏”修完，用户就丢了一句：**”播放效果有改进，但完全达不到正常观看标准。”**

这句话的价值在于它逼我回头看那些”已经优化过很多轮”的数字。结果一查不要紧——我们盯了三个月的帧率，从头到尾都是错的。

这篇记录两件事：一个是统计口径的陷阱（数字骗人），一个是真正的性能突破（读帧 17 倍提速），以及一个被推翻的方案（差点把设备搞崩）。

二、真正的瓶颈：88% 的时间不在解码上

知道真实帧率是 8.9fps 之后，我需要知道时间去哪了。播放器里早就有分段计时：

113ms 出一帧，对应 8.85fps——和实测的 8.9 完全吻合。这三段耗时拆开看：

段 耗时 占比 是什么
段循环 32.6ms 29% 投喂 AU + 等厂商排空
读帧 44.3ms 39% 3MB memcpy（ION → staging）
渲染 33.0ms 29% NV12 → ARGB → 旋转 → 写 fb

而厂商自己的解码耗时，828 次采样全部是 14ms，纹丝不动。

换句话说：VSP 硬件解码只占了 12%，88% 的时间是我们的后处理。 硬件完全不是瓶颈，瓶颈在”把解码好的帧搬到屏幕上”这段路上。

这个认知很重要——它意味着所有”优化硬解性能”的方向都是错的，方向应该是”优化数据搬运”。

三、突破：uncached 内存是元凶

读帧段 44.3ms 干的事就一件：

3MB / 44.3ms = 68MB/s。这个带宽低得离谱——正常 DDR 内存 memcpy 能到 1GB/s 以上。

原因在 ION 分配的 flags：

flags=0 意味着 uncached 映射。在 uncached 映射上，每读一个 cache line 都要独立发起一次总线事务，硬件预取完全帮不上忙，68MB/s 就是这么来的。

这里踩了一个坑，位置很关键：invalidate 必须在 staging memcpy 之前。因为 memcpy 的源就是那块 DMA 区，先拷后 invalidate 等于白做。原来的代码只在 pipeline 路径的渲染线程里做了一次 invalidate，而且是在 memcpy 之后——单线程路径开着 cached 就会读到脏数据（花屏）。

教训二：当一个数字明显偏离物理常识时（68MB/s），先怀疑映射属性，再怀疑算法。 同样的 memcpy，改一个 flag 就快 17 倍。

四、被推翻的方案：换个堆来躲池子

改完 cached 之后我遇到一个新问题：厂商解码器的 C1 缓冲区分配开始报 OOM：

更糟的是，厂商拿不到 C1 之后会退回到 CPU 虚拟地址当物理地址用（”三级取址全失败 → 退回 CPU VA(假PA, 花帧风险!)”），然后 VSP 往一个无效地址写帧 → SIGSEGV。

诊断后发现是同池竞争：我们的输出 buffer 是 3.2MB，必须 order-8 连续块；而厂商那 5 块 638KB 的 C1 DPB 也要 order-8（它的 align=8）。carveout 池里的 order-8 大块总数只有 4 块（8MB），我们占 1 块，厂商就不够了。

我的第一反应是：那我们换个池子不就行了——把输出 buffer 改用 mask=2（System RAM）而不是 mask=8（carveout_mm）。厂商自己的 2MB C1 本来就用 mask=2，看起来完全可行。

于是我改代码、编译、部署、跑验证。然后设备直接重启了。

没有 oops，没有 panic，/proc/sys/kernel/watchdog = 1，dmesg 是一堆 powerdown_cpus。查物理地址才发现原因：

mask=2 和 mask=8 拿到的是同一个 carveout 区域（0x9f8xxxxx），并不是”System RAM”。而真正的 System RAM 在 0x80000000-0xbfffffff，mask=2 抢到的是那里的高地址——超出了 VSP 硬件能访问的地址窗口，VSP 往那儿写就飞了，硬件看门狗直接复位。

教训三：同一个 mask 名字在不同上下文里可能完全不是一回事。 我看到”厂商用 mask=2 能成功”，就以为 mask=2 = System RAM = 安全的另一块池子——但那两个 mask=2 的分配落到了完全不同的物理区域，一个是 0x9f8xxxxx（carveout），一个是 0x8xxxxxxx（真 RAM）。参数名相同不等于语义相同，必须看实际物理地址。

好在这个方案在造成硬件复位之前就被测出来了，没有造成更大后果。回滚到 mask=8。

六、再进一步：把渲染的 30ms 也拆开

改完 cached，我给 fb_render 加了分段计时（转换 vs 写 fb）：

写 fb 只占 1ms——3.6MB 写进 mmap 的 framebuffer 几乎不花钱（内存带宽足够）。30ms 全在”NV12 → ARGB + 旋转 + 3/2 降采样”这段纯算术上。

但纯算术不该这么慢。算一下：92 万像素，每像素 3 次乘法 + 6 次移位 + 6 次分支 clamp，总共 200 多万次乘加，在 Cortex-A7 上撑死 1~2ms。差的 28ms 去哪了？

cache miss。 渲染的访存模式是转置的——输出第 (oy, ox) 像素取源图的 [1079-ox*3/2][oy*3/2]，源行随输出列走、源列随输出行走，每个源像素的相邻输出像素在源图里隔了 1.5 像素。源图 3MB，一帧要跨 1080 个源行各取 720 个点，每次换行都是一次新的 cache line 拉取。

这解释了为什么之前”查表化”反而更慢（39.3ms vs 32.5ms）——查表把 miss 从源侧搬到了表侧，净收益为零。

解法不是改算法，是改分组粒度：原来的实现每次处理 16 个输出行（一个”带”），每个源行只读 24 字节（约 37% 条 cache line）。改成 64 行后，每个源行读 96 字节，而相邻带读的正是同一批 cache line 的相邻段——在 L2 里就能复用。

实测：渲染 34.3 → 30.3ms，真实帧率 12.4 → 13.1fps。抓屏确认画面几何无任何变形（台标位置、字幕、色彩全部正常）。

教训五：算术便宜不代表访存便宜。 同样是 200 万次乘加，标量和 NEON 差不多；但”每个源像素拉一次 cache line”和”每 4 个源像素拉一次”，差 10 倍。

每帧墙钟 113.0 ms 70.6 ms
[STAT] 帧率口径 虚高 2 倍 真实帧数

厂商解码 14ms 是硬底线，理论上限 1000/(14+30) ≈ 23fps。

八、这轮还踩了两个坑，值得单独记一笔

坑一：把”更省内存”当成”更好对齐”

我们的输出 buffer 是 3.25MB，精确帧尺寸是 3.13MB——我以为首选精确尺寸能省 140KB、给厂商的 C1 多留点空间。结果 OOM 从 1 次涨到 28 次。

原因很朴素：3.13MB 凑不出 order-8 的整块，3.25MB 能凑。尺寸阶梯的第一项不是”最省的”，是”最好对齐的”。

坑二：perf 采样系数写死，两个指标开始互相打架

把带高从 16 改成 64 之后，[perf] fb_render 均值 报 133ms，而 [perf] AU 里的”渲染=”报 30.3ms——同一份代码，两个指标差 4 倍。

采样换算系数是写死的 * 20（80 个带、每 20 个采样一次）。带高变 64 之后变成 20 个带、每 5 个采样一次，系数应该改成 * 5。这种”魔法数字”一旦和结构参数脱钩，指标就废了。

教训六：性能工具本身也是需要维护的代码。 它的常量跟被测对象耦合得越紧，改一边就要改另一边。

九、下一步

  1. 带高继续加大（64 → 128 / 256）：验证 DRAM 流量是否还能降，直到渲染段不再随带高变化
  2. NEON 化 YUV→ARGB：设备 CPU（ARMv7 rev5）支持 neon，编译链也已带 -mfpu=neon-vfpv4，
    之前只是没人写 intrinsics。算术部分（3 乘法 + clamp）用饱和指令 vqmovun 可以压到 1/4
  3. 换转置的实现方式：当前是”读源侧顺序、写输出侧转置”，天然的 cache 灾难。
    改成”双线性缩放 + 先缩到 720×1280 再转置”可能让访存变连续
  4. fb 直写优化：当前是 mmap 写 3 页 fb + PAN，有没有硬件 overlay 路径
  5. 池冲突根治：让我们的输出分配排在厂商 C1 之后

最后一句：这轮最有价值的产出不是那 17 倍，而是把”16.9fps”这个假数字变成了”8.9fps”这个真数字。一个虚高的指标会让你以为”再优化一点就够了”，而真实数字告诉你：还差得远，但方向明确——不在解码，在搬运。
