把网络电视调通：从一天崩三次到连续播 4800 帧

设备：展讯 SC9832A（sc8830 系列），Alpine/armv7l，720×1280 竖屏，LVGL 桌面。
目标：HLS 直播流用 VSP 硬件解码输出到 framebuffer，达到安卓官方播放效果。
最终：辽宁卫视《乡村财富》稳定播出，uptime 36 分钟零重启，4808 帧上屏。

起点：每轮必崩

新版代码每跑必崩，崩在相位桩最后一行：

sigsetjmp 拦不住，dmesg 无 OOM，内存还剩 882 MB。内核态崩溃。

五个根因，五次 A/B

根因 1：调试代码自己就是崩因

10-18 晚上我加了一套”挂死现场取证”：vrp_hook() hook 厂商的 VSP 寄存器写函数，
每次调用都从 rb + 0x60901000 / rb + 0x60908000 直接读 MMIO 寄存器窗口；
tr_line() 更狠，每次 DRIVE 前后各读一次。

vrp_hook 是每一轮轮询都会走的高频路径。于是 VSP 状态机被打乱，
崩在紧随其后的 DRIVE fill(out)#1。

崩溃点不在调试代码那行，所以栈、日志、信号处理全都指不到它。
旧版（能跑的）完全没有这段代码——这才让我想到去比。

修法：NETTV_TRACE_MMIO 默认 0，直接 return 不碰 MMIO。
验证：跑到 AU[1100]+，564 次 fill 全返回，零重启。

根因 2：NAL 切碎

三次崩溃现场的铁证——崩点永远紧跟一个被切成多片的 NAL：

A/B 决定性：NETTV_CHUNK=0 → 1200 帧跑到 AU[1100]+ 零重启；默认 4096 → 每轮必崩。

机理推断：厂商库对”同一 NAL 分多次 nOffset 续投同一 buffer”的处理有缺陷。
（我最初查错了方向——NETTV_SPLIT 管的是拆 NAL 边界，切碎由 g_chunk 决定，两者不同。）

根因 3：虚拟地址当成物理地址 → 一片绿

日志里两行并列就是铁证（同一个 fd=12）：

厂商 VSP 按 handle->ints[12] 当物理地址写帧，我填的却是 mmap 的虚拟地址。
硬件访问不到用户态虚拟地址 → 写不进真显存 → 屏上一片绿。

修法：新增 g_gh_pa[] 存真 PA，4 处 fh[12] 全部改填 PA，VA 只留给 CPU 读帧。

根因 4：ION 抢不到 + 不释放

自管 ION（heap mask=8 carveout_mm，物理连续）抢到时一切正常，抢不到时
ghOut 会退回 gralloc 的真 handle——而 gralloc 走 IOMMU heap，无物理连续 backing，
VSP 拿假 PA 写帧必崩内核。

两个改动：重试 6 轮 + 120ms 退避 + 尺寸阶梯；仍抢不到就 _exit(12) 让看门狗重生，
宁可不出画面也不打飞内核。另外退出前调 ION_IOC_FREE(0xc0044901) 主动释放。

根因 5：最贵的那个——是我自己

ps | grep -c nettv_player 显示堆了 12~23 个僵尸进程。

每轮调试我都 nohup 起一个脚本，而 monitor 内部还会自己重生 worker/worker-dl/mplayer，
每轮实验多留一整套，每个抢 2MB C1 缓冲 → 池被撑爆 → 后续起不来。

pgrep -x nettv_player 只数主进程，看不到这些，所以我一度误判成”内核泄漏”，
还专门写了个 ion_release() 去救火。

pkill -f nettv_player 全清后，池立刻回到 total 0，立刻就能正常播。

这一条最值钱：**症状和真因差了十万八千里，而唯一的分界线是”多问一句 ps”**。

最后一小时：抓屏骗了我一小时

画面明明上屏了，我抓屏看到的却是旧的 WiFi 设置页，连抓 4 张内容一模一样。

真因：/sys/class/graphics/fb0/virtual_size = 720,3840 —— fb 有 4 页，
我的抓屏脚本只读第 0 页。而 fb_render() 每帧写 g_fbpg*720*1280*4 偏移
并 fb_pan() 翻页，内容在第 1/2 页。

抓屏看到旧画面 ≠ 没上屏。 先查 virtual_size，再下结论。

顺手把抓屏脚本改成自动：驱动 pan_offset 恒 0 读不到当前页，于是逐页统计
色彩种类数取最多者（实测 page0=55 色残留旧页 vs page1=617 色真实画面）。
中间试过”采样求和”，结果选反了——求和反映亮度不反映多样性。

最终验证

方法论复盘

1. 「调试代码自己就是崩因」是一类独立故障模式。
它不会崩在自己那行，所以栈和日志全都指不到它。
只有把能跑的旧版和崩的新版摆在一起，逐字段比对运行时状态，才看得出”旧版没有这段”。

2. 崩点模式比”猜假设”有力得多。
根因 2 是靠”崩点永远紧跟 subN/M”这个模式一眼看出来的，
而不是靠推理。拿到多次崩溃现场，第一件事是找它们的共同模式。

3. 排查期必须有绝对可靠的取证通道。
这个项目 stdout 被自定义 stdio 的 4KB 块缓冲吞掉，崩溃时缓冲区全丢——
我一度靠空日志误判过三次。后来改用 O_SYNC 直写的相位桩，
每次脚本上传都 md5sum 校验（踩过 3 次 0 字节脚本导致误判”新版不崩”）。

4. 「跑不起来」先 ps 一遍。
真的，这个成本 1 秒，能省掉一小时的错误归因。

5. A/B 是唯一诚实的实验。
本文五个根因，每一个都是”改一个变量、跑一次、对比”定出来的。
凭推理猜出来的假设，我试了八个，全错。
