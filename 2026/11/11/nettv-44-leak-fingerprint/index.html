netTV 硬解（44）：给「泄漏」造一台秤——崩溃间隔指纹与观测有效性闸门

wlb
2026-11-11
Debugging Methods, Embedded, Hardware Decode, Spreadtrum SC9832A, VSP

🌐 语言：简体中文 · 繁體中文 · English

系列第 44 篇。上一轮把崩溃定性成「累积漂移」，也就是要按泄漏查。
但「泄漏」是个太便宜的词——它可以是内存池耗散、可以是句柄、也可以是每 N 段的固定动作。
这一轮不碰播放器一行代码，只做一件事：造一台能称出”是哪种”的秤。

定性之后，问题变成了”哪种”

设备那天依旧没上电，只能离线推进。翻回上一轮的结论：两个 1200 秒的臂各崩 6 次和 7 次，
间隔 151~186 秒，帧率正常，崩溃点随真实流推进走。结论是「累积漂移」——但这句话能推出的
下一步动作有好几个，方向完全不同：

  • 如果间隔在缩短，那是典型的泄漏曲线（每轮少一点余量，越到后面越快撞墙）；
  • 如果间隔恒定，那更像固定槽位/定时器——每 N 帧、每 N 段、每 N 秒必然越过某条边界；
  • 如果内存曲线在掉但间隔不变，那是耗散与崩溃两个独立现象，别硬捆在一起归因。

这三种情况的修法完全不重叠。所以真正缺的不是采样器（早就有了逐线程 SigBlk、RSS、ION 的
轮询脚本），而是一台判决器：把「间隔序列」和「内存序列」变成一个有名字、带前提条件的结论。

分工：设备只做哑采集，判决全在 PC

这条链的设计原则是能不说话的一律不说话：

  • 设备端只有一个采集器：跑一次单臂 2400 秒（约 40 分钟），每 10 秒记一行
    MemFree / CmaFree / ION / 各进程线程数、RSS、fd，同时把 phase.log 里新出现的
    mon-child-signal=11 连同墙钟时间抄进崩溃台账；
  • 判决全部放在 PC 侧的脚本里，因为设备上没有 Python，而且 SSH 会话绝不能挂 40 分钟——
    长任务必须拆成「设备后台脚本 + 短轮询」。

采集器还做一件容易被忽略的事：它自己也出一份完整性闸门。跑完写 GATE=OK 或
GATE=FAIL 原因=...，条件包括开跑残留为零、结束时残留为零、有帧率统计、采样条数够、
跨度够。这份 GATE 会被 PC 端再算一遍。

先证明”这轮观测有效”，再谈趋势

这是整个方法论里最贵的一条经验，也是我反复踩的坑：最省事的运行永远看起来最干净。
解码器没起来、源挂了、进程被残留挡住——这些情况下崩溃数当然是 0，而 0 会被顺理成章
读成”这个配置不崩”。

所以判决器的第一段代码不是统计，是闸门：

闸门 判据 不满足说明什么
开跑残留 0 上一轮没清干净，配置可能没生效
帧率 fps_x10 ≥ 50 且统计行 ≥3 根本没解码，崩溃数为 0 无意义
收尾残留 0 收尾没收干净，下一轮污染
采样条数/跨度 ≥ 期望的 80% 采集被截断，趋势是半截数据
采样断档 相邻样本 ≤ max(60s, 5×间隔) 中间缺了一大段，不能当连续趋势

任何一条不过，判决直接是 INVALID，并且明确写”禁止据此改任何代码”。

更进一步：闸门和判决各写两遍。设备端是 shell 的 gate_eval，PC 端是 Python 的
_gates()，两套独立实现，结论不一致就判 INVALID（交叉不一致）。这一条不是洁癖——
本轮正是靠它抓到了自己的一个 bug（见下）。

判决档位：把”泄漏”拆成能动手的几种

间隔趋势不看方差，只看「首末相对变化 + 线性拟合的 r²」；内存趋势看 CmaFree 的斜率、
r² 和总跌幅，按量级分「泄漏量级」与「漂移量级」两档。

VERDICT 触发条件 下一步该查什么
LEAK_CONFIRMED 间隔递减且内存耗散达泄漏量级 每轮崩溃周期内新分配未释放的对象
LEAK_LIKELY 间隔递减，内存只有漂移量级 先按泄漏查，核对 fd/线程数与崩溃速率是否同比
LEAK_SUSPECTED 间隔递减但内存平稳 非内存类累积：fd、线程、池槽位、厂商内部句柄
PERIODIC_WITH_DRIFT 间隔恒定但内存在掉 固定槽位/定时器，耗散是伴生现象
PERIODIC_TIMER 间隔恒定且内存平稳 每 N 帧/N 段/N 秒的固定动作（重连、重新 init、指针回绕）
SLOWING 间隔变长 可能与源切换、GOP 长度变化相关
RANDOM 无规律 偏向随机踩内存，回去做 pc 映射与缓冲区边界
STABLE 零崩溃且观测够长 不能据此说修好了，要 ≥4~5 个故障周期

最后一行值得单独说：断言”配置 X 不崩”，观测时长必须是故障周期的 4~5 倍。这是泊松分布
给的数——跑 1 个周期就”没复现”的概率还有 37%，5 个周期才降到 0.7%。

四个 bug：全都是”工具把自己伪装成结论”

这一轮最有价值的部分不是那两个脚本，而是自检抓出来的四个自伤：

① 贪婪正则把间隔全算成 0。
崩溃行的格式是 t=1117000 mon-child-signal=11 st=0x8b。想取毫秒时间戳，于是写了
sub(/^.*t=/,"")——行尾的 st= 里也含 t=，贪婪匹配一路吞到那里，剩下的 0x8b
再被剥成 0。四个崩溃算出来三个间隔，全是 0，看起来像”节拍极其稳定”。改成按首字段
split 取值，自检当场由 FAIL 转 PASS。

② Windows 文本模式写 shell 脚本，变成 CRLF。
用 Python 打个补丁改了脚本里的几行，open(p,"w") 在 Windows 上会把 \n 翻成 \r\n。
dash 解析到第 46 行报 "|" unexpected——因为上一行结尾是反斜杠续行，\ 后面跟的
是 \r 而不是换行，续行失效。这个错误离真正的问题（文件编码）隔了 250 行，纯属
“报错位置骗人”。设备上没有 CRLF 转换工具，这种脚本传上去只会全盘失败。

③ 交叉校验恒报不一致，而且不一致没有降级。
meta 里一行 GATE=OK 被按首个 = 切分成 key=GATE, value=OK，而校验代码写的是
value.startswith("GATE=OK")——永远 False，于是每一轮都报”交叉不一致”。
更糟的是不一致只往原因列表里塞了一条，没有把 ok 置假：结果是判决照样给出
PERIODIC_WITH_DRIFT，而理由里写着”交叉不一致”。结论和前提自相矛盾，这比不校验更危险。
修法是先归一化，再让不一致必须降级。

④ 用方差判”在加速”，把 186→128 判成了恒定节拍。
cv（标准差/均值）小既可能是恒定节拍，也可能是均匀地越崩越快——本轮 demo 数据
186、179、168、155、141、128 秒，cv=0.13 很”稳”，r²=0.99 是漂亮的直线下降，
却因为 cv≤0.20 先命中了 PERIODIC。判据改成「首末相对变化 ≤15% 且 cv 小」才算恒定，
方向性交给 r² 和相对斜率。

四个 bug 的共性很清楚：它们都不是让程序崩，而是让程序给出一个”看起来很合理”的错误结论。
对策也就三条，都不新鲜但必须落地：

  1. 自检要断言期望的判决名，而不只是”没有 FAIL 行”——上次的教训是相位函数没载入时
    计数器为 0，测试工具直接变成”永远通过”；
  2. 关键判据写两遍，用两份独立实现互相对账；
  3. 加变异用例：把同一个数据集里的帧率改成 0、残留改成 2，判决必须掉进 INVALID。
    如果变异后结论不变，说明闸门根本没在起作用。

现状与下一步

这一轮没有编译、没有部署、没有改现网二进制的任何一个字节——采集器跑的是现网包装脚本的
原样配置。离线验证做到两件事：shell 自检 13 项（间隔解析、码率余量、闸门六态、全零假通过）、
Python 端 17 项（含 4 组变异与 2 条解析/交叉回归），以及闸门失败分支在本机的实跑
（不会启动播放器，只验证参数流、闸门与 meta 生成）。

设备上电后的顺序是固定的：先跑 2400 秒单臂，把 meta 和崩溃台账取回，再让判决器说话。
如果它说 PERIODIC_TIMER，泄漏这条线就得让位给”固定动作”假设；如果说 LEAK_*，
那就顺着 fd/线程数曲线去定位每轮的净增量。在拿到 4~5 个崩溃间隔之前，任何改动都是猜。
