netTV 硬解（34）：SIGSEGV 處理器一次都沒跑到——把「猜」換成「可證偽的測量」

wlb
2026-11-01
Linux 信號, VSP 硬解, 展訊 SC9832A, 崩潰取證, 嵌入式

🌐 語言：简体中文 · 繁體中文 · English

系列第 34 篇。上一輪把「fork 提前到 VSP 之前」這個假設證偽之後，手上只剩一條線索：worker 每跑 4000~5000 幀被 SIGSEGV 殺一次，而我們的 SIGSEGV 處理器一次都沒有執行過。這一篇不修 bug，先把「為什麼處理器跑不到」在核心層面解釋清楚，再把剩下的三種可能做成各自可以被否定的測量，並配一套零改碼的取證工具。

1. 上一輪留下的那條線索

10 分鐘回歸裡出現了三次：

st=0xb = 被 SIGSEGV 殺死。詭異的地方有三點：

  1. 不是啟動期就死，而是老老實實跑了四五千幀才死（約 150 秒）；
  2. /tmp/nettv_segv.log 根本不存在——處理器一次都沒進去；
  3. 加過 sigaltstack + SA_ONSTACK 之後依然零輸出，於是堆疊溢位這條被排除。

2. 核心層面：為什麼處理器必然跑不到

排除掉「處理器本身寫崩了」之後，只剩一種系統性解釋：產生故障的那個執行緒把 SIGSEGV 遮蔽了。

關鍵點在核心的 force_sig_info()：硬體同步異常（缺頁、越界）產生的是執行緒導向信號，如果這個執行緒把該信號遮蔽了，核心不會讓行程掛住，而是——

  • 把該信號的動作**強制改回 SIG_DFL**；
  • 把該執行緒遮罩裡這一位清掉；
  • 然後立刻按預設動作殺掉整個行程。

於是現場表現恰好就是：行程死於 SIGSEGV，但使用者態處理器一次都不會被呼叫。這條語義把現象完全解釋通了，也把排查方向從「哪裡踩了記憶體」換成「哪個執行緒在遮蔽 SIGSEGV」。

順帶記一個便宜的讀取方式：執行緒的信號遮罩就在 /proc/<pid>/task/<tid>/status 的 SigBlk: 裡，是一個 16 位十六進位遮罩，信號 n 對應 bit (n-1)。SIGSEGV = 11 → bit 10 → 0x400。按末四位十六進位拆：

末四位位置 覆蓋信號 SIGSEGV 落在哪
d1（右數第 4 位） 13~16 —
d2（右數第 3 位） 9~12 是這一位
d3（右數第 2 位） 5~8 —
d4（右數第 1 位） 1~4 —

所以判定口訣只有一句：末四位右數第 3 個字元落在 {4,5,6,7,c,d,e,f} 裡，這個執行緒就遮蔽了 SIGSEGV。

3. 三條互斥假說，各自配一條能否定的判據

假說 內容 判據（看到什麼算成立） 被否定的樣子
H1 資源洩漏觸頂（每幀/每段/每 GOP 漏一樣東西） 執行緒數 / RSS / VSZ / fd / ION clients 單調上漲，死亡點落在峰值附近 曲線平坦，死亡點隨機
H2 某執行緒遮蔽 SIGSEGV（廠商函式庫自建執行緒最常見） 存在 SigBlk 命中上面那條口訣的執行緒 所有執行緒 SigBlk 為 0
H3 真的隨機踩記憶體 H1、H2 雙雙被否 —

三條假說都寫成「可以被否定的形狀」，價值在於：跑一次實驗，無論結果如何都有進展。這比「再猜一個原因改一版程式碼」便宜得多。

4. 為什麼這一輪堅持「零改碼取證」

  • 改碼會改變被觀測的對象。上一輪 v33 為了做假設改了 fork 時機，結果既沒修好崩潰，又引入了一個難以重現的核心重置疑點。
  • 在這個環境裡加日誌不便宜。播放器是裸 bionic（nostdlib + --entry=main），日誌只能靠手寫 write；歷史上就因為無節制寫日誌把磁碟撐到過 1GB。
  • 這套環境最貴的是連線時間。設備經常不在線（這幾輪連著幾次都是沒上電），能連線時應該先做「零編譯、零部署、結果確定」的動作。

所以本輪只做兩個腳本，不動一行 C：

_hw34.sh：純 /proc 採樣器

每 3 秒採一輪，三個日誌檔：

  • nettv_health.log：每個 nettv 行程一行 —— 執行緒數、RSS、VSZ、fd 數；
  • nettv_thr.log：每 18 秒記一次 worker 的逐執行緒明細 —— tid、執行緒名、SigBlk、SigCgt；
  • nettv_sys.log：系統面 —— MemFree、CmaFree、ION clients 數。

三個日誌都做了 400KB 封頂旋轉，避免重蹈 1GB 的覆轍。

_crash34.sh：一條命令的編排 + 自動彙總

起採樣器 → 清殘留 → 起播放器 → 坐等 → 彙總。彙總裡直接給出：

  • worker 的首個 / 末個 / 峰值樣本（一眼看出是不是單調上漲）；
  • 執行緒數時間線；
  • 執行緒名分布（出現新名字 = 執行緒洩漏的指紋）；
  • 命中 SIGSEGV 遮蔽口訣的執行緒（去重）；
  • 最接近崩潰那一幀的完整執行緒快照。

跑法是「設備端背景自跑」：腳本 2 秒內返回，PC 端只做短輪詢取 /tmp/cr34.log——這是連線約束逼出來的習慣（本機 sandbox 會對超時的 SSH 發 SIGTERM，洩漏的會話會耗盡 dropbear）。

5. 判據表：量出來之後該做什麼

量到的結果 結論 下一步
某個廠商執行緒 SigBlk 命中 H2 成立：崩潰被靜默化 在 fork 出的子行程裡顯式復位信號遮罩；能攔到就要攔 pthread_create
執行緒數 / fd / ION 單調漲到閾值就死 H1 成立：洩漏觸頂 按漲的那個量追分配點；順手把「每 N 段主動重生」作為兜底
全部平坦、無人遮蔽 SIGSEGV H3 才輪到 shm 黑盒子（每幀寫環節 id/幀號/段號，monitor 死後列印）
ION clients 一路漲 與 H1 同源，但更具體 回收路徑查 dmabuf fd 繼承（渲染池曾踩過）

6. 三條方法論回顧

  1. 「處理器沒跑到」本身就是最強的一條線索。它把原因空間從「所有可能的記憶體踩踏」壓縮到「信號被遮蔽的執行流」。
  2. 先做能否定的測量，再改程式碼。三個假說都預先寫好否定條件，跑一次就有進展，不至於「改了一版、結果沒變、什麼都沒學到」。
  3. 零改碼取證優先。不改二進位意味著結果可以和現網基線直接對比，也意味著設備不在線時照樣能把工具寫好。
