netTV 硬解（34）：SIGSEGV 处理器一次都没跑到——把「猜」换成「可证伪的测量」

wlb
2026-11-01
Linux 信号, VSP 硬解, 展讯 SC9832A, 崩溃取证, 嵌入式

🌐 语言：简体中文 · 繁體中文 · English

系列第 34 篇。上一轮把「fork 提前到 VSP 之前」这个假设证伪之后，手上只剩一条线索：worker 每跑 4000~5000 帧被 SIGSEGV 杀一次，而我们的 SIGSEGV 处理器一次都没有执行过。这一篇不修 bug，先把”为什么处理器跑不到”在内核层面解释清楚，再把剩下的三种可能做成各自可以被否定的测量，配一套零改码的取证工具。

1. 上一轮留下的那条线索

10 分钟回归里出现了三次：

st=0xb = 被 SIGSEGV 杀死。诡异的地方有三点：

  1. 不是启动期死，是老老实实跑了四五千帧才死（约 150 秒）；
  2. /tmp/nettv_segv.log 根本不存在——处理器一次都没进去；
  3. 加过 sigaltstack + SA_ONSTACK 之后依然零输出，于是栈溢出这条被排除。

2. 内核层面：为什么处理器必然跑不到

排除掉”处理器写崩了”之后，只剩一种系统性解释：产生故障的那个线程把 SIGSEGV 屏蔽了。

关键点在内核的 force_sig_info()：硬件同步异常（缺页、越界）产生的是线程定向信号，如果这个线程把该信号屏蔽了，内核不会让进程挂起，而是——

  • 把该信号的动作**强制改回 SIG_DFL**；
  • 把该线程掩码里这一位清掉；
  • 然后立刻按默认动作杀死整个进程。

于是现场表现恰好就是：进程死于 SIGSEGV，但用户态处理器一次都不会被调用。这条语义把现象完全解释通了，也把排查方向从”哪里踩了内存”换成了”哪个线程在屏蔽 SIGSEGV”。

顺带记住一个便宜的读取方式：线程的信号掩码就在 /proc/<pid>/task/<tid>/status 的 SigBlk: 里，是一个 16 位十六进制掩码，信号 n 对应 bit (n-1)。SIGSEGV = 11 → bit 10 → 0x400。按末四位十六进制拆：

末四位位置 覆盖信号 SIGSEGV 落在哪
d1（右数第 4 位） 13~16 —
d2（右数第 3 位） 9~12 是这一位
d3（右数第 2 位） 5~8 —
d4（右数第 1 位） 1~4 —

所以判定口诀只有一句：末四位右数第 3 个字符落在 {4,5,6,7,c,d,e,f} 里，这个线程就屏蔽了 SIGSEGV。

3. 三条互斥假说，各自配一条能被否定的判据

假说 内容 判据（看到什么算成立） 被否定的样子
H1 资源泄漏触顶（每帧/每段/每 GOP 漏一样东西） 线程数 / RSS / VSZ / fd / ION clients 单调上涨，死亡点落在峰值附近 曲线平坦，死亡点随机
H2 某线程屏蔽 SIGSEGV（厂商库自建线程最常见） 存在 SigBlk 命中上面那条口诀的线程 所有线程 SigBlk 为 0
H3 真·随机踩内存 H1、H2 双双被否 —

三条假说都写成”可以被否定的形状”，价值在于：跑一次实验，无论结果如何都有推进。这比”再猜一个原因改一版代码”便宜得多。

4. 为什么这一轮坚持”零改码取证”

  • 改码会改变被观测的对象。上一轮 v33 为了做假设改了 fork 时机，结果既没修好崩溃，又引入了一个难以复现的内核复位疑点。
  • 在这个环境里加日志不便宜。播放器是裸 bionic（nostdlib + --entry=main），日志只能靠手写 write；历史上就因为无节制写日志把磁盘撑到过 1GB。
  • 这套环境最贵的是联机时间。设备经常不在线（这几轮连着几次都是没上电），能联机时应该先做”零编译、零部署、结果确定”的动作。

所以本轮只做两个脚本，不动一行 C：

_hw34.sh：纯 /proc 采样器

每 3 秒采一轮，三个日志文件：

  • nettv_health.log：每个 nettv 进程一行 —— 线程数、RSS、VSZ、fd 数；
  • nettv_thr.log：每 18 秒记一次 worker 的逐线程明细 —— tid、线程名、SigBlk、SigCgt；
  • nettv_sys.log：系统面 —— MemFree、CmaFree、ION clients 数。

三个日志都做了 400KB 封顶旋转，避免重蹈 1GB 的覆辙。

_crash34.sh：一条命令的编排 + 自动汇总

起采样器 → 清残留 → 起播放器 → 坐等 → 汇总。汇总里直接给出：

  • worker 的首个 / 末个 / 峰值样本（一眼看出是不是单调上涨）；
  • 线程数时间线；
  • 线程名分布（出现新名字 = 线程泄漏的指纹）；
  • 命中 SIGSEGV 屏蔽口诀的线程（去重）；
  • 最接近崩溃那一帧的完整线程快照。

跑法是”设备端后台自跑”：脚本 2 秒内返回，PC 端只做短轮询取 /tmp/cr34.log——这是联机约束逼出来的习惯（本机 sandbox 会对超时的 SSH 发 SIGTERM，泄漏的会话会耗尽 dropbear）。

5. 判据表：量出来之后该干什么

量到的结果 结论 下一步
某个厂商线程 SigBlk 命中 H2 成立：崩溃被静默化 在 fork 出的子进程里显式复位信号掩码；能拦到就要拦 pthread_create
线程数 / fd / ION 单调涨到阈值就死 H1 成立：泄漏触顶 按涨的那个量追分配点；顺手把”每 N 段主动重生”作为兜底
全部平坦、无人屏蔽 SIGSEGV H3 才轮到 shm 黑匣子（每帧写环节 id/帧号/段号，monitor 死后打印）
ION clients 一路涨 与 H1 同源，但更具体 回收路径查 dmabuf fd 继承（渲染池曾踩过）

6. 三条方法论复盘

  1. “处理器没跑到”本身就是最强的一条线索。它把原因空间从”所有可能的内存踩踏”压缩到”信号被屏蔽的执行流”。
  2. 先做能被否定的测量，再改代码。三个假说都预先写好否定条件，跑一次就有推进，不至于”改了一版、结果没变、什么都没学会”。
  3. 零改码取证优先。不改二进制意味着结果可以和现网基线直接对比，也意味着设备不在线时照样能把工具写好。
