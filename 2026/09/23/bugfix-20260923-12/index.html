bugfix_20260923_12 — GBA 退出逻辑改为与 FC 逐行一致（取消 GBA 专属分支）

项目 内容
发现时间 2026-09-23
修复时间 2026-09-23
模块 lv_pages/gba_game_page.c
涉及版本 承接 bugfix_20260923_11 之后的现场（前端已分离）
现象等级 中（无新故障，属”消除结构分歧”的收敛性修复）
触发方式 用户明确要求：「你把 GBA 的改成 FC 的退出逻辑吧」

1. 问题现象

前端分离（bugfix_20260923_11）之后，GBA 与 FC 虽然各用一个二进制，但退出逻辑仍不是同一套：
GBA 页保留了一条 FC 页没有的”提前放行”路径（exiting 标志 + 后台收尸线程 + 画面连刷 3 帧）。

这条路径是 09→10→11 三轮故障中反复出问题的地方。用户据此判断”两边逻辑混在一起、退出莫名其妙”，
要求直接把 GBA 的退出逻辑改成 FC 那一套。

用户的判断是对的：FC 那套是唯一被实机长期验证过的退出路径，任何”改进版”目前都没有可信的验证基础。

2. 影响范围

  • lv_pages/gba_game_page.c：退出路径（gba_wait_thread / gba_exit_to_list / gba_timer_cb / 状态结构体）。
  • 不涉及 miniretro_gba（前端二进制不动），不涉及 FC 页（FC 页保持原样，一行未改）。
  • 结构层面：消除”同构组件之间的人为差异”——差异本身就是后续故障的藏身处。

3. 根因分析

3.1 修复前的四处差异（GBA 相对 FC 的额外复杂度）

# 差异点 FC 页 GBA 页（修复前）
1 等待判据 阻塞 waitpid，只认”子进程真的消失” 5ms 轮询，认 exiting 标志 或 子进程消失
2 退出函数副作用 只 SIGTERM → 120ms → SIGKILL 追加 s_gba.exiting = true
3 收尸兜底 无（阻塞必然拿到尸） gba_reap_bg() 独立后台线程
4 画面恢复 lv_obj_invalidate() ×1 invalidate() + for(3) lv_refr_now()

3.2 为什么这四处差异是风险

  • 第 1 处是 09/10/11 三轮卡死/卡黑屏的同一个病灶。只要等待判据里出现”标志位”或”时间上限”这类
    非硬事件，就存在”把仍在运行的游戏判成已退出”的可能，后果固定为两条：
    ① hardware_keys_set_interceptor(NULL) 摘掉按键拦截器 → 退出键失效，再也退不出游戏；
    ② app_runtime_set_lvgl_paused(false) 让 LVGL 抢回 fb0 → 与仍在运行的游戏互相覆盖。
    历史两版的差别只是”误判的触发条件不同”（时间上限 / 标志位被读到），本质同源。
  • 第 3、4 处是为第 1 处的时序问题打的补丁。提前放行意味着”标志已消费但子进程仍在碰 fb0”，
    于是不得不连刷 3 帧来抢画面、不得不另开线程收尸。改回硬事件判据后，这两个补丁不再有存在理由，
    留着反而是多余的失败面。
  • 结构性理由：FC 页这套逻辑经过长期实机验证；GBA 页却带着一条”只此一处”的路径。
    同一份设计意图在两处写法不同，未来任何一次修改都容易只改一边 —— 这正是 11 号文档里
    “共用二进制被改坏”那类问题的翻版，只是从”共享产物”变成了”共享语义、各自实现”。

3.3 代价的取舍（明确接受）

FC 那套的唯一代价是：恢复 UI 要等内核回收 evdev fd，实测发信号→收尸完成约 455ms
（其中子进程内部收尾 ~34ms，其余是内核固有开销）。09/10 两轮就是试图”省掉这几百毫秒”才出的故障。

本次明确选择承担这 ~400ms，换取”GBA 与 FC 行为逐行一致”。理由：

  • 455ms 的黑屏一闪在用户感受上属于”退出有一下停顿”，可接受；
  • 相比”偶发卡死、退出键失效、只能重启”，这个代价小得多；
  • 一致性带来的可验证性 > 几百毫秒的性能收益。

4. 修复方案

原则：GBA 页退出路径照抄 FC 页，不给任何专属分支。

4.1 gba_wait_thread() 改为阻塞 waitpid

安全性依据：上游 gba_exit_to_list() 保证 SIGTERM 后 120ms 必然补上 SIGKILL，
而 SIGKILL 不可捕获 ⇒ 子进程必然结束 ⇒ 阻塞的 waitpid 必然返回，不存在死等。

4.2 gba_exit_to_list() 去掉提前放行

4.3 删除 gba_reap_bg() 后台收尸线程

阻塞 waitpid 必然拿到尸，兜底线程没有存在意义。删除后同时消除”两处代码都去 child_pid
赋值”的竞态空间。

4.4 状态结构体去掉 exiting 字段

gba_state_t 的 exiting 及 gba_launch() 里对它的复位一并删除，字段布局回到与 fc_state_t 对齐。

4.5 gba_timer_cb() 画面恢复回到单次 invalidate

4.6 文件头注释重写

把”我们比 FC 更快”的叙述改成”刻意与 FC 完全一致，并说明为什么不再追求更快“，
同时把两轮失败方案（SIGUSR1 握手 / 时间上限）作为反例留在注释里，防止后来者再走一遍。

5. 验证方法与结果

5.1 代码一致性核对（本地）

  • grep -n "exiting\|reaped\|reap_bg\|lv_refr_now\|SIGUSR1\|RELEASE_SIGNAL" →
    仅命中注释内容，无任何代码残留；
  • gba_wait_thread() 与 fc_wait_thread() 逐行对照 → 结构、判据、恢复顺序、顺序注释全部相同，
    仅 s_gba / s_fc 前缀与缩进不同。

5.2 构建与部署（设备端）

ssh_tools/gba_redeploy.py（不带 --mini，只部署页面 + 编译 + 重启）：

检查项 结果
make -j2 MAKE_RC=0，error: 计数 = 0
二进制替换 ATOMIC_OK（编到 .tmp 再 mv -f，原子）
部署前在跑的游戏 无
重启后进程 lvgl_demo ×1 + lvgl_watchdog ×1，单实例，无僵尸

5.3 实机功能验证（交由用户）

  1. 桌面 → GBA 游戏 → 选 ROM → 确认，进入游戏；
  2. 按买单键退出 → 预期约半秒黑屏一闪后回到游戏列表，退出键全程有效；
  3. 进入游戏后停留 5 秒以上再退出（重点：验证不再有”跑满 N 秒被误判”）→ 表现应与第 2 步相同；
  4. 再进一次并正常玩一段 → 退出，确认无残留黑屏、列表可继续操作；
  5. 对照 FC 游戏：进入 → 退出，行为应与 GBA 表现一致（同为”半秒黑屏一闪”）。

6. 回归风险

风险 评估
退出比上一版慢约 400ms 已明确接受，这是与 FC 对齐的必然代价，也是唯一被验证过的时序
单次 invalidate 是否够用 FC 页同样只 invalidate 一次且长期正常；恢复时机现已与 FC 相同，判断为足够。若实机出现”退出后残留游戏画面”，则说明 GBA 侧 fb 清理与 FC 有差异，需从 miniretro_gba 的 fb_restore() 查，而不是再加连刷
阻塞 waitpid 会不会死等 不会：SIGKILL 不可捕获，上游必然发出
pthread_create 失败的极端分支 该分支（gba_launch 内）里是 waitpid(pid, NULL, 0) 且未先 kill，理论上会阻塞到游戏自行结束。FC 页存在完全相同写法，为保持逐行一致本次未改；属极低概率路径，如要修应两侧同时修
FC 页 本次一行未改

7. 相关文件

文件 说明
lv_pages/gba_game_page.c 本次改动全部集中于此（退出路径 + 结构体 + 文件头注释）
lv_pages/fc_game_page.c 参照基准，未改动
extern/miniretro/miniretro_gba GBA 专用前端，未改动
ssh_tools/gba_redeploy.py 部署脚本；本次顺带修正取 PID 方式（见下）
bugfix_20260923_11 上一环：前端分离、卡黑屏根因

附：部署脚本的一处修正

gba_redeploy.py 原先用 ps -o pid,args | grep 'lvgl_demo' 取 PID 再 kill -9。
该命令经由 sh -c 执行，承载它的 shell 自身命令行里就含 lvgl_demo 字样 →
被 grep 匹配 → 杀掉自己 → SSH 连接被重置（上一轮部署时就断在这里）。
现改为 ps -o pid,comm | awk '$2=="lvgl_demo"{print $1}'：comm 是进程名（不含参数），
承载 shell 的 comm 是 sh，不会自匹配。miniretro 系列改用 $2 ~ /^miniretro/ 前缀匹配。
