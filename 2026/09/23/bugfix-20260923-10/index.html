GBA退出直接卡死_回滚握手方案

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_10 — GBA 退出直接卡死（回滚 SIGUSR1「画面交还」握手方案）

项目 内容
发现时间 2026-09-23
修复时间 2026-09-23
模块 extern/miniretro/miniretro.c、lv_pages/gba_game_page.c
涉及版本 回滚 bugfix_20260923_09 的全部改动
现象等级 高（退出功能完全不可用，并波及原本正常的 FC 页）

1. 问题现象

用户在实机上反馈两条：

  1. GBA 游戏退出时直接卡死（此前是”偶尔卡一下”，仍可用）；
  2. FC 游戏也卡死了，而它原来没问题。

这是典型的回归，且第 2 条说明问题不在 GBA 页面本身 —— FC 与 GBA 共用同一个
extern/miniretro/miniretro 前端，因此元凶必然在 miniretro 侧那次改动里。

2. 影响范围

  • 所有从 LVGL 页面拉起 miniretro 的入口：FC 游戏页、GBA 游戏页；
  • 由于 setenv 是主进程级的，污染会跨页面残留，直到 lvgl_demo 重启为止 ——
    即”从 GBA 出来之后，FC 也跟着坏”，与用户描述完全一致。

3. 根因分析

bugfix_09 为”省掉内核回收 /dev/input/eventX 的那 ~340ms”引入了两个机制，
两条都错：

3.1 _exit(0) 省不掉内核的时间，只会让进程更久不消失

原以为 _exit(0) 跳过用户态 close() 就能立刻消失。实测相反：

  • _exit(0) 只是跳过用户态逐个 close()，内核 exit_files() 照样要收掉
    这些 fd，而且是在进程退出路径上不可中断地收；
  • 于是子进程在 _exit 之后比正常 return 更久才消失。

设备日志是铁证（同一进程，以收到 SIGTERM 为 0 点）：

39.9ms 就走完了所有收尾，进程却 5s 都没被回收 —— 时间全耗在内核退出路径里。

3.2 把”等收尸”的超时循环放在互斥锁内 → UI 恢复被拖满 5 秒

GBA 页 gba_wait_thread 的结构是：

子进程迟迟不消失 → 阶段② 跑满 5s → UI 整整 5 秒后才恢复 = “退出直接卡死”。

FC 页则是 waitpid(pid, NULL, 0) 无超时阻塞在同一个不消失的子进程上，
同样卡死 —— 这就是”FC 原来没问题，现在也卡”的原因。

3.3 附带缺陷：握手门禁污染了主进程环境

gba_launch() 在 fork() 之前调用 setenv("MINIRETRO_UI_RELEASE_SIGNAL", "1", 1)。
setenv 改的是当前进程（lvgl_demo）的环境块，一旦设上就永久保留：

  • 之后 FC 页 fork() 出的子进程也会继承该变量，从而也去给父进程发 SIGUSR1；
  • SIGUSR1 默认动作是终止进程 —— 门禁一旦失效（例如页面侧 handler 被改回去），
    父进程会被自己拉起的子进程打死。

结论：不要跟内核赛跑。 退出路径的快慢由内核决定，用户态唯一能做的是
“不等它自己走完”。

4. 修复方案

完整回滚 bugfix_09，改用 FC 页那套已长期实机验证的退出策略。

miniretro 侧（子进程）

  • 删除 notify_parent_ui_released() 及其调用、环境变量门禁；
  • _exit(0) → 恢复为正常 return 0（原样交给 glibc/内核收尾）；
  • 保留 on_quit_signal（SIGTERM → quit=1 走优雅收尾）与 fb_restore()
    （翻回第 0 页 + 清屏，防画面残留）—— 这两项是 bugfix_07 的正确修复，不在回滚范围；
  • 保留 td() 分阶段计时日志，后续定位同类问题仍需要它。

页面侧（lv_pages/gba_game_page.c）

  • 删除 s_gba_ui_released、gba_ui_release_handler、setenv、signal(SIGUSR1,…)；

  • gba_exit_to_list() 恢复为 FC 同款：

  • gba_wait_thread() 收尸改为 WNOHANG 轮询、上限 3s、绝不死等；
    超时才 SIGKILL 并交给 gba_reap_bg() 后台线程收干净（不留僵尸）。
    与 FC 的差别仅在于多了一道上限保险，正常路径 200ms 内返回，不会触发。

5. 验证方法与结果

设备端一次性测量（复刻页面侧新逻辑：SIGTERM → 120ms → SIGKILL → 轮询收尸）：

指标 结果
120ms 时子进程是否还活着 True（正常，正在内核中收尾）
SIGKILL 发出时刻 120.4 ms
从 SIGTERM 到收尸完成 455.0 ms（原方案 >5000 ms）
fb_restore 完成时刻 33.8 ms（画面在此之前已交还）
退出码 0
新增僵尸 无
恢复后进程 lvgl_demo ×1、lvgl_watchdog ×1（单实例）

编译侧：miniretro gcc 返回 0、0 error / 0 warning；lvgl_demo make -j2 返回 0、0 error。
部署采用”编到 *.tmp 再 mv -f 原子替换”，避免用户正在玩时 exec 到半覆盖的二进制。

6. 回归风险

  • 退出仍有约 0.45s 的等待：其中 120ms 是我们主动等它复位画面，后 ~335ms 是内核
    收 fd 的固有开销，且发生在”画面已黑”之后，主观为”屏幕黑一下”而非”僵住”。
    这是与 FC 页一致的表现，属于可接受成本。
  • 若日后仍嫌慢，正确方向是**”画面已交还就恢复 UI，收尸完全后台化”**，
    而不是缩短子进程的生命周期 —— 注意不要再用 setenv 之类的主进程级开关做门禁。
  • 页面销毁路径（onDestroy）本来就先 SIGKILL 再 waitpid，未受影响。
  • 本次未改动渲染（双缓冲/pitch/240×160）与音频链路，颜色与音质不应有变化。

7. 相关文件

文件 说明
extern/miniretro/miniretro.c 删除 SIGUSR1 通知与环境变量门禁；_exit(0) 改回 return 0
lv_pages/gba_game_page.c 退出策略回滚为 FC 同款（SIGTERM→120ms→SIGKILL）；收尸加 3s 上限 + 后台兜底
bugfix_20260923_09_GBA退出游戏返回列表卡顿.md 被本次回滚的方案（保留作为反面记录）
