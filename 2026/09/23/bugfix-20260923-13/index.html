bugfix_20260923_13 — GBA 退出”卡黑屏”：真凶是前端退出时自己清屏（不是 fork 形式的问题）

  • 日期：2026-09-23
  • 设备：展讯 SC9832A / armv7l / Alpine / 720×1280 fb0（yres_virtual=3840，3 页）/ 4 物理键
  • 涉及文件：
    • 设备 extern/miniretro/miniretro.c（GBA 专用前端，编译产物 miniretro_gba）
    • 本地 ssh_tools/_tmp/miniretro.c（同源）
    • 本地 ssh_tools/gba_redeploy.py（部署脚本，本次修掉一处会误伤 FC 的隐患）
  • 证据脚本：ssh_tools/gba_black_probe.py、ssh_tools/gba_black_run.py、ssh_tools/ssh_run.py

1. 问题现象

用户反馈：GBA 游戏退出时”卡黑屏”；而 FC 游戏用同样的退出方式（同样是 fork + 独立前端进程）一直很流畅。

用户提出的疑问是：”GBA 这个前端不是 fork 这种形式吗？” ——
是。GBA 与 FC 走的是完全相同的 fork + execl 形式（父进程 = lvgl_demo，子进程 = extern/miniretro/miniretro_gba 或 miniretro，前端直接写 /dev/fb0）。
正因为形式相同，”为什么一个流畅一个卡”只能到屏幕内容上去找，而不是在进程模型上找。

2. 影响范围

  • 仅 GBA 页退出路径（lv_pages/gba_game_page.c → miniretro_gba）。
  • FC 页未受影响：它的前端 extern/miniretro/miniretro 是 git 仓库原版、不捕获 SIGTERM，本次一行未动（md5 校验见 §5）。

3. 根因分析

3.1 实测：两个前端收到 SIGTERM 后，屏幕到底发生什么

停掉 lvgl_demo/watchdog，直接拉起两个前端跑 3s，然后发 SIGTERM，按时间点采样屏幕中心区域
（”非黑比例 / 平均亮度”，fb0 有 3 个虚拟页，采样按当前 yoffset 取当前显示页）：

3.2 结论

差别只有一个：退出时前端要不要清屏。

  • miniretro（FC）不捕获 SIGTERM、不做任何 fb 操作 → 被内核直接杀掉，屏幕停在游戏最后一帧。
  • miniretro_gba（GBA）捕获 SIGTERM 走优雅收尾，其中 fb_restore() 里有一句 memset(fb_buf, 0, fb_total_bytes)，
    在第 20 ms 就把整块虚拟显存清黑 → 屏幕立刻变黑。

而两个前端的子进程”真正消失”都要 ~1020 ms（内核 exit_files() 逐个回收继承来的 5 个 /dev/input/eventX 与 fb0 映射的固有开销，与前端写不写 fb 无关）。
父进程（GBA 页）当前用的是阻塞 waitpid，要等收尸完成才恢复 UI（这是 12 号文档按用户要求对齐 FC 的做法）。

于是两条时间线是：

  • FC：0~1020 ms 屏幕定格在游戏最后一帧 → 恢复 UI 重绘。用户看到的是”画面定了一下，很流畅”。
  • GBA（修前）：20~1020 ms 屏幕是纯黑 → 恢复 UI。用户看到的就是”卡黑屏“。

一句话：**”卡”是两个前端共有的（~1s 的内核回收开销，FC 也一样）；”黑”才是 GBA 独有的、由自己清屏造成的。**

3.3 为什么当初会写上 memset 清屏

原本的担心是”残留游戏画面”：LVGL 恢复后只刷脏区，残留会糊在屏幕上。
但 GBA 页恢复时本来就做了 lv_obj_invalidate(lv_screen_active()) 整屏重绘，这个担心不成立 ——
清屏是多余动作，代价却是整整 1 秒的纯黑屏。

4. 修复方案

4.1 fb_restore()：清屏 → 跨页定格拷贝（核心修复）

  • 翻回第 0 页的动作保留（yoffset 不归零 = LVGL 画在不可见页 = 永久黑屏，这个是必须的）。
  • 不再清屏；若退出瞬间前台是第 1 页，则把第 1 页整页拷到第 0 页，保证”屏幕内容与退出前逐像素一致”（定格，不闪黑、不跳帧）。
  • 页偏移用既有变量 fb_page_bytes（= 一屏字节），与渲染侧 fb_dst = fb_buf + target * fb_page_bytes 完全一致，不存在越界。

4.2 部署脚本 gba_redeploy.py：修掉一处会误伤 FC 的隐患

--mini 分支原本写死 gcc ... -o miniretro.tmp ... mv -f miniretro ——
即把 GBA 源码编成 FC 的二进制名，会把上一轮辛苦还原的 FC 原版覆盖掉。
本次改为只产出 miniretro_gba，并加了保护：编前备份 + 编后 cmp 校验，一旦 FC 前端 md5 变化就报错。

教训：同一目录下两个”同名家族”的产物，构建脚本必须用不同的目标名，并在脚本头写死约束。

5.2 实机验证（AI 自测，已按要求执行）

验证一：退出时屏幕是否还黑（两个前端各跑 3s → SIGTERM → 采样到子进程消失）

  • FC：全程 非黑 0.954 / 亮度 227.4，与退出前完全一致（定格）。
  • GBA（修后）：全程 非黑 1.000 / 亮度 248.0，与退出前完全一致（定格）。
  • 黑屏窗口从 ~1s 降为 0。

验证二：拷贝分支是否真的被执行到（双缓冲下前台页在 0/1 间切换）

  • 采样 4 次运行中 yoffset 均为 0（详见 §6 遗留项 3），但退出日志显示 fb pan 回第0页 17.8ms
    → fb 定格最后一帧(不清屏) 33.0ms，耗时 15 ms —— 正是整页 3.7 MB 的拷贝用时，证明拷贝分支已执行。
  • 无任何 pan 失败 告警。

验证三：收尾状态

  • lvgl_demo ×1、lvgl_watchdog ×1（测试期间产生的重复 watchdog 已清理为单实例）。
  • FC 前端 md5 = a95d9171d8d8b82a52c12ac84e68aaa2，与编前备份一致。

6. 遗留与观察（未处理，供后续参考）

  1. 退出后回列表仍要等约 1 秒：这是阻塞 waitpid 等收尸 + 内核回收 fd 的固有开销，FC 完全一样（1015ms）。
    若将来要做到”画面一交还就恢复 UI”，需要重新引入”提前放行”机制 ——
    但那正是 09/10 两轮翻车的方向（当时的错误是：_exit(0) + 超时循环放在互斥锁内 + setenv 跨页污染）。
    本次按用户要求”与 FC 逐行一致”，不做该优化。
  2. 内核回收 fd 需 ~1020 ms，比早先实测的 ~455 ms 更长（可能受当时系统负载影响）。属内核固有行为，前端无法影响。
  3. 驱动回读 yoffset 不可靠：即使 pan 实际生效（拷贝分支被触发，说明 g_front=1），FBIOGET_VSCREENINFO 回读仍是 0。
    因此 fb_restore() 里那段”yoffset 回读校验”不会误报，但也发现不了 pan 失败 —— 不宜把它当作 pan 是否成功的判据（早先的记忆记载需相应修正）。
  4. 设备在本轮测试期间自行重启过一次（uptime 45 min），与本 bug 无关。
