GBA退出卡黑屏与FC被污染_前端分离

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_11 — GBA 退出卡黑屏，且 FC 被牵连（前端彻底分离）

项目 内容
发现时间 2026-09-23
修复时间 2026-09-23
模块 extern/miniretro/*（新增分离产物）、lv_pages/gba_game_page.c
涉及版本 承接 bugfix_20260923_10 之后的现场
现象等级 高（GBA 退出不可用，且把原本正常的 FC 一起带坏）

1. 问题现象

用户连续两轮反馈：

  1. 「退出逻辑还是有问题 还是卡黑屏」；
  2. 「把 GBA 的和 FC 的 miniretro 分开吧，FC 原来版本都是好用的，被 GBA 修改的污染了，
    导致 FC 的 miniretro 也不好用了，导致 FC 不能玩，退出莫名其妙。」

第 2 条是关键判断：两个游戏页共用一个前端二进制，改 GBA 必然波及 FC。用户的诉求
（物理隔离）比”继续在共用件上打补丁”更正确。

2. 影响范围

  • GBA 游戏页：退出后黑屏、退出键失效；
  • FC 游戏页：被同一份 miniretro 的改动连带影响，退出异常；
  • 根因层面：任何”多个页面共用一个可执行前端”的设计，都是这类跨模块污染的温床。

3. 根因分析

3.1 ★ 等待循环设了”跑满 N 秒就算退出”的上限（卡黑屏的直接原因）

gba_wait_thread 原来写成”等够一定时长就往下走”：

游戏正常跑满 3 秒，就满足”循环结束”这个条件，于是：

  1. hardware_keys_set_interceptor(NULL, NULL) 把按键拦截器摘掉 → 买单键不再被拦截 → 退不出游戏；
  2. app_runtime_set_lvgl_paused(false) 让 LVGL 恢复绘制 → 父进程抢回 fb0，与还在跑的游戏互相覆盖；
  3. 两者叠加 = 用户看到的「卡黑屏」，且只能重启。

这正是”FC 没问题、GBA 有问题”的分水岭：FC 页用的是阻塞式
while(waitpid(pid, &status, 0) < 0) {...}（无上限），所以从来不误判。
GBA 页当初为了”快点恢复 UI”引入了上限，反而制造了 bug。

3.2 UI 恢复被绑在”子进程消失”上（把黑屏拉长）

本机内核回收 /dev/input/eventX 要几百毫秒，实测从发信号到收尸完成 ~455ms，
而画面在 ~40ms 就已交还。等收尸才恢复 UI，就白等了 400ms —— 这段时间屏幕全黑。

3.3 细节问题

  • gba_timer_cb 只 lv_obj_invalidate(lv_screen_active()) 一次，可能与 LVGL 恢复的
    时序错开而被吞掉（标志已消费、画面却没画回来）；
  • fb_restore() 调 FBIOPAN_DISPLAY 后不检查结果：若 yoffset 没真的归零，
    LVGL 会画在第 0 页而屏幕仍显示第 1 页 → 永久黑屏且完全静默，无法定位。

3.4 结构性根因：共用前端

FC 与 GBA 共用 extern/miniretro/miniretro。为 GBA 加的 双缓冲页翻转、pitch 寻址、
240×160 放行、音频重采样、退出信号处理 全都落在这一份共用产物上。FC 因此被反复牵连 ——
这是”改 A 坏 B”的必然结果，不是某一次改动没写好。

4. 修复方案

4.1 ★ 前端彻底分离（用户方案）

产物 归属 说明
extern/miniretro/miniretro FC 专用 git checkout 恢复成仓库里的原始版本，此后永不重编、不被 GBA 改动触碰
extern/miniretro/miniretro_gba GBA 专用 含双缓冲/pitch/240×160/音频修正/退出修复
extern/miniretro/miniretro_gba.c GBA 源码
extern/miniretro/miniretro.c FC 源码 已随二进制一并还原成原始版本
extern/miniretro/build.sh — **只编 miniretro_gba**，并在脚本头写明”不要再把产物写成 miniretro”

页面侧 gba_find_bin() 的首选路径改为 miniretro_gba，并保留 miniretro 作为兜底：

4.2 退出逻辑四项修复（只落在 GBA 页）

  1. 等待循环去掉时长上限，只认两个真实终止条件：

  2. 新增 exiting 标志：画面一交还就恢复 UI，不等收尸

  3. 恢复时连刷 3 帧，不依赖单次 invalidate：

  4. fb_restore() 校验翻页结果：只在 yoffset != 0 时才 pan，pan 后回读确认，
    不归零就打警告日志（把”永久黑屏且无任何线索”变成可定位）。

同时给等待线程加了”仍是我这一局的 pid”判断，避免上一局的线程醒来把新一局的状态清掉。

5.2 两个前端各自实跑（ssh_tools/split_verify.py）

前端 核心 画面（非黑像素比） 退出码 收尸耗时 退出后 yoffset 僵尸
FC miniretro（原版） fceumm 0.600 ✓ -15（被 SIGTERM 直接杀，原版行为） 549 ms 0 ✓ 无
GBA miniretro_gba mGBA 0.380 ✓ 0（优雅退出） 575 ms 0 ✓ 无
  • FC 退出码 -15 符合”原版无信号处理”的预期；其页面侧在 120ms 后探测到进程已消失，
    直接恢复 UI —— 这正是用户记忆中”FC 原来好用”的表现。
  • GBA 侧 exiting 标志使 UI 在 ~125ms 即可恢复，收尸移到后台；yoffset 归零确认无黑屏隐患。
  • 恢复后 lvgl_demo ×1 + lvgl_watchdog ×1，单实例，无残留。

5.3 部署脚本的一处修正

gba_redeploy.py 用 ps -o pid,args | grep '<名>' 取 PID 来 kill，
而该命令自身的命令行含这个字符串 → 匹配到承载命令的 sh -c → 杀掉自己的 SSH 连接
（本次实测 ConnectionResetError）。已统一改为 ps -o pid,comm（承载 shell 的 comm 是 sh，
不会误伤），见 split_miniretro_gba.py / split_verify.py。

6. 回归风险

  • miniretro 已还原为原版：FC 侧要的任何未来改动都必须独立做，且不能再走
    “重编 miniretro” 这条路（build.sh 已只产 miniretro_gba）。若确需改 FC，
    应先 git checkout 一份到别的名字（如 miniretro_fc）再改，保持三者互不干扰。
  • **GBA 侧不再有”时长上限”**：等待线程在游戏运行期间会一直循环（每 5ms 一次，开销可忽略）。
    这是刻意选择 —— 宁可多转几次，也不能误判成”已退出”。
  • gba_reap_bg / onDestroy 两条收尸路径都可能对同一 pid waitpid，双方均已处理 ECHILD。
  • 本次未改渲染与音频链路，颜色、音质、帧率不应有变化。
