> 系列第 45 篇。上一轮把崩溃定性成「累积漂移」，工具造好了，设备却一直没上电。
> 这一轮换了个审计维度——不看等待，看分配——结果抓到的不是厂商库，而是我们自己替身层里
> 6 行从来没被读过的赋值。

一个查了半个月的「周期性 SIGSEGV」，最后落在自己代码的 6 行赋值上。这 6 行不是 `memcpy`，所以两轮「逐处审计 memcpy 边界」都没扫到它。这篇记录方法上的那个盲区，以及怎么用二进制反汇编把「对象到底多大」这件事钉死。

## 背景：症状与既有结论

设备上的网络电视播放器（展讯 SC9832A，VSP 硬件解码）稳定播放时，约每 3 分钟死一次 SIGSEGV，帧率正常、与 IDR 尺寸无关；崩溃地址出现 `0x747474` 这种「ASCII 感」的值。此前已经排查掉的方向：

- 信号处理器本身写过（带 `sigaltstack`、纯 `write` 避免持锁死锁），但从没执行到；
- 我方的 9 处 `memcpy` 逐处判过边界，全部有界；
- 渲染池、线程信号掩码、fork 时机都做过 A/B，均非主因。

剩下的假说是「累积漂移」：某个每帧都会走到的路径在缓慢消耗资源。问题是——**哪个路径**。

## 方法：把「分配/释放配对」做成函数级审计

上一轮审的是「等待/超时」，这轮换成分配行为。工具思路很朴素：

1. 用 `.dynsym` 里的 FUNC 符号（带 size）拿精确函数边界；未导出的静态函数用 `push {…, lr}` 序言补齐（stripped 库里这是唯一可靠的分界）；
2. 用 `.plt` + `.rel.plt` 建 PLT 地址 → 符号名映射，抓函数体内 `bl/blx` 到 `malloc/calloc/new/mmap` 与 `free/delete/munmap` 的调用点；
3. 判断该调用点是否落在函数内某个回跳分支构成的循环体里（per-iteration 分配的气味）；
4. 回溯 12 条指令复原 `r0`（含 `movw/movt` 拼装）＝ 申请大小；
5. 以逐帧入口（`onQueueFilled`、`H264DecDecode` 等）为根建调用图，BFS 标注「从逐帧路径是否可达」。

两个防止自欺的门槛：

- **覆盖率必须打印**。线性反汇编遇到常量池会中断，覆盖率不足时工具直接打 `INCOMPLETE`——否则「没找到分配点」会被读成「没有分配」。
- **阴性对照**。寄存器层那个库的导入表里根本没有 `malloc`，工具必须报「堆分配点 0 个」，而不是「无泄漏」。这是给自己设的反向测试。

## 关键一步：对象到底多大

审计报告里有一行不起眼的东西：某个回调里有 `_Znwj`，复原出来的 `r0 = 0x1c`。

`0x1c` = 28。这 28 字节随后被交给 `MemoryHeapIon` 的构造函数。于是顺着反汇编把 4 个构造点全看了一遍，3 个都是 `mov r0, #0x1c; bl _Znwj` ——**这个对象就是 28 字节**。

回到我们自己的源码：为了绕开 ION 分配失败，播放器里把 `MemoryHeapIon` 的构造函数整个替身掉了，替身里按「字段偏移表」往对象上填值：

```c
*(void    **)(o +  0) = ...;
*(int      *)(o +  8) = ...;
*(unsigned *)(o + 12) = ...;
*(int      *)(o + 16) = ...;
*(unsigned *)(o + 20) = ...;
*(void    **)(o + 24) = ...;   /* 28 字节到此为止 */
*(unsigned *)(o + 28) = handle;   /* 越界 1 */
*(int      *)(o + 32) = fd;       /* 越界 2 */
*(int      *)(o + 36) = buf_fd;   /* 越界 3，实际写到 o+39 */
```

**每次构造越界写 12 字节。** 而这三个字段没有任何读取点——`getBase()` 读 +24，`getHeapID()` 读 +16，`get_phy_addr_from_ion()`/`get_iova()` 读 +8/+12/+16/+24。三条赋值是纯死写。

调用频度决定了量级：mbinfo 缓冲区大约每 2 帧申请一次，25fps 下 12.5 次/秒，3 分钟约 2200 次越界写，每次都踩在紧邻 malloc 块的 12 字节上（块头或邻块数据）。

## 为什么两轮 memcpy 审计都没抓到

这是这次最值得记的一点。

「越界写」在直觉里等于 `memcpy` 长度算错。于是审计就按 `memcpy` 去审：逐个看长度变量、看源缓冲大小、看有无 `min()` 截断。这个做法对**数据搬运**有效，对**定偏移结构体写**完全失效——`*(int*)(o + 36) = fd;` 里没有任何长度变量，它「看起来」只是给某个字段赋值，而正确性问题隐藏在「这个对象真实有多大」这个外部事实上。

所以审计法则要补一条：**按「写入偏移 vs 对象真实大小」审，不能只按「有没有长度参数」审。** 对象大小往往不在本文件里——它由库里的 `new(N)` 决定，必须反汇编去取。

顺带一个反直觉的结论：这 6 行从代码的第二个版本就存在，一路活到被部署的版本，中间经历了多次「内存安全专项检查」。它不是隐蔽，而是**检查项不覆盖**。

## 两条互斥假说，一次实验分流

至此有两条候选，它们的预测互相排斥：

| 假说 | 预测 |
|------|------|
| A：每帧字节泄漏 | CMA 可用量线性下降，151s 对应约 1.94 KB/帧，186s 约 1.58 KB/帧（按 7 MB 池、25fps 反推） |
| B：堆元数据被踩坏（本文） | **CMA 可以不降也照样崩**，崩溃时机取决于分配器何时用到被踩的块 |

这很重要：此前的排查都在盯「内存余量」，而 B 假说根本不消耗余量。如果只采 CmaFree，B 假说永远不会被看见。

所以下一步只做一件事：删掉那 3 行 ×2 处（共 6 行），编译，跑满 4~5 个故障周期。崩溃消失即定因；间隔显著变长说明是真因之一；完全不变则本假说被否，回到 CMA 斜率分支。

顺便说明为什么没有顺手改别的东西：这段代码上还压着一个「信号掩码净化版」的改动，两者混在一次实验里，出结果也无法归因。**一次只动一个变量**这条纪律，价值不在谨慎，而在让结论可复用。

## 小结

- 静态审计的产出不一定是「厂商库有问题」，也可能是「自己的替身层有问题」——而替身层恰恰是最容易被当成「已经验证过」的部分。
- 函数级符号 + 覆盖率自证 + 阴性对照，这三件是让静态报告能当证据用的最低配置。
- 崩溃地址长得像 ASCII（`0x747474`）不代表它就是字符串，别顺着这个直觉走太远；本轮也没能证明它的直接来源。
