前十篇一直在跟「崩」死磕：核心崩、掛死、綠畫面、黑畫面。等這些都解決了，能連續播 4800 幀之後，剩下最後一個字是——**卡**。240 秒只上螢幕 19 幀，約 0.08fps，畫面基本是幻燈片。

這篇講怎麼把這個數字抬到 6.3fps（約 80 倍），以及中間怎樣用一次診斷實驗**否證了追了三天的錯誤假設**。

## 一、先證偽：問題不在 IDR

之前一直有個假設：**「餵第二個 IDR 必掛死」**。日誌裡每一代行程都止於 GOP#2 的 IDR 附近，三種串流一致，看起來鐵證如山。

要區分兩種可能：

- **A**：串流狀態下解碼器見到任何第二個 IDR 就掛 → 修法是 GOP 邊界軟重置
- **B**：前 36 輪累積了漂移/洩漏 → 修法是查資源洩漏

這兩條修法完全不同，猜錯就是白幹一週。所以 10-19 在播放器裡埋了個診斷開關 `NETTV_IDRREPLAY=K`：捕獲第一個 IDR 之後，**連投 K 次同一份 IDR**（零累積，排掉所有漂移因素）。

10-20 凌晨第一次真正跑起來（上一輪腳本上傳時變成 0 位元組，白等了一天——這條後面單獨說）：

```
[diag] NETTV_IDRREPLAY=3 (首 IDR 连投次数)
[diag] 捕获首 IDR 106336B(t=5), 之后连投 3 次
[diag] AU[4] 重投首 IDR 106336B(t=24), 剩 2 次
[diag] AU[5] 重投首 IDR 106336B(t=24), 剩 1 次
[diag] AU[6] 重投首 IDR 106336B(t=24), 剩 0 次
★ 帧#20 已上屏 @4887ms
★ 帧#21 已上屏 @5028ms
```

**連投三次，一次沒掛，影格還在繼續出。**

假設 A 直接出局。IDR 本身無罪，「第二個 IDR 必掛」這個說法從根上就是錯的——它只是**表象**，真正的問題是 IDR 到達前後那段時間裡發生的另一件事。

## 二、真兇：一個只會減速的 A-V 同步

同一份日誌往下翻，有一行反覆刷：

```
[ptsync] 视频落后, 暂缓解码 (累计 960)
```

240 秒裡出現了 138 次（每 16 次丟影格打一行），換算下來丟了兩千多次影格。

對應的程式碼長這樣：

```c
/* 傳回 1=要等(影片超前), -1=要丟(影片落後太多), 0=正常 */
static int pts_should_skip_or_wait(void)
{
    ...
    long long diff = (long long)vp - (long long)target;
    if (diff < -(long long)thresh) return -1;   /* 落後太多 → 丟影格 */
    return 0;
}
```

注意函式簽名承諾了兩件事：「超前就等」和「落後就丟」。但** `return 1` 這個分支從來沒被實作過**——整個函式只有兩種結局：丟影格，或者什麼都不做。

於是邏輯變成單向的：

1. 影片落後 → 丟影格
2. 丟影格 = 消費得更慢（程式碼裡是 `rb_take` 扔掉一個 NAL 然後 `continue`）
3. 更慢 = 更落後
4. 回到第 1 步

**這是個正回饋。** 觸發之後只會越來越卡，永遠不會收斂。更要命的是觸發條件極易滿足：直播串流的 `video_pts_ms` 每 6 秒（一個 TS 段）才更新一次，而牆鐘 `target` 每毫秒都在漲，中間那 6 秒裡 `diff` 一路走負，只要超過閾值（當時已放寬到 5000ms）就必然觸發。

順便說，拿它當 A-V 同步基準本身也不成立：音訊走的是獨立的 mplayer + `bt_audio.fifo`，跟影片根本不是一個時鐘源。

## 三、A/B：一個 env 的差距

不改程式碼，只加一個環境變數，同一份二進位檔、同一個源（瀘縣 1080p）、同樣 240 秒：

| 輪次 | NETTV_PTSSYNC | 上螢幕影格數 | AU 推進 | ptsync 丟影格 |
|------|---------------|---------|---------|------------|
| v13  | 預設開 | 19 | AU[27] 後停滯 | 累計 960 |
| v14  | `=0` 關 | 1191（63.6s 就跑滿 400 影格上限） | AU[441] | 0 |

**約 80 倍。** 而且關掉之後 AU 一路推到 441，之前「止於 AU[36]」的現象也一併消失了——那同樣是丟影格風暴造成的假象，不是解碼器崩了。

## 四、修復

結論既然是「這條邏輯在目前架構下有害無益」，修復就是把已驗證的 env 行為固化成預設值，程式碼和開關都留著：

```c
g_ptssync = (e && e[0] == '1') ? 1 : 0;   /* 10-20: 預設關 */
```

並在註解裡寫清楚為什麼。整輪改動只有這一個字元層級的差異，建置產物大小完全沒變（還是 128028 位元組）——**這也說明這次不能靠二進位檔大小判版本，得看時間戳記和行為**。

## 五、四條教訓

**1. 單向的回饋環比沒有回饋更危險。**
有減速沒加速的控制器，一旦進入負向區間就是單程票。寫「A-V 同步」這類閉環邏輯時，先確認兩個方向都真的實作了，別讓函式簽名騙了自己。

**2. 表象會偽裝成根因，而且偽裝得很像。**
「第二個 IDR 必掛」追了三天，真相是 IDR 到達前後恰好觸發了丟影格風暴。**先設計能一刀切開兩種假設的實驗（IDRREPLAY），再動手修。**

**3. 上傳完一定要 md5。**
上一輪 /tmp/r26.sh 是 0 位元組卻顯示 PUSHED，導致「實驗跑過、結論沒拿到」被誤記成「實驗失敗」。這次改掉了流程，每一步都 `md5sum` 對照。

**4. 卡和崩要用同一套嚴謹度對待。**
崩有 backtrace，卡什麼都沒有，很容易靠猜。但卡的定位其實更便宜——一個 env 開關，四分鐘就有答案。
