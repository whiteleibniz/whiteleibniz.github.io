# bugfix_20260923_05 — GBA 画面呈纵向条纹/撕裂（源 pitch 被忽略）

> **现象**：有画面了，但满屏**规则的纵向条纹**、内容横向错位，像是"撕裂"。
> **根因层**：`miniretro` 帧回调 `video_cb` 的**源行跨距（pitch）寻址** + 帧缓冲并发扫描。
> **修复工作量**：`extern/miniretro/miniretro.c` 累计 +81/-13（含本项与 `bugfix_20260923_04` 黑屏修复；本项为主要部分）。
> **文件名**：`bugfix_20260923_05_GBA画面纵向条纹撕裂.md`
> **关联提交**：（待提交后回填）
> **日期**：2026-09-23

## 现象

1. GBA 游戏能进了（见 `bugfix_20260923_04`），但屏幕上是**规则的纵向条纹**：内容被切成一条条竖带，
   带与带之间有黑缝，整体横向错位、不可读（用户描述为"撕裂状"）。
2. 对照：FC 游戏画面完全正常、无条纹。

初步疑点：这是**时序撕裂**（vsync 缺失）还是**寻址错位**？两者外观可能都"像撕裂"，必须先区分。

## 影响范围

- **受影响**：GBA（240×160, RGB565, pitch=512）。
- **不受影响**：FC（fceumm，pitch 恰等于 width×2）——线性读也正确，故一直正常。
  本次改动对 FC 透明。

## 根因

`miniretro.c` 的 `video_cb` **完全忽略核心给的行跨距**：

```c
static void video_cb(const void *data, unsigned width, unsigned height, size_t pitch)
{
    (void)pitch;                       /* ← pitch 被丢弃 */
    ...
    const uint16_t *src16 = (const uint16_t *)data;
    for(int i = 0; i < (int)(width * height); i++)   /* ← 线性读, 步长=width */
        temp32[i] = convert(src16[i]);
```

- FC：`pitch = 256 × 2 = 512` 字节，恰好 `= width × 2` → 线性读 **碰巧正确**。
- GBA：核心日志实测 `video_cb: 240x160 pitch=512` —— 即**每行 256 像素，而可视宽度只有 240**。
  线性读时每行少跳过 `(256-240)=16` 像素，**逐行累积错位 160 行 ≈ 10 行源数据**，
  于是画面被横向剪切、并因跨行回卷产生规则条纹。

**实锤证据**：在 `video_cb` 加一次性打印，重编后日志输出
`[miniretro] video_cb: 240x160 pitch=512 fmt=2 (每行像素=256)` —— pitch 与 width 确实不一致。

## 定位过程

1. **弯路一（关键）**：最初判定为 **vsync 撕裂**，于是给 `miniretro` 加了**双缓冲页翻转**
   （fb 有 `yres_virtual=3840` 即 3 页，用 `FBIOPAN_DISPLAY` 换页）。
   但用户反馈"还是这样没修复" → 说明**根本不是撕裂，是数据错位**。
2. **抓屏区分**：人眼看不见设备屏幕，于是**实机抓屏**——
   设备端 `python3 os.pread` dump `/dev/fb0`（按当前 `yoffset` 抓前台页）→ SFTP 取回 → 本地按 `[R,G,B,X]` 解成 PNG → 打开看图。
   一看便知：是**规则的纵向条纹**（内容错位、有黑缝），**不是**撕裂线。方向立刻转到寻址。
3. **定位到 pitch**：读 `video_cb` 源码，发现 `(void)pitch;` 与线性读；
   再加一次性打印确认 `pitch=512 ≠ 240×2=480`。
4. **排除双缓冲是元凶**：双缓冲保留（无副作用，且对未来真撕裂有防御价值），但补上 pitch 修复才是根治。

## 解决办法

`extern/miniretro/miniretro.c` 的 `video_cb`：

1. **三个像素格式分支全部改为按 stride 逐行取数**（`pitch==0` 时回退 `width*2`）：

   ```c
   if(pitch == 0) pitch = (size_t)width * 2;

   /* RGB565 */
   const uint16_t *src16 = (const uint16_t *)data;
   size_t stride = pitch / 2;                     /* 字节 → 像素 */
   for(unsigned y = 0; y < height; y++) {
       const uint16_t *row = src16 + (size_t)y * stride;
       uint32_t *dst = temp32 + (size_t)y * width;
       for(unsigned x = 0; x < width; x++) {
           uint16_t p = row[x];
           dst[x] = 0xFF000000U | (((p>>11)&0x1F)<<19) | (((p>>5)&0x3F)<<10) | ((p&0x1F)<<3);
       }
   }
   scale_rotate90(temp32, fb_dst, width, height, fb_w, fb_h);
   ```

   `XRGB8888`（pitch/4）与 `0RGB1555`（pitch/2）同理。
   注意结果仍是 `0xAARRGGBB`，由 `scale_rotate90` 统一做 R/B 字节交换后落盘。

2. **保留双缓冲页翻转**（`g_dbuf`，`FBIOPAN_DISPLAY`；首次失败自动降级单缓冲）——
   本机 `FBIO_WAITFORVSYNC` 返回 `EPERM` 不可用，换页是唯一可行的防撕裂手段。

3. 重编：`cd extern/miniretro && sh build.sh`。

  - **无纵向条纹、无撕裂、无黑缝**。

## 经验教训

1. **"撕裂"与"条纹/错位"是两种病，必须先分开。**
   - 撕裂 = **时序**问题（帧缓冲正被扫描时被改写）→ 双缓冲/页翻转/vsync。
   - 条纹 = **寻址**问题（每行步长算错）→ 核对 pitch/stride。
   不加区分就上双缓冲，会白改一轮（本 bug 就是如此，浪费了一次往返）。
2. **接不同 libretro 核心时，`pitch` 必须用，绝不能假设 `pitch == width × bpp/8`。**
   mGBA 的缓冲行对齐到 256 像素，导致 `pitch/2 = 256 ≠ width(240)`。
   线性读在 width 恰好整除 pitch 时"碰巧对"，换个分辨率立刻暴露。
3. **看不到设备屏幕时，实机抓屏是最高性价比的诊断手段**：
   `os.pread("/dev/fb0")` → SFTP → 本地按 `[R,G,B,X]` 解 PNG → 人眼看图。
   一眼看出是条纹还是撕裂，胜过一堆日志推理。
4. **"非黑像素占比"这类量化指标只能证明"有画面"**，证明不了"画面正确"；
   判"画面对不对"必须人眼。
5. **别把"改了没效果"当噪声**：用户两次说"还是这样"，恰恰是"根因判断错了"的最强信号。
