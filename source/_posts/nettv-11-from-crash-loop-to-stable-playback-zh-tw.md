# 把網路電視調通：從一天崩三次到連續播 4800 幀

> 裝置：展訊 SC9832A（sc8830 系列），Alpine/armv7l，720×1280 直式螢幕，LVGL 桌面。
> 目標：HLS 直播串流用 VSP 硬解輸出到 framebuffer，達到安卓官方播放效果。
> 最終：遼寧衛視《鄉村財富》穩定播出，uptime 36 分鐘零重啟，4808 幀上螢幕。

## 起點：每輪必崩

新版程式每跑必崩，崩在相位樁最後一行：

```
>> fill(out)#1 开始 g_nout=1
   fill(out) 交第0路 hdr=0xb6d8ec80 pBuffer=0xb6d9ba80
                                    ← 没有下一行，设备重启
```

`sigsetjmp` 攔不住，`dmesg` 無 OOM，記憶體還剩 882 MB。核心模式崩潰。

## 五個根因，五次 A/B

### 根因 1：除錯程式自己就是崩因

10-18 晚上我加了一套「掛死現場取證」：`vrp_hook()` hook 廠商的 VSP 暫存器寫函式，
每次呼叫都從 `rb + 0x60901000` / `rb + 0x60908000` **直接讀 MMIO 暫存器視窗**；
`tr_line()` 更狠，每次 DRIVE 前後各讀一次。

`vrp_hook` 是每一輪輪詢都會走的高頻路徑。於是 VSP 狀態機被打亂，
崩在緊隨其後的 `DRIVE fill(out)#1`。

**崩潰點不在除錯程式那行**，所以堆疊、日誌、訊號處理全都指不到它。
舊版（能跑的）完全沒有這段程式碼——這才讓我想到去比。

修法：`NETTV_TRACE_MMIO` 預設 0，直接 return 不碰 MMIO。
驗證：跑到 AU[1100]+，564 次 fill 全返回，零重啟。

### 根因 2：NAL 切碎

三次崩潰現場的鐵證——**崩點永遠緊跟一個被切成多片的 NAL**：

```
AU[109] sub1/4  4096B 后崩
AU[369] sub1/2  4096B 后崩
AU[36]  sub28/28 3048B 后崩
而 sub1/1（未切碎）从不崩
```

A/B 決定性：`NETTV_CHUNK=0` → 1200 幀跑到 AU[1100]+ 零重啟；預設 4096 → 每輪必崩。

機理推論：廠商函式庫對「同一個 NAL 分多次 nOffset 續投同一個 buffer」的處理有缺陷。
（我最初查錯了方向——`NETTV_SPLIT` 管的是拆 NAL 邊界，切碎由 `g_chunk` 決定，兩者不同。）

### 根因 3：虛擬位址當成實體位址 → 一片綠

日誌裡兩行並列就是鐵證（同一個 fd=12）：

```
登记 fd=12 → pa=0xb1ce6000            ← 虚拟地址（错）
[ion] Get_phy_addr#1 fd=12 真PA=0x9fa00000   ← 真物理地址（对）
```

廠商 VSP 把 `handle->ints[12]` 當**實體位址**寫影格，我填的卻是 mmap 的虛擬位址。
硬體存取不到使用者空間虛擬位址 → 寫不進真顯示記憶體 → 螢幕上一片綠。

修法：新增 `g_gh_pa[]` 存真 PA，4 處 `fh[12]` 全部改填 PA，VA 只留給 CPU 讀影格。

### 根因 4：ION 搶不到 + 不釋放

自管 ION（heap mask=8 `carveout_mm`，實體連續）搶到時一切正常，搶不到時
`ghOut` 會退回 gralloc 的真 handle——而 gralloc 走 IOMMU heap，**無實體連續 backing**，
VSP 拿假 PA 寫影格必崩核心。

兩個改動：重試 6 輪 + 120ms 退避 + 尺寸階梯；仍搶不到就 `_exit(12)` 讓看門狗重生，
**寧可不出畫面也不打飛核心**。另外退出前呼叫 `ION_IOC_FREE`(0xc0044901) 主動釋放。

### 根因 5：最貴的那個——是我自己

`ps | grep -c nettv_player` 顯示堆了 **12~23 個殭屍行程**。

每輪除錯我都 `nohup` 起一個腳本，而 monitor 內部還會自己重生 worker/worker-dl/mplayer，
每輪實驗多留一整套，每個搶 2MB C1 緩衝 → 池被撐爆 → 後續起不來。

`pgrep -x nettv_player` 只數主行程，看不到這些，所以我一度誤判成「核心洩漏」，
還專門寫了個 `ion_release()` 去救火。

`pkill -f nettv_player` 全清後，池立刻回到 `total 0`，**立刻就能正常播**。

> 這一條最值錢：**症狀和真因差了十萬八千里，而唯一的分界線是「多問一句 ps」**。

## 最後一小時：抓畫面騙了我一小時

畫面明明上螢幕了，我抓畫面看到的卻是舊的 WiFi 設定頁，連抓 4 張內容一模一樣。

真因：`/sys/class/graphics/fb0/virtual_size = 720,3840` —— fb 有 4 頁，
我的截圖腳本只讀**第 0 頁**。而 `fb_render()` 每影格寫 `g_fbpg*720*1280*4` 偏移
並 `fb_pan()` 翻頁，內容在第 1/2 頁。

**抓畫面看到舊畫面 ≠ 沒上螢幕。** 先查 `virtual_size`，再下結論。

順手把截圖腳本改成自動：驅動 `pan_offset` 恆 0 讀不到目前頁面，於是逐頁統計
**色彩種類數**取最多者（實測 page0=55 色殘留舊頁 vs page1=617 色真實畫面）。
中間試過「取樣求和」，結果選反了——求和反映亮度不反映多樣性。

```
uptime 36min  零重启
上屏 4808 帧
画面: 辽宁卫视《乡村财富》  人物清晰 / 字幕可读 / 台标正常 / 色彩正确
```

## 方法論檢討

**1. 「除錯程式自己就是崩因」是一類獨立故障模式。**
它不會崩在自己那行，所以堆疊和日誌全都指不到它。
只有把能跑的舊版和崩的新版**擺在一起**，逐欄位比對執行時期狀態，才看得出「舊版沒有這段」。

**2. 崩點模式比「猜假設」有力得多。**
根因 2 是靠「崩點永遠緊跟 subN/M」這個模式一眼看出來的，
而不是靠推論。**拿到多次崩潰現場，第一件事是找它們的共同模式。**

**3. 排查期必須有絕對可靠的取證通道。**
這個專案 stdout 被自訂 stdio 的 4KB 塊緩衝吞掉，崩潰時緩衝區全丟——
我一度靠空日誌誤判過三次。後來改用 `O_SYNC` 直寫的相位樁，
每次腳本上傳都 `md5sum` 校驗（踩過 3 次 0 位元組腳本導致誤判「新版不崩」）。

**4. 「跑不起來」先 `ps` 一遍。**
真的，這個成本 1 秒，能省掉一小時的錯誤歸因。

**5. A/B 是唯一誠實的實驗。**
本文五個根因，每一個都是「改一個變數、跑一次、對比」定出來的。
憑推論猜出來的假設，我試了八個，全錯。
