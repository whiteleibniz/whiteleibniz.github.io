> 系列第 28 篇。上一篇把 10.3 秒的段间隙拆成「选段 5.0s + 音频排空 5.2s」，本篇先把选段这 5 秒**量出来**，再把它**砍到 0.3 秒**。根因说出来有点丢人：我们一直在等一个还没生成的分片，而窗口里躺着 4 段现成内容没播。

## 一、先给选段装表

上一篇的仪器化只到 `pick_seg()` 这一层，只知道「选段一共 5.0 秒」，不知道这 5 秒是**在下载**、**在 sleep**、还是**在重试**。所以第一步是给 `hls_pick()` 每次拉列表计时，并统计段条数、末段名、`g_last_seg` 命中的位置。

改动纯计时 + 日志，行为零改变。泸县源跑一轮，打点长这样：

```
[hls] 拉列表 2330ms 段数=5 r=1 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 选段 总=2330ms 拉列表=2330ms/1次 段数=5 命中=1 失败=0
[hls] 拉列表  215ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  245ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  245ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  276ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 选段 总=4981ms 拉列表=981ms/4次 段数=5 命中=0 失败=0
>>> [hls] 无新段: 重播上一段保持画面
```

账单立刻清楚了：**4 次重试里拉列表一共只花 981ms（每次约 250ms），剩下 4000ms 全是 `sleep(1)` 空等**。网络不是瓶颈，逻辑才是。

## 二、5 秒空等的真身

把三行信息摆在一起看，结论几乎是自证的：

| 观察 | 数字 |
|---|---|
| 播放列表里的分片数 | **5 段**（Num15825006 ~ Num15825010） |
| 我们每轮实际取的 | **只有最后一条** Num15825010 |
| 4 次重试结果 | 全部 `r=0`（末段没变） |
| 兜底动作 | **重播上一段** |

旧逻辑是「取列表最后一条 → 跟上一条比 → 相同就 sleep 1 秒重试 4 次 → 还相同就重播上一段」。它隐含一个假设：**我们总是贴着直播边缘在播，所以只有最新那一段值得播，下一块内容只能等服务器生成。**

可我们根本不贴着边缘——每轮段间隙 10.3 秒，一段内容才 5.96 秒，我们比直播**越落越远**。窗口里 4 段没播过的现成内容就这么躺在那儿，我们一边空等、一边把刚播过的那一段再播一遍。

「重播上一段」这个兜底当初是为了**画面别黑**（见第 15 篇），但它在源刷新慢时会变成「画面原地循环」。日志里 3/3 轮都是 `命中=0`。

顺带一个意外发现：**泸县源当天凌晨的末段号 Num15825010 在两轮共 15 分钟里纹丝不动**，源已经停止刷新了。这既解释了为什么怎么测都是 15fps，也说明「拿一个源测到底」这件事本身有风险。

## 三、修法：窗口内顺序推进

思路很直白——**别只盯最后一条，在窗口里找到上次播的那一段，播它的下一段**。

```c
/* 列表全量解析进 g_segs[](不再只留 best) */
int at = -1;
for (int i = 0; i < g_segs_n; i++)
    if (!strcmp(g_segs[i], g_last_seg)) { at = i; break; }

if (at >= 0 && at + 1 < g_segs_n) {
    /* 窗口内还有下一段: 立刻前进, 零等待 */
    snprintf(full, sizeof full, "%s", g_segs[at + 1]);
} else if (at >= 0) {
    /* 已经播到窗口末尾: 只有末尾真的更新了才前进, 否则返回 0 等新段 */
    if (strcmp(g_segs[g_segs_n - 1], g_last_seg))
        snprintf(full, sizeof full, "%s", g_segs[g_segs_n - 1]);
    else { r = 0; goto done; }
} else {
    /* 首播 或 g_last_seg 已滑出窗口: 从倒数第 (1+HLSBUF) 段起播, 主动建缓冲 */
    int off = 1 + hlsbuf(); if (off > g_segs_n) off = g_segs_n;
    snprintf(full, sizeof full, "%s", g_segs[g_segs_n - off]);
}
```

三个分支对应三种处境：窗口内有存量 → 白拿；真到边缘 → 才等；首播/滑出 → 主动往回退几段**建缓冲**。

最后这个分支是关键。`NETTV_HLSBUF`（默认 3）让首次取段从「倒数第 4 段」开始，等于一上来就攒了 3 段约 18 秒的余量。之后每播完一段就往前挪一格，只要服务器按段时长出货，就永远有下一段可播——**等待从常态变成例外**。

## 四、实测

修复后泸县源（窗口里那 4 段存量）：

```
[hls] 选段 总=2311ms 拉列表=2311ms/1次 段数=5 命中=1 位=-1   ← 首播, 建缓冲
[hls] 选段 总= 225ms 拉列表= 225ms/1次 段数=5 命中=1 位=1
[hls] 选段 总= 202ms 拉列表= 202ms/1次 段数=5 命中=1 位=2
[hls] 选段 总= 225ms 拉列表= 225ms/1次 段数=5 命中=1 位=3
```

选段从 **4981ms → 225ms（-95%）**，「重播上一段」在存量耗尽前一次都没触发。对应的段间隙：

```
[供数] 段2: 段间隙=6029ms  成分: 选段=250ms   预取=5557ms 音频=5009ms
[供数] 段3: 段间隙=6431ms  成分: 选段=481ms   预取=11541ms 音频=10987ms
[供数] 段4: 段间隙=6234ms  成分: 选段=705ms   预取=17333ms 音频=16774ms
```

段间隙 **10309ms → 6029~6431ms（-40%）**。剩下的 5 秒清一色是 `音频`——那是上一篇定位的 `audio_feed()` 物理排空，属于下一刀。

为了拿到真稳态（泸县源已停刷），换到仍在刷新的松潘源跑 120 秒：

```
[hls] 选段 总=304ms 命中=1 段数=3      ← 11 段全部命中, 无一次重播
[hls] 选段 总=322ms 命中=1 段数=3
[hls] 选段 总=331ms 命中=1 段数=3
...
[STAT] frames=5125 real=2439 elapsed=111993ms fps_x10=217
signal=11 = 0
```

**21.7fps，零崩溃**，选段稳定在 310ms 上下。段间隙仍显示 11.2 秒，但那是因为松潘一段内容本来就约 10 秒、且 `音频` 一项占了 8.6 秒——**选段已经不是瓶颈**。

不过只报修复后的数字是没有说服力的，所以补了一组同二进制族对照（v23 = 修复前的选段逻辑），同样是松潘源、同样 120 秒：

| | fps | 段间隙 EMA | 选段 | rb 深度 | 命中率 |
|---|---|---|---|---|---|
| v23（旧选段） | **14.2** | 19029ms | ~310ms | 296 → 146（被抽干） | — |
| v28（新选段） | **21.7** | 11400ms | 304~338ms | 377 → 489（持续涨） | 11/11 |

有意思的是：**松潘源上旧逻辑其实也不空等**——这个源刷新够快，拉列表时总有新段，选段同样只要 310ms。差距不来自 sleep，而来自**缓冲深度**：旧逻辑贴着直播边缘跑，rb 一路被抽干到 146（worker 等米下锅）；新逻辑首播就建了 2~3 段余量，rb 一路涨到 489。所以帧率差 53% 的真实原因是**供数不再断顿**，而不是省下了那几次 `sleep(1)`。

换句话说：这个修法在源刷新快时靠「建缓冲」，在源刷新慢时靠「吃窗口存量」，两种处境都能兜住。

## 五、代价与取舍

天下没有免费的帧率。这个修法把「延迟低但卡顿」换成了「流畅但延迟高」：起播时主动往回退 `HLSBUF` 段，默认 3 段约 18 秒延迟。

对电视直播来说我认为这笔交易划算：18 秒延迟用户基本无感，而「每 10 秒卡一下 + 画面原地循环」是肉眼可见的糟。真要贴直播边缘，`NETTV_HLSBUF=0` 就能退回旧行为。

另外提醒一句：**这套逻辑依赖 `g_last_seg` 能在列表里精确匹配到**。如果源在 URL 上挂了会变的 query 参数（鉴权串、`?m=` 时间戳之类），匹配会失败并退化成「每轮都跳回建缓冲」。实测的源段名是稳定路径，没踩到，但换源时值得先看一眼 `[hls] 拉列表 ... 位=` 这一列——**正常应该是 -1 之后递增，如果一直是 -1，就是匹配坏了**。

## 六、下一刀

段间隙的账单现在长这样：

| 项 | 修复前 | 现在 |
|---|---|---|
| 选段 | 4918ms | **~320ms** |
| 音频排空 | 5231ms | **5231ms（未动）** |
| 下载 + 入池 | ~220ms | ~220ms |

77% 的黑洞已经集中在 `audio_feed()` 一家身上。第 27 篇做好的**异步音频泵**（`NETTV_AUDIO_ASYNC=1`，把整段 `rename` 给子进程慢喂）单独测过能把音频从 5231ms 压到 1ms、帧率 +30%。两刀叠加后，段周期会短于段内容时长，瓶颈将正式交给 worker 侧（渲染 23.2ms）——那时候才是真的打硬仗。

## 附：本次踩到的两个坑

1. **日志被重生截断**：`child_log_bound()` 用 `O_TRUNC` 打开 `/tmp/nettv_child.log`，monitor 每重启一次子进程，前面的 `[STAT]`/`[供数]` 全没了。95 秒跑出 973 帧，日志里却只剩 1 条 `[供数]`——差点误判成「一开局就崩」。已改成 `O_APPEND` + 每次重生打分隔标记。
2. **别拿一个源测到底**：泸县源凌晨停刷，同一份代码测出来是 15fps；换松潘源是 21.7fps。**偏离结论的往往不是代码，是源的状态**。判源活没活，隔 9 秒拉两次 m3u8 比末段号就够了。
