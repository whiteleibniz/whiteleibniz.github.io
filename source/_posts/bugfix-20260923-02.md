# bugfix_20260923_02 — 页面离场不清焦点组，导致桌面焦点环消失

> **现象**：进过任意页面再返回桌面后，按方向键**粉色焦点框凭空消失**、且走不到目标图标；
> 重启应用即恢复。触摸点击不受影响。
> **根因层**：LVGL 页面框架的焦点组生命周期（`lv_pm/lv_page_manager.cc`）/ 桌面自定义导航（`main.c`）。
> **修复工作量**：2 个文件（`lv_pm/lv_page_manager.cc` +49、`main.c` +7/-1）。
> **文件名**：`bugfix_20260923_02_页面离场不清焦点组导致桌面焦点环消失.md`
> **关联提交**：221fa7d
> **日期**：2026-09-23

## 现象

在**任何非桌面页面**里返回桌面之后，桌面按方向键会出现：

1. **粉色焦点框凭空消失** —— 按了键，界面上看不出当前选中了哪个图标；
2. 继续按方向键**走不到想去的图标**（比如想回到「收音机」，却卡在别处或原地不动）；
3. 反复按也没有规律，**重启应用（不是重启设备）后恢复正常**，一进页面再返回又坏。

即在"进过页面 → 返回桌面"这条路径上，桌面导航会被污染。

> 这是排查「蓝牙显示已连接实际未连接」过程中**连带发现**的 bug：
> 为了给蓝牙页做按键验证（进页面 → 返回 → 走到蓝牙图标），发现根本走不到，
> 一查才知道桌面焦点早就坏了。

## 影响范围

| | |
|---|---|
| **受影响** | 桌面（launcher）的按键导航；所有"进过页面再返回"的场景；间接触发了本会话另一处「收音机页进不去」的误判 |
| **不受影响** | 触摸点击（不走焦点组）；页面内部自身的导航；页面渲染；FM 收音机、蓝牙等业务逻辑 |

触摸能点、按键不能走，是本 bug 最典型的表现。

## 根因

**两处独立缺陷叠加**，各自都能让导航失灵。

### 3.1 页面离场时，不把自己的控件从"公共焦点组"里摘掉

LVGL 的默认焦点组是**全局共享**的。各页面在 `onCreate` 里调用
`lv_group_add_obj(lv_group_get_default(), obj)` 把自己的控件挂进去，
但**离开时几乎没有人调用 `lv_group_remove_obj()`** ——
全仓只有 3 个文件做了这一对操作，其余页面全是"只加不减"。

于是每进一次页面，就有一批**已经随页面一起被删除、或已不可见**的控件
残留在组里，变成"幽灵焦点"。实测计数（`lv_group_get_obj_count`）：

```
干净启动进桌面        默认焦点组 objcnt = 18   (桌面 17 个图标格 + 状态栏音量滑块 1)
进收音机页            默认焦点组 objcnt = 37   (+19，收音机页挂进来的)
返回桌面(修复前)      默认焦点组 objcnt = 37   ← 19 个一个都没收回
页面销毁时清理后      默认焦点组 objcnt = 18   ← 只减不减的"组计数"才是真凶
```

`group_find_neighbor` 在这些幽灵里挑邻居，于是：
- 选中一个**没有 `user_data`** 的控件 → 桌面画焦点框的代码拿不到格子信息 → **框消失**；
- 方向键的"邻居关系"被幽灵搅乱 → **走不到目标图标**。

### 3.2 `group_find_neighbor` 只看控件自己的 HIDDEN，不看祖先

`main.c` 的自定义导航里，原判定是：

```c
if(lv_obj_has_flag(o, LV_OBJ_FLAG_HIDDEN)) continue;   /* ← 只看自己 */
```

而 LVGL 里**隐藏一个面板，隐藏的是外层容器**，里面的子控件自己**并不带**
`LV_OBJ_FLAG_HIDDEN`。结果：状态栏那个**收起状态的音量浮层滑块**
（父面板 340×42，滑块自己 252×14）被当成合法候选选中了。

定位到它靠的是"打印幽灵对象的形状再反查"（见 §4.2）：

```
cls=slider  pos=(66,5)  size=(252,14)  abs=(256,69)
父容器 size=(340,42) 子对象数=2   -> lv_status_bar/volume_control.c:207 的 s_volume_slider
```

选中它同样没有可用 `user_data` → 焦点框画不出来。

> 一句话：**① 组里有幽灵；② 判定可见性只看了自己，没看祖先。**

## 定位过程

### 4.1 先确认"焦点到底落在谁身上"

在桌面渲染焦点框的那段代码里加了一行 stderr 打点（`printf` 会因块缓冲延迟，
**必须用 `fprintf(stderr, ...)`**）：

```c
if(cell == f)
    fprintf(stderr, "[fc] focus idx=%u/%u cell=%p content=%p box=%p\n",
            (unsigned)i, (unsigned)cnt, (void*)cell, (void*)content, (void*)box);
```

- **故障时**（页面管理器清理已上、祖先感知未上的中间状态）：
  `[fc] focus idx=17/18 cell=0x... content=(nil) box=(nil)`
  → `content`/`box` 为 **空指针** = 当前焦点对象**没有 `user_data`**，
  桌面拿不到"这个焦点属于哪个图标格"的信息，**框自然画不出来**。
  `idx=17/18` 也印证了：桌面只往组里加了 17 个格子，**第 17 个（0 基）根本不是桌面的**。
- **修复后**：`[fc] focus idx=7/18 cell=0xb70881d4 content=0xb7088374 box=0xb7088444`
  → 三个指针都有值 = 焦点框能正常画出来。

`idx` 的**分母**（组内对象总数）本身就是线索：把每个页面进/出时的组计数打出来，
会看到数字**只涨不跌**（见 §3.1 与 §6.1）—— 这正是"幽灵在累积"的直接证据。

### 4.2 把幽灵"打印出来"再反查

只加焦点打点不够，还需要知道幽灵长什么样。临时在页面管理器里加了一段 dump：

```c
/* 临时诊断：把默认组里不属于本页的对象形状打出来 */
for(uint32_t i = 0; i < lv_group_get_obj_count(g); i++) {
    lv_obj_t *o = lv_group_get_obj_by_index(g, i);
    fprintf(stderr, "  [g] #%u cls=%s pos=(%d,%d) size=(%d,%d) abs=(%d,%d) kids=%u\n",
            i, lv_obj_get_class(o)->name,
            (int)lv_obj_get_x(o), (int)lv_obj_get_y(o),
            (int)lv_obj_get_width(o), (int)lv_obj_get_height(o),
            (int)lv_obj_get_coords(o)->x1, (int)lv_obj_get_coords(o)->y1,
            (unsigned)lv_obj_get_child_count(lv_obj_get_parent(o)));
}
```

靠 `size=(252,14)` + `父容器 340×42` 这两个特征，在 `lv_status_bar/volume_control.c:207`
找到 `s_volume_slider`，反证了 §3.2。诊断打点定位完后已清理。

### 4.3 排除掉的方向

| 尝试 | 结果 |
|---|---|
| 怀疑桌面自己算错邻居（左右跨行问题） | ❌ 桌面逻辑没变过，且**重启应用就恢复** → 是"被外部污染"，不是算法错 |
| 怀疑 `lv_obj_clean` 删对象后组里留悬垂指针导致崩溃 | ❌ 没有崩溃，只是焦点错位；LVGL 删对象时会自动移出组 |
| 怀疑是"收音机页没销毁" | ❌ `[pm] destroy 'radio'` 正常打出，页面确实销毁了 —— 但**控件还在组里**（组和对象生命周期是两回事） |
| 只修 §3.1（页面管理器统一清理） | ⚠️ 大部分恢复，但组计数仍是 18（= 桌面 17 格 + **1 个非桌面对象**）→ 说明还有一个不属于桌面的成员，必须同时修 §3.2 |

## 解决办法

### 5.1 页面管理器统一清理（一处修好所有页）

在 `lv_pm/lv_page_manager.cc` 里新增：

```c
/**
 * @brief 把某个页面根对象下的控件从默认焦点组里全部摘掉
 *
 * 为什么必须做：默认焦点组是全局共享的，各页面在 onCreate 里把自己的控件
 * add 进去，但离开时从来没有人 remove（全仓只有 3 个文件做对了）。
 * 残留控件变成"幽灵焦点"：桌面按方向键会被吸到一个没有 user_data 的控件上，
 * 选中框直接消失，而且走不到想去的图标（实测默认组 17 -> 18）。
 * 集中放在页面管理器里做，所有页面一次修好，新页面也不用再记这条规矩。
 */
static void pm_purge_group_objs_of(lv_obj_t *root)
{
    lv_group_t *g = lv_group_get_default();
    if(!g || !root) return;
    uint32_t cnt = lv_group_get_obj_count(g);
    for(uint32_t i = cnt; i > 0; i--) {          /* 倒序：删除会改变下标 */
        lv_obj_t *o = lv_group_get_obj_by_index(g, i - 1);
        if(!o || !lv_obj_is_valid(o)) continue;
        lv_obj_t *p = o;
        bool mine = false;
        while(p) { if(p == root) { mine = true; break; } p = lv_obj_get_parent(p); }
        if(mine) lv_group_remove_obj(o);          /* 沿父链找根，判定归属 */
    }
}
```

在 `pm_page_destroy()` 里、`page->onDestroy(page)` **之前**调用
（此时对象都还合法；`onDestroy` 里可能已经释放定时器/回调）：

```c
if(pm_obj_valid(root)) {
    lv_group_t *dbg_g = lv_group_get_default();
    uint32_t before = dbg_g ? lv_group_get_obj_count(dbg_g) : 0;
    pm_purge_group_objs_of(root);
    uint32_t after = dbg_g ? lv_group_get_obj_count(dbg_g) : 0;
    if(after != before) {
        fprintf(stderr, "[pm] 页面 '%s' 离场，摘掉 %u 个焦点组残留控件（现共 %u）\n",
                page->page_name ? page->page_name : "?",
                (unsigned)(before - after), (unsigned)after);
    }
}
```

正常情况摘掉数量应为 0（不打日志）；一旦有残留就打一行，
**方便以后发现"某个页面又忘了清理"**。

> 该文件是 `.cc` 但原来只 include 了 `<string.h>`，用 `fprintf/stderr` 需补
> `#include <stdio.h>`，否则编译报 `MAKE_RC=2 'stderr' was not declared`。

### 5.2 可见性判定改为"祖先感知"

`main.c` 的 `group_find_neighbor()`：

```c
-    if(lv_obj_has_flag(o, LV_OBJ_FLAG_HIDDEN)) continue;
+    /* 必须连同祖先一起判断可见性（nav_obj_visible）。
+     * 只看对象自己的 HIDDEN 是不够的：面板收起时隐藏的是外层容器，
+     * 里面的控件自己并不带 HIDDEN，于是会被当成合法候选选中 ——
+     * 表现就是桌面按方向键时选中框凭空消失、走不到想去的图标。 */
+    if(!nav_obj_visible(o)) continue;
```

`nav_obj_visible()` 是 `main.c` 里已有的工具函数，会**沿父链逐级检查** HIDDEN。

### 6.2 按键实测（`ssh_tools/nav_trace.py "E B L L"`）

干净重启应用 → 进收音机 → 返回桌面 → 连按两次左键：

## 经验教训

1. **全局共享的容器，进和出要成对。** 焦点组是全局单例，页面只 add 不 remove，
   等于把垃圾倒进了公共区域 —— 而且**症状出现在受害者（桌面）身上，不在肇事者（页面）身上**，
   极难从现象反推。凡是"全局注册表"，就该由框架层统一托管生命周期，别指望每个页面自觉。
2. **生命周期要分两层看：对象被删 ≠ 从组里摘掉。** 页面销毁得干干净净（`[pm] destroy` 正常），
   控件照样赖在组里。查这类问题时，**打印"容器里现有多少元素"比打印"我删了什​么"有效得多**。
3. **可见性判定必须祖先感知。** `LV_OBJ_FLAG_HIDDEN` 只描述对象自己；
   "这个控件现在用户能不能看见"是一个**沿父链**的问题。LVGL 里凡是"隐藏容器"的写法，
   都会踩这个坑。
4. **"重启应用就好"是强烈的"外部污染"信号。** 它说明故障不是算法本身错，
   而是运行期状态被别处改脏了 —— 排查方向应立刻从"算得对不对"转向"谁动过共享状态"。
5. **诊断打点用 `fprintf(stderr, ...)`。** `printf` 写文件是块缓冲，日志会滞后很久，
   容易误判成"代码没执行"（排查 FM 页面时也踩过同一个坑）。
6. **把"规范"下沉到框架层，而不是写进文档。** 本例最初只是在文档里写"记得 remove"，
   结果没人执行；搬进 `pm_page_destroy` 后，新旧页面一次性合规。
   **能被代码强制的约定，不要靠自觉。**
