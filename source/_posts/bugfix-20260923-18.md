# bugfix_20260923_18 — GBA 退出后**偶发**残留游戏画面（强制翻页）

- **日期**：2026-09-23
- **现象**：退出 GBA 游戏后，屏幕**有时**仍显示"退出那一刻的游戏画面"，界面没回来；
  **不是必然发生** —— 同样的操作，有时正常回到游戏列表，有时就定格在游戏画面上。
- **影响面**：`lv_pages/gba_game_page.c`（**只改这一个文件**，前端不动）
- **是否影响 FC**：不影响（FC 前端不翻页，无页概念）
- **与第 14 篇的关系**：14 篇治的是"退出后**必卡**"（加 `gba_reset_fb_page()` 兜底），
  **本次 18 篇治的是那个兜底自己带来的偶发性** —— 它带了一个不该有的前置判断。

---

## 1. 背景：谁在画哪一页

设备 framebuffer 有 3 个虚拟页（`yres_virtual = 3840 = 3 × 1280`）。

| 谁 | 怎么用 fb0 |
|---|---|
| **LVGL**（`lv_linux_fbdev`） | 只用 mmap 基址绘制 = **永远写第 0 页**；`yoffset` 初始化后不再改，源码里 `FBIOPAN_DISPLAY` 零命中 |
| **GBA 前端**（`miniretro_gba`） | 用 `FBIOPAN_DISPLAY` 双缓冲页翻转消撕裂 → 前台在**第 0/1 页之间来回切** |

**推论**：退出时若前台停在第 1 页，LVGL 画什么都看不见 → 屏幕定格游戏画面。
第 14 篇就是靠这个推论定位的，父进程侧加了 `gba_reset_fb_page()` 兜底。

## 2. 根因：兜底里那个"看起来无害"的前置判断

第 14 篇加的兜底实现是**带条件**的：

```c
if(ioctl(fd, FBIOGET_VSCREENINFO, &v) == 0 && v.yoffset != 0) {
    v.yoffset = 0;  v.activate = 0;
    ioctl(fd, FBIOPAN_DISPLAY, &v);
}
```

当时的判断依据是"实测这个驱动的 yoffset 回读是可靠的"。**这次的问题是：这句话即使成立，
也不足以支撑这个判断** —— 因为它还隐含假设了：

> 「回读 `yoffset == 0`」等价于「扫描输出正在读第 0 页」

`yoffset` 只是驱动内部的**记账值**（下一次 pan 的请求参数），它**不保证等于**扫描输出
（scanner / LCDC）当前正在读的那一页。两者一旦不一致：

- 屏幕实际显示第 1 页（游戏画面）；
- 回读 `yoffset` 却是 0；
- 判断为假 → **整段翻页被跳过** → 残留。

而"两者是否一致"取决于退出那一刻驱动内部状态（上一帧提交方式、SIGKILL 落在哪一拍），
**与代码路径无关** —— 这正好解释了用户说的"**不是必然发生**"。

> 换句话说：第 14 篇的兜底，把"一定会卡"变成了"**偶尔**会卡"。
> 它只在"回读恰好不可信"时失效，所以看起来像随机。

**第二处隐患**：翻页与整屏重绘分处**两个执行流**（前者在收尸线程、后者被
`lv_async_call` 排给主线程）。这是同一个视觉事务的两半，中间任何打断
（回调被吞、页面先被销毁、主循环那一拍没跑到）都会留下"翻回去了但没重绘"
或"重绘了但前台还在第 1 页"的中间态，单独看都表现为**画面没回来**。

## 3. 修复（一个文件，4 处改动）

全部在 `lv_pages/gba_game_page.c`。

### 3.1 `gba_reset_fb_page()` — 去掉判断，**无条件**翻页（核心）

```c
static void gba_reset_fb_page(void)
{
    int fd = open("/dev/fb0", O_RDWR);
    if(fd < 0) return;
    struct fb_var_screeninfo v;
    memset(&v, 0, sizeof(v));
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) < 0) { close(fd); return; }  /* 只为拿到一份完整参数 */

    unsigned was = v.yoffset;          /* 只用于打日志 */
    v.yoffset  = 0;
    v.activate = 0;                    /* 与前端 fb_restore() 用同一组参数 */
    if(ioctl(fd, FBIOPAN_DISPLAY, &v) < 0) { ...留日志; return; }

    /* 读回校验 + 失败重发一次(个别驱动要两拍才落定) */
    ...GET 若仍非 0 → 再发一次...
}
```

**关键差别**：GET 只用一次——为了拿到一份完整合法的 `fb_var_screeninfo` 当底稿；
**它绝不参与"要不要翻页"的决策**。翻页请求每次都发。

### 3.2 `gba_repaint_async()` — 翻页与重绘**同拍**

```c
static void gba_repaint_async(void *unused)
{
    (void)unused;
    gba_reset_fb_page();                 /* ★ 紧挨着重绘再翻一次 */
    lv_obj_invalidate(lv_screen_active());
    lv_refr_now(NULL);
}
```

两件事放进同一个主线程回调、中间不插任何操作 → 必然同拍完成，不留中间态。

### 3.3 `gba_timer_cb()` — 主线程侧双保险

主线程恢复路径（`finished` 标志那条）在重绘前同样补一次翻页。与 3.2 谁先跑到都行，
翻页幂等。

### 3.4 前端 `miniretro_gba.c` — **不动**

它的 `fb_restore()` 早在第 14 篇就已经是"**无条件**翻回第 0 页"，
本次要修的正是页面侧漏掉的那半边对称性。

**共 5 个调用点**（`grep -c 'gba_reset_fb_page();'` = 5）：
`gba_repaint_async` / `gba_wait_thread` / `gba_timer_cb` / `gba_on_create` / `gba_on_destroy`。

### 为什么"无条件"是安全的

所有调用点都在**子进程已经消失之后**（或页面刚创建、根本没有子进程时），
不存在并发写 fb0 的对手；`FBIOPAN_DISPLAY` 本身幂等，已经在第 0 页时多发一次零副作用。

## 5. 反模式记录（已并入 skill）

- **★ 「幂等操作 + 前置判断」是自找分支**。判断所依赖的那个值（这里是驱动回读）
  只要存在"与真实状态不一致"的可能，判断就会把**零成本的幂等操作**变成
  "**偶发不执行**"，而症状看起来像随机故障。**对幂等且成本可忽略的操作：直接做，不要问。**
- **★ 同一个视觉事务的两半不要分处两个执行流**。"让前台页归位"和"把新画面画上去"
  是同一件事，拆到两个线程/两个回调就会留下人人都看不懂的中间态。
- **★ 「实测 X 可靠」这类结论必须带上它支撑的推论范围**。
  "回读可靠"≠"回读值等于扫描输出"，后者才是代码真正依赖的假设。
- **偶发故障的第一侦查方向是"判断条件"而不是"时序"**：先问"这段代码有没有可能
  在正确输入下选择不做" —— 收益远高于先怀疑竞态。
