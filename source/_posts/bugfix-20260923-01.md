# bugfix_20260923_01 — 蓝牙显示「已连接」但实际未连接

> **现象**：蓝牙页显示「已连接: 小爱音箱-1303」，实际没有可用连接 —— 音箱不出声，
> 约 1 分钟后状态自己翻回「已配对」，反复重连都一样。
> **根因层**：用户态蓝牙协议栈 `bt_user_daemon` 的 `conn` 语义 / LVGL 蓝牙页判据。
> **修复工作量**：1 个文件 +64/-13 行（`lv_pages/bluetooth_page.c`）。
> **文件名**：`bugfix_20260923_01_蓝牙显示已连接实际未连接.md`
> **关联提交**：221fa7d
> **日期**：2026-09-23

## 现象

蓝牙设置页显示 **`已连接: 小爱音箱-1303`**，设备行右侧也是**绿色「已连接」**，
但：

- 音箱没有任何反应（不播提示音、手机/音箱侧也不显示被连接）；
- 过一段时间（约 1 分钟）状态会**自己变回「已配对」**；
- 反复点击设备重连都一样，永远"连上又像是没连"。

即：**UI 说已连接，实际没有可用连接。**

## 影响范围

| | |
|---|---|
| **受影响** | 蓝牙页的连接状态显示；A2DP 音频输出（音箱不出声）；用户无法判断到底连没连上 |
| **不受影响** | 蓝牙开关、扫描/配对列表读取、配对记录本身；FM 收音机；桌面与其它页面 |

## 根因

**两层原因叠加**，缺一不可。

### 3.1 直接原因：蓝牙页把"ACL 链路存在"当成了"已连接"

`bt_user_daemon` 的 `conn` 命令只表示 **ACL（基带链路）已建立**，不代表上层 profile
（A2DP）可用。而 `bluetooth_page.c` 原来就是这个判据：

```c
bp_get_conn_mac(conn_mac, sizeof(conn_mac));   /* conn 命令 */
if(conn_mac[0]) snprintf(detail, ..., "已连接: %s", nm);   /* ← 直接当成已连接 */
```

### 3.2 根本原因：本机存的 link key 已被音箱侧作废，认证失败

- link key 存在 `/tmp/bt_linkkey.conf`（`<MAC> <32位十六进制>`，16 字节）。
- 音箱侧把这条配对记录丢了/重新生成过 → 本机的 key **对不上**。
- 但 daemon 收到控制器的 `Link Key Request` 时，**只要本地有 key 就回 positive**
  （日志原话：`[pair] link key req -> positive(已存 key, 免 SSP)`），于是**没有走重新配对**。
- 结果：HCI 认证失败——

```
[pair] auth complete status=5        ← 0x05 = Authentication Failure
[pair] done paired=1 auth_ok=1 enc_ok=0 -> A2DP
[auth] auth complete status=5
[auth] auth failed
```

- `enc_ok=0` 表示**链路加密从未建立**，A2DP 自然建不起来（`AVDTP_START` 不会发出）。
- 但 **ACL 已经建上了**（L2CAP 能通、SDP 能查），所以 daemon 的 `conn` 照样回
  `OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303` → UI 显示"已连接"。
- 约 60 秒后音箱侧放弃，链路断开（`[main] disconnect complete evt`），daemon 才翻回 `IDLE`。

一句话：**ACL 通、认证挂、加密没建立、A2DP 没起，UI 却只看 ACL。**

## 定位过程

### 4.1 关键判真器：`/tmp/bt_audio.fifo` 有没有读者

daemon 的 A2DP 媒体循环启动时会**打开 `/tmp/bt_audio.fifo` 的读端**。
于是用非阻塞方式打开写端即可判断媒体循环是否在跑：

```python
import os
try:
    fd = os.open("/tmp/bt_audio.fifo", os.O_WRONLY | os.O_NONBLOCK); os.close(fd)
    print("a2dp=True  (有读者，媒体循环在跑)")
except OSError as e:
    print("a2dp=False (无读者)", e)      # ENXIO(6) = No such device or address
```

这是本机能拿到的**唯一用户态可见的 A2DP 真相**。实测：

```
T+00  conn='OK IDLE'                                  a2dp=False
T+02  conn='OK CONN c5:09:... 小爱音箱-1303'          a2dp=False   ← 假连接
...   （持续 60 秒）                                   a2dp=False
T+62  conn='OK IDLE'                                  a2dp=False
RESULT connect -> 'RC 0'        ← connect 还回成功！
```

**`connect` 返回 `RC 0` + `conn` 报 CONN，但 fifo 始终没有读者** → 判定为假连接。

### 4.2 试错与排除

| 尝试 | 结果 |
|---|---|
| 怀疑 UI 只查一次、不刷新 | ❌ 页面本来就有 15 s 自动刷新（`BP_AUTO_REFRESH_MS`），排除 |
| 怀疑 daemon 挂了 | ❌ `state/paired` 正常，socket 正常 |
| 用 `/etc/init.d/bt_daemon restart` 重启以清内存里的旧 key | ❌ **没生效**！openrc 报 `udev failed to start`，且 pid 仍是 1222（没换进程）→ 旧 key 还在内存里，修复无效 |
| 按 `bt_bringup.start` 的方式 `kill -9` + `setsid` 重启 | ✅ pid 1222 → 382，key 真的清了 |
| 用高频循环 `connect` 撑住"假连接"窗口以便截图 | ⚠️ 打满 daemon accept 队列，后续请求 `errno 11 (EAGAIN)`。**不要高频探测 daemon** |

### 4.3 修好之后协议栈的原话

```
[auth] auth complete status=0            ← 原来是 5
[auth] auth ok -> Set Encryption (0x0413)
[auth] encryption change status=0 enc=1  ← 加密建立
[l2cap] SDP 断开 + 认证完成 -> 建 AVDTP
[a2dp] avdtp begin: L2CAP conn req PSM=0x0019
[avdtp] DISCOVER_RSP seid=4 tsep=0 media=0
[a2dp] media channel ready, sent AVDTP_START seid=4
[a2dp] media loop start GOLD NF=7 bp=35 fl=83 persamp=128 framedur=2902us nch=2
```

## 解决办法

### 5.1 现场处置（可回滚）

```sh
# 0) 备份
cp /tmp/bt_linkkey.conf /tmp/bt_linkkey.good

# 1) 删掉失效的 link key（文件里那一行）
grep -v '^c5:09:5d:3e:bd:3c' /tmp/bt_linkkey.conf > /tmp/lk.tmp && mv /tmp/lk.tmp /tmp/bt_linkkey.conf

# 2) 真重启 daemon（openrc restart 不生效，必须 kill + setsid）
for p in $(pidof bt_user_daemon); do kill -9 $p; done
sleep 2; rm -f /tmp/bt_ctl.sock
setsid /usr/local/bin/bt_user_daemon >/tmp/bt_daemon.log 2>&1 </dev/null &
sleep 10

# 3) 重新连接 -> 这一次会走完整配对(SSP)，并把新 key 写回 /tmp/bt_linkkey.conf
printf 'connect c5:09:5d:3e:bd:3c\n' | nc -U /tmp/bt_ctl.sock   # 或走 fm_ctl 同类客户端
```

### 5.2 代码修改：`lv_pages/bluetooth_page.c`

新增"音频是否真的通了"的判据，并把三处文案全部改为以它为准：

```c
#include <fcntl.h>
#define BP_A2DP_FIFO "/tmp/bt_audio.fifo"
#define BP_CONN_AUDIO_WAIT_MS 25000

/* ★ 判断 A2DP 音频流是否真的跑起来了
 * daemon 的 conn 只表示 ACL 链路存在；Link Key 失效时认证失败(status=5)，
 * A2DP 建不起来、音箱不出声，但 conn 照样回 OK CONN。
 * 判据: 非阻塞打开 fifo 写端 —— 有读者才说明 media loop 在跑。 */
static bool bp_a2dp_ready(void)
{
    int fd = open(BP_A2DP_FIFO, O_WRONLY | O_NONBLOCK);
    if(fd >= 0) { close(fd); return true; }
    return false;
}
```

1. **状态区文案**：`conn_mac[0] && bp_a2dp_ready()` 才写"已连接: xx"；
   `conn_mac[0]` 但音频没通时写 **"链路已建立但音频未连通"**。
2. **设备行标签**：只有链路 → 橙色 **「无音频」**；链路+音频 → 绿色「已连接」；仅配对 → 灰色「已配对」。
3. **连接结果 toast**：`connect` 返回 `RC 0` 后**不立刻报成功**，而是每 300 ms 检查一次
   `bp_a2dp_ready()`，最多等 25 s：等到了才提示"已连接 xx"，超时才提示"链路已建立，但音频未连通"。

## 验证

### 6.1 正例（真连接）

```
[conn] -> 'OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303'
bt_audio.fifo 有读者: True (OK)          ← 媒体循环真在跑
```
截图 `shots/btlive_0.png`：状态区「已连接: 小爱音箱-1303」，设备行右侧**绿色「已连接」**。
→ 这次 UI 说的是真话。

### 6.2 反例（故意把 link key 写坏，复现原来的假连接）

把 key 整条替换成 16 个 `0x00` 并重启 daemon 后重连：

```
connect -> RC 0
T+00 conn='OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303'   a2dp=False
T+02 conn='OK IDLE'                                     a2dp=False
[pair] auth complete status=5 / enc_ok=0 -> ABORT
```
截图 `shots/btfake_0.png`：状态区 **「链路已建立但音频未连通」**，设备行右侧**橙色「无音频」**。
→ 同样的硬件状态，UI 不再谎报"已连接"。

### 6.3 端到端：音频通路确实是通的

连上后持续把静音 PCM 灌进 fifo（格式由 daemon 日志反推：44100Hz / 2ch / S16_LE）：

```
fifo 写端已打开，开始灌静音 PCM（50.0s）
写完 8634780 字节 (约 49.0 秒音频)
conn(after) = OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303
[hci] credit inflight=5/1776   ← 全程在收发
```

**链路在持续供数时 50 s 不掉**，HCI 信用持续变化 → SBC 帧真的发上去了。

## 经验教训

1. **"已连接"必须由最末端的证据来定义。** ACL 存在 ≠ profile 可用 ≠ 流在跑。
   用中间层状态代理末端的结论，迟早要说谎。本次的正确判据是"fifo 有没有读者"。
2. **link key 失效要作为音箱类设备的一级排查项。** 音箱换手机连过、被重置、
   固件升级都可能作废本机 key；此时现象就是"连上又像没连"，很容易误判成信号/兼容性问题。
3. **`openrc restart` 不一定真的重启。** 本机 `bt_daemon` 的 `restart` 因 `udev` 依赖失败而空转，
   pid 没变 —— 凡是"改了状态/清了缓存要生效"的场合，**必须校验 pid 是否真的变了**。
4. **不要写高频探测脚本打自己的 daemon。** 1 秒一次 `connect` 会把 accept 队列打满，
   后续全部 `errno 11`，反而搞乱现场。
5. **daemon 的接口语义要写进文档**：`conn` = ACL，不等于连接可用。
   已同步到 `lv_pages/bluetooth_page.c` 顶部注释与项目记忆。
6. **"没声音"不一定是通路坏了。** 本机 A2DP 媒体循环是"有数据才活"：
   没有 PCM 进 fifo，音箱会因超时主动断开。判断"音频链路是否可用"要**同时**看
   fifo 有无读者 + 连接是否维持，不能只看其中一个。
