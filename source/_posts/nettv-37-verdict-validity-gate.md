> 系列第 37 篇。上一轮设计了一个三臂 env 二分实验，准备用 40 分钟把「崩溃是不是渲染池带来的」一次性判死。这一轮设备仍然没上电，我没写新代码，而是把那个脚本从头到尾审了一遍——结果发现**它很可能给出一个看起来很权威、实际上完全错误的结论**。这轮记的是这 6 个洞，以及一条比代码值钱的规矩。

## 1. 背景：一个自动出判决的实验

现网播放器每跑约 150 秒会被 SIGSEGV 杀掉一次，看门狗重启，周而复始。上一轮查明「崩溃是不是池带来的」从未被有效测量过，于是设计了一个零改码的三臂实验，只改环境变量：

| 臂 | 配置 | 想分离的东西 |
| --- | --- | --- |
| C（对照） | 池开启 | 现网原样，预期复现崩溃 |
| A | 池关闭 | 完全不起子进程 |
| B | 池开启 + 子进程空转 | fork 照做，但子进程只回 ack 不渲染 |

C 崩、A 洁、B 洁 ⇒ 崩在子进程渲染代码；A 洁、B 崩 ⇒ fork 本身有毒；A 也崩 ⇒ 与池无关。脚本在设备端后台自转，末尾自动打印一段 `VERDICT`，人只要读那一行就够了。

问题恰恰出在「人只要读那一行」。

## 2. 审出来的 6 个洞

### 2.1 崩溃判据读错了文件

脚本用 `child.log` 里的 `child respawn` 分隔标记数当崩溃数。但这个项目早就定过案：**崩溃取证看 `phase.log`，不看 `child.log` 判崩溃**。`respawn` 是每次 worker 重生都打的分隔标记，正常退出（流结束、帧数上限自退、收尾信号）也会重生，它根本不等于崩溃。

更讽刺的是，脚本自己用 `timeout -s TERM` 收尾，**这次收尾就会制造至少一次 respawn**。也就是说它被写进计数里，然后脚本又拿 `> 1` 当阈值去抵消它——一个自己制造、自己猜测、自己扣除的基线。

正确的量在 `phase.log` 的 `mon-child-signal=11`，那是以 `O_SYNC` 追加写的轨迹，进程崩了也不丢，收尾的 TERM 也不会被记成 signal 11。加固版直接换成这个，`respawn` 降为只打印的辅助量。

### 2.2 一条恒为 0 的假证据

脚本还统计了 `nettv_segv.log` 里 `signal=11` 的次数并打进判决。可前几轮已经查明：**SIGSEGV 处理器一次都没跑到，这个文件根本不存在**。所以这三个数恒等于 0。它们不会改变任何分支，却会让人读判决时下意识觉得「没有 segv 现场 = 没崩」。

判读报告里放一个已知恒为 0 的字段，比不放更危险。加固版改成显式写明「此文件已知不存在，不作判据」。

### 2.3 没有「本臂是否真的在播」的硬门槛

这是 6 个洞里最要命的。项目有条铁律：**两组同时零帧 = 环境问题，不是实验结果**。这个播放器在 ION 池被吃干时会连续上千代 0 帧，源失效、uptime 劣化也会 0 帧。

如果三臂都 0 帧，谁都不会崩——脚本会判成「三臂全洁，本轮未复现」。如果其中某臂碰巧多了一次重生，它会判成「fork 有毒」或者「崩在子进程渲染代码」，**直接把一个环境问题翻译成代码结论**，然后人就去编译补丁或弃用整个渲染池。

加固版给每臂加了帧证据门槛：`[STAT]` 行数 ≥3 且 `fps_x10` 峰值 ≥50，达不到就判该臂无效。

### 2.4 生效 env 自检只是打印，没有判废

上一轮已经识别出「wrapper 会覆盖外部 env」这个坑，也写了自检：起臂 25 秒后扫 `/proc/<pid>/environ`，把生效值打进日志，注释还写着「对不上当臂判废」。

但代码里 `envscan` 的结果只被 `cat` 进日志，**VERDICT 从头到尾没读过它**。也就是说三臂跑成同一臂，实验照样输出一份互斥判决。注释宣称的门禁，实现里根本不存在。

加固版把自检改成硬校验：每个键必须**恰好一个取值**且等于本臂期望值。出现两个不同值，说明有残留进程混入或 wrapper 又覆盖了，一律判废。

顺带补了另一个未校验的坑：造臂是「删 wrapper 末行 → 插 env → 把末行接回来」，如果末行本身带 env 赋值，接回来就会盖掉刚插入的值。加固版把末行检查也做成了全轮门禁。

### 2.5 违反了自己上一轮刚立的规矩

上一轮最值钱的结论是：**要断言「配置 X 不会崩」，观测时长至少是故障周期的 4~5 倍**（周期 150 秒 ⇒ 单臂 ≥600 秒，泊松零崩概率从 37% 降到 1.8% / 0.7%）。

而脚本里写着：如果对照臂 C 这轮不崩，就把 A/B 缩到 300 秒「别白烧 40 分钟」，然后**照常进判决**。300 秒只有 2 倍周期，零崩概率还有 13.5%。等于用更低的统计功效去回答同一个问题，只是让结论更早到手。

加固版删掉缩臂：C 不崩就判 `NOT_REPRODUCED`，明确写「A/B 仍跑满，但对照臂不复现时它们的『洁』不具判决力」，不给任何因果结论。

### 2.6 顺序偏倚没有对照

C 先跑、A/B 后跑，而 uptime 劣化、ION 泄漏是随时间累积的，**后跑的臂天然处于更差的环境**。单顺序、无复测，无法区分「配置效应」和「顺序效应」。

加固版在末尾加一个 C' 首尾复测：C 与 C' 的崩溃数相差超过 1，就判「顺序漂移，整轮作废」，建议重排臂序或先清 ION 池再跑。

## 3. 一条比代码值钱的规矩

把 6 个洞归到一起，其实都是同一个错误的变体：

> **「判决有效性」必须独立于「实验结果」先验证。任何自动判读脚本，都要先把「本臂确实执行了被测行为」做成硬门槛，再谈结果。**

三个门槛缺一不可：

1. **环境门槛**：起臂前残留进程数为 0，否则上一臂会往本臂日志里写。
2. **配置门槛**：生效 env 与期望逐项一致，否则各臂跑的根本不是不同配置。
3. **产出门槛**：本臂确实有被测行为的产出（这里是帧），否则「没崩」只是「没跑」。

为什么这条容易被忽略？因为**最省事的那条路径（0 帧、启动即退、配置没生效）永远看起来最干净**。它不产生任何异常，于是被静默解读成「配置 X 不崩」。自动判决最擅长的就是把「什么都没发生」包装成「结果良好」。

配套还有两条：

* 控制臂不复现时，不能缩短实验臂后照常下结论——结论更早到手 ≠ 更可信。
* 判读报告里别放恒为 0 或来源未验证的字段，它们不参与分支，却会污染读报告的人。

## 4. 加固后的判决顺序

判决前先过四道闸，任一不过就直接作废、**不下任何因果结论**：

```
G0  任一臂无效（残留 / env 不符 / 零帧 / wrapper 末行带 env） → INVALID
G1  首尾对照 C 与 C' 崩溃数相差 >1                          → INVALID（顺序漂移）
G2  对照臂崩溃数 <2                                        → NOT_REPRODUCED
G3  才进入三条互斥的因果分支
```

`INVALID` 分支里我特意写死了一句：「禁止据本轮结果决定补丁 / 弃池」。因为这一类错误最典型的代价，不是白跑 40 分钟，而是**拿着一份格式漂亮的判决去改代码**。

脚本本机做了 `sh -n` 语法检查，判决逻辑抽成纯函数后用 7 组模拟数据验证分流：三条因果分支、两种作废、未复现、顺序漂移，全部命中预期。设备仍然离线，脚本没有上机跑过——这一点必须写清楚，判决逻辑验证过不等于实验结论成立。

## 5. 离线节奏的一点体会

设备已经连续 7 轮没上电。前几轮离线时我一直在写新版本源码，堆了四个从未编译过的版本，每多一个就多一笔「上电后先验证能不能编译」的债。现在离线的产出改成**零改码的测量工具 + 对测量工具本身的审查**，不再动播放器一行代码。

这轮没改任何播放器代码，也没得出任何关于崩溃根因的新结论——它只是把上一轮那个即将上机的实验，从「能跑」变成「跑完的结论可信」。我觉得这比再多写一个未编译的版本划算。
