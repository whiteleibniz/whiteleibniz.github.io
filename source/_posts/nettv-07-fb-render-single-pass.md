前面几篇把 VSP 硬解、mbinfo 假物理地址、GOP 重播这些坑都填了，画面能出，但**只有 4fps**。采样器一抓，100% CPU 全花在 `fb_render` 上——不是厂商库死锁，就是我们自己的 NV12→ARGB+旋转 90°+缩放。这篇记录怎么把它从 250ms/帧 干到 19-21ms/帧。

## 一、先看旧的渲染长什么样

VSP 解码输出是 NV12 1920x1088，屏幕是 720x1280 竖屏，所以每帧要做三件事：NV12 转 ARGB、旋转 90°、缩放到 720x1280。旧实现是规规矩矩的三遍法：

```c
/* pass1: 全分辨率 NV12 → ARGB */
for (iy = 0; iy < 1080; iy++)
    for (ix = 0; ix < 1920; ix += 2) {
        uu = Cl[ix] - 128; vv = Cl[ix+1] - 128;
        dr[ix]   = yuv2px(Yl[ix],   uu, vv);
        dr[ix+1] = yuv2px(Yl[ix+1], uu, vv);
    }
/* pass2a: 16x16 块转置 + 垂直翻转 → g_targb */
/* pass2b: targb 1080x1920 → fb 720x1280（NN 3/2 采样） */
```

中间那两个 `g_argb` / `g_targb` 各 8.3MB，合起来每帧要吞掉约 25MB 的内存流量（2.07M 像素 × 4B × 读改写好几轮）。在 Cortex-A7 上这就是 250ms。

## 二、关键洞察：中间那一层全分辨率是纯浪费

盯着输出尺寸看了一眼就明白了：**最终只有 720×1280 = 921,600 个像素，中间却按 1920×1080 = 2,073,600 个像素算了一遍**。也就是说辛辛苦苦算出来的像素里有 56% 根本不会被采样到，直接扔了。

既然如此，为什么不直接算出"会被用到的那 44%"？

把三个几何变换合成一下（转置 + 垂直翻转 + 3/2 最近邻采样），可以得到一个直接映射：

```
fb[oy][ox] = src_argb[1079 - ox*3/2][oy*3/2]
```

推导：`targb[tx][ty] = argb[1079-ty][tx]`，而 `fb[oy][ox] = targb[oy*3/2][ox*3/2]`，代进去就出来了。**注意行列角色别搞反**——我第一版就把它们写反了，画面整体转置、底部还多出一条空带，抓帧对比才现形（后面细说）。

还有一个绕不开的矛盾：**转置问题里，「按输出行顺序写」和「按源行顺序读」不可能同时成立**。按输出行写，源就要按列读（步长 1920 字节，每像素一条 cache line）；按源行读，输出就要按列写。解法是分块：把输出按 16 行一条带，先算进一个 `band[16][720]` 的暂存区，再整行 memcpy 到 framebuffer：

```c
static unsigned band[16][720];
for (int oy0 = 0; oy0 < 1280; oy0 += 16) {
    int c0 = oy0*3/2;
    for (int i = 0; i < 720; i++) {          /* ox = i, 源行固定 */
        int r = 1079 - i*3/2;
        const unsigned char *Yl = Y + (size_t)r*1920;
        const unsigned char *Cl = C + (size_t)(r>>1)*1920;
        for (int j = 0; j < 16; j++) {       /* oy = oy0+j, 源列连续窗口 */
            int c  = c0 + j*3/2;
            int cb = c & ~1;                 /* NV12 交错：u 在偶列，v 紧随 */
            int uu = Cl[cb] - 128, vv = Cl[cb+1] - 128;
            band[j][i] = yuv2px(Yl[c], uu, vv);
        }
    }
    for (int j = 0; j < 16; j++)
        memcpy(dst + (size_t)(oy0+j)*720, band[j], 720*4);
}
```

这样读侧每条源行只碰 1~2 条 cache line（24 字节窗口），写侧每输出行是一次 2880 字节的连续突发，两边都舒服了。

三个细节值得记：

- **UV 必须按偶列取**。`c` 可能是奇数（3/2 采样出来的列号是 0,1,3,4,6...），NV12 里 u/v 是交错成对存放的，所以要用 `cb = c & ~1` 对齐到偶列，再取 `Cl[cb]`、`Cl[cb+1]`。写错就是半边画面偏色。
- **访问局部性**。输出行是顺序写的；输入 Y 行号 `r` 每行只走 1~2 行、列是顺序读的，cache 友好。这比"整帧转置"那种跳 4.3KB 写一个 4 字节的写法健康得多。

顺带把两个 8.3MB 的中间缓冲也删了，省 16.6MB 内存——在只有几百 MB 的设备上不是小数目。

## 三、量化：从 4fps 到 12fps

播放器里有 `bench` 自测入口（30 次渲染逐次计时），第一版（错误几何、无转置矛盾）跑出 19-21ms/帧。修正几何、加上带状 staging 后，端到端实测 **25 帧 / 2057ms = 12.1fps**——比旧的 4fps 提了 3 倍。中途还踩了一个隐形的坑：

**「看不到视频」的真正原因不在渲染，而在翻页。** 播放器一直把画面写进 framebuffer 的第 1/2 页（双缓冲），但 `fb_pan()` 里是一句 `return; /* no-pan 实验 */`——FBIOPAN 从来没真正执行过，屏幕永远停在 LVGL 桌面用的第 0 页。也就是说：**解码、渲染、写屏全都在正常工作，唯独最后一步「把可见窗口切过去」没做**，用户看到的就是纹丝不动的桌面。修法用安全姿势（这是之前内核崩过的血泪定案）：只信 `FBIOGET_VSCREENINFO` 取回的真结构体，校验 `yres_virtual >= 3840`，改 `yoffset` 后再 `ioctl(FBIOPAN_DISPLAY)`。顺带给监控进程加了 `fb_sys_home()`——子进程被 SIGKILL 时来不及自己翻回第 0 页，屏幕会冻在最后一帧上，监控得负责把画面切回来。

教训很朴素：**换了几何映射，先抓一帧 framebuffer 和已验证的基准帧逐位比对，再谈上线。** 我当时凭 bench 计时好看就当了真，结果方向是错的——性能好和画面对，是两回事。

## 四、差点误判：提速是不是引爆了厂商库崩溃？

中间出了个插曲。刚换上新渲染跑直播源，20 秒里 SIGSEGV 91 次、监控进程重启 124 次。看现场日志，崩在厂商库 `libstagefright_sprd_h264dec.so` 处理完一帧之后，和之前定案的"OMX 输入队列 use-after-free"长得一模一样。

第一反应是：**渲染快了 12 倍 → 喂码流的节奏快了 → 把厂商库的竞态/UAF 逼出来了**。听起来很合理，差点就这么写进结论。

但一次观测不能定性。于是加了个环境变量开关 `NETTV_RENDER=0` 回退旧三遍法，**用同一个二进制**做 A/B：

| 渲染路径 | 时长 | SIGSEGV | monitor 重启 |
|---|---|---|---|
| 慢（三遍） | 40s | 0 | 6 |
| 快（单遍） | 40s | **0** | 3 |

快路径不但没崩，重启次数还更少。**那批崩溃是当时设备/源的状态问题**（反复 kill 之后的 ION/CMA 状态、加上凌晨直播源干涸），跟渲染路径没关系。

教训很朴素：性能优化之后的第一批异常，很容易被归因为"优化改了时序"。在定案之前，先做一个只切换优化、其它都不动的 A/B，成本很低，但能省掉一次错误定案。

## 五、顺手踩到的几个坑

1. **裸 bionic 下 `_exit` 不 flush stdio**。我们是 `-nostdlib -Wl,--entry=main` 直接进 main 的，bench 的计时、帧率心跳全打不出来——因为 `_exit` 直接走了，stdio 缓冲没落盘。所有测点后面都得跟一句 `fflush(0)`，否则"没有日志"会被误读成"没执行到"。

2. **子进程日志被监控进程重生时 O_TRUNC 截断**。监控每隔几秒重生一次子进程，日志每次都被清空，崩溃现场根本留不下来。改成 SIGSEGV 处理器追加写一个独立文件 `/tmp/nettv_segv.log`，跨重启保留。

3. **GCC 的块分区重排 bug**。加了点代码之后编译器报错：

   ```
   .size expression for c1_reuse.part.0 does not evaluate to a constant
   Error: junk at end of line, first unrecognized character valued 0x4
   ```

   是 GCC 把函数切成 `.part.0` 之后给汇编器下了非法的 `.size`。构建脚本加 `-fno-reorder-blocks-and-partition` 解决。

4. **单条 SSH 命令里用 `&` 起后台进程不靠谱**，后面的命令会被会话断开截断，连重定向文件都没创建。长任务一律写成脚本上传，再 `nohup sh xxx.sh &`。

5. **子进程每轮固定停在 31 帧，不是崩溃**。帧上限参数默认是 0（无限），真正原因是 `load_chunk()` 在 m3u8 段边界拿不到新段（源干涸）干净退出。看到"每轮帧数一样"别急着往挂死上想。

## 六、现状与下一步

渲染这一环已经不是瓶颈了（20ms）。但端到端帧率还没提上去——因为源本身干涸，每轮子进程只活到 31 帧，量不出真实 fps。接下来要用本地多 GOP 的 `.ts` 文件源把解码喂满，排除源的干扰，再收拾剩下的：每轮 3MB 的 `memcpy`、`slice` 轮里的 `usleep(20ms)`、以及签名扫描。

**一句话总结这类优化的思路**：别急着给热点函数上 NEON、上汇编，先问一句"我算的这些像素，最后有几个真的会被看见"。很多时候把中间层砍掉，收益比指令级优化大一个数量级。
