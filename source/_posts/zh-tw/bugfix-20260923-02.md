# bugfix_20260923_02 — 頁面離場不清焦點組，導致桌面焦點環消失

> **現象**：進過任意頁面再返回桌面後，按方向鍵**粉色焦點框憑空消失**、且走不到目標圖標；
> 重啟應用即恢復。觸摸點擊不受影響。
> **根因層**：LVGL 頁面框架的焦點組生命週期（`lv_pm/lv_page_manager.cc`）/ 桌面自定義導航（`main.c`）。
> **修復工作量**：2 個文件（`lv_pm/lv_page_manager.cc` +49、`main.c` +7/-1）。
> **文件名**：`bugfix_20260923_02_頁面離場不清焦點組導致桌面焦點環消失.md`
> **關聯提交**：221fa7d
> **日期**：2026-09-23

## 現象

在**任何非桌面頁面**裡返回桌面之後，桌面按方向鍵會出現：

1. **粉色焦點框憑空消失** —— 按了鍵，界面上看不出當前選中了哪個圖標；
2. 繼續按方向鍵**走不到想去的圖標**（比如想回到「收音機」，卻卡在別處或原地不動）；
3. 反覆按也沒有規律，**重啟應用（不是重啟設備）後恢復正常**，一進頁面再返回又壞。

即在"進過頁面 → 返回桌面"這條路徑上，桌面導航會被汙染。

> 這是排查「藍牙顯示已連接實際未連接」過程中**連帶發現**的 bug：
> 為了給藍牙頁做按鍵驗證（進頁面 → 返回 → 走到藍牙圖標），發現根本走不到，
> 一查才知道桌面焦點早就壞了。

## 影響範圍

| | |
|---|---|
| **受影響** | 桌面（launcher）的按鍵導航；所有"進過頁面再返回"的場景；間接觸發了本會話另一處「收音機頁進不去」的誤判 |
| **不受影響** | 觸摸點擊（不走焦點組）；頁面內部自身的導航；頁面渲染；FM 收音機、藍牙等業務邏輯 |

觸摸能點、按鍵不能走，是本 bug 最典型的表現。

## 根因

**兩處獨立缺陷疊加**，各自都能讓導航失靈。

### 3.1 頁面離場時，不把自己的控件從"公共焦點組"裡摘掉

LVGL 的默認焦點組是**全局共享**的。各頁面在 `onCreate` 裡調用
`lv_group_add_obj(lv_group_get_default(), obj)` 把自己的控件掛進去，
但**離開時幾乎沒有人調用 `lv_group_remove_obj()`** ——
全倉只有 3 個文件做了這一對操作，其餘頁面全是"只加不減"。

於是每進一次頁面，就有一批**已經隨頁面一起被刪除、或已不可見**的控件
殘留在組裡，變成"幽靈焦點"。實測計數（`lv_group_get_obj_count`）：

```
乾淨啟動進桌面        默認焦點組 objcnt = 18   (桌面 17 個圖標格 + 狀態欄音量滑塊 1)
進收音機頁            默認焦點組 objcnt = 37   (+19，收音機頁掛進來的)
返回桌面(修復前)      默認焦點組 objcnt = 37   ← 19 個一個都沒收回
頁面銷燬時清理後      默認焦點組 objcnt = 18   ← 只減不減的"組計數"才是真兇
```

`group_find_neighbor` 在這些幽靈裡挑鄰居，於是：
- 選中一個**沒有 `user_data`** 的控件 → 桌面畫焦點框的代碼拿不到格子信息 → **框消失**；
- 方向鍵的"鄰居關係"被幽靈攪亂 → **走不到目標圖標**。

### 3.2 `group_find_neighbor` 只看控件自己的 HIDDEN，不看祖先

`main.c` 的自定義導航裡，原判定是：

```c
if(lv_obj_has_flag(o, LV_OBJ_FLAG_HIDDEN)) continue;   /* ← 只看自己 */
```

而 LVGL 裡**隱藏一個面板，隱藏的是外層容器**，裡面的子控件自己**並不帶**
`LV_OBJ_FLAG_HIDDEN`。結果：狀態欄那個**收起狀態的音量浮層滑塊**
（父面板 340×42，滑塊自己 252×14）被當成合法候選選中了。

定位到它靠的是"打印幽靈對象的形狀再反查"（見 §4.2）：

```
cls=slider  pos=(66,5)  size=(252,14)  abs=(256,69)
父容器 size=(340,42) 子對象數=2   -> lv_status_bar/volume_control.c:207 的 s_volume_slider
```

選中它同樣沒有可用 `user_data` → 焦點框畫不出來。

> 一句話：**① 組裡有幽靈；② 判定可見性只看了自己，沒看祖先。**

## 定位過程

### 4.1 先確認"焦點到底落在誰身上"

在桌面渲染焦點框的那段代碼里加了一行 stderr 打點（`printf` 會因塊緩衝延遲，
**必須用 `fprintf(stderr, ...)`**）：

```c
if(cell == f)
    fprintf(stderr, "[fc] focus idx=%u/%u cell=%p content=%p box=%p\n",
            (unsigned)i, (unsigned)cnt, (void*)cell, (void*)content, (void*)box);
```

- **故障時**（頁面管理器清理已上、祖先感知未上的中間狀態）：
  `[fc] focus idx=17/18 cell=0x... content=(nil) box=(nil)`
  → `content`/`box` 為 **空指針** = 當前焦點對象**沒有 `user_data`**，
  桌面拿不到"這個焦點屬於哪個圖標格"的信息，**框自然畫不出來**。
  `idx=17/18` 也印證了：桌面只往組裡加了 17 個格子，**第 17 個（0 基）根本不是桌面的**。
- **修復後**：`[fc] focus idx=7/18 cell=0xb70881d4 content=0xb7088374 box=0xb7088444`
  → 三個指針都有值 = 焦點框能正常畫出來。

`idx` 的**分母**（組內對象總數）本身就是線索：把每個頁面進/出時的組計數打出來，
會看到數字**只漲不跌**（見 §3.1 與 §6.1）—— 這正是"幽靈在累積"的直接證據。

### 4.2 把幽靈"打印出來"再反查

只加焦點打點不夠，還需要知道幽靈長什麼樣。臨時在頁面管理器里加了一段 dump：

```c
/* 臨時診斷：把默認組裡不屬於本頁的對象形狀打出來 */
for(uint32_t i = 0; i < lv_group_get_obj_count(g); i++) {
    lv_obj_t *o = lv_group_get_obj_by_index(g, i);
    fprintf(stderr, "  [g] #%u cls=%s pos=(%d,%d) size=(%d,%d) abs=(%d,%d) kids=%u\n",
            i, lv_obj_get_class(o)->name,
            (int)lv_obj_get_x(o), (int)lv_obj_get_y(o),
            (int)lv_obj_get_width(o), (int)lv_obj_get_height(o),
            (int)lv_obj_get_coords(o)->x1, (int)lv_obj_get_coords(o)->y1,
            (unsigned)lv_obj_get_child_count(lv_obj_get_parent(o)));
}
```

靠 `size=(252,14)` + `父容器 340×42` 這兩個特徵，在 `lv_status_bar/volume_control.c:207`
找到 `s_volume_slider`，反證了 §3.2。診斷打點定位完後已清理。

### 4.3 排除掉的方向

| 嘗試 | 結果 |
|---|---|
| 懷疑桌面自己算錯鄰居（左右跨行問題） | ❌ 桌面邏輯沒變過，且**重啟應用就恢復** → 是"被外部汙染"，不是算法錯 |
| 懷疑 `lv_obj_clean` 刪對象後組裡留懸垂指針導致崩潰 | ❌ 沒有崩潰，只是焦點錯位；LVGL 刪對象時會自動移出組 |
| 懷疑是"收音機頁沒銷燬" | ❌ `[pm] destroy 'radio'` 正常打出，頁面確實銷燬了 —— 但**控件還在組裡**（組和對象生命週期是兩回事） |
| 只修 §3.1（頁面管理器統一清理） | ⚠️ 大部分恢復，但組計數仍是 18（= 桌面 17 格 + **1 個非桌面對象**）→ 說明還有一個不屬於桌面的成員，必須同時修 §3.2 |

## 解決辦法

### 5.1 頁面管理器統一清理（一處修好所有頁）

在 `lv_pm/lv_page_manager.cc` 裡新增：

```c
/**
 * @brief 把某個頁面根對象下的控件從默認焦點組裡全部摘掉
 *
 * 為什麼必須做：默認焦點組是全局共享的，各頁面在 onCreate 裡把自己的控件
 * add 進去，但離開時從來沒有人 remove（全倉只有 3 個文件做對了）。
 * 殘留控件變成"幽靈焦點"：桌面按方向鍵會被吸到一個沒有 user_data 的控件上，
 * 選中框直接消失，而且走不到想去的圖標（實測默認組 17 -> 18）。
 * 集中放在頁面管理器裡做，所有頁面一次修好，新頁面也不用再記這條規矩。
 */
static void pm_purge_group_objs_of(lv_obj_t *root)
{
    lv_group_t *g = lv_group_get_default();
    if(!g || !root) return;
    uint32_t cnt = lv_group_get_obj_count(g);
    for(uint32_t i = cnt; i > 0; i--) {          /* 倒序：刪除會改變下標 */
        lv_obj_t *o = lv_group_get_obj_by_index(g, i - 1);
        if(!o || !lv_obj_is_valid(o)) continue;
        lv_obj_t *p = o;
        bool mine = false;
        while(p) { if(p == root) { mine = true; break; } p = lv_obj_get_parent(p); }
        if(mine) lv_group_remove_obj(o);          /* 沿父鏈找根，判定歸屬 */
    }
}
```

在 `pm_page_destroy()` 裡、`page->onDestroy(page)` **之前**調用
（此時對象都還合法；`onDestroy` 裡可能已經釋放定時器/回調）：

```c
if(pm_obj_valid(root)) {
    lv_group_t *dbg_g = lv_group_get_default();
    uint32_t before = dbg_g ? lv_group_get_obj_count(dbg_g) : 0;
    pm_purge_group_objs_of(root);
    uint32_t after = dbg_g ? lv_group_get_obj_count(dbg_g) : 0;
    if(after != before) {
        fprintf(stderr, "[pm] 頁面 '%s' 離場，摘掉 %u 個焦點組殘留控件（現共 %u）\n",
                page->page_name ? page->page_name : "?",
                (unsigned)(before - after), (unsigned)after);
    }
}
```

正常情況摘掉數量應為 0（不打日誌）；一旦有殘留就打一行，
**方便以後發現"某個頁面又忘了清理"**。

> 該文件是 `.cc` 但原來只 include 了 `<string.h>`，用 `fprintf/stderr` 需補
> `#include <stdio.h>`，否則編譯報 `MAKE_RC=2 'stderr' was not declared`。

### 5.2 可見性判定改為"祖先感知"

`main.c` 的 `group_find_neighbor()`：

```c
-    if(lv_obj_has_flag(o, LV_OBJ_FLAG_HIDDEN)) continue;
+    /* 必須連同祖先一起判斷可見性（nav_obj_visible）。
+     * 只看對象自己的 HIDDEN 是不夠的：面板收起時隱藏的是外層容器，
+     * 裡面的控件自己並不帶 HIDDEN，於是會被當成合法候選選中 ——
+     * 表現就是桌面按方向鍵時選中框憑空消失、走不到想去的圖標。 */
+    if(!nav_obj_visible(o)) continue;
```

`nav_obj_visible()` 是 `main.c` 裡已有的工具函數，會**沿父鏈逐級檢查** HIDDEN。

## 驗證

### 6.1 組計數（頁面管理器日誌）

修復後進/出收音機頁：

```
[pm] 頁面 'radio' 離場，摘掉 19 個焦點組殘留控件（現共 18）
```

19 個正是收音機頁掛進去的控件數。剩 1 個即為 §3.2 的滑塊
（它由狀態欄常駐創建，不歸任何頁面管，只能靠"祖先感知導航"繞開）。

### 6.2 按鍵實測（`ssh_tools/nav_trace.py "E B L L"`）

乾淨重啟應用 → 進收音機 → 返回桌面 → 連按兩次左鍵：

```
--- 按 ENTER(28) ---   [ukbd] key=10
--- 按 ESC(1)   ---   [ukbd] key=33554459
--- 按 LEFT(105) ---  [ukbd] key=20
                      [fc] focus idx=7/18 cell=0xb70881d4 content=0xb7088374 box=0xb7088444
--- 按 LEFT(105) ---  [ukbd] key=20
                      [fc] focus idx=6/18 cell=0xb7087bd0 content=0xb7087d6c box=0xb7087e3c
```

- 焦點**連續左移**：`idx 8(收音機) → 7(藍牙) → 6`，符合桌面圖標順序；
- `content` / `box` **均非空** → 焦點框每次都畫得出來；
- 對比修復前 `content=(nil) box=(nil)`，問題消失。

截圖 `shots/btz_3.png`：桌面「藍牙」圖標外圈有粉色焦點框（人眼確認）。

## 經驗教訓

1. **全局共享的容器，進和出要成對。** 焦點組是全局單例，頁面只 add 不 remove，
   等於把垃圾倒進了公共區域 —— 而且**症狀出現在受害者（桌面）身上，不在肇事者（頁面）身上**，
   極難從現象反推。凡是"全局註冊表"，就該由框架層統一託管生命週期，別指望每個頁面自覺。
2. **生命週期要分兩層看：對象被刪 ≠ 從組裡摘掉。** 頁面銷燬得乾乾淨淨（`[pm] destroy` 正常），
   控件照樣賴在組裡。查這類問題時，**打印"容器裡現有多少元素"比打印"我刪了什​麼"有效得多**。
3. **可見性判定必須祖先感知。** `LV_OBJ_FLAG_HIDDEN` 只描述對象自己；
   "這個控件現在用戶能不能看見"是一個**沿父鏈**的問題。LVGL 裡凡是"隱藏容器"的寫法，
   都會踩這個坑。
4. **"重啟應用就好"是強烈的"外部汙染"信號。** 它說明故障不是算法本身錯，
   而是運行期狀態被別處改髒了 —— 排查方向應立刻從"算得對不對"轉向"誰動過共享狀態"。
5. **診斷打點用 `fprintf(stderr, ...)`。** `printf` 寫文件是塊緩衝，日誌會滯後很久，
   容易誤判成"代碼沒執行"（排查 FM 頁面時也踩過同一個坑）。
6. **把"規範"下沉到框架層，而不是寫進文檔。** 本例最初只是在文檔裡寫"記得 remove"，
   結果沒人執行；搬進 `pm_page_destroy` 後，新舊頁面一次性合規。
   **能被代碼強制的約定，不要靠自覺。**
