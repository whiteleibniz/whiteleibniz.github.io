# bugfix_20260923_05 — GBA 畫面呈縱向條紋/撕裂（源 pitch 被忽略）

> **現象**：有畫面了，但滿屏**規則的縱向條紋**、內容橫向錯位，像是"撕裂"。
> **根因層**：`miniretro` 幀回調 `video_cb` 的**源行跨距（pitch）尋址** + 幀緩衝併發掃描。
> **修復工作量**：`extern/miniretro/miniretro.c` 累計 +81/-13（含本項與 `bugfix_20260923_04` 黑屏修復；本項為主要部分）。
> **文件名**：`bugfix_20260923_05_GBA畫面縱向條紋撕裂.md`
> **關聯提交**：（待提交後回填）
> **日期**：2026-09-23

## 現象

1. GBA 遊戲能進了（見 `bugfix_20260923_04`），但屏幕上是**規則的縱向條紋**：內容被切成一條條豎帶，
   帶與帶之間有黑縫，整體橫向錯位、不可讀（用戶描述為"撕裂狀"）。
2. 對照：FC 遊戲畫面完全正常、無條紋。

初步疑點：這是**時序撕裂**（vsync 缺失）還是**尋址錯位**？兩者外觀可能都"像撕裂"，必須先區分。

## 影響範圍

- **受影響**：GBA（240×160, RGB565, pitch=512）。
- **不受影響**：FC（fceumm，pitch 恰等於 width×2）——線性讀也正確，故一直正常。
  本次改動對 FC 透明。

## 根因

`miniretro.c` 的 `video_cb` **完全忽略核心給的行跨距**：

```c
static void video_cb(const void *data, unsigned width, unsigned height, size_t pitch)
{
    (void)pitch;                       /* ← pitch 被丟棄 */
    ...
    const uint16_t *src16 = (const uint16_t *)data;
    for(int i = 0; i < (int)(width * height); i++)   /* ← 線性讀, 步長=width */
        temp32[i] = convert(src16[i]);
```

- FC：`pitch = 256 × 2 = 512` 字節，恰好 `= width × 2` → 線性讀 **碰巧正確**。
- GBA：核心日誌實測 `video_cb: 240x160 pitch=512` —— 即**每行 256 像素，而可視寬度只有 240**。
  線性讀時每行少跳過 `(256-240)=16` 像素，**逐行累積錯位 160 行 ≈ 10 行源數據**，
  於是畫面被橫向剪切、並因跨行回捲產生規則條紋。

**實錘證據**：在 `video_cb` 加一次性打印，重編後日志輸出
`[miniretro] video_cb: 240x160 pitch=512 fmt=2 (每行像素=256)` —— pitch 與 width 確實不一致。

## 定位過程

1. **彎路一（關鍵）**：最初判定為 **vsync 撕裂**，於是給 `miniretro` 加了**雙緩衝頁翻轉**
   （fb 有 `yres_virtual=3840` 即 3 頁，用 `FBIOPAN_DISPLAY` 換頁）。
   但用戶反饋"還是這樣沒修復" → 說明**根本不是撕裂，是數據錯位**。
2. **抓屏區分**：人眼看不見設備屏幕，於是**實機抓屏**——
   設備端 `python3 os.pread` dump `/dev/fb0`（按當前 `yoffset` 抓前臺頁）→ SFTP 取回 → 本地按 `[R,G,B,X]` 解成 PNG → 打開看圖。
   一看便知：是**規則的縱向條紋**（內容錯位、有黑縫），**不是**撕裂線。方向立刻轉到尋址。
3. **定位到 pitch**：讀 `video_cb` 源碼，發現 `(void)pitch;` 與線性讀；
   再加一次性打印確認 `pitch=512 ≠ 240×2=480`。
4. **排除雙緩衝是元兇**：雙緩衝保留（無副作用，且對未來真撕裂有防禦價值），但補上 pitch 修復才是根治。

## 解決辦法

`extern/miniretro/miniretro.c` 的 `video_cb`：

1. **三個像素格式分支全部改為按 stride 逐行取數**（`pitch==0` 時回退 `width*2`）：

   ```c
   if(pitch == 0) pitch = (size_t)width * 2;

   /* RGB565 */
   const uint16_t *src16 = (const uint16_t *)data;
   size_t stride = pitch / 2;                     /* 字節 → 像素 */
   for(unsigned y = 0; y < height; y++) {
       const uint16_t *row = src16 + (size_t)y * stride;
       uint32_t *dst = temp32 + (size_t)y * width;
       for(unsigned x = 0; x < width; x++) {
           uint16_t p = row[x];
           dst[x] = 0xFF000000U | (((p>>11)&0x1F)<<19) | (((p>>5)&0x3F)<<10) | ((p&0x1F)<<3);
       }
   }
   scale_rotate90(temp32, fb_dst, width, height, fb_w, fb_h);
   ```

   `XRGB8888`（pitch/4）與 `0RGB1555`（pitch/2）同理。
   注意結果仍是 `0xAARRGGBB`，由 `scale_rotate90` 統一做 R/B 字節交換後落盤。

2. **保留雙緩衝頁翻轉**（`g_dbuf`，`FBIOPAN_DISPLAY`；首次失敗自動降級單緩衝）——
   本機 `FBIO_WAITFORVSYNC` 返回 `EPERM` 不可用，換頁是唯一可行的防撕裂手段。

3. 重編：`cd extern/miniretro && sh build.sh`。

## 經驗教訓

1. **"撕裂"與"條紋/錯位"是兩種病，必須先分開。**
   - 撕裂 = **時序**問題（幀緩衝正被掃描時被改寫）→ 雙緩衝/頁翻轉/vsync。
   - 條紋 = **尋址**問題（每行步長算錯）→ 核對 pitch/stride。
   不加區分就上雙緩衝，會白改一輪（本 bug 就是如此，浪費了一次往返）。
2. **接不同 libretro 核心時，`pitch` 必須用，絕不能假設 `pitch == width × bpp/8`。**
   mGBA 的緩衝行對齊到 256 像素，導致 `pitch/2 = 256 ≠ width(240)`。
   線性讀在 width 恰好整除 pitch 時"碰巧對"，換個分辨率立刻暴露。
3. **看不到設備屏幕時，實機抓屏是最高性價比的診斷手段**：
   `os.pread("/dev/fb0")` → SFTP → 本地按 `[R,G,B,X]` 解 PNG → 人眼看圖。
   一眼看出是條紋還是撕裂，勝過一堆日誌推理。
4. **"非黑像素佔比"這類量化指標只能證明"有畫面"**，證明不了"畫面正確"；
   判"畫面對不對"必須人眼。
5. **別把"改了沒效果"當噪聲**：用戶兩次說"還是這樣"，恰恰是"根因判斷錯了"的最強信號。
