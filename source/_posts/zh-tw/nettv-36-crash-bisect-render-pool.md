> 系列第 36 篇。前兩輪我們把「為什麼處理器一次都沒跑到」一路追到內核的 `force_sig_info`，甚至把解掩碼的代碼（v34）都寫完了。這一輪我停下手，回頭查一件更基礎的事——**我們手上每一次夠長的實測，都開著渲染池**。換句話說，「崩潰是不是池帶來的」這個問題，至今沒有被有效測量過。

## 1. 一個被忽略的測量漏洞

現網的崩潰長這樣：worker 每跑約 4000~5000 幀（≈150 秒）就被 SIGSEGV 殺掉一次，monitor 重啟，週而復始。

我整理了歷史上每一次「連續播放」的實測：

| 時間 | 版本 / 配置 | 時長 | 有沒有崩 |
| --- | --- | --- | --- |
| 10-26 | v28（那時**還沒有**渲染池） | 120s | signal=11 = 0 |
| 10-30 | v31，`NETTV_RPOOL=0` | 45s | 0 |
| 10-30 | v31，`RPOOL=2/4/8` | 45s | 2 路出過一次無限崩潰（v32 已修） |
| 10-31 | v33，`RPOOL=2 + AF=1 + HLSBUF=1` | 300s | 1 次 |
| 現網 | v32，`RPOOL=2 + AF=1 + HLSBUF=1` | 600s | 3 次 |

看出問題了嗎：**所有 ≥150 秒的實測，`NETTV_RPOOL` 都等於 2**。而唯一跑過 `RPOOL=0` 的兩次，臂長分別是 45 秒和 120 秒——**都沒活到第一個崩潰週期**。

這在實驗設計上是個硬傷：如果崩潰週期是 150 秒，那麼一個 120 秒的「乾淨」結果什麼都不能證明，它只是還沒來得及崩。我們卻一直把它當成「串行路徑是安全的」這條結論在用。

## 2. 方法論：實驗臂長必須顯著大於故障週期

這條是我這輪最想留下的東西，比代碼值錢：

> 要斷言「配置 X 不會崩」，觀測時長至少要是已知故障週期的 **4~5 倍**。週期 150s ⇒ 單臂 ≥600s。

理由很樸素：故障近似泊松過程，週期 `T` 下觀測 `t` 秒一次都沒崩的概率是 `e^(-t/T)`。`t = T` 時這個概率是 37%——**三分之一的概率你會把一個會崩的配置判成乾淨**。`t = 4T` 時降到 1.8%，`t = 5T` 時 0.7%，才夠下結論。

反過來，這條也解釋了為什麼前面幾輪 A/B 總「看起來通過」：它們本來就不是為抓崩潰設計的，是為比幀率設計的，45 秒足夠看 fps，但根本不夠看 MTTF。

## 3. 三臂設計：唯一變量是「子進程到底做不做渲染」

好在驗證成本極低——崩潰二分的開關現網二進制裡已經有了，不需要改一行代碼：

| 臂 | 配置 | 含義 |
| --- | --- | --- |
| C（對照） | `RPOOL=2 AF=1 HLSBUF=1` | 現網原樣，預期復現崩潰 |
| A | `RPOOL=0 AF=1 HLSBUF=1` | 完全不起池，串行渲染 |
| B | `RPOOL=2 IDLE=1 AF=1` | 池子進程照常 fork，但**只回 ack 不渲染**（v32 已內置該開關） |

B 臂是關鍵。它把「fork 這個動作」和「子進程裡跑渲染代碼」這兩件事拆開了：

* A 潔、B 潔、C 崩 ⇒ 崩在**子進程渲染代碼**裡，fork 只是載體；
* A 潔、B 崩 ⇒ **fork 本身有毒**（在持有 VSP 的進程裡 fork）；
* A 也崩 ⇒ 跟池完全無關，問題在解碼 / 供數 / 音頻側。

三條互斥，跑完即可對號入座，不需要再猜。

**控制臂先跑**。如果 C 這一輪壓根不崩，說明源或環境變了，前提不成立，後面兩臂縮短到 300 秒只作確認——不然要白燒 40 分鐘。

## 4. 工程細節：三個不做就會靜默作廢的坑

### 4.1 wrapper 會覆蓋你的 env

現網入口 `/usr/local/bin/nettv_player` 是個 shell wrapper，`RPOOL/AF/HLSBUF` 三個值都寫在裡面。如果你在它外面 `export NETTV_RPOOL=0` 再調它，**wrapper 自己的 `export` 會把你的值蓋掉**——三臂跑成同一個配置，實驗靜默作廢，而且日誌上完全看不出來。

造臂的辦法是：複製 wrapper，刪掉末行（`exec` 那行），把本臂的 env 追加進去，再把末行接回去：

```sh
{
  sed -e "s/NETTV_RPOOL=[0-9]*/NETTV_RPOOL=$rp/" ... $WRAP | sed '$d'
  echo "export NETTV_RPOOL=$rp"
  echo "export NETTV_RPOOL_IDLE=$idle"
  tail -1 $WRAP          # 把 exec 那行接回去
} > /tmp/w_$tag.sh
```

這樣既保留了 wrapper 自帶的全部環境（`LD_LIBRARY_PATH` 之類一個不少），又保證我們的值在 `exec` 之前最後生效。

### 4.2 生效 env 必須自檢

光造對了還不夠，得**驗證**。起臂 25 秒後掃一遍真進程的環境塊：

```sh
for d in /proc/[0-9]*; do
  e=$(readlink "$d/exe" 2>/dev/null)
  case "$e" in *nettv_player*) tr '\0' '\n' < "$d/environ" | grep -a NETTV_ ;; esac
done | sort -u
```

日誌裡直接打出「生效 env 自檢」，`IDLE` 的值對不上，這一臂當場判廢。這比事後對著結果懷疑人生便宜太多。

### 4.3 找進程只能匹配 `/proc/<pid>/exe`

這個坑在這個項目裡已經是第 5 次出現了：用 `ps -ef | grep nettv_player` 找進程要殺，而腳本自己的命令行裡就含 `nettv_player` 這個字串 ⇒ **把自己也匹配進去**。10-30 那次 A/B 腳本就是這麼「自殺」的，基線臂一跑完就把自己 TERM 掉，後面三個臂一個沒跑。

一律改成讀 `/proc/<pid>/exe` 的符號鏈接目標來匹配，命令行裡出現什麼都無所謂。

## 5. 判讀表（腳本末尾自動出）

| A（RPOOL=0） | B（+IDLE） | C（對照） | 結論 | 下一步 |
| --- | --- | --- | --- | --- |
| 潔 | 潔 | 崩 | 崩在子進程渲染代碼 | 編譯 v34（解掩碼 + 處理器探針），確認 RPOOL=2 零崩潰後申請部署 |
| 潔 | 崩 | 崩 | fork 本身有毒 | 池挪到獨立進程，或 `RPOOL` 永久設 0，優化重心放回單核 `fb_render` |
| 崩 | 崩 | 崩 | 與池無關 | 繼續二分 `AF` / `HLSBUF`，同時跑資源趨勢採樣 |
| 潔 | 潔 | 潔 | 本輪未復現 | 延長臂長到 1200s，或改用 UI 入口觸發 |

## 6. 順帶記一筆：這個項目的離線/在線節奏

設備已經連續 6 輪離線（未上電）。前幾輪的應對是「離線繼續寫新版本代碼」，結果堆了 v29/v30/v31/v34 四個**從未編譯過**的版本——每上一輪新代碼，就多一份「上電後要先驗證它能不能編譯」的債。

這輪換了個思路：**離線只產出「零改碼」的測量工具**。不改播放器，只用現網二進制 + env 組合，把不確定性壓到一個 40 分鐘的自動腳本里。等設備一上電，一條命令就能拿到判決，而不是再添一筆編譯債。
