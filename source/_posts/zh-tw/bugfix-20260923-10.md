# bugfix_20260923_10 — GBA 退出直接卡死（回滾 SIGUSR1「畫面交還」握手方案）

| 項目 | 內容 |
| --- | --- |
| 發現時間 | 2026-09-23 |
| 修復時間 | 2026-09-23 |
| 模塊 | `extern/miniretro/miniretro.c`、`lv_pages/gba_game_page.c` |
| 涉及版本 | 回滾 bugfix_20260923_09 的全部改動 |
| 現象等級 | 高（退出功能完全不可用，並波及原本正常的 FC 頁） |

## 1. 問題現象

用戶在實機上反饋兩條：

1. **GBA 遊戲退出時直接卡死**（此前是"偶爾卡一下"，仍可用）；
2. **FC 遊戲也卡死了，而它原來沒問題**。

這是典型的**迴歸**，且第 2 條說明問題不在 GBA 頁面本身 —— FC 與 GBA 共用同一個
`extern/miniretro/miniretro` 前端，因此元兇必然在 miniretro 側那次改動裡。

## 2. 影響範圍

- 所有從 LVGL 頁面拉起 miniretro 的入口：FC 遊戲頁、GBA 遊戲頁；
- 由於 `setenv` 是**主進程級**的，汙染會跨頁面殘留，直到 `lvgl_demo` 重啟為止 ——
  即"從 GBA 出來之後，FC 也跟著壞"，與用戶描述完全一致。

## 3. 根因分析

bugfix_09 為"省掉內核回收 `/dev/input/eventX` 的那 ~340ms"引入了兩個機制，
兩條都錯：

### 3.1 `_exit(0)` 省不掉內核的時間，只會讓進程更久不消失

原以為 `_exit(0)` 跳過用戶態 `close()` 就能立刻消失。實測相反：

- `_exit(0)` 只是跳過用戶態逐個 `close()`，內核 `exit_files()` **照樣**要收掉
  這些 fd，而且是在**進程退出路徑上不可中斷地收**；
- 於是子進程在 `_exit` 之後比正常 `return` **更久**才消失。

設備日誌是鐵證（同一進程，以收到 SIGTERM 為 0 點）：

```
[miniretro][timing] fb_restore 完成          t=   33.8 ms
[miniretro][timing] 收尾完成(快退出)         t=   39.9 ms
[gba] 子進程 17830 未按時退出, SIGKILL 兜底        ← 5 秒後才出現這一行
```

`39.9ms` 就走完了所有收尾，進程卻 5s 都沒被回收 —— 時間全耗在內核退出路徑裡。

### 3.2 把"等收屍"的超時循環放在互斥鎖內 → UI 恢復被拖滿 5 秒

GBA 頁 `gba_wait_thread` 的結構是：

```
階段① 等 SIGUSR1 / 子進程退出（≤500ms）
pthread_mutex_lock(&s_gba.lock);
階段② 等收屍，最多 1000 × 5ms = 5s          ← 在鎖內
pthread_mutex_unlock(&s_gba.lock);
hardware_keys_set_grab(true);
app_runtime_set_lvgl_paused(false);        ← UI 恢復在鎖外，必須等階段② 結束
```

子進程遲遲不消失 → 階段② 跑滿 5s → **UI 整整 5 秒後才恢復** = "退出直接卡死"。

FC 頁則是 `waitpid(pid, NULL, 0)` **無超時阻塞**在同一個不消失的子進程上，
同樣卡死 —— 這就是"FC 原來沒問題，現在也卡"的原因。

### 3.3 附帶缺陷：握手門禁汙染了主進程環境

`gba_launch()` 在 `fork()` 之前調用 `setenv("MINIRETRO_UI_RELEASE_SIGNAL", "1", 1)`。
`setenv` 改的是**當前進程**（`lvgl_demo`）的環境塊，一旦設上就永久保留：

- 之後 FC 頁 `fork()` 出的子進程也會繼承該變量，從而也去給父進程發 `SIGUSR1`；
- `SIGUSR1` 默認動作是**終止進程** —— 門禁一旦失效（例如頁面側 handler 被改回去），
  父進程會被自己拉起的子進程打死。

結論：**不要跟內核賽跑。** 退出路徑的快慢由內核決定，用戶態唯一能做的是
"不等它自己走完"。

## 4. 修復方案

**完整回滾 bugfix_09，改用 FC 頁那套已長期實機驗證的退出策略。**

### miniretro 側（子進程）

- 刪除 `notify_parent_ui_released()` 及其調用、環境變量門禁；
- `_exit(0)` → 恢復為正常 `return 0`（原樣交給 glibc/內核收尾）；
- 保留 `on_quit_signal`（SIGTERM → `quit=1` 走優雅收尾）與 `fb_restore()`
  （翻回第 0 頁 + 清屏，防畫面殘留）—— 這兩項是 bugfix_07 的正確修復，不在回滾範圍；
- 保留 `td()` 分階段計時日誌，後續定位同類問題仍需要它。

### 頁面側（`lv_pages/gba_game_page.c`）

- 刪除 `s_gba_ui_released`、`gba_ui_release_handler`、`setenv`、`signal(SIGUSR1,…)`；
- `gba_exit_to_list()` 恢復為 FC 同款：

  ```c
  kill(pid, SIGTERM);            /* 讓它優雅收尾: 翻頁+清屏, 實測 ~40ms */
  usleep(120 * 1000);            /* 足夠它把 fb 交還 */
  if(kill(pid, 0) == 0) kill(pid, SIGKILL);   /* 不等它在內核裡慢慢收 fd */
  ```

- `gba_wait_thread()` 收屍改為 **WNOHANG 輪詢、上限 3s、絕不死等**；
  超時才 `SIGKILL` 並交給 `gba_reap_bg()` 後臺線程收乾淨（不留殭屍）。
  與 FC 的差別僅在於多了一道上限保險，正常路徑 200ms 內返回，不會觸發。

## 5. 驗證方法與結果

設備端一次性測量（復刻頁面側新邏輯：SIGTERM → 120ms → SIGKILL → 輪詢收屍）：

```bash
python3 /tmp/gba_exit_verify.py
```

| 指標 | 結果 |
| --- | --- |
| 120ms 時子進程是否還活著 | `True`（正常，正在內核中收尾） |
| SIGKILL 發出時刻 | 120.4 ms |
| **從 SIGTERM 到收屍完成** | **455.0 ms**（原方案 >5000 ms） |
| `fb_restore` 完成時刻 | 33.8 ms（畫面在此之前已交還） |
| 退出碼 | 0 |
| 新增殭屍 | 無 |
| 恢復後進程 | `lvgl_demo` ×1、`lvgl_watchdog` ×1（單實例） |

編譯側：miniretro `gcc` 返回 0、0 error / 0 warning；`lvgl_demo` `make -j2` 返回 0、0 error。
部署採用"編到 `*.tmp` 再 `mv -f` 原子替換"，避免用戶正在玩時 exec 到半覆蓋的二進制。

## 6. 迴歸風險

- **退出仍有約 0.45s 的等待**：其中 120ms 是我們主動等它復位畫面，後 ~335ms 是內核
  收 fd 的固有開銷，且發生在"畫面已黑"之後，主觀為"屏幕黑一下"而非"僵住"。
  這是與 FC 頁一致的表現，屬於可接受成本。
- 若日後仍嫌慢，正確方向是**"畫面已交還就恢復 UI，收屍完全後臺化"**，
  而不是縮短子進程的生命週期 —— 注意不要再用 `setenv` 之類的主進程級開關做門禁。
- 頁面銷燬路徑（`onDestroy`）本來就先 `SIGKILL` 再 `waitpid`，未受影響。
- 本次未改動渲染（雙緩衝/pitch/240×160）與音頻鏈路，顏色與音質不應有變化。
