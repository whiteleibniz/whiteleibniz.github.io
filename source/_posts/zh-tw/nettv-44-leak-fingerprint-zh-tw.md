> 系列第 44 篇。上一輪把崩潰定性成「累積漂移」，也就是要按洩漏查。
> 但「洩漏」是個太便宜的詞——它可以是記憶體池耗散、可以是句柄、也可以是每 N 段的固定動作。
> 這一輪不碰播放器一行程式碼，只做一件事：**造一台能稱出「是哪一種」的秤**。

## 定性之後，問題變成了「哪一種」

裝置那天依舊沒上電，只能離線推進。翻回上一輪的結論：兩個 1200 秒的臂各崩 6 次和 7 次，
間隔 151～186 秒，影格率正常，崩潰點隨真實流推進。結論是「累積漂移」——但這句話能推出的
下一步動作有好幾個，方向完全不同：

- 如果間隔在**縮短**，那是典型的洩漏曲線（每輪少一點餘量，越到後面越快撞牆）；
- 如果間隔**恆定**，那更像固定槽位／定時器——每 N 格、每 N 段、每 N 秒必然越過某條邊界；
- 如果記憶體曲線在掉但間隔不變，那是耗散與崩潰**兩個獨立現象**，別硬捆在一起歸因。

這三種情況的修法完全不重疊。所以真正缺的不是取樣器（早就有了逐執行緒 SigBlk、RSS、ION 的
輪詢腳本），而是一台**判決器**：把「間隔序列」和「記憶體序列」變成一個有名字、帶前提條件的結論。

## 分工：裝置只做啞採集，判決全在 PC

這條鏈的設計原則是能不說話的一律不說話：

- 裝置端只有一個採集器：跑一次單臂 2400 秒（約 40 分鐘），每 10 秒記一行
  `MemFree / CmaFree / ION / 各行程執行緒數、RSS、fd`，同時把 `phase.log` 裡新出現的
  `mon-child-signal=11` 連同牆鐘時間抄進崩潰台帳；
- 判決全部放在 PC 端的腳本裡，因為裝置上沒有 Python，而且 SSH 連線絕不能掛 40 分鐘——
  長任務必須拆成「裝置背景腳本 + 短輪詢」。

採集器還做一件容易被忽略的事：**它自己也出一份完整性閘門**。跑完寫 `GATE=OK` 或
`GATE=FAIL 原因=...`，條件包括開跑殘留為零、結束時殘留為零、有影格率統計、取樣條數夠、
跨度夠。這份 GATE 會被 PC 端**再算一遍**。

## 先證明「這輪觀測有效」，再談趨勢

這是整個方法論裡最貴的一條經驗，也是我反覆踩的坑：**最省事的執行永遠看起來最乾淨**。
解碼器沒起來、來源掛了、行程被殘留擋住——這些情況下崩潰數當然是 0，而 0 會被順理成章
讀成「這個配置不崩」。

所以判決器的第一段程式碼不是統計，是閘門：

| 閘門 | 判據 | 不滿足說明什麼 |
| --- | --- | --- |
| 開跑殘留 | 0 | 上一輪沒清乾淨，配置可能沒生效 |
| 影格率 | `fps_x10 ≥ 50` 且統計行 ≥3 | 根本沒解碼，崩潰數為 0 無意義 |
| 收尾殘留 | 0 | 收尾沒收乾淨，下一輪污染 |
| 取樣條數／跨度 | ≥ 期望的 80% | 採集被截斷，趨勢是半截資料 |
| 取樣斷檔 | 相鄰樣本 ≤ max(60s, 5×間隔) | 中間缺了一大段，不能當連續趨勢 |

任何一條不過，判決直接是 `INVALID`，並且明確寫「禁止據此改任何程式碼」。

更進一步：閘門和判決**各寫兩遍**。裝置端是 shell 的 `gate_eval`，PC 端是 Python 的
`_gates()`，兩套獨立實作，結論不一致就判 `INVALID（交叉不一致）`。這一條不是潔癖——
本輪正是靠它抓到了自己的一個 bug（見下）。

## 判決檔位：把「洩漏」拆成能動手的幾種

間隔趨勢不看變異數，只看「首末相對變化 + 線性擬合的 r²」；記憶體趨勢看 `CmaFree` 的斜率、
`r²` 和總跌幅，按量級分「洩漏量級」與「漂移量級」兩檔。

| VERDICT | 觸發條件 | 下一步該查什麼 |
| --- | --- | --- |
| `LEAK_CONFIRMED` | 間隔遞減且記憶體耗散達洩漏量級 | 每輪崩潰週期內新配置未釋放的物件 |
| `LEAK_LIKELY` | 間隔遞減，記憶體只有漂移量級 | 先按洩漏查，核對 fd／執行緒數與崩潰速率是否同比 |
| `LEAK_SUSPECTED` | 間隔遞減但記憶體平穩 | 非記憶體類累積：fd、執行緒、池槽位、廠商內部句柄 |
| `PERIODIC_WITH_DRIFT` | 間隔恆定但記憶體在掉 | 固定槽位／定時器，耗散是伴生現象 |
| `PERIODIC_TIMER` | 間隔恆定且記憶體平穩 | 每 N 格／N 段／N 秒的固定動作（重連、重新 init、指標回繞） |
| `SLOWING` | 間隔變長 | 可能與來源切換、GOP 長度變化相關 |
| `RANDOM` | 無規律 | 偏向隨機踩記憶體，回去做 pc 映射與緩衝區邊界 |
| `STABLE` | 零崩潰且觀測夠長 | **不能據此說修好了**，要 ≥4～5 個故障週期 |

最後一行值得單獨說：斷言「配置 X 不崩」，觀測時長必須是故障週期的 4～5 倍。這是泊松分布
給的數——跑 1 個週期就「沒復現」的機率還有 37%，5 個週期才降到 0.7%。

## 四個 bug：全都是「工具把自己偽裝成結論」

這一輪最有價值的部分不是那兩個腳本，而是自檢抓出來的四個自傷：

**① 貪婪正則把間隔全算成 0。**
崩潰行的格式是 `t=1117000 mon-child-signal=11 st=0x8b`。想取毫秒時間戳，於是寫了
`sub(/^.*t=/,"")`——行尾的 `st=` 裡也含 `t=`，貪婪匹配一路吞到那裡，剩下的 `0x8b`
再被剝成 `0`。四個崩潰算出來三個間隔，全是 0，看起來像「節拍極其穩定」。改成按首欄位
`split` 取值，自檢當場由 FAIL 轉 PASS。

**② Windows 文字模式寫 shell 腳本，變成 CRLF。**
用 Python 打個補丁改了腳本裡的幾行，`open(p,"w")` 在 Windows 上會把 `\n` 翻成 `\r\n`。
dash 解析到第 46 行報 `"|" unexpected`——因為上一行結尾是反斜線續行，`\` 後面跟的
是 `\r` 而不是換行，續行失效。這個錯誤離真正的問題（檔案編碼）隔了 250 行，純屬
「報錯位置騙人」。裝置上沒有 CRLF 轉換工具，這種腳本傳上去只會全盤失敗。

**③ 交叉校驗恆報不一致，而且不一致沒有降級。**
meta 裡一行 `GATE=OK` 被按首個 `=` 切成 `key=GATE, value=OK`，而校驗程式碼寫的是
`value.startswith("GATE=OK")`——永遠 False，於是**每一輪**都報「交叉不一致」。
更糟的是不一致只往原因清單裡塞了一條，沒有把 `ok` 置假：結果是判決照樣給出
`PERIODIC_WITH_DRIFT`，而理由裡寫著「交叉不一致」。**結論和前提自相矛盾**，這比不校驗更危險。
修法是先歸一化，再讓不一致必須降級。

**④ 用變異數判「在加速」，把 186→128 判成了恆定節拍。**
`cv`（標準差／均值）小既可能是恆定節拍，也可能是**均勻地越崩越快**——本輪 demo 資料
186、179、168、155、141、128 秒，`cv=0.13` 很「穩」，`r²=0.99` 是漂亮的直線下降，
卻因為 `cv≤0.20` 先命中了 `PERIODIC`。判據改成「首末相對變化 ≤15% 且 cv 小」才算恆定，
方向性交給 `r²` 和相對斜率。

四個 bug 的共性很清楚：**它們都不是讓程式崩，而是讓程式給出一個「看起來很合理」的錯誤結論。**
對策也就三條，都不新鮮但必須落地：

1. 自檢要斷言**期望的判決名**，而不只是「沒有 FAIL 行」——上次的教訓是相位函式沒載入時
   計數器為 0，測試工具直接變成「永遠通過」；
2. 關鍵判據寫兩遍，用兩份獨立實作互相對帳；
3. 加**變異用例**：把同一個資料集裡的影格率改成 0、殘留改成 2，判決必須掉進 `INVALID`。
   如果變異後結論不變，說明閘門根本沒在起作用。

## 現狀與下一步

這一輪沒有編譯、沒有部署、沒有改現網二進位檔的任何一個位元組——採集器跑的是現網包裝腳本的
原樣配置。離線驗證做到兩件事：shell 自檢 13 項（間隔解析、碼率餘量、閘門六態、全零假通過）、
Python 端 17 項（含 4 組變異與 2 條解析／交叉回歸），以及閘門失敗分支在本機的實跑
（不會啟動播放器，只驗證參數流、閘門與 meta 生成）。

裝置上電後的順序是固定的：先跑 2400 秒單臂，把 meta 和崩潰台帳取回，再讓判決器說話。
如果它說 `PERIODIC_TIMER`，洩漏這條線就得讓位給「固定動作」假設；如果說 `LEAK_*`，
那就順著 fd／執行緒數曲線去定位每輪的淨增量。**在拿到 4～5 個崩潰間隔之前，任何改動都是猜。**
