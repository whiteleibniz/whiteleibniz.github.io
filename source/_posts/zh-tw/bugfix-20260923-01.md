# bugfix_20260923_01 — 藍牙顯示「已連接」但實際未連接

> **現象**：藍牙頁顯示「已連接: 小愛音箱-1303」，實際沒有可用連接 —— 音箱不出聲，
> 約 1 分鐘後狀態自己翻回「已配對」，反覆重連都一樣。
> **根因層**：用戶態藍牙協議棧 `bt_user_daemon` 的 `conn` 語義 / LVGL 藍牙頁判據。
> **修復工作量**：1 個文件 +64/-13 行（`lv_pages/bluetooth_page.c`）。
> **文件名**：`bugfix_20260923_01_藍牙顯示已連接實際未連接.md`
> **關聯提交**：221fa7d
> **日期**：2026-09-23

## 現象

藍牙設置頁顯示 **`已連接: 小愛音箱-1303`**，設備行右側也是**綠色「已連接」**，
但：

- 音箱沒有任何反應（不播提示音、手機/音箱側也不顯示被連接）；
- 過一段時間（約 1 分鐘）狀態會**自己變回「已配對」**；
- 反覆點擊設備重連都一樣，永遠"連上又像是沒連"。

即：**UI 說已連接，實際沒有可用連接。**

## 影響範圍

| | |
|---|---|
| **受影響** | 藍牙頁的連接狀態顯示；A2DP 音頻輸出（音箱不出聲）；用戶無法判斷到底連沒連上 |
| **不受影響** | 藍牙開關、掃描/配對列表讀取、配對記錄本身；FM 收音機；桌面與其它頁面 |

## 根因

**兩層原因疊加**，缺一不可。

### 3.1 直接原因：藍牙頁把"ACL 鏈路存在"當成了"已連接"

`bt_user_daemon` 的 `conn` 命令只表示 **ACL（基帶鏈路）已建立**，不代表上層 profile
（A2DP）可用。而 `bluetooth_page.c` 原來就是這個判據：

```c
bp_get_conn_mac(conn_mac, sizeof(conn_mac));   /* conn 命令 */
if(conn_mac[0]) snprintf(detail, ..., "已連接: %s", nm);   /* ← 直接當成已連接 */
```

### 3.2 根本原因：本機存的 link key 已被音箱側作廢，認證失敗

- link key 存在 `/tmp/bt_linkkey.conf`（`<MAC> <32位十六進制>`，16 字節）。
- 音箱側把這條配對記錄丟了/重新生成過 → 本機的 key **對不上**。
- 但 daemon 收到控制器的 `Link Key Request` 時，**只要本地有 key 就回 positive**
  （日誌原話：`[pair] link key req -> positive(已存 key, 免 SSP)`），於是**沒有走重新配對**。
- 結果：HCI 認證失敗——

```
[pair] auth complete status=5        ← 0x05 = Authentication Failure
[pair] done paired=1 auth_ok=1 enc_ok=0 -> A2DP
[auth] auth complete status=5
[auth] auth failed
```

- `enc_ok=0` 表示**鏈路加密從未建立**，A2DP 自然建不起來（`AVDTP_START` 不會發出）。
- 但 **ACL 已經建上了**（L2CAP 能通、SDP 能查），所以 daemon 的 `conn` 照樣回
  `OK CONN c5:09:5d:3e:bd:3c 小愛音箱-1303` → UI 顯示"已連接"。
- 約 60 秒後音箱側放棄，鏈路斷開（`[main] disconnect complete evt`），daemon 才翻回 `IDLE`。

一句話：**ACL 通、認證掛、加密沒建立、A2DP 沒起，UI 卻只看 ACL。**

## 定位過程

### 4.1 關鍵判真器：`/tmp/bt_audio.fifo` 有沒有讀者

daemon 的 A2DP 媒體循環啟動時會**打開 `/tmp/bt_audio.fifo` 的讀端**。
於是用非阻塞方式打開寫端即可判斷媒體循環是否在跑：

```python
import os
try:
    fd = os.open("/tmp/bt_audio.fifo", os.O_WRONLY | os.O_NONBLOCK); os.close(fd)
    print("a2dp=True  (有讀者，媒體循環在跑)")
except OSError as e:
    print("a2dp=False (無讀者)", e)      # ENXIO(6) = No such device or address
```

這是本機能拿到的**唯一用戶態可見的 A2DP 真相**。實測：

```
T+00  conn='OK IDLE'                                  a2dp=False
T+02  conn='OK CONN c5:09:... 小愛音箱-1303'          a2dp=False   ← 假連接
...   （持續 60 秒）                                   a2dp=False
T+62  conn='OK IDLE'                                  a2dp=False
RESULT connect -> 'RC 0'        ← connect 還回成功！
```

**`connect` 返回 `RC 0` + `conn` 報 CONN，但 fifo 始終沒有讀者** → 判定為假連接。

### 4.2 試錯與排除

| 嘗試 | 結果 |
|---|---|
| 懷疑 UI 只查一次、不刷新 | ❌ 頁面本來就有 15 s 自動刷新（`BP_AUTO_REFRESH_MS`），排除 |
| 懷疑 daemon 掛了 | ❌ `state/paired` 正常，socket 正常 |
| 用 `/etc/init.d/bt_daemon restart` 重啟以清內存裡的舊 key | ❌ **沒生效**！openrc 報 `udev failed to start`，且 pid 仍是 1222（沒換進程）→ 舊 key 還在內存裡，修復無效 |
| 按 `bt_bringup.start` 的方式 `kill -9` + `setsid` 重啟 | ✅ pid 1222 → 382，key 真的清了 |
| 用高頻循環 `connect` 撐住"假連接"窗口以便截圖 | ⚠️ 打滿 daemon accept 隊列，後續請求 `errno 11 (EAGAIN)`。**不要高頻探測 daemon** |

### 4.3 修好之後協議棧的原話

```
[auth] auth complete status=0            ← 原來是 5
[auth] auth ok -> Set Encryption (0x0413)
[auth] encryption change status=0 enc=1  ← 加密建立
[l2cap] SDP 斷開 + 認證完成 -> 建 AVDTP
[a2dp] avdtp begin: L2CAP conn req PSM=0x0019
[avdtp] DISCOVER_RSP seid=4 tsep=0 media=0
[a2dp] media channel ready, sent AVDTP_START seid=4
[a2dp] media loop start GOLD NF=7 bp=35 fl=83 persamp=128 framedur=2902us nch=2
```

## 解決辦法

### 5.1 現場處置（可回滾）

```sh
# 0) 備份
cp /tmp/bt_linkkey.conf /tmp/bt_linkkey.good

# 1) 刪掉失效的 link key（文件裡那一行）
grep -v '^c5:09:5d:3e:bd:3c' /tmp/bt_linkkey.conf > /tmp/lk.tmp && mv /tmp/lk.tmp /tmp/bt_linkkey.conf

# 2) 真重啟 daemon（openrc restart 不生效，必須 kill + setsid）
for p in $(pidof bt_user_daemon); do kill -9 $p; done
sleep 2; rm -f /tmp/bt_ctl.sock
setsid /usr/local/bin/bt_user_daemon >/tmp/bt_daemon.log 2>&1 </dev/null &
sleep 10

# 3) 重新連接 -> 這一次會走完整配對(SSP)，並把新 key 寫回 /tmp/bt_linkkey.conf
printf 'connect c5:09:5d:3e:bd:3c\n' | nc -U /tmp/bt_ctl.sock   # 或走 fm_ctl 同類客戶端
```

### 5.2 代碼修改：`lv_pages/bluetooth_page.c`

新增"音頻是否真的通了"的判據，並把三處文案全部改為以它為準：

```c
#include <fcntl.h>
#define BP_A2DP_FIFO "/tmp/bt_audio.fifo"
#define BP_CONN_AUDIO_WAIT_MS 25000

/* ★ 判斷 A2DP 音頻流是否真的跑起來了
 * daemon 的 conn 只表示 ACL 鏈路存在；Link Key 失效時認證失敗(status=5)，
 * A2DP 建不起來、音箱不出聲，但 conn 照樣回 OK CONN。
 * 判據: 非阻塞打開 fifo 寫端 —— 有讀者才說明 media loop 在跑。 */
static bool bp_a2dp_ready(void)
{
    int fd = open(BP_A2DP_FIFO, O_WRONLY | O_NONBLOCK);
    if(fd >= 0) { close(fd); return true; }
    return false;
}
```

1. **狀態區文案**：`conn_mac[0] && bp_a2dp_ready()` 才寫"已連接: xx"；
   `conn_mac[0]` 但音頻沒通時寫 **"鏈路已建立但音頻未連通"**。
2. **設備行標籤**：只有鏈路 → 橙色 **「無音頻」**；鏈路+音頻 → 綠色「已連接」；僅配對 → 灰色「已配對」。
3. **連接結果 toast**：`connect` 返回 `RC 0` 後**不立刻報成功**，而是每 300 ms 檢查一次
   `bp_a2dp_ready()`，最多等 25 s：等到了才提示"已連接 xx"，超時才提示"鏈路已建立，但音頻未連通"。

## 驗證

### 6.1 正例（真連接）

```
[conn] -> 'OK CONN c5:09:5d:3e:bd:3c 小愛音箱-1303'
bt_audio.fifo 有讀者: True (OK)          ← 媒體循環真在跑
```
截圖 `shots/btlive_0.png`：狀態區「已連接: 小愛音箱-1303」，設備行右側**綠色「已連接」**。
→ 這次 UI 說的是真話。

### 6.2 反例（故意把 link key 寫壞，復現原來的假連接）

把 key 整條替換成 16 個 `0x00` 並重啟 daemon 後重連：

```
connect -> RC 0
T+00 conn='OK CONN c5:09:5d:3e:bd:3c 小愛音箱-1303'   a2dp=False
T+02 conn='OK IDLE'                                     a2dp=False
[pair] auth complete status=5 / enc_ok=0 -> ABORT
```
截圖 `shots/btfake_0.png`：狀態區 **「鏈路已建立但音頻未連通」**，設備行右側**橙色「無音頻」**。
→ 同樣的硬件狀態，UI 不再謊報"已連接"。

### 6.3 端到端：音頻通路確實是通的

連上後持續把靜音 PCM 灌進 fifo（格式由 daemon 日誌反推：44100Hz / 2ch / S16_LE）：

```
fifo 寫端已打開，開始灌靜音 PCM（50.0s）
寫完 8634780 字節 (約 49.0 秒音頻)
conn(after) = OK CONN c5:09:5d:3e:bd:3c 小愛音箱-1303
[hci] credit inflight=5/1776   ← 全程在收發
```

**鏈路在持續供數時 50 s 不掉**，HCI 信用持續變化 → SBC 幀真的發上去了。

## 經驗教訓

1. **"已連接"必須由最末端的證據來定義。** ACL 存在 ≠ profile 可用 ≠ 流在跑。
   用中間層狀態代理末端的結論，遲早要說謊。本次的正確判據是"fifo 有沒有讀者"。
2. **link key 失效要作為音箱類設備的一級排查項。** 音箱換手機連過、被重置、
   固件升級都可能作廢本機 key；此時現象就是"連上又像沒連"，很容易誤判成信號/兼容性問題。
3. **`openrc restart` 不一定真的重啟。** 本機 `bt_daemon` 的 `restart` 因 `udev` 依賴失敗而空轉，
   pid 沒變 —— 凡是"改了狀態/清了緩存要生效"的場合，**必須校驗 pid 是否真的變了**。
4. **不要寫高頻探測腳本打自己的 daemon。** 1 秒一次 `connect` 會把 accept 隊列打滿，
   後續全部 `errno 11`，反而搞亂現場。
5. **daemon 的接口語義要寫進文檔**：`conn` = ACL，不等於連接可用。
   已同步到 `lv_pages/bluetooth_page.c` 頂部註釋與項目記憶。
6. **"沒聲音"不一定是通路壞了。** 本機 A2DP 媒體循環是"有數據才活"：
   沒有 PCM 進 fifo，音箱會因超時主動斷開。判斷"音頻鏈路是否可用"要**同時**看
   fifo 有無讀者 + 連接是否維持，不能只看其中一個。
