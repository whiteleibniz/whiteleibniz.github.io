# bugfix_20260922_01 mplayer 播放視頻紅藍通道錯亂

> **現象**：桌面圖標與 FC 遊戲顏色已修正後，用「視頻」頁播放 mp4 時顏色仍然不對（紅藍互換）。
> **根因層**：framebuffer 色彩元數據 × 外部播放器（mplayer `-vo fbdev`）。
> **修復工作量**：2 個源文件 +54/-2 與 +50/-2，外加 miniretro 重編。
> **文件名**：`bugfix_20260922_01_mplayer視頻紅藍通道錯亂.md`
> **關聯提交**：`5113a12`
> **日期**：2026-09-22

---

## 1. 現象

同一塊屏幕上，不同功能的顏色表現**不一致**：

| 功能 | 顏色表現 |
|---|---|
| 桌面圖標、文字、背景 | 正常（此前已修正） |
| FC 遊戲（miniretro） | 正常 |
| **「視頻」頁播放 mp4** | **紅藍互換**（紅色物體顯示成藍色） |

關鍵點：**只有視頻播放器不對**。這本身就說明問題不在"整個屏幕的色彩方案"，
而在"視頻播放器這條獨立路徑"。

## 2. 影響範圍

- **受影響**：`lv_pages/video_player_page.c` 走的外部 mplayer 進程播放的所有視頻。
- **不受影響**：LVGL 自繪部分（桌面/各頁面）、miniretro（FC 遊戲）——
  它們各自有獨立的寫 fb 路徑與本地的 R/B 交換，無需改動。

## 3. 根因

### 3.1 前提：本機屏幕真實字節序與驅動報告相反

`FBIOGET_VSCREENINFO` 報告 `r16:8 g8:8 b0:8`（語義 `[B,G,R,X]`），
但用純色寫 fb + 人眼確認，**真實字節序是 `[R,G,B,X]`**：

| 寫入 fb 的內存字節 | 屏幕實際顯示 |
|---|---|
| `[00,00,FF,FF]` | **藍** |
| `[FF,00,00,FF]` | **紅** |

→ `offset0 = 紅`、`offset2 = 藍`，**與驅動報告恰好相反**。

### 3.2 核心機制：外部播放器會**讀取**這份元數據並據此寫像素

`libs/mplayer/mplayer`（MPlayer 1.4-13）的 `fbdev` 輸出驅動在初始化時讀
`FBIOGET_VSCREENINFO`，**按讀到的 offset 決定自己把顏色寫到哪個字節**，
並在日誌裡打印它選定的佈局：

```
var = r16:8 g8:8 b0:8   ->  VO: [fbdev] 720x1280 => 720x1280 BGRA
var = r0:8  g8:8 b16:8  ->  VO: [fbdev] 720x1280 => 720x1280 RGBA
```

- `BGRA` = 藍在字節 0 → 但本面板要紅在字節 0 → 屏幕上紅藍互換 ✗
- `RGBA` = 紅在字節 0 → 與面板一致 ✓

**所以 mplayer 的代碼沒錯，它只是老實照驅動謊報的參數辦事。**

### 3.3 為什麼這裡不能靠改代碼解決

| 消費者 | 取色方式 | 可否改代碼 |
|---|---|---|
| LVGL（`main.c` `fb_flush_cb`） | 自己打包像素、直接寫內存 | ✅ 已改（交換 R/B） |
| miniretro（`scale_rotate90`） | 自己打包像素、直接寫內存 | ✅ 已改（交換 R/B） |
| **mplayer（`-vo fbdev`）** | **讀 fb 元數據，據此寫** | ❌ 第三方預編譯二進制，無源碼 |

mplayer 是 13.7 MB 的預編譯 ELF（`libs/mplayer/mplayer`），設備上**沒有源碼**，
所以改不了它的代碼 —— 只能改**它讀到的參數**。

## 4. 定位過程

### 4.1 走過的彎路（記錄下來避免重走）

| 錯誤方向 | 為什麼錯 |
|---|---|
| 在系統路徑找 mplayer（`/usr/bin`、`/usr/local/bin`） | 全部不存在 → 一度誤判"設備上沒有播放器"。實際在 `libs/mplayer/mplayer`，由 `video_find_mplayer()` 的相對路徑候選命中 |
| 試 `-vf format=bgr32` / `format=rgb32` / `format=bgra` | **全部無效**。fbdev vo 會覆蓋 format 濾鏡的選擇，四組輸出字節**完全相同** |
| 試 `-vo fbdev2` | 與 `fbdev` 行為相同，仍是 BGRA |
| 想改自定義 `lvfb` 驅動 | 該 mplayer 裡確有 `lvfb`（"LVGL-style framebuffer output"）驅動，但它**拒絕**本機格式：`[lvfb] unsupported framebuffer format: 720x1280 32bpp r16:8 g8:8 b0:8`（校正成 `r0:8 b16:8` 後**依然拒絕**）。設備上沒有 lvfb 源碼，無法修改 |
| 用 `ffmpeg -f lavfi` 造純色測試視頻 | 設備**沒有 ffmpeg**，此路不通。改用現有 mp4 直接比對 |

### 4.2 決定性實驗：只改 fb var，看輸出字節是否變化

**控制變量**：同一條命令、同一個 mp4，**唯一變化是 fb var**。

```sh
# A) 出廠 var（r16 g8 b0）
./mplayer -vo fbdev:/dev/fb0 -nodouble -bpp 32 \
          -vf scale=720:-2,expand=720:1280 -ao null -frames 1 <video.mp4>

# B) 校正 var（r0 g8 b16）後，跑完全相同的命令
```

結果（屏中央採樣）：

| 情形 | `VO:` 日誌行 | 屏中央字節 |
|---|---|---|
| A 出廠 var | `VO: [fbdev] ... BGRA` | `[e5 d7 cc ff]` |
| B 校正 var | `VO: [fbdev] ... RGBA` | `[cc d7 e5 ff]` |

**只有 R/B 兩個字節互換，其餘完全一致** —— 乾淨地指向 fb var 這一個變量。

### 4.3 關鍵排除實驗：改 var 會不會影響控制器實際取色？

這是決定"疊加修正"還是"替換修正"的分水嶺。

**做法**：把 var 校正為 `r0:8 b16:8` 後，往 fb 寫**同樣的** `[FF 00 00 FF]`，
讓用戶目視報告顏色。

**結果**：用戶答「紅色」——與改 var **之前**看到的顏色**完全相同**。

**結論**：`red/green/blue.offset` **只是給軟件讀取的元數據，控制器不理會它**。
改 var 不影響硬件掃描取色，隻影響"讀這份元數據的軟件"（即 mplayer）。

→ 因此修正是**疊加式**：必須校正 var（修 mplayer），
而 LVGL/miniretro 自己的 R/B 交換**必須保留**（刪了就雙重交換，反而變回錯的）。

## 5. 解決辦法

### 5.1 新增一個冪等的 var 校正函數

在 `fb_init()` 裡（打開 fb 之後立刻）調用一次，把 var 校正為 `r0:8 g8:8 b16:8`：

```c
/* 校正 fb 參數, 讓讀取該元數據的外部播放器(mplayer)自動取對字節序。
   實測: 改 var 不影響控制器取色, 隻影響讀元數據的軟件。 */
static void fb_fix_color_spec(int fd)
{
    struct fb_var_screeninfo v;
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) < 0) { perror("[fb] fix: FBIOGET"); return; }
    if(v.red.offset == 0 && v.blue.offset == 16 &&
       v.red.length == 8 && v.green.length == 8 && v.blue.length == 8)
        return;                                    /* 已是目標佈局, 冪等 */
    v.red.offset   = 0;  v.red.length   = 8;
    v.green.offset = 8;  v.green.length = 8;
    v.blue.offset  = 16; v.blue.length  = 8;
    if(ioctl(fd, FBIOPUT_VSCREENINFO, &v) < 0) {
        fprintf(stderr, "[fb] fix: FBIOPUT failed: %s\n", strerror(errno));
        return;
    }
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) == 0)
        fprintf(stderr, "[fb] color spec -> r%u:%u g%u:%u b%u:%u\n",
                v.red.offset, v.red.length, v.green.offset, v.green.length,
                v.blue.offset, v.blue.length);
}
```

### 5.2 在兩處 `fb_init()` 中調用

| 文件 | 位置 | 作用 |
|---|---|---|
| `main.c` | `fb_init()` 打開 `g_fb_fd` 後 | mplayer 是 lvgl_demo 的**子進程**，自然繼承正確狀態 |
| `extern/miniretro/miniretro.c` | `fb_init()` 打開 `fb_fd` 後 | 脫離主程序單獨跑遊戲時，fb 狀態也正確 |

### 5.3 **保持不變**的部分（重要）

- `main.c` 的 `fb_flush_cb`：**保留** R/B 交換
- `extern/miniretro/miniretro.c` 的 `scale_rotate90`：**保留** R/B 交換

這兩者直接寫內存、不讀元數據，刪掉交換就會雙重交換變回錯的。

## 7. 經驗教訓

1. **"同一個屏幕上，不同進程的修法不同"** —— 這是本次最大的認知躍遷。
   寫 fb 的消費者分三類：
   - **自繪程序**（LVGL、miniretro）→ 改**代碼**，在自己寫入點交換
   - **讀元數據的外部程序**（mplayer `-vo fbdev`）→ 改**參數**（校正 fb var）
   - **內核/控制器** → 通常不可改，且實測**忽略** var

   只修一類就會留下"某個功能顏色還是錯的"。**排查顏色問題第一步應先枚舉所有寫 fb 的進程。**

2. **先看外部程序自己打印的選擇**。`mplayer` 的 `VO: [fbdev] ... BGRA` 一行
   直接說明了它的判斷依據，比任何推理都快。有日誌就別猜。

3. **控制變量的 A/B 實驗優於"改一堆再試"**。同命令 + 同素材 + 只改一個變量
   （fb var），得到"只有 R/B 兩字節互換"的乾淨結論，直接鎖定因果。

4. **區分"元數據"與"硬件行為"**。改 `var.red.offset` 前先問：
   "它是被硬件用的，還是隻被軟件讀的？" —— 用"改前後寫同樣字節看屏幕是否變化"
   就能回答。這個判斷決定了修正是疊加還是替換，**判錯就會雙重交換**。

5. **命令行選項要先驗證再放棄**。`-vf format=...`、`-vo fbdev2` 看起來合理，
   實測全部無效。花幾分鐘證偽，勝過憑直覺重編播放器。

6. **不要用 `pkill -f <pattern>` 殺守護進程**。`pkill -9 -f lvgl_watchdog` 會匹配到
   **承載該命令的 shell 自身**（其命令行含該字符串）→ 殺掉自己的 SSH 會話，
   表現為 `RC: -1` 且輸出被截斷，看起來像"命令根本沒執行"。**按 PID 殺**：
   ```sh
   for p in $(ps -o pid,args | grep lvgl_watchdog.sh | grep -v grep | awk '{print $1}'); do kill -9 $p; done
   ```

7. **給遠端打補丁後，用 `git diff --ignore-cr-at-eol` 複核**。
   `git diff` 曾把 54 行的真實改動顯示成 1618 行"整文件重寫"——
   那只是 CRLF/LF 觸發 git 行尾啟發式，不是改壞了。
