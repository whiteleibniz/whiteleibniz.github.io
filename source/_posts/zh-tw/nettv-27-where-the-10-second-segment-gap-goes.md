> 系列第 27 篇。上一篇把「穩態 14.2fps」歸因為源本身只有 14.6fps，本篇用 PTS 把這條結論**推翻**了，然後把真正的 10 秒黑洞拆成兩張賬單。

## 一、先翻案：源是 25fps，不是 14.6fps

上一篇的算法是「一段 155 幀 ÷ 段間隙 10.6s = 14.6fps」。問題出在分母：**段間隙是牆鍾，不是段內容時長**。要拿真幀率，只能問碼流自己。

於是寫了 `nalcount.c`：按 188 字節切包，在 PUSI 處解析 PES 頭取 PTS，用「AU 數 ÷ PTS 跨度」算真幀率，同時用「平均 PTS 間隔」交叉驗證。瀘縣源一個分片的實測：

```
packets=14034 pes=150 au(pts)=150
nal: idr=5 nonidr=145 sps=5 pps=5 sei=5 aud=150
pts_span=5.960s  fps_by_span=25.00
avg_pts_delta=3600.00 ticks  fps_by_delta=25.00
```

**150 幀 / 5.96s / PTS 間隔恆定 3600 ticks（90000/25）—— 真 25fps，鐵證。** 兩種算法互相印證，不存在丟幀或 VFR。

也就是說：我們把 5.96 秒的內容播了 10.3 秒，**慢的從來不是源，是我們**。「提幀到 25fps」重新變成物理可達的目標。

順帶一個坑：`mplayer -identify` 報的 `ID_VIDEO_FPS=25.000` 對 MPEG-TS 基本是容器默認值，不能當證據（它對錢江、CloudFront 也報 25.000，但那兩路的平均 PTS 間隔是 8359/8704 ticks ≈ 10.8fps，明顯是另一回事）。

六個源的普查結果：

| 源 | 分辨率 | AU/段 | PTS 跨度 | 真幀率 |
|---|---|---|---|---|
| 瀘縣 | 1920×1088 | 150 | 5.96s | **25.00** |
| 上虞 | 1920×1088 | 200 | 7.96s | **25.00** |
| 松潘 | 1920×1088 | 270 | 10.76s | **25.00** |
| 錢江 | 1920×1088 | 200 | 7.92s | 25.13（間隔不均） |
| CloudFront | 960×544 | 100 | 3.96s | 25.00 |
| 北方廣電 | — | — | — | 拉不到列表 |

## 二、10.3 秒的賬單

給 dl 循環的每一段都裝上計時（`g_dl_t_pick / pref / af / hist`），現網默認配置跑一輪：

| 段 | 段間隙 | 選段 | 預取(含下載) | 音頻 | 下載解析 | 入池 |
|---|---|---|---|---|---|---|
| 2 | 10439ms | 4983ms | 5236ms | 5231ms | 212ms | 6ms |
| 3 | 10470ms | 5075ms | 5172ms | 5167ms | 214ms | 6ms |
| 4 | 10402ms | 4980ms | 5211ms | 5206ms | 213ms | 6ms |

（累計計時器，逐行相減即為單段值。）

結論非常乾淨：**下載 0.21s、入池 6ms，加起來不到 3%**；10.3 秒裡 5.2 秒是 `audio_feed()`、5.0 秒是 `pick_seg()`。

`audio_feed()` 為什麼是 5.2 秒？它把整段 2.6MB 的 TS 寫進一個 64KB 的 fifo，mplayer 按實時 1x 排空——**這不是背壓，這是物理排空時間**，等於段內容時長。而它偏偏寫在了「選下一段 + 預取」的**前面**，於是每一輪循環都被音頻鎖死。

這裡有個容易上當的地方：`NETTV_AF_RETRY` 只限制「停滯重試次數」（默認 300 次 × 20ms），治不了整段排空。實測把它調成 1，幀率 16.0 → 19.0，段間隙只掉到 8.1s；再把 mplayer 臨時改名讓音頻徹底失效，段間隙**還是 8.1s**、幀率還是 19.0。這兩組對照說明：音頻只佔 2.2s 的停滯，5.2s 的主體必須靠改結構，不能靠調參。

## 三、修法：異步音頻泵

思路很簡單——dl 解析完一段之後，這份 raw 文件對它已經沒用了，`rename` 給一個子進程獨佔，讓子進程慢慢喂，dl 立刻進下一輪：

```c
static void audio_feed_async(const char *path)
{
    if (g_afifo < 0) return;
    if (g_aud_pump > 0) {                 /* 非阻塞收屍; 還活著就跳過本段 */
        int st = 0;
        if (waitpid(g_aud_pump, &st, WNOHANG) == 0) return;
        g_aud_pump = -1;
    }
    snprintf(sp, sizeof sp, "%s.aud", path);
    rename(path, sp);                     /* dl 已解析完, 交給音頻子進程 */
    pid_t p = fork();
    if (p == 0) { signal(SIGPIPE, SIG_IGN); audio_feed(sp); unlink(sp); _exit(0); }
    if (p > 0) g_aud_pump = p;
}
```

三個細節不能省：

1. **必須 `waitpid(WNOHANG)` 收屍，不能用 `kill(pid,0)` 判活**。殭屍進程的 `kill(pid,0)` 照樣返回 0，會讓泵永遠被判定為「還活著」，音頻從第二段起就再也不餵了。
2. **必須 `rename` 而不是直接 fork 讀原路徑**：2 槽輪轉，子進程還在慢慢讀的時候原路徑會被下一段下載覆蓋，讀出來的就是半截段。
3. 上一段沒喂完就跳過本段——**視頻優先**，寧可音頻有間隙也不讓音頻拖住供數。

實測（同源、同 95s、同二進制，唯一變量 `NETTV_AUDIO_ASYNC`）：

| 配置 | 段間隙 | 音頻 | 選段 | 穩態幀率 |
|---|---|---|---|---|
| 現網默認 | 10309ms | 5231ms | 4983ms | 15.2 |
| `AF_RETRY=1` | 8100ms | — | — | 19.0 |
| 音頻鏈路移除 | 8100ms | 0 | — | 19.0 |
| **異步音頻泵** | **8228ms** | **1ms** | 5104ms | **19.8** |

音頻那 5.2 秒被徹底抹掉（5231ms → 1ms），幀率 **15.2 → 19.8，+30%**。

## 四、剩下的 8.2 秒歸誰

異步泵跑完，賬單重排：**選段 5.1s + 下載 2.9s = 8.2s**，而段內容只有 5.96s。

- 下載 2.9s 是硬成本（2.6MB ÷ 約 900KB/s），而且已經是異步預取了，跟別的事重疊著。
- **選段 5.1s 是純浪費**，現在是頭號目標。`pick_seg()` → `hls_pick()` 拉一次播放列表，沒拿到新段就 `sleep(1)` 重試，最多 4 次——4 次重試 + 4 次列表拉取正好 5 秒左右。但日誌裡一條「無新段」都沒打，說明最後那次是成功的，即**每輪都要白等 3 次左右**。

為什麼明明落後於直播還在等新段？這是下一個待解問題：要麼播放列表的滑動窗口比想象中窄，要麼 `g_last_seg` 的比較邏輯在某個環節失效（比如 URL 帶 query 參數、重定向後 URL 變了）。下一步就是把 `hls_pick()` 的重試次數和每次拉列表的耗時分別打點。

## 五、這一輪的教訓

1. **別拿牆鍾當內容時長。** 上一條錯誤結論活了整整一輪，就因為「段間隙」這個名字起得太順手。凡是「X 秒」都要問一句：這是內容的秒還是我們耗掉的秒。
2. **調參的收益有天花板，改結構沒有。** `AF_RETRY` 從 300 調到 1 只拿回 2.2s，因為 5.2s 的主體是排空時間不是重試；把整段活挪出主循環才拿回全部。
3. **A/B 要兩個方向都做。** 只做「AF_RETRY=1」會得出「音頻背壓是主因」的錯誤結論；補一組「徹底關掉音頻」才發現它倆一樣，說明那個參數動的是別的東西。
4. **取證工具要能自證。** `nalcount` 同時給「跨度法」和「間隔法」兩個幀率，兩個對得上才敢拿去推翻前一輪的結論。
