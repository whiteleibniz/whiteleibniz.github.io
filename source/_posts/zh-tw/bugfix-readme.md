# Bug 修復歸檔

本目錄歸檔**每一次 bug 修復的說明文檔**。規則：每修復一個 bug，就在本目錄新增一份
`bugfix_<日期>_<序號>_簡述.md`，寫清「現象 → 根因 → 定位過程 → 解決辦法 → 驗證」。

## 隱私紅線（強制）

與 `AI工作流/README.md` 一致：**文檔、git 備註、歸檔文件中禁止出現真實 SSH 密碼、賬號、真實 IP**。
一律使用佔位符：`<設備IP>` / `<密碼>`。

## 命名規範

```
bugfix/
├── README.md                              # 本文件（約定說明 + 索引）
├── bugfix_20260922_01_mplayer視頻紅藍通道錯亂.md
├── bugfix_20260922_02_xxx.md
└── ...
```

- 文件名格式：`bugfix_<日期>_<序號>_簡述.md`
  - **日期**：修復完成日，`YYYYMMDD` 八位（如 `20260922`）。
  - **序號**：**當日**兩位遞增編號，從 `01` 起（如 `01`、`02`）。
  - **簡述**：中文，不加空格。
  - 示例：`bugfix_20260922_01_mplayer視頻紅藍通道錯亂.md`
  這樣文件名天然按時間排序，一眼看出修復先後，且不依賴 git 提交 SHA
  （文件名會改變提交自身的 SHA，存在先有雞還是先有蛋的循環依賴，故不採用）。
- 序號一經分配不復用、不重排；修復被回退也保留文檔，在正文標註「已回退」。
- 新增後**必須**在本文件末尾的「索引」表裡補一行。
- 若該項目有 git 倉庫，**建議**在文檔頭部「關聯提交」一行填寫修復該 bug 的提交短 SHA
  （提交後再回填，不影響文件名）。

## 文檔結構（每篇必含）

| 章節 | 內容要求 |
|---|---|
| **現象** | 用戶/測試看到的外部表現。只寫看得見的事實，不寫猜測 |
| **影響範圍** | 哪些功能/頁面/進程受影響；哪些**不受**影響（避免誤傷無辜） |
| **根因** | 機制層面講清"為什麼會這樣"。要能回答"為什麼偏偏是這個字節/這一步" |
| **定位過程** | 怎麼一步步逼近真相的：**關鍵實驗**、排除掉的錯誤方向、以及**為什麼先前判斷是錯的** |
| **解決辦法** | 具體改了哪些文件、哪幾行、為什麼這樣改。附代碼片段 |
| **驗證** | 可復現的驗證步驟 + 實際結果。**顏色/顯示類問題必須有人眼確認** |
| **經驗教訓** | 可遷移的方法論或踩過的坑（這一節最容易被省略，但最有複用價值） |

## 寫作紀律（承自本項目既有教訓）

1. **區分"假設"與"實測"**：只把人眼/日誌/探針實測的結論寫成事實；推理一律標註為推理。
2. **自證循環不算驗證**：抓數據→按假設解碼→"看起來對"不是證據。顯示類問題必須人眼閉環。
3. **記錄失敗的方向**：把走錯的路也寫下來，否則後來者會重走一遍。
4. **命令可復現**：定位/驗證命令要能直接粘貼執行（注意替換佔位符）。
5. **不寫"已修復"了事**：必須寫清驗證條件與結果，未完全驗證的明確標出。
