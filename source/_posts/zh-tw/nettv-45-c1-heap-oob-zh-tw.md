> 系列第 45 篇。上一輪把崩潰定性成「累積漂移」，工具造好了，設備卻一直沒上電。
> 這一輪換了個審計維度——不看等待，看分配——結果抓到的不是廠商庫，而是我們自己替身層裡
> 6 行從來沒被讀過的賦值。

一個查了半個月的「週期性 SIGSEGV」，最後落在自己程式的 6 行賦值上。這 6 行不是 `memcpy`，所以兩輪「逐處審計 memcpy 邊界」都沒掃到它。這篇記錄方法上的那個盲區，以及怎麼用二進位反組譯把「物件到底多大」這件事釘死。

## 背景：症狀與既有結論

設備上的網路電視播放器（展訊 SC9832A，VSP 硬體解碼）穩定播放時，約每 3 分鐘死一次 SIGSEGV，影格率正常、與 IDR 大小無關；崩潰位址出現 `0x747474` 這種「像 ASCII」的值。先前已排查掉的方向：

- 訊號處理程式本身寫過（帶 `sigaltstack`、純 `write` 避免持鎖死鎖），但從沒被執行到；
- 我們自己的 9 處 `memcpy` 逐處判過邊界，全部有界；
- 渲染池、執行緒訊號遮罩、fork 時機都做過 A/B，均非主因。

剩下的假說是「累積漂移」：某個每幀都會走到的路徑在緩慢消耗資源。問題是——**哪個路徑**。

## 方法：把「配置／釋放配對」做成函式級審計

上一輪審的是「等待／逾時」，這輪換成配置行為。工具思路很樸素：

1. 用 `.dynsym` 裡的 FUNC 符號（帶 size）取得精確函式邊界；未匯出的靜態函式用 `push {…, lr}` 前言補齊（stripped 的庫裡這是唯一可靠的分界）；
2. 用 `.plt` + `.rel.plt` 建 PLT 位址 → 符號名對映，抓函式體內 `bl/blx` 到 `malloc/calloc/new/mmap` 與 `free/delete/munmap` 的呼叫點；
3. 判斷該呼叫點是否落在函式內某個往回跳的分支所構成的迴圈體內（per-iteration 配置的氣味）；
4. 回溯 12 條指令還原 `r0`（含 `movw/movt` 拼裝）＝ 申請大小；
5. 以逐幀入口（`onQueueFilled`、`H264DecDecode` 等）為根建呼叫圖，BFS 標注「從逐幀路徑是否可達」。

兩道防止自我欺騙的門檻：

- **覆蓋率必須印出來**。線性反組譯遇到常數池會中斷，覆蓋率不足時工具直接標 `INCOMPLETE`——否則「沒找到配置點」會被讀成「沒有配置」。
- **陰性對照**。暫存器層那個庫的匯入表裡根本沒有 `malloc`，工具必須回報「堆積配置點 0 個」，而不是「無洩漏」。這是給自己設的反向測試。

## 關鍵一步：物件到底多大

審計報告裡有一行不起眼的東西：某個回呼裡有 `_Znwj`，還原出來的 `r0 = 0x1c`。

`0x1c` = 28。這 28 位元組隨後被交給 `MemoryHeapIon` 的建構函式。於是順著反組譯把 4 個建構點全看了一遍，3 個都是 `mov r0, #0x1c; bl _Znwj`——**這個物件就是 28 位元組**。

回到我們自己的程式：為了繞開 ION 配置失敗，播放器裡把 `MemoryHeapIon` 的建構函式整個替身掉了，替身裡按「欄位偏移表」往物件上填值：

```c
*(void    **)(o +  0) = ...;
*(int      *)(o +  8) = ...;
*(unsigned *)(o + 12) = ...;
*(int      *)(o + 16) = ...;
*(unsigned *)(o + 20) = ...;
*(void    **)(o + 24) = ...;   /* 28 位元組到此為止 */
*(unsigned *)(o + 28) = handle;   /* 越界 1 */
*(int      *)(o + 32) = fd;       /* 越界 2 */
*(int      *)(o + 36) = buf_fd;   /* 越界 3，實際寫到 o+39 */
```

**每次建構就越界寫 12 位元組。** 而這三個欄位沒有任何讀取點——`getBase()` 讀 +24，`getHeapID()` 讀 +16，`get_phy_addr_from_ion()`／`get_iova()` 讀 +8/+12/+16/+24。三條賦值是純死寫。

呼叫頻率決定量級：mbinfo 緩衝區大約每 2 幀申請一次，25fps 下每秒 12.5 次，3 分鐘約 2200 次越界寫，每次都踩在緊鄰 malloc 區塊的 12 位元組上（區塊標頭或鄰塊資料）。

## 為什麼兩輪 memcpy 審計都沒抓到

這是這次最值得記的一點。

「越界寫」在直覺裡等於 `memcpy` 長度算錯。於是審計就按 `memcpy` 去審：逐個看長度變數、看來源緩衝大小、看有無 `min()` 截斷。這個做法對**資料搬運**有效，對**固定偏移的結構體寫入**完全失效——`*(int*)(o + 36) = fd;` 裡沒有任何長度變數，它「看起來」只是給某個欄位賦值，而正確性問題藏在「這個物件真實有多大」這個外部事實上。

所以審計法則要補一條：**按「寫入偏移 vs 物件真實大小」審，不能只按「有沒有長度參數」審。** 物件大小往往不在本檔案裡——它由庫裡的 `new(N)` 決定，必須反組譯去取。

順帶一個反直覺的結論：這 6 行從程式的第二個版本就存在，一路活到被部署的版本，中間經歷過多次「記憶體安全專項檢查」。它不是隱蔽，而是**檢查項目不覆蓋**。

## 兩條互斥假說，一次實驗分流

至此有兩條候選，它們的預測互相排斥：

| 假說 | 預測 |
|------|------|
| A：每幀位元組洩漏 | CMA 可用量線性下降，151s 對應約 1.94 KB/幀，186s 約 1.58 KB/幀（按 7 MB 池、25fps 反推） |
| B：堆積中介資料被踩壞（本文） | **CMA 可以不降也照樣崩**，崩潰時機取決於配置器何時用到被踩的區塊 |

這很重要：先前的排查都在盯「記憶體餘量」，而 B 假說根本不消耗餘量。如果只採 CmaFree，B 假說永遠不會被看見。

所以下一步只做一件事：刪掉那 3 行 ×2 處（共 6 行），編譯，跑滿 4~5 個故障週期。崩潰消失即定因；間隔顯著變長說明是真因之一；完全不變則本假說被否，回到 CMA 斜率分支。

順便說明為什麼沒有順手改別的東西：這段程式上還壓著一個「訊號遮罩淨化版」的改動，兩者混在一次實驗裡，出結果也無法歸因。**一次只動一個變數**這條紀律，價值不在謹慎，而在讓結論可重複使用。

## 小結

- 靜態審計的產出不一定是「廠商庫有問題」，也可能是「自己的替身層有問題」——而替身層恰恰是最容易被當成「已經驗證過」的部分。
- 函式級符號 + 覆蓋率自證 + 陰性對照，這三件是讓靜態報告能當證據用的最低配置。
- 崩潰位址長得像 ASCII（`0x747474`）不代表它就是字串，別順著這個直覺走太遠；本輪也沒能證明它的直接來源。
