# bugfix 16 — GBA「改完遊戲都進不去了」：把「超時補刀」放進收屍線程 = 給遊戲設了 600ms 壽命

- **日期**：2026-09-23
- **影響範圍**：`lv_pages/gba_game_page.c`（GBA 遊戲應用，進遊戲 100% 失敗）
- **嚴重級別**：P0（功能完全不可用，且是我自己上一輪改動引入的迴歸）
- **關聯**：bugfix 09~15（同一退出鏈路的連續迭代）
- **回滾點**：`lv_pages/gba_game_page.c.bak_exit2`（第 14 篇狀態：能進遊戲、偶發卡畫面）

---

## 1. 現象

用戶反饋：**「改完遊戲都進不去了」**。按確認鍵選中 ROM 後，遊戲畫面「閃一下」就回到列表（有時連列表也一起退回桌面），看起來像"根本進不去"。

注意與上一篇（bugfix 15）的區別：

| | bugfix 15 | bugfix 16（本篇） |
|---|---|---|
| 現象 | 能進遊戲、能玩，**退出時偶發卡在遊戲畫面** | **進遊戲就秒退**，根本沒得玩 |
| 玩家感受 | "偶爾不正常" | "完全不能用" |

**這是我在修 15 的過程中引入的新迴歸**——"越改越亂"的來源。

---

## 2. 取證（決定性日誌）

`/tmp/lvgl_demo.log` 中一次"進遊戲"的完整序列：

```
[HW Key] code=115 value=1 -> ENTER          ← 用戶按確認鍵
[gba] 封面: .../Advance Wars (USA) (Rev 1).png
[system] LVGL draw paused                    ← 進入遊戲
[Key Thread] 臨時按鍵攔截器已啟用。
[Key Thread] EVIOCGRAB 請求釋放
[Key Thread] EVIOCGRAB 已釋放(交給外部進程)
[Key Thread] EVIOCGRAB 請求恢復獨佔           ← ★ 緊接著就恢復了
[gba] fb 兜底翻回第0頁(前端退出時停在第 1 頁)   ← ★ 前端已經死了
[system] LVGL draw resumed[nav] key=27
[pm] 頁面 'gba_game' 離場
```

**兩個決定性事實**：

1. `EVIOCGRAB 已釋放` 與 `EVIOCGRAB 請求恢復獨佔` 之間**沒有 `[miniretro]` 的任何啟動日誌**——而正常進遊戲這一段必然有 12 行（映射 fb、打開 5 個 evdev、加載 core、加載 ROM…）。
2. 順序上"恢復獨佔 + 兜底翻頁"緊跟在"釋放獨佔"之後，說明**子進程已經退出**，且退得極快。

→ **前端不是自己退的，是被父進程殺掉的。**

---

## 3. 根因

上一輪（bugfix 15）我把收屍邏輯從「阻塞 `waitpid`」改成了：

```c
/* ★ 錯誤寫法（bugfix 15 引入） */
bool reaped = false;
for(int i = 0; i < 60; i++) {            /* 最多 600ms */
    pid_t r = waitpid(pid, &status, WNOHANG);
    if(r == pid) { reaped = true; break; }
    usleep(10 * 1000);
}
if(!reaped) {
    if(kill(pid, 0) == 0) kill(pid, SIGKILL);   /* ★ 把還在正常跑的遊戲殺了 */
    waitpid(pid, &status, 0);
}
```

**當時的動機是好的**：想給"前端掛死"留一個硬保證，同時不佔用按鍵線程。註釋裡甚至寫著"絕不設跑滿 N 秒就算退出的上限"——

**但這段代碼本身就是那個上限。** 判據從「子進程真的消失」偷偷變成了「600ms 到了」，於是：

> 用戶按確認 → 前端啟動 → 渲染第一幀 → **600ms 到了 → 父進程補 SIGKILL → 遊戲"閃一下就沒了"**。

而且這解釋了為什麼"第一次進有時能看到一幀畫面"——前端啟動 + 渲染第一幀大約就在 600ms 上下，運氣好能出一幀。

**這條坑在項目記憶裡被記過**（"六條已被證偽的路"第 ① 條：給等待循環設"跑滿 N 秒就算退出"的上限），我明知故犯。

---

## 4. 修復

**原則：回到"判據只有一個硬事件——子進程真的消失"，把"等待"和"補刀"從收屍路徑上徹底剝離出去。**

| # | 位置 | 改動 |
|---|---|---|
| A | 新增 `gba_kill_later()` | **專職補刀線程**：唯一持有"睡 600ms 再補 SIGKILL"的地方。與 wait 線程持同一把鎖、用 `kill(pid,0)` + `child_pid` 一致性校驗，避免誤傷複用 pid |
| B | `gba_wait_thread()` | 刪除 600ms 輪詢超時，**恢復為阻塞 `waitpid`（無上限）**——與 FC 頁 `fc_wait_thread` 逐行相同 |
| C | `gba_exit_to_list()` | 不在按鍵線程 `sleep`（會漏鍵把本頁彈掉），改為 `kill(SIGTERM)` + 起補刀線程後**立即返回**去吞鍵 |
| D | `gba_on_destroy()` | 不變（主線程罕見路徑，`SIGTERM` + 300ms 輪詢保護 `.sav` 落盤） |

前端 `miniretro_gba.c` 本次**未改動**。

**補刀線程的關鍵實現**：

```c
static void *gba_kill_later(void *arg)
{
    pid_t pid = (pid_t)(intptr_t)arg;
    usleep(GBA_KILL_TIMEOUT_MS * 1000);

    pthread_mutex_lock(&s_gba.lock);
    bool alive = (s_gba.child_pid == pid);      /* wait 線程收屍後會置 -1 */
    if(alive && kill(pid, 0) == 0) {
        printf("[gba] 前端 %dms 未退出, 補 SIGKILL pid=%d\n", GBA_KILL_TIMEOUT_MS, (int)pid);
        kill(pid, SIGKILL);
    }
    pthread_mutex_unlock(&s_gba.lock);
    return NULL;
}
```

**為什麼鎖必須包住判斷與補刀**：wait 線程把 `child_pid` 置 `-1` 也在同一把鎖內。若 wait 已收屍（`child_pid != pid`），補刀線程直接跳過 → 不會對已回收、可能被複用的 pid 下手；若還能取到 `child_pid == pid`，說明進程確實還沒被收屍、確實活著 → 補刀正當。

## 5. 自測（本次由 AI 實測通過）

**方法**：設備上注入 uinput 按鍵導航（`LEFT×2 → DOWN×3 → ENTER×2`，走 `usb_map` 路徑）進入《Advance Wars》，然後檢查前端存活。

| 檢查項 | 結果 |
|---|---|

| fb 前臺頁 | `yoffset=1280`（頁 1）→ **前端在正常翻頁渲染** |
| 日誌誤殺痕跡 | `grep -c '未退出, 補 SIGKILL'` = **0** |

**結論**：600ms 誤殺已消除，遊戲可正常進入並持續運行。

## 6. 「FC 為什麼流暢、GBA 為什麼不行」——差異表

這是用戶反覆問的核心問題，也是這條鏈路反覆出錯的根源。

| 維度 | FC（fceumm） | GBA（mgba） | 後果 |
|---|---|---|---|
| **fb 多緩衝頁翻轉** | **不翻頁**，固定寫第 0 頁 | **每幀 `FBIOPAN_DISPLAY` 在 0/1 頁間切** | GBA 退出必須**把頁翻回 0**，否則 LVGL（只畫頁 0）畫的界面看不見 → 屏幕定格遊戲畫面 |
| **退出時落盤量** | `.sav` 小，收尾快 | `.sav` 可達 32~128KB，真寫 SD 卡可能數百 ms | GBA 需要更長的"等它收尾"時間 |
| **等待放哪兒** | 按鍵線程裡 `usleep(120ms)` 就夠（前端 ~30ms 就退） | 若同樣睡在按鍵線程，**600ms 期間沒人讀 event0** → 堆著的事件漏給 LVGL 變成"返回"鍵 → 本頁被彈掉 | GBA 必須把等待挪出按鍵線程 |
| **收屍判據** | 阻塞 `waitpid`，從來沒有超時 | 曾被我加上 600ms 超時 → 變成"給遊戲設壽命" | **這就是本篇的 P0** |
| **前端是否碰 fb 殘留** | 不碰 | 翻頁 + （曾）整頁 memcpy 定格 | 決定"退出後畫面由誰負責" |

**一句話**：FC 的前端**不碰 framebuffer 的結構**（不翻頁、不拷頁），所以它的退出只需要"殺進程 + 等收屍"；GBA 的前端**改了 framebuffer 的顯示狀態**（前臺頁），所以退出時**必須有人負責把它改回去**——多出來的這一份責任，如果圖省事塞進"收屍線程"或"按鍵線程"，就會分別炸出"遊戲進不去"和"退出卡畫面"。

## 7. 教訓 / 反模式

**新增反模式（已寫入 `child-exit-hang-diagnosis` skill）：**

> **把「超時補刀」寫進收屍線程 = 變相給子進程設壽命。**
> 看起來是"給掛死留硬保證"，實際把判據從「子進程真的消失」偷偷換成了「N 毫秒到了」。
> 症狀很有迷惑性：**遊戲/程序"閃一下就沒了"、"進不去"**，而日誌裡收屍線程一切正常。
> 正解：**補刀必須掛在一個"只在收到退出請求後才存在"的專職線程上**，收屍路徑永遠只有一句
> 無上限的阻塞 `waitpid`。

**其他：**

1. **"判據只有一個硬事件"這條鐵律必須落到代碼上，不能只寫在註釋裡。** 本次我的註釋寫著"絕不設上限"，代碼卻在設上限。
2. **迴歸的代價高於不修。** bugfix 15 為了解決"偶發卡畫面"（低概率、可容忍），引入了"完全進不去"（100%、不可用）。**修概率性問題時，改動必須比問題本身更保守。**
3. **`EVIOCGRAB 請求釋放` 到 `請求恢復獨佔` 之間的距離**是一個很好用的診斷量：太短 = 子進程被殺了（而不是自己退的）；太正常 = 前端正常在跑。**建議把這條寫進排查清單。**
4. 靜態校驗比日誌更快：`grep -c 'i < 60'`、`grep -c 'bool reaped'` 歸零就能確認"超時邏輯已徹底刪除"。
