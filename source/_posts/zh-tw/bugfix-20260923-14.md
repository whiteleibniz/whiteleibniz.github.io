# bugfix_20260923_14 — GBA 退出後"卡死"（頁翻轉殘留：屏幕定格在遊戲畫面）

- **日期**：2026-09-23
- **現象**：GBA 遊戲退出後屏幕**不黑**（顯示遊戲畫面），但**界面永遠回不來、按鍵像失靈**，
  只能重啟應用。用戶描述為"不黑屏了，直接卡死"。**偶發** —— 有時正常，有時必卡。
- **影響面**：`lv_pages/gba_game_page.c`、`extern/miniretro/miniretro_gba.c`（GBA 前端）
- **是否影響 FC**：**不影響**（FC 用原版 `miniretro`，它從來不翻頁）

---

## 1. 背景：兩個驅動對"頁"的理解不一致

設備 framebuffer 有 3 個虛擬頁（`yres_virtual=3840` = 3×1280）。

| 誰 | 怎麼用 fb0 |
|---|---|
| **LVGL**（`lv_linux_fbdev`） | **只用 mmap 基址繪製 = 永遠寫第 0 頁**；`vinfo.yoffset` 在 init 時設 0 後再不改；源碼裡 **`FBIOPAN_DISPLAY` 零命中** |
| **GBA 前端**（`miniretro_gba`） | 用 `FBIOPAN_DISPLAY` **雙緩衝頁翻轉**消撕裂 → 前臺在**第 0/1 頁之間來回切** |

**關鍵推論**：只要退出時前臺停在第 1 頁，**LVGL 畫什麼都看不見** ——
因為 LVGL 永遠往第 0 頁寫，而屏幕顯示的是第 1 頁。

## 2. 根因

1. 前端每渲染一幀就翻一次頁，**前臺頁是 0 還是 1 取決於"退出那一刻"**。
   實測抓幀：啟動遊戲後依次測到 `yoffset=1280 → 0 → 1280 → 1280 → 1280`（同一局遊戲內）。
2. 前端退出時本會在 `fb_restore()` 裡翻回第 0 頁（**定點實測：SIGTERM 後 0.4s `yoffset` 由 1280 變 0**），
   但父進程 `gba_exit_to_list()` 在 **SIGTERM 後 120ms 就補 `SIGKILL`**；
   而前端收尾裡包含 `core_deinit()` —— **把 .sav 電池存檔落盤到 SD 卡**，寫卡慢時遠超 120ms。
3. 一旦被 SIGKILL 打斷 → **翻頁沒做 → 前臺永久停在第 1 頁 → 屏幕定格遊戲畫面** → "卡死"。

> 這解釋了**為什麼它偶發**：存檔早就在頁緩存裡 → 收尾 <120ms → 正常；
> 真要寫 SD 卡 → 被殺 → 卡死。

## 3. 證據

| 證據 | 內容 |
|---|---|
| 源碼 | `lv_linux_fbdev.c:174 dsc->vinfo.yoffset = 0;`（此後不改）、`grep -n 'PAN'` **零命中** |
| 抓幀 | 圖 `shots/final/01..10`：運行期 `yoffset` 在 0/1 間切換 |
| 定點實驗 | 單獨跑 `miniretro_gba`：運行中 `yoffset=1280` → SIGTERM 後 0.4s **→0**（說明前端收尾**能**翻頁，問題只在"有沒有機會走到"） |
| 殘留取證 | `shots/guard/01`：重啟應用後抓到的"桌面"其實是**頁1 裡的上一局遊戲畫面**（`yoffset=1280`）—— 正是卡死的物質形態 |
| 排除項 | 前端退出日誌完整（`收尾完成 t=30.8ms`）、無殭屍、無崩潰循環、`hardware_keys` 的 `EVIOCGRAB` 冪等正常 |

## 4. 修復（三層兜底，全部"冪等 + 只在異常時才有動作"）

### 4.1 前端 `miniretro_gba.c` — `fb_restore()` 改為**無條件**翻回第 0 頁
去掉"先讀 `yoffset`、非 0 才翻"的分支：翻到第 0 頁本身是冪等操作，
判斷只會多一個可能出錯的分支（雖然實測本驅動回讀可靠，但沒必要依賴）。
失敗/翻不動時打印 `★ 翻回第0頁失敗`，便於現場定位。

### 4.2 GBA 頁 — 新增 `gba_reset_fb_page()`，**父進程自己兜底翻頁**
打開 `/dev/fb0`，若 `yoffset != 0` 就 `FBIOPAN_DISPLAY` 到 0。
**無論前端有沒有被打死都成立** —— 這是治本的一層。在 **3 處**調用：

| 調用點 | 作用 |
|---|---|
| `gba_wait_thread()` 恢復段（`set_lvgl_paused(false)` **之前**） | 遊戲退出 → 恢復 UI 前先保證可見頁 = 第 0 頁 |
| `gba_on_destroy()` | 頁面離場時再兜一次 |
| `gba_on_create()` | 進頁面先歸零（若上次異常留下頁1 殘留） |

### 4.3 補刀時間 120ms → 600ms
給"落存檔 + 翻頁"留出時間。**補刀必須保留**（子進程真掛死時，沒有 SIGKILL 會讓阻塞的
`waitpid` 永不返回）。這 600ms 只花在**按鍵線程**裡，不拖慢 UI 恢復。

### 4.4 恢復重繪後補一次 `lv_refr_now(NULL)`
只 `invalidate` 的話要等下一輪 `lv_timer_handler` 才真正出圖；立即刷一幀，
消除"標誌被消費、畫面卻沒畫回來"的窗口。

| 項 | 結果 |

## 6. 反模式記錄（本次新增，已併入 skill）

- **多緩衝頁翻轉必須"退出時歸位"**：只要有一個消費者（LVGL）不做翻頁、
  而另一個生產者（外部播放器/模擬器）做翻頁，**退出時不清算前臺頁 = 永久黑屏/定格**。
  且**歸位責任不能只交給會被強殺的子進程** —— 父進程必須能自己兜底。
- **給子進程的 SIGKILL 時限要考慮它的落盤開銷**（存檔/截圖/日誌刷盤），
  否則"以為在防掛死，實際在製造故障"。

## 7. 遺留

- 退出到恢復 UI 仍有 ~400ms（內核回收 evdev fd 的固有開銷），**刻意保留**（與 FC 一致）。
- 本文件描述的三層兜底中，只有"前端無條件翻頁"需要重編前端；另三層都在頁面側。
- 若將來給 FC 頁也上雙緩衝（當前 FC 前端不翻頁、無此問題），**必須同時搬這三層兜底**。
