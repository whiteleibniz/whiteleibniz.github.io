上一篇把「卡」從 0.08fps 抬到 6.3fps（**約 80 倍）之後，我一度以為剩下的就是硬解本身的極限——日誌裡白紙黑字寫著「VSP 單幀解碼 43ms，硬件上限 ≈23fps」，監控採樣**也說 fb_render 要 33ms。按這個賬算，25fps 天花板碰不動了。

但那是對照安卓的表現後不甘心又回頭算的一筆賬：**43ms 的「解碼」裡，廠商庫自己報硬件只花了 14ms**。剩下 29ms 是什麼？順著這個問題往下挖，最後挖出來的東西完全不在解碼器裡——是**我自己一行一行加上去的取證日誌**。

這篇記這個「日誌吃幀率」的完整定位過程：每幀 140ms 的構成表、O_SYNC 的實測代價、以及一個反直覺的結論——**為了抓掛死而加的 trace，讓每次解碼都慢了 3 倍**。

## 一、先有賬本，再開刀：每幀 140ms 拆成五段

不改代碼，先從上一輪的完整日誌裡摳時間。日誌裡本來就有足夠的埋點（AU 頭、DRIVE 返回、9c 等待退出、上屏時間戳），寫個 30 行的 awk 把它們按 AU 對齊：

| 段                 | 耗時         | 內容                                     |
| ----------------- | ---------- | -------------------------------------- |
| DRIVE（empty 同步投遞） | **43ms**   | 廠商庫自報：**硬件解碼 14ms**                    |
| snap_state + 診斷打印 | ~37ms      | 狀態快照 4 行 + pa_of 查詢                    |
| 讀幀 + 渲染           | ~62ms      | memcpy 3MB 暫存 + 簽名掃描 + fb_render（33ms） |
| 尾部                | ~21ms      | fill(out)×2 + REFILL kick + 狀態行        |
| **合計**            | **~140ms** | ≈7fps（監控 [STAT] 真值 13.2fps，多幀批處理拉回來的）  |

兩個數字當場就對不上：**廠商庫日誌明寫 `decRet: 0, 14ms`**，DRIVE 卻花了 43ms；監控已有采樣說 fb_render 33ms，但「讀幀+渲染」整段 62ms。多出來的時間都在哪？

## 二、第一個兇手：15ms 一次的 O_SYNC

先測閃存寫入的底價。設備 /tmp 在 eMMC 上，用 dd 循環各寫 60 次 128 字節：

```
fsync  60×128B: 1110ms   ← 每次約 18.5ms
普通寫 60×128B:  200ms   ← 每次約 3.3ms（含 fork/exec）
```

然後數一下熱循環裡到底有多少次同步寫。這個項目為了「掛死時 stdout 全丟、相位日誌必須活」，有兩套日誌都帶 `O_SYNC`：

- `tr_line`：每次 DRIVE 前後各寫一行 vsp_trace.log——**每次投遞 2 次，每幀 6 次以上，而且默認是開的**。它是 10-19 為抓「第二個 IDR 掛死」加的，寄存器 MMIO 讀（那次內核崩的真兇）後來已經默認關了，但**寫文件這件事忘了關**。
- `phx`：REFILL_OUT 每路 2 行，加上每 AU 必觸發的 kick 補隊列，每幀 3~5 次。
- `ph`：段頭一行。

**每幀約 11 次 O_SYNC**。按 15ms 算就是 165ms——比一整幀的時間還多；就算 eMMC 對小寫入有合併、實際按 3~~5ms 算，也是每幀 30~~55ms。這把「解碼 43ms」直接腰斬再腰斬。

最諷刺的點：`tr_line` 的註釋裡寫著它是為了定位「掛在哪個 DRIVE」而加的。但它自己就是那個讓 DRIVE 變慢的東西——**取證手段改變了被取證的系統**。這個項目裡這已經是第三次了：調試代碼打亂 VSP 狀態機導致內核崩、ptsync 為治卡而加的限速器變成卡的放大器、O_SYNC trace 為抓掛死而拖慢每一幀。套路完全一樣。

## 三、動手：一個變量——「診斷默認關」

按項目鐵律一次只改一個變量，這輪的改動就只有一句話：**熱循環診斷全部默認關，env 可恢復**。

```c
/* tr_line: 默認從「開」翻成「關」，NETTV_TRACE=1 才開 */
if (!(e && e[0] == '1')) { g_tr_off = 1; return; }

/* phx / snap_state / [r%04d] / AU頭 / DRIVE返回 / [9c等] 統一走 kdiag_on() */
static int kdiag_on(void) {
    if (g_kdiag < 0) {
        const char *e = getenv("NETTV_KDIAG");
        g_kdiag = (e && *e && *e != '0') ? 1 : 0;
    }
    return g_kdiag || vlog_on();
}
```

同時補了一套**零 I/O 開銷的分段聚合計時器**（每 200 AU 打一次均值）：牆鍾、段循環、snap、讀幀、渲染。診斷關了，賬不能也跟著關——不然下一輪又要重新考古。

```c
{ long _pw = sys_time_ms();
  if (p_au_prev) { g_t_wall += _pw - p_au_prev; g_t_n++;
      if (g_t_n % 200 == 0)
          P("  [perf] AU#%d 均值: 牆鍾=%.1f 段循環=%.1f snap=%.1f 讀幀=%.1f 渲染=%.1f (ms)\n", ...);
  }
  p_au_prev = _pw; }
```

新二進制 128256 字節（舊版 128028 備份 .bak_1020），構建部署走既有腳本。

## 四、驗證卡在一次「資源衝突」上

A/B 腳本早就寫好了（A=新默認，B=`NETTV_STAGE=0` 直讀 ION 省掉 3MB memcpy），兩輪卻都在 20 秒內崩成 `_exit(12)` 重啟循環。查進程才發現：**用戶桌面上正在放 TV**，VSP/ION 那口約 7MB 的池子被佔著，我的第二個實例一路退避重試都搶不到輸出 buffer。

兩次都是同一個退出碼 12（代碼裡寫死的「自管 ION 仍 0 路，拒絕把 IOMMU handle 交給 VSP」），結合「改動只碰日誌和計時器、昨天同時段無其他播放器時正常」兩點，可以排除迴歸。這給項目記憶又補了一條：**幀率實驗和用戶播放互斥**，ION 池是獨佔資源，起實驗前先確認沒有活著的播放會話。

所以定論分兩半：

- **已確鑿**：O_SYNC 每幀 11 次、15ms/次的底價、43ms 裡只有 14ms 是硬件（都有日誌實測支撐）。
- **待量化**：關掉之後端到端到底多少 fps、直讀 ION 能不能省掉那 20ms memcpy——腳本 `/tmp/v16_ab.sh` 已經放在設備上，用戶停播後一條命令的事。

按賬本估：關診斷約省 30~55ms，加直讀 ION 再省 ~20ms，140ms → ~65ms ≈ **15fps**；再往上的 25fps 要動 fb_render 的 33ms（NEON 化或用 VSP 縮放——已確認解碼端不支持，只能 CPU 側做）和 DRIVE 裡那 29ms 的廠商側開銷（我們的 Get_phy_addr hook 每幀重查 ion ioctl，fd→PA 可以做緩存）。

## 五、三條可帶走的經驗

1. **日誌不是免費的，同步日誌尤其不是。** 普通寫 3ms、O_SYNC 15ms 的閃存上，一行 trace 就是半幀解碼的時間。凡是掛在熱循環裡的日誌，先按幀數乘一下再留。
2. **「硬件上限」要先問是不是。** 廠商庫自己報的 14ms 和 DRIVE 外的 43ms 差了 3 倍，差的部分全在庫外——mbinfo 回調、phys ioctl、bind/unbind、雙份 FilledDone。性能定位要尊重廠商自己的計時，那是唯一不帶我們濾鏡的尺子。
3. **取證代碼要有「保質期」。** 為抓一個 bug 加的 trace，bug 修完那天就是它的退休日。更好的做法是加的時候就定好默認值和關閉開關，別讓臨時代碼變成默認路徑——這個項目已經用三次內核崩和一次幀率慘案交了學費。
