前面二十几篇基本都在跟"崩溃"和"帧率"缠斗，而且**绝大多数结论只跑过 60 秒**。60 秒能证明"能出帧"，证明不了"能一直看"。这次把窗口拉到 6 分钟，拿一批以前没量过的东西：ION 有没有缓慢泄漏、帧率会不会随时间衰减、热不热、以及一个意外翻案——**这台机器到底有几个核在干活**。

## 一、先看结论

| 指标 | 结果 |
|---|---|
| 连续播放时长 | 386 s（SIGTERM 主动收尾，非崩溃） |
| 回调数 / 真帧数 | 11700 / 5571 |
| 稳态帧率 | **14.4 fps**（`fps_x10` 全程 143~150，无衰减） |
| SIGSEGV | 0 |
| ION 客户端 | 播放中恒为 3，退出后归 0（**无泄漏**） |
| 温度 / 主频 | 27.7 ℃ / 1.3 GHz（**无热降频**） |
| 桌面 / framebuffer | 桌面存活，收尾后 fb 恢复正常 |

**长时间稳定性这项目前是达标的。** 剩下的真问题是：为什么长时间稳态只有 14.4fps，而 10-22 单段 60s 测试是 21.8fps。

## 二、翻案：sysfs 的 online 文件在骗人

10-22 我给"档 2（fork 渲染流水线）判负"找的根因是"在线 CPU 只有 2 核"。这次复查，读到的是更极端的东西：

```
/sys/devices/system/cpu/online  = [0]
/sys/devices/system/cpu/offline = [1-3]
/proc/cpuinfo 里 processor 只列了 1 个
```

照这个读数，机器是**单核**。但顺手写了个固定工作量的并行基准（每个进程 1.5 亿次整数乘加，用 `CLOCK_MONOTONIC` 自计时），结果完全对不上：

| 并发路数 | 各路耗时 |
|---|---|
| 1 路 | 2080 ms |
| 2 路 | 2080 / 2080 ms |
| 3 路 | 2080 / 2087 / 2110 ms |
| 4 路 | 2085 / 2095 / 2098 / 2135 ms |

**四路同时跑，每路耗时和单路几乎一样**——这是教科书级的"真·多核"曲线。单核上四路并行应该各花 8 秒左右。而且基准跑完再读 `online`，值变成了 `[0-3]`。

所以：

- **sysfs 的 `online`/`offline` 和 `/proc/cpuinfo` 在这台机器上都不可信**，它们是 hotplug 记账，不等于"有没有核在跑"。
- 判核数的可靠办法是**吞吐反推**，不是读文件。
- 顺带推翻 10-22 的定案：**档 2 判负不是因为核不够**，那个 -20% 得重新找原因（大概率是 3MB 帧在跨进程共享内存里来回搬 + 握手粒度）。

另外顺手试了热插拔写入，`echo 1 > cpu1/online` 返回失败、但状态确实在动——这个内核的 hotplug sysfs 行为很怪，**别拿它当实验变量**。

## 三、新账本：62.6ms 里有 21.6ms 不在任何计时器里

长时间稳态的 perf 行长这样：

```
[perf] AU#5400 均值: 墙钟=62.6 段循环=14.1 (bsOnMsg=14.1 睡眠=0.0[refill=0.0 aux=0.0] 9c等=0.0)
                     snap=0.0 读帧=2.5 渲染=23.8 (ms) pan=0
```

把已剖析项加起来：14.1 + 2.5 + 23.8 = **40.4ms**。墙钟 62.6ms，**差 21.6ms 没人认领**。对比单段文件模式（10-22）：墙钟 41.5ms ≈ 剖析和 41.3ms，一毫秒都不差。

差额只在"边下边播"的直播模式下出现，方向很明确：**卡在等数据上**。看 `rb_take`：

```c
static const unsigned char *rb_take(unsigned *len, unsigned char *flags, int *eof)
{
    for (;;) {
        unsigned w = g_rb->wpos, r = g_rb->rpos;
        if (r != w) { /* 取走一个 NAL */ return ...; }
        if (g_rb->dl_done) { *eof = 1; return 0; }
        usleep(2000);          /* ★ 环形缓冲空：2ms 粒度空转，不计入任何计时器 */
    }
}
```

环形缓冲一空就 2ms 一睡地轮询，这段等待**没有落到 `g_t_slp`/`g_t_read`/`g_t_ren` 任何一项里**，于是就成了"墙钟里凭空多出来的 21.6ms"。它占掉整帧时间的三分之一还多。

这也解释了稳态 14.4fps 的来源：供给侧（下载 + 解复用 + 写环）跟不上消费侧，消费者有三分之一的时间在空转等米下锅。**这时候再去优化渲染那 23.8ms，性价比已经不高了**——先让米下锅。

## 四、可以立刻做的三件事（按性价比）

1. **给 `rb_take` 的空转加计时**（新增 `g_t_wait`，10 行以内）。现在 21.6ms 是"推算"出来的，必须变成"量"出来的，否则后面所有优化都是在猜。
2. **量化 dl 侧供数能力**：单次 `curl` 拿一段的平均耗时、段间隙多长、rb 深度曲线。如果段间隙是大头，就把"提前拉下一段"做成默认（双槽预取的逻辑在，但没验过它在真实 CDN 上的效果）。
3. **把 `usleep(2000)` 的粒度降下来**（200~500us，或换成 futex/条件变量）。2ms 粒度意味着平均每次白白多睡 1ms，一帧里若空转十次就是 10ms。

## 五、方法论沉淀

- **"稳定"必须单独测**：60 秒的 A/B 和 6 分钟的连续播放是两件事。这次如果不是拉长窗口，就看不到"墙钟 55ms → 63ms"的爬升，也看不到 ION 恒 3 不涨这种好消息。
- **剖析项加不满墙钟，本身就是最大的线索**。账对不上时，先找"没被计时的路径"（阻塞读、轮询睡、隐式同步），别急着怀疑硬件。
- **不要用 sysfs/`/proc` 的记账值当硬件事实**。能反推就反推：固定工作量 + 不同并发度，看耗时拐点。
- 收尾继续用 SIGTERM + `usleep(800ms)` 排空 DMA，全程没碰过 SIGKILL，设备零重启。

## 六、下一步

先把 `g_t_wait` 计时加上重建一版，把 21.6ms 坐实；然后看它是不是真的大头——是的话，提帧的主战场就从"渲染"换到"供数"，目标 14.4 → 20fps 以上。
