上一篇把「卡」從 0.08fps 抬到 6.3fps（**約 80 倍**）之後，我一度以為剩下的就是硬解本身的極限——日誌裡白紙黑字寫著「VSP 單影格解碼 43ms，硬體上限 ≈23fps」，監控取樣也說 fb_render 要 33ms。按這個帳算，25fps 天花板碰不動了。

但那是對照安卓的表現後不甘心又回頭算的一筆帳：**43ms 的「解碼」裡，廠商函式庫自己回報硬體只花了 14ms**。剩下 29ms 是什麼？順著這個問題往下挖，最後挖出來的東西完全不在解碼器裡——是**我自己一行一行加上去的採證日誌**。

這篇記錄這個「日誌吃影格率（fps）」的完整定位過程：每影格 140ms 的構成表、O_SYNC 的實測代價，以及一個反直覺的結論——**為了抓卡死而加的 trace，讓每次解碼都慢了 3 倍**。

## 一、先有帳本，再開刀：每影格 140ms 拆成五段

不改程式碼，先從上一輪的完整日誌裡摳時間。日誌裡本來就有足夠的埋點（AU 頭、DRIVE 回傳、9c 等待退出、上螢幕時間戳記），寫個 30 行的 awk 把它們按 AU 對齊：

| 段 | 耗時 | 內容 |
|---|---|---|
| DRIVE（empty 同步投遞） | **43ms** | 廠商函式庫自報：**硬體解碼 14ms** |
| snap_state + 診斷列印 | ~37ms | 狀態快照 4 行 + pa_of 查詢 |
| 讀影格 + 渲染 | ~62ms | memcpy 3MB 暫存 + 簽章掃描 + fb_render（33ms） |
| 尾部 | ~21ms | fill(out)×2 + REFILL kick + 狀態行 |
| **合計** | **~140ms** | ≈7fps（監控 [STAT] 真值 13.2fps，多影格批次處理拉回來的） |

兩個數字當場就對不上：**廠商函式庫日誌明寫 `decRet: 0, 14ms`**，DRIVE 卻花了 43ms；監控已有取樣說 fb_render 33ms，但「讀影格+渲染」整段 62ms。多出來的時間都在哪？

## 二、第一個兇手：15ms 一次的 O_SYNC

先測快閃記憶體寫入的底價。裝置 /tmp 在 eMMC 上，用 dd 迴圈各寫 60 次 128 位元組：

```
fsync  60×128B: 1110ms   ← 每次約 18.5ms
普通寫 60×128B:  200ms   ← 每次約 3.3ms（含 fork/exec）
```

然後數一下熱迴圈裡到底有多少次同步寫。這個專案為了「卡死時 stdout 全丟、相位日誌必須活」，有兩套日誌都帶 `O_SYNC`：

- `tr_line`：每次 DRIVE 前後各寫一行 vsp_trace.log——**每次投遞 2 次，每影格 6 次以上，而且預設是開的**。它是 10-19 為抓「第二個 IDR 卡死」加的，暫存器 MMIO 讀（那次核心崩潰的真兇）後來已經預設關了，但**寫檔案這件事忘了關**。
- `phx`：REFILL_OUT 每路 2 行，加上每 AU 必觸發的 kick 補佇列，每影格 3~5 次。
- `ph`：段頭一行。

**每影格約 11 次 O_SYNC**。按 15ms 算就是 165ms——比一整影格的時間還多；就算 eMMC 對小寫入有合併、實際按 3~~5ms 算，也是每影格 30~~55ms。這把「解碼 43ms」直接腰斬再腰斬。

最諷刺的點：`tr_line` 的註解裡寫著它是為了定位「卡在哪個 DRIVE」而加的。但它自己就是那個讓 DRIVE 變慢的東西——**採證手段改變了被採證的系統**。這個專案裡這已經是第三次了：除錯程式碼打亂 VSP 狀態機導致核心崩潰、ptsync 為治卡而加的限速器變成卡的放大器、O_SYNC trace 為抓卡死而拖慢每一影格。手法完全一樣。

## 三、動手：一個變數——「診斷預設關」

按專案鐵律一次只改一個變數，這輪的改動就只有一句話：**熱迴圈診斷全部預設關，env 可恢復**。

```c
/* tr_line: 預設從「開」翻成「關」，NETTV_TRACE=1 才開 */
if (!(e && e[0] == '1')) { g_tr_off = 1; return; }

/* phx / snap_state / [r%04d] / AU頭 / DRIVE回傳 / [9c等] 統一走 kdiag_on() */
static int kdiag_on(void) {
    if (g_kdiag < 0) {
        const char *e = getenv("NETTV_KDIAG");
        g_kdiag = (e && *e && *e != '0') ? 1 : 0;
    }
    return g_kdiag || vlog_on();
}
```

同時補了一套**零 I/O 開銷的分段彙總計時器**（每 200 AU 打一次平均值）：牆鐘、段迴圈、snap、讀影格、渲染。診斷關了，帳不能也跟著關——不然下一輪又要重新考古。

```c
{ long _pw = sys_time_ms();
  if (p_au_prev) { g_t_wall += _pw - p_au_prev; g_t_n++;
      if (g_t_n % 200 == 0)
          P("  [perf] AU#%d 平均值: 牆鐘=%.1f 段迴圈=%.1f snap=%.1f 讀影格=%.1f 渲染=%.1f (ms)\n", ...);
  }
  p_au_prev = _pw; }
```

新二進位檔 128256 位元組（舊版 128028 備份 .bak_1020），建置部署走既有腳本。

## 四、驗證卡在一次「資源衝突」上

A/B 腳本早就寫好了（A=新預設，B=`NETTV_STAGE=0` 直讀 ION 省掉 3MB memcpy），兩輪卻都在 20 秒內崩成 `_exit(12)` 重啟迴圈。查行程才發現：**使用者桌面上正在放 TV**，VSP/ION 那口約 7MB 的池子被占著，我的第二個實例一路退避重試都搶不到輸出 buffer。

兩次都是同一個結束碼 12（程式碼裡寫死的「自管 ION 仍 0 路，拒絕把 IOMMU handle 交給 VSP」），結合「改動只碰日誌和計時器、昨天同時段無其他播放器時正常」兩點，可以排除迴歸。這給專案記憶又補了一條：**影格率實驗和使用者播放互斥**，ION 池是獨占資源，起實驗前先確認沒有活著的播放工作階段。

所以定論分兩半：

- **已確鑿**：O_SYNC 每影格 11 次、15ms/次的底價、43ms 裡只有 14ms 是硬體（都有日誌實測支撐）。
- **待量化**：關掉之後端對端到底多少 fps、直讀 ION 能不能省掉那 20ms memcpy——腳本 `/tmp/v16_ab.sh` 已經放在裝置上，使用者停播後一條命令的事。

按帳本估：關診斷約省 30~55ms，加直讀 ION 再省 ~20ms，140ms → ~65ms ≈ **15fps**；再往上的 25fps 要動 fb_render 的 33ms（NEON 化或用 VSP 縮放——已確認解碼端不支援，只能 CPU 側做）和 DRIVE 裡那 29ms 的廠商側開銷（我們的 Get_phy_addr hook 每影格重查 ion ioctl，fd→PA 可以做快取）。

## 五、三條可帶走的經驗

1. **日誌不是免費的，同步日誌尤其不是。** 普通寫 3ms、O_SYNC 15ms 的快閃記憶體上，一行 trace 就是半個影格解碼的時間。凡是掛在熱迴圈裡的日誌，先按影格數乘一下再留。
2. **「硬體上限」要先問是不是。** 廠商函式庫自己回報的 14ms 和 DRIVE 外的 43ms 差了 3 倍，差的部分全在函式庫外——mbinfo 回呼、phys ioctl、bind/unbind、雙份 FilledDone。效能定位要尊重廠商自己的計時，那是唯一不帶我們濾鏡的尺子。
3. **採證程式碼要有「保質期」。** 為抓一個 bug 加的 trace，bug 修完那天就是它的退休日。更好的做法是加的時候就定好預設值和關閉開關，別讓臨時代碼變成預設路徑——這個專案已經用三次核心崩潰和一次影格率慘案交了學費。
