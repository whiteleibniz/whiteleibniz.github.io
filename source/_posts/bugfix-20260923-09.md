# bugfix_20260923_09 — GBA 退出游戏返回列表卡顿（内核回收输入设备 fd 极慢）

- 日期：2026-09-23
- 模块：GBA 游戏页退出路径 / `extern/miniretro/miniretro.c` / 内核输入子系统
- 影响：GBA 退出返回列表的响应速度（FC 页共用 miniretro，同理但本次未改）；另含一次"兜底强杀后未收尸"的僵尸进程问题

> 与 bugfix_07 的区别：07 修的是"退出后画面**僵住/残留**"（fb 停在翻转页）。
> 本次修的是 07 之后仍然存在的"画面**回得慢**"——按买单键要等约 0.35~0.4 秒才回到列表。

## 1. 问题现象

按"买单"键（116）退出游戏，画面已经不再是游戏画面，但要过约 0.35~0.4 秒列表才出现，体感是"卡一下"。用户反馈："退出游戏返回到列表还是卡顿"。

## 2. 影响范围

- GBA 游戏退出返回列表（本次修复）
- FC 游戏退出（共用同一份 miniretro，理论同样慢；FC 页未改，行为不变）
- 附带修掉：一次 `SIGKILL` 兜底后未收尸 → 子进程变僵尸挂在 lvgl_demo 名下

## 3. 根因分析

用 2ms 粒度采样 + 在 miniretro 退出路径里加分段计时（`ssh_tools/gba_exit_latency.py`）实测：

```
修复前  exit_latency = 394.5 ms
[miniretro][timing] 主循环退出            t=  5.1 ms
[miniretro][timing] core_deinit 完成      t=  5.4 ms
[miniretro][timing] dlclose 完成          t=  5.4 ms
[miniretro][timing]   fb pan 回第0页      t= 23.0 ms
[miniretro][timing]   fb 清屏(memset)     t= 28.4 ms
[miniretro][timing] munmap 完成           t= 28.7 ms
[miniretro][timing] close(evdev) 完成     t=385.0 ms   ← 349ms 全耗在这一步
```

逐个设备复现（**不需要 miniretro，单独 open/close 就能复现**）：

| 设备 | 节点 | 驱动 | close 耗时 |
|---|---|---|---|
| 物理四键 | `/dev/input/event0` | sprd-gpio-keys | 39 ~ 215 ms |
| 另一组按键 | `/dev/input/event1` | sprd-eic-keys | ~80 ms |
| 耳机键 | `/dev/input/event2` | headset-keyboard | ~80 ms |

结论：

1. 子进程内部收尾**不是**瓶颈（deinit/pan/清屏合计约 30ms）。
2. 本机内核关闭 sprd 输入设备固定要几十~几百毫秒。**进程退出时内核必然要关这些 fd，用户态怎么改都躲不掉** —— 所以"子进程真正消失"至少要 ~340ms。
3. 父进程侧还有两段白等：
   - `gba_exit_to_list()` 里 `usleep(250ms)` 死等；
   - `gba_wait_thread()` 用阻塞式 `waitpid` 等子进程"真正消失"（= 内核那 340ms 之后）才恢复 LVGL。
4. 两段叠加 → 约 0.35~0.4s。**卡顿不是渲染问题，是"等一个不必要的事件"。**

## 4. 修复方案

核心思路：**UI 恢复不再等子进程死亡**，改由子进程在"画面已交还"的那一刻主动通知父进程。

### miniretro 侧（子进程）

- cleanup 顺序固定为：`core_deinit()`（**必须保留**，mGBA 要在这里落盘电池存档 `.sav`）→ `fb_restore()`（翻回第 0 页 + 清屏，约 35ms）→ `notify_parent_ui_released()` → `_exit(0)`。
- `notify_parent_ui_released()`：给父进程发 `SIGUSR1`。
  **必须由父进程用环境变量 `MINIRETRO_UI_RELEASE_SIGNAL` 显式开启才发** —— `SIGUSR1` 默认动作是终止进程，没装处理函数的调用方（如 FC 页）一旦收到就会被打死。
- `_exit(0)` 之后不再逐个 `close(fd)`/`munmap`：反正内核退出时都要做，而那 340ms 丢到后台去，不阻塞 UI。

### 页面侧（`lv_pages/gba_game_page.c`）

- `gba_launch()`：fork **之前**装 `signal(SIGUSR1, gba_ui_release_handler)` + `setenv("MINIRETRO_UI_RELEASE_SIGNAL","1",1)`（必须早于 fork，否则信号可能先到 → 默认动作杀进程）。
- `gba_exit_to_list()`：只 `kill(pid, SIGTERM)`，一行都不等。
- `gba_wait_thread()` 两阶段：
  - **阶段①** 5ms 粒度等"收到 SIGUSR1 **或** 子进程真退出"（≤500ms 兜底），一满足就 `hardware_keys_set_grab(true)` → 摘拦截器 → `app_runtime_set_lvgl_paused(false)`；
  - **阶段②** 后台收尸：5s 超时后 `SIGKILL` 并**同步 `waitpid` 收尸**。
- 保留分秒计时 `[miniretro][timing]` 日志，方便下次回归直接看数字。

## 5. 验证方法与结果

**① 退出耗时对比（受控测量）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 子进程内部收尾 | 385 ms | **37 ms** |
| 父进程收到"画面已交还" | — | **40.6 ms** |
| 子进程真正消失（内核回收） | 394 ms | 337 ms（**已与 UI 无关**） |

**② 握手协议验证**（`ssh_tools/gba_ui_release_test.py`，python 伪父进程，无需按物理键）

```
用例 A 开启通知  : SIGTERM 后 40.6ms 收到 SIGUSR1（yoffset 17ms 已翻回第 0 页）
用例 B 未开通知  : 收不到信号(-1.0ms)，且父进程存活   ← 门禁生效，FC 页安全
```

**③ 恢复是否"瞬时"**：`lv_tick_inc()` 在主循环里**无条件**执行（`main.c:635`），暂停期间 LVGL 时间照走，所以恢复后 100ms 定时器早已过期，**第一次 `lv_timer_handler()` 就触发整屏重绘**；主循环 10ms 一跳。即恢复路径没有额外等待。

预期观感：按买单 → ~40ms 交还画面 → 立即重绘列表（原 0.35~0.4s）。

## 6. 回归风险

- **子进程既不通知也不退出**：阶段① 500ms 后仍会恢复 UI，退化为旧行为，不会卡死；阶段② 5s 后强杀收尸。
- 子进程退出期间（~0.3~0.4s）仍持有 fb0/evdev 的 fd（内核正在回收），但它已不再绘制，不影响 LVGL（LVGL 自己持有 fb0；`yoffset` 是设备级状态）。
- **FC 页未改**：退出仍等子进程消失（~340ms）。若要一并提速，把上述页面侧三处改动搬到 `fc_game_page.c` 即可（miniretro 侧已就绪，且默认不开信号门禁）。
- **部署纪律（本次踩坑）**：`extern/miniretro/build.sh` 是 `gcc ... -o miniretro`，**直接写目标文件**。用户正在玩时重编，恰有启动动作 exec 到半覆盖的二进制 → 子进程卡在 exec 里、启动失败、2.5s 后被兜底强杀且未收尸（僵尸）。
  现统一要求：二进制一律"编到 `*.tmp` → `mv -f` 原子替换"，部署走 `ssh_tools/gba_redeploy.py`。
