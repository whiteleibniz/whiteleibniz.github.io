> 系列第 30 篇。目标板连续四轮（10-27 ~ 10-30）处于离线状态，第 29 篇写的「常驻 fork 并行渲染池」**一次都没有编译过**。本篇记录一种在设备不在手边时仍然能真推进的做法：**面向「不崩但悄悄错」的静态审查**，以及它在这次审查里挖出来的四处真实缺陷。

## 1. 离线不等于停摆，但也不能瞎改

这个项目有个很尴尬的现状：唯一的交叉编译器在目标板上，源码本地写、设备上编。设备一断电，新代码就变成「写完没验证」的悬空债——攒得越多，下次上电那一轮越容易全耗在编译报错上。

所以离线时的正确姿势不是继续写新功能，而是**把已写未验的代码当成审查对象**。审查要有靶心，我用的判据只有一条：

> 优先找**不会崩、不会报错、只会悄悄错**的问题。

理由很实在：编译错误和崩溃在下一次联机时会立刻暴露，五分钟就能修；而「画面偶尔错位」「帧率数字是假的」「资源慢慢泄漏」这三类，上线后能骗你好几轮实验，甚至让你得出反向结论。第 29 篇里「私有 staging = 冻结副本」就是典型——它不崩，只是子进程一直在渲染上一帧。

## 2. 缺陷一：切分点没对齐带高（会撕裂，也会越界写）

渲染被切成若干「带」（band），每带渲染输出行 `[oy0, oy0+bandh)`。并行派发时我原来的切法极其自然：

```c
int rows = 1280 / n;                 /* 每个子进程分到的输出行数 */
j.y0 = i * rows;
j.y1 = (i == n - 1) ? 1280 : (i + 1) * rows;
```

问题在于 `fb_render_range` 的内层循环**永远渲染整条带**，它不认识 `y1`：

```c
for (int oy0 = y0; oy0 < y1; oy0 += g_bandh)
    for (int j = 0; j < g_bandh; j++)
        memcpy(dst + (oy0 + j) * 720, band[j], 720 * 4);   /* 写满 bandh 行 */
```

只要 `(y1 - y0)` 不是 `bandh` 的整数倍，最后一个子进程就会写出 `[y1, oy0+bandh)`：既覆盖下一个子进程负责的行（画面撕裂），末段还会越过 fb 页尾（SIGSEGV）。默认带高 64 时，逐个档位算一遍：

| 路数 n | rows = 1280/n | 是否 64 的倍数 | 后果 |
|---|---|---|---|
| 2 | 640 | ✅ | 安全 |
| 3 | 426 | ❌ | 撕裂 + 越界 |
| 4 | 320 | ✅ | 安全 |
| 6 | 213 | ❌ | 撕裂 + 越界 |
| 7 | 182 | ❌ | 撕裂 + 越界 |
| 8 | 160 | ❌ | 撕裂 + 越界 |

也就是说，**原本计划里要测的三臂（2/4）恰好都躲开了这个坑**，而最能体现并行的 8 路一定会炸。这种「测过的档位恰好没问题」是并行改动里最阴的失败模式。

修法不是去改内层循环（要把 `g_bandh` 换成逐带的 `bh`，十来处，容易漏），而是让切分点落到 `bandh` 的倍数上——因为 `1280 % bandh == 0`（bandh 只允许 16/32/64/128/256），只要 `rows` 也是倍数，所有边界就都是倍数，永远不存在残缺带：

```c
int rows = ((1280 / n) + g_bandh - 1) / g_bandh * g_bandh;
if (rows < g_bandh) rows = g_bandh;
j.y0 = i * rows;  if (j.y0 > 1280) j.y0 = 1280;      /* 末尾可能有空任务 */
j.y1 = j.y0 + rows; if (j.y1 > 1280) j.y1 = 1280;
```

代价是负载略有不均（8 路时前 6 路各 192 行、第 7 路 128 行、第 8 路空转），换来的是**结构性地不可能越界**。

## 3. 缺陷二：失败回退时会和孩子抢着写同一段行

原版派发逻辑一遇到读写失败就 `break`，然后父进程立刻串行重渲整帧：

```c
for (i...) if (read(g_rp_c2p[i], &ack, 1) != 1) { bad = 1; break; }
if (bad) fb_render_range(nv, dst, 0, 1280);    /* 整帧重做 */
```

但此时 `i+1 … n-1` 号子进程**已经拿到任务、正在写自己的行**。父进程紧接着覆盖全 1280 行，两边同时写同一段内存——画面撕裂，而且是「只在子进程异常退出时出现」的偶发撕裂，极难复现。

修法：**先把已派发的 ack 全部收齐，再判定失败**。收齐意味着所有孩子都已写完（或已确认死亡），此后串行重做才是独占的：

```c
for (int i = 0; i < sent; i++)
    if (read(g_rp_c2p[i], &ack, 1) != 1) bad = 1;   /* 不 break */
if (bad) { g_rp_dead = 1; g_rp_on = 0; fb_render_range(nv, dst, 0, 1280); }
```

注意这里读失败也要继续往下读：管道读是阻塞的，活着的孩子一定会回 ack，不会卡死；死掉的孩子返回 0，正好作为「确认已死」的凭证。

## 4. 缺陷三：常驻子进程会一直攥着 ION 缓冲不放

池是在**第一帧**才 fork 的——那时父进程已经打开了一批 ION / dmabuf 的 fd。fork 会把 fd 表整个复制给孩子，于是每个常驻子进程都持有一份引用。父进程那边 `close()` 了，缓冲并不会释放，因为孩子的引用还在。

这个平台的 carveout 池只有 640KB，ION 泄漏的结局是黑屏且必须重启（见本系列「黑屏 SOP」）。孩子什么设备都不碰，所以直接把它们不需要的 fd 全关掉：

```c
for (int fd = 3; fd < 64; fd++)
    if (fd != rfd && fd != wfd) close(fd);
```

顺带一个教训：**任何 long-lived fork 子进程，都该显式收缩自己的 fd 表**。每帧 fork 的短命进程不用管（马上就退），常驻池必须管。

## 5. 缺陷四：自检用的草稿区不能拿 fb 页 0 顶

首帧自检要串行渲一遍、并行渲一遍、比哈希。我原先图省事直接拿 fb 的页 0 当草稿区（播放只用页 1/2）。

但页 0 是**归位页**：退出播放时 `fb_home()` 会 PAN 回它。往里写一整帧的结果，就是退出后桌面停在最后一帧的残影上。改成一次性 `malloc` 的私有内存即可——串行参考渲染的目标地址根本不需要是显存。

同一次审查里还顺手改了一处**测量口径**问题：并行模式下「转换 / 写 fb」两项分项耗时恒为 0，因为子进程各改各的私有副本，父进程看不到。原版照打这个 0，下一轮 A/B 极可能有人拿它当证据。改成只报墙钟并注明口径：

```
[perf] fb_render 池4路 均值 Xms (上限 Y fps) [墙钟] (转换/写fb 为子进程私有, 此处不计)
```

## 6. 方法论小结

离线审查能挖出这些，靠的不是仔细，而是**换了提问方式**。把「这段代码对不对」换成下面四问，命中率明显高：

1. **边界和余数**：切分、分块、取模，余数是怎么处理的？内层循环认不认边界？
2. **失败路径的并发**：异常发生时，别人还在跑吗？我的兜底动作和它们是互斥的吗？
3. **资源的隐性持有者**：fork 出来的常驻进程攥着什么？谁在替它计数？
4. **测量口径**：这个数字是谁在写、谁能读到？它可能是恒 0 的假数吗？

还有一个排序经验：**并行改动的失败模式，按危害排是「悄悄错」＞「崩」＞「慢」**。所以并行优化里，首帧哈希自检（串行 vs 并行比整页 FNV）比优化本身更重要——它是唯一能挡住第一类失败的闸门。这次的 A/B 脚本也专门补了 8 路这一臂，用最可能踩坑的档位去证明修复真的生效，而不是只测「恰好没问题的那几档」。
