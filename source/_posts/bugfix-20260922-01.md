# bugfix_20260922_01 mplayer 播放视频红蓝通道错乱

> **现象**：桌面图标与 FC 游戏颜色已修正后，用「视频」页播放 mp4 时颜色仍然不对（红蓝互换）。
> **根因层**：framebuffer 色彩元数据 × 外部播放器（mplayer `-vo fbdev`）。
> **修复工作量**：2 个源文件 +54/-2 与 +50/-2，外加 miniretro 重编。
> **文件名**：`bugfix_20260922_01_mplayer视频红蓝通道错乱.md`
> **关联提交**：`5113a12`
> **日期**：2026-09-22

---

## 1. 现象

同一块屏幕上，不同功能的颜色表现**不一致**：

| 功能 | 颜色表现 |
|---|---|
| 桌面图标、文字、背景 | 正常（此前已修正） |
| FC 游戏（miniretro） | 正常 |
| **「视频」页播放 mp4** | **红蓝互换**（红色物体显示成蓝色） |

关键点：**只有视频播放器不对**。这本身就说明问题不在"整个屏幕的色彩方案"，
而在"视频播放器这条独立路径"。

## 2. 影响范围

- **受影响**：`lv_pages/video_player_page.c` 走的外部 mplayer 进程播放的所有视频。
- **不受影响**：LVGL 自绘部分（桌面/各页面）、miniretro（FC 游戏）——
  它们各自有独立的写 fb 路径与本地的 R/B 交换，无需改动。

## 3. 根因

### 3.1 前提：本机屏幕真实字节序与驱动报告相反

`FBIOGET_VSCREENINFO` 报告 `r16:8 g8:8 b0:8`（语义 `[B,G,R,X]`），
但用纯色写 fb + 人眼确认，**真实字节序是 `[R,G,B,X]`**：

| 写入 fb 的内存字节 | 屏幕实际显示 |
|---|---|
| `[00,00,FF,FF]` | **蓝** |
| `[FF,00,00,FF]` | **红** |

→ `offset0 = 红`、`offset2 = 蓝`，**与驱动报告恰好相反**。

### 3.2 核心机制：外部播放器会**读取**这份元数据并据此写像素

`libs/mplayer/mplayer`（MPlayer 1.4-13）的 `fbdev` 输出驱动在初始化时读
`FBIOGET_VSCREENINFO`，**按读到的 offset 决定自己把颜色写到哪个字节**，
并在日志里打印它选定的布局：

```
var = r16:8 g8:8 b0:8   ->  VO: [fbdev] 720x1280 => 720x1280 BGRA
var = r0:8  g8:8 b16:8  ->  VO: [fbdev] 720x1280 => 720x1280 RGBA
```

- `BGRA` = 蓝在字节 0 → 但本面板要红在字节 0 → 屏幕上红蓝互换 ✗
- `RGBA` = 红在字节 0 → 与面板一致 ✓

**所以 mplayer 的代码没错，它只是老实照驱动谎报的参数办事。**

### 3.3 为什么这里不能靠改代码解决

| 消费者 | 取色方式 | 可否改代码 |
|---|---|---|
| LVGL（`main.c` `fb_flush_cb`） | 自己打包像素、直接写内存 | ✅ 已改（交换 R/B） |
| miniretro（`scale_rotate90`） | 自己打包像素、直接写内存 | ✅ 已改（交换 R/B） |
| **mplayer（`-vo fbdev`）** | **读 fb 元数据，据此写** | ❌ 第三方预编译二进制，无源码 |

mplayer 是 13.7 MB 的预编译 ELF（`libs/mplayer/mplayer`），设备上**没有源码**，
所以改不了它的代码 —— 只能改**它读到的参数**。

## 4. 定位过程

### 4.1 走过的弯路（记录下来避免重走）

| 错误方向 | 为什么错 |
|---|---|
| 在系统路径找 mplayer（`/usr/bin`、`/usr/local/bin`） | 全部不存在 → 一度误判"设备上没有播放器"。实际在 `libs/mplayer/mplayer`，由 `video_find_mplayer()` 的相对路径候选命中 |
| 试 `-vf format=bgr32` / `format=rgb32` / `format=bgra` | **全部无效**。fbdev vo 会覆盖 format 滤镜的选择，四组输出字节**完全相同** |
| 试 `-vo fbdev2` | 与 `fbdev` 行为相同，仍是 BGRA |
| 想改自定义 `lvfb` 驱动 | 该 mplayer 里确有 `lvfb`（"LVGL-style framebuffer output"）驱动，但它**拒绝**本机格式：`[lvfb] unsupported framebuffer format: 720x1280 32bpp r16:8 g8:8 b0:8`（校正成 `r0:8 b16:8` 后**依然拒绝**）。设备上没有 lvfb 源码，无法修改 |
| 用 `ffmpeg -f lavfi` 造纯色测试视频 | 设备**没有 ffmpeg**，此路不通。改用现有 mp4 直接比对 |

### 4.2 决定性实验：只改 fb var，看输出字节是否变化

**控制变量**：同一条命令、同一个 mp4，**唯一变化是 fb var**。

```sh
# A) 出厂 var（r16 g8 b0）
./mplayer -vo fbdev:/dev/fb0 -nodouble -bpp 32 \
          -vf scale=720:-2,expand=720:1280 -ao null -frames 1 <video.mp4>

# B) 校正 var（r0 g8 b16）后，跑完全相同的命令
```

结果（屏中央采样）：

| 情形 | `VO:` 日志行 | 屏中央字节 |
|---|---|---|
| A 出厂 var | `VO: [fbdev] ... BGRA` | `[e5 d7 cc ff]` |
| B 校正 var | `VO: [fbdev] ... RGBA` | `[cc d7 e5 ff]` |

**只有 R/B 两个字节互换，其余完全一致** —— 干净地指向 fb var 这一个变量。

### 4.3 关键排除实验：改 var 会不会影响控制器实际取色？

这是决定"叠加修正"还是"替换修正"的分水岭。

**做法**：把 var 校正为 `r0:8 b16:8` 后，往 fb 写**同样的** `[FF 00 00 FF]`，
让用户目视报告颜色。

**结果**：用户答「红色」——与改 var **之前**看到的颜色**完全相同**。

**结论**：`red/green/blue.offset` **只是给软件读取的元数据，控制器不理会它**。
改 var 不影响硬件扫描取色，只影响"读这份元数据的软件"（即 mplayer）。

→ 因此修正是**叠加式**：必须校正 var（修 mplayer），
而 LVGL/miniretro 自己的 R/B 交换**必须保留**（删了就双重交换，反而变回错的）。

## 5. 解决办法

### 5.1 新增一个幂等的 var 校正函数

在 `fb_init()` 里（打开 fb 之后立刻）调用一次，把 var 校正为 `r0:8 g8:8 b16:8`：

```c
/* 校正 fb 参数, 让读取该元数据的外部播放器(mplayer)自动取对字节序。
   实测: 改 var 不影响控制器取色, 只影响读元数据的软件。 */
static void fb_fix_color_spec(int fd)
{
    struct fb_var_screeninfo v;
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) < 0) { perror("[fb] fix: FBIOGET"); return; }
    if(v.red.offset == 0 && v.blue.offset == 16 &&
       v.red.length == 8 && v.green.length == 8 && v.blue.length == 8)
        return;                                    /* 已是目标布局, 幂等 */
    v.red.offset   = 0;  v.red.length   = 8;
    v.green.offset = 8;  v.green.length = 8;
    v.blue.offset  = 16; v.blue.length  = 8;
    if(ioctl(fd, FBIOPUT_VSCREENINFO, &v) < 0) {
        fprintf(stderr, "[fb] fix: FBIOPUT failed: %s\n", strerror(errno));
        return;
    }
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) == 0)
        fprintf(stderr, "[fb] color spec -> r%u:%u g%u:%u b%u:%u\n",
                v.red.offset, v.red.length, v.green.offset, v.green.length,
                v.blue.offset, v.blue.length);
}
```

### 5.2 在两处 `fb_init()` 中调用

| 文件 | 位置 | 作用 |
|---|---|---|
| `main.c` | `fb_init()` 打开 `g_fb_fd` 后 | mplayer 是 lvgl_demo 的**子进程**，自然继承正确状态 |
| `extern/miniretro/miniretro.c` | `fb_init()` 打开 `fb_fd` 后 | 脱离主程序单独跑游戏时，fb 状态也正确 |

### 5.3 **保持不变**的部分（重要）

- `main.c` 的 `fb_flush_cb`：**保留** R/B 交换
- `extern/miniretro/miniretro.c` 的 `scale_rotate90`：**保留** R/B 交换

这两者直接写内存、不读元数据，删掉交换就会双重交换变回错的。

## 6. 验证

### 6.1 自动化验证（var 是否自愈 + mplayer 布局是否改变）

## 7. 经验教训

1. **"同一个屏幕上，不同进程的修法不同"** —— 这是本次最大的认知跃迁。
   写 fb 的消费者分三类：
   - **自绘程序**（LVGL、miniretro）→ 改**代码**，在自己写入点交换
   - **读元数据的外部程序**（mplayer `-vo fbdev`）→ 改**参数**（校正 fb var）
   - **内核/控制器** → 通常不可改，且实测**忽略** var

   只修一类就会留下"某个功能颜色还是错的"。**排查颜色问题第一步应先枚举所有写 fb 的进程。**

2. **先看外部程序自己打印的选择**。`mplayer` 的 `VO: [fbdev] ... BGRA` 一行
   直接说明了它的判断依据，比任何推理都快。有日志就别猜。

3. **控制变量的 A/B 实验优于"改一堆再试"**。同命令 + 同素材 + 只改一个变量
   （fb var），得到"只有 R/B 两字节互换"的干净结论，直接锁定因果。

4. **区分"元数据"与"硬件行为"**。改 `var.red.offset` 前先问：
   "它是被硬件用的，还是只被软件读的？" —— 用"改前后写同样字节看屏幕是否变化"
   就能回答。这个判断决定了修正是叠加还是替换，**判错就会双重交换**。

5. **命令行选项要先验证再放弃**。`-vf format=...`、`-vo fbdev2` 看起来合理，
   实测全部无效。花几分钟证伪，胜过凭直觉重编播放器。

6. **不要用 `pkill -f <pattern>` 杀守护进程**。`pkill -9 -f lvgl_watchdog` 会匹配到
   **承载该命令的 shell 自身**（其命令行含该字符串）→ 杀掉自己的 SSH 会话，
   表现为 `RC: -1` 且输出被截断，看起来像"命令根本没执行"。**按 PID 杀**：
   ```sh
   for p in $(ps -o pid,args | grep lvgl_watchdog.sh | grep -v grep | awk '{print $1}'); do kill -9 $p; done
   ```

7. **给远端打补丁后，用 `git diff --ignore-cr-at-eol` 复核**。
   `git diff` 曾把 54 行的真实改动显示成 1618 行"整文件重写"——
   那只是 CRLF/LF 触发 git 行尾启发式，不是改坏了。
