# bugfix_20260923_17 · GBA 音画延迟 1~2 秒：定位到音箱端缓冲，设备侧无可修点

- 日期：2026-09-23
- 设备：展讯 SC9832A / Alpine Linux / 720x1280 fb
- 应用：GBA 游戏（`miniretro_gba` + `mgba_libretro.so`）→ 蓝牙 A2DP（小爱音箱）
- 分类：音频链路 / 延迟预算定位
- **结论：设备侧全链路延迟 ≤0.25s，与用户实测 1~2s 差 4~8 倍；超出部分在蓝牙音箱端的应用层缓冲，设备侧既不可观测也不可控 → 本轮不做代码改动**

---

## 1. 现象

用户反馈：GBA 游戏「**声音比游戏画面落后**」，量级 **1~2 秒**，且**固定**（一进游戏就落后那么多，长时间玩也没有明显变化）。

**"固定"这一条是决定性的**：它排除了"设备侧积压"这一类原因（积压会随时间累积、越玩越久），指向链路中某一段的**固定缓冲**。

## 2. 定位方法：链路分段量化（延迟预算表）

把「游戏音频生成 → 出声」拆成 5 段，逐段量化出延迟，找出**量级对不上**的那一段：

| # | 段 | 延迟 | 依据（可复现） |
|---|---|---|---|
| 1 | mGBA core 内部音频缓冲 | **~33ms** | `libretro.c`：`internalAudioBufferSize = audioSamplesPerFrame * 2`（上限 `0x4000`）；GBA 每帧 ~1097 样本 → 约 2 帧；且 `retro_run` 每帧 `mAudioBufferRead(buffer, ..., audioSamplesPerFrameAvg)` **一次取走**，不累积 |
| 2 | 前端 `miniretro_gba` | **0** | `fifo_write()` 是**收到就写、非阻塞**（EAGAIN 直接丢）；重采样为**无状态丢样**（`s_out_acc` 累加器 + 直接复制样本），**无内部队列、无攒批** |
| 3 | `/tmp/bt_audio.fifo` 积压 | **80ms** | 水位闭环后实测 `back ≈ 14000B`（原始 0.21s 已压到 ~0.08s） |
| 4 | daemon 在途包 | **≤122ms** | `A2DP_MEDIA_INFLIGHT_MAX=6` × 20.3ms/包；实测 `inflight=0/1776`、`credit busy=0` |
| 5 | **蓝牙空口 + 音箱应用层缓冲** | **不可观测** | 见 §3 |
| — | **设备侧小计** | **≤0.25s** | |

对照用户实测的 1~2 秒：**差额全部落在第 5 段**。

## 3. 为什么判定在音箱端（以及为什么设备侧测不到）

**判定依据**：设备侧四段都有硬实测、加起来 ≤0.25s；「固定」的性质又排除了累积型原因。剩下的量级只能来自音箱。

**为什么设备侧观测不到音箱缓冲**（这三条是本节的重点，别再白费力气找）：

1. **ACL 层的 `Number-Completed(0x13)` 不等于应用层消费确认** —— 它由**蓝牙控制器**回，只表示"空口传完了"，音箱把包放进自己缓冲后并不会因此额外通知。
2. **A2DP 媒体通道走 L2CAP basic mode，没有 credit 流控** —— sink 不会告诉 source"我手里还压着多少"。
3. **daemon 的发送节奏是设备侧绝对时钟**（每 20.3ms 一包），与音箱的消费节奏完全解耦；设备侧只能知道"我发了多少"，无法知道"它播到哪"。

**旁证**：daemon 源码注释（v48R22 那次修复）自述「**sink 缓冲约 2s**」。那次是异常态（缺 START 直接推流）下观察到的，但侧面印证该音箱的缓冲深度就在**秒级**。

## 4. 本轮结论与决策

- **不做设备侧代码改动**。理由：设备侧剩下可压的只有约 90ms（fifo 水位 60→30ms、在途窗口 6→3），相对 1~2s 是 5% 量级，收益可忽略；且收紧蓝牙发送窗口有历史「CP 复位」风险，风险收益比不划算。
- 上一轮已落地的**fifo 水位闭环**（把积压从 0.21s 压到 0.08s）保留，它是有效的、无副作用的改进。
- **可行的改善方向只在音箱端**：音箱 App / 音箱本体的「低延迟 / 游戏模式」开关；或换一台延迟更小的蓝牙音箱/耳机做对照。

## 5. 验证

- 用户已确认：**固定落后**、量级 **1~2 秒** → 与"音箱固定缓冲"模型完全吻合。
- **对照实验（推荐用户做，一步定论）**：把设备连到**另一个蓝牙耳机/音箱**，若延迟显著改变 → 100% 确认是音箱端；若换谁都一样 1~2 秒 → 再回头查链路。

## 6. 反模式与踩坑

- **★ 别用"设备侧的缓冲指标"去解释"秒级"延迟** —— 先做延迟预算表，看哪个量级对不上，再深挖那一段。凭直觉猜"肯定是缓冲"会一直在设备侧空转。
- **★ `Number-Completed` ≠ 应用层消费确认**（见 §3.1），拿它估音箱缓冲是错的。
- **★ 测量时注意计数方式**：全文件计数做差分才有意义；用"固定前缀计数"做差分必然为 0（自己给自己挖的坑，本轮真踩了）；日志轮转也会污染差值。
- **★ `FIONREAD` 量 fifo 积压是可信的**：它返回管道内可读字节数，与读端数量无关；只读 FIONREAD、不 read，就不会抢走消费者的数据。
- **★ 前端"把音频拉伸到实时"的设计是正确的**：核心产出随实际帧率变化，前端按 `s_fpc × s_fps_meas` 归一后恒以 44100 帧/秒输出，音画**内容速率**保持同步（代价是音调随帧率下降）。别再怀疑这里。
