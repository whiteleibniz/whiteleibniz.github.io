> 系列第 27 篇。上一篇把「稳态 14.2fps」归因为源本身只有 14.6fps，本篇用 PTS 把这条结论**推翻**了，然后把真正的 10 秒黑洞拆成两张账单。

## 一、先翻案：源是 25fps，不是 14.6fps

上一篇的算法是「一段 155 帧 ÷ 段间隙 10.6s = 14.6fps」。问题出在分母：**段间隙是墙钟，不是段内容时长**。要拿真帧率，只能问码流自己。

于是写了 `nalcount.c`：按 188 字节切包，在 PUSI 处解析 PES 头取 PTS，用「AU 数 ÷ PTS 跨度」算真帧率，同时用「平均 PTS 间隔」交叉验证。泸县源一个分片的实测：

```
packets=14034 pes=150 au(pts)=150
nal: idr=5 nonidr=145 sps=5 pps=5 sei=5 aud=150
pts_span=5.960s  fps_by_span=25.00
avg_pts_delta=3600.00 ticks  fps_by_delta=25.00
```

**150 帧 / 5.96s / PTS 间隔恒定 3600 ticks（90000/25）—— 真 25fps，铁证。** 两种算法互相印证，不存在丢帧或 VFR。

也就是说：我们把 5.96 秒的内容播了 10.3 秒，**慢的从来不是源，是我们**。「提帧到 25fps」重新变成物理可达的目标。

顺带一个坑：`mplayer -identify` 报的 `ID_VIDEO_FPS=25.000` 对 MPEG-TS 基本是容器默认值，不能当证据（它对钱江、CloudFront 也报 25.000，但那两路的平均 PTS 间隔是 8359/8704 ticks ≈ 10.8fps，明显是另一回事）。

六个源的普查结果：

| 源 | 分辨率 | AU/段 | PTS 跨度 | 真帧率 |
|---|---|---|---|---|
| 泸县 | 1920×1088 | 150 | 5.96s | **25.00** |
| 上虞 | 1920×1088 | 200 | 7.96s | **25.00** |
| 松潘 | 1920×1088 | 270 | 10.76s | **25.00** |
| 钱江 | 1920×1088 | 200 | 7.92s | 25.13（间隔不均） |
| CloudFront | 960×544 | 100 | 3.96s | 25.00 |
| 北方广电 | — | — | — | 拉不到列表 |

## 二、10.3 秒的账单

给 dl 循环的每一段都装上计时（`g_dl_t_pick / pref / af / hist`），现网默认配置跑一轮：

| 段 | 段间隙 | 选段 | 预取(含下载) | 音频 | 下载解析 | 入池 |
|---|---|---|---|---|---|---|
| 2 | 10439ms | 4983ms | 5236ms | 5231ms | 212ms | 6ms |
| 3 | 10470ms | 5075ms | 5172ms | 5167ms | 214ms | 6ms |
| 4 | 10402ms | 4980ms | 5211ms | 5206ms | 213ms | 6ms |

（累计计时器，逐行相减即为单段值。）

结论非常干净：**下载 0.21s、入池 6ms，加起来不到 3%**；10.3 秒里 5.2 秒是 `audio_feed()`、5.0 秒是 `pick_seg()`。

`audio_feed()` 为什么是 5.2 秒？它把整段 2.6MB 的 TS 写进一个 64KB 的 fifo，mplayer 按实时 1x 排空——**这不是背压，这是物理排空时间**，等于段内容时长。而它偏偏写在了「选下一段 + 预取」的**前面**，于是每一轮循环都被音频锁死。

这里有个容易上当的地方：`NETTV_AF_RETRY` 只限制「停滞重试次数」（默认 300 次 × 20ms），治不了整段排空。实测把它调成 1，帧率 16.0 → 19.0，段间隙只掉到 8.1s；再把 mplayer 临时改名让音频彻底失效，段间隙**还是 8.1s**、帧率还是 19.0。这两组对照说明：音频只占 2.2s 的停滞，5.2s 的主体必须靠改结构，不能靠调参。

## 三、修法：异步音频泵

思路很简单——dl 解析完一段之后，这份 raw 文件对它已经没用了，`rename` 给一个子进程独占，让子进程慢慢喂，dl 立刻进下一轮：

```c
static void audio_feed_async(const char *path)
{
    if (g_afifo < 0) return;
    if (g_aud_pump > 0) {                 /* 非阻塞收尸; 还活着就跳过本段 */
        int st = 0;
        if (waitpid(g_aud_pump, &st, WNOHANG) == 0) return;
        g_aud_pump = -1;
    }
    snprintf(sp, sizeof sp, "%s.aud", path);
    rename(path, sp);                     /* dl 已解析完, 交给音频子进程 */
    pid_t p = fork();
    if (p == 0) { signal(SIGPIPE, SIG_IGN); audio_feed(sp); unlink(sp); _exit(0); }
    if (p > 0) g_aud_pump = p;
}
```

三个细节不能省：

1. **必须 `waitpid(WNOHANG)` 收尸，不能用 `kill(pid,0)` 判活**。僵尸进程的 `kill(pid,0)` 照样返回 0，会让泵永远被判定为「还活着」，音频从第二段起就再也不喂了。
2. **必须 `rename` 而不是直接 fork 读原路径**：2 槽轮转，子进程还在慢慢读的时候原路径会被下一段下载覆盖，读出来的就是半截段。
3. 上一段没喂完就跳过本段——**视频优先**，宁可音频有间隙也不让音频拖住供数。

实测（同源、同 95s、同二进制，唯一变量 `NETTV_AUDIO_ASYNC`）：

| 配置 | 段间隙 | 音频 | 选段 | 稳态帧率 |
|---|---|---|---|---|
| 现网默认 | 10309ms | 5231ms | 4983ms | 15.2 |
| `AF_RETRY=1` | 8100ms | — | — | 19.0 |
| 音频链路移除 | 8100ms | 0 | — | 19.0 |
| **异步音频泵** | **8228ms** | **1ms** | 5104ms | **19.8** |

音频那 5.2 秒被彻底抹掉（5231ms → 1ms），帧率 **15.2 → 19.8，+30%**。

## 四、剩下的 8.2 秒归谁

异步泵跑完，账单重排：**选段 5.1s + 下载 2.9s = 8.2s**，而段内容只有 5.96s。

- 下载 2.9s 是硬成本（2.6MB ÷ 约 900KB/s），而且已经是异步预取了，跟别的事重叠着。
- **选段 5.1s 是纯浪费**，现在是头号目标。`pick_seg()` → `hls_pick()` 拉一次播放列表，没拿到新段就 `sleep(1)` 重试，最多 4 次——4 次重试 + 4 次列表拉取正好 5 秒左右。但日志里一条「无新段」都没打，说明最后那次是成功的，即**每轮都要白等 3 次左右**。

为什么明明落后于直播还在等新段？这是下一个待解问题：要么播放列表的滑动窗口比想象中窄，要么 `g_last_seg` 的比较逻辑在某个环节失效（比如 URL 带 query 参数、重定向后 URL 变了）。下一步就是把 `hls_pick()` 的重试次数和每次拉列表的耗时分别打点。

## 五、这一轮的教训

1. **别拿墙钟当内容时长。** 上一条错误结论活了整整一轮，就因为「段间隙」这个名字起得太顺手。凡是「X 秒」都要问一句：这是内容的秒还是我们耗掉的秒。
2. **调参的收益有天花板，改结构没有。** `AF_RETRY` 从 300 调到 1 只拿回 2.2s，因为 5.2s 的主体是排空时间不是重试；把整段活挪出主循环才拿回全部。
3. **A/B 要两个方向都做。** 只做「AF_RETRY=1」会得出「音频背压是主因」的错误结论；补一组「彻底关掉音频」才发现它俩一样，说明那个参数动的是别的东西。
4. **取证工具要能自证。** `nalcount` 同时给「跨度法」和「间隔法」两个帧率，两个对得上才敢拿去推翻前一轮的结论。
