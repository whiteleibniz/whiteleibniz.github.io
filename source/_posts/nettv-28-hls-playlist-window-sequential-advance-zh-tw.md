> 系列第 28 篇。上一篇把 10.3 秒的段間隙拆成「選段 5.0s + 音頻排空 5.2s」，本篇先把選段這 5 秒**量出來**，再把它**砍到 0.3 秒**。根因說出來有點丟人：我們一直在等一個還沒生成的分片，而窗口裡躺著 4 段現成內容沒播。

## 一、先給選段裝表

上一篇的儀器化只到 `pick_seg()` 這一層，只知道「選段一共 5.0 秒」，不知道這 5 秒是**在下載**、**在 sleep**、還是**在重試**。所以第一步是給 `hls_pick()` 每次拉列表計時，並統計段條數、末段名、`g_last_seg` 命中的位置。

改動純計時 + 日誌，行為零改變。瀘縣源跑一輪，打點長這樣：

```
[hls] 拉列表 2330ms 段数=5 r=1 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 选段 总=2330ms 拉列表=2330ms/1次 段数=5 命中=1 失败=0
[hls] 拉列表  215ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  245ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  245ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 拉列表  276ms 段数=5 r=0 末=seg/Num15825010.ts 首=seg/Num15825006.ts
[hls] 选段 总=4981ms 拉列表=981ms/4次 段数=5 命中=0 失败=0
>>> [hls] 无新段: 重播上一段保持画面
```

帳單立刻清楚了：**4 次重試裡拉列表一共只花 981ms（每次約 250ms），剩下 4000ms 全是 `sleep(1)` 空等**。網路不是瓶頸，邏輯才是。

## 二、5 秒空等的真身

把三行資訊擺在一起看，結論幾乎是自證的：

| 觀察 | 數字 |
|---|---|
| 播放列表裡的分片數 | **5 段**（Num15825006 ~ Num15825010） |
| 我們每輪實際取的 | **只有最後一條** Num15825010 |
| 4 次重試結果 | 全部 `r=0`（末段沒變） |
| 兜底動作 | **重播上一段** |

舊邏輯是「取列表最後一條 → 跟上一段比 → 相同就 sleep 1 秒重試 4 次 → 還相同就重播上一段」。它隱含一個假設：**我們總是貼著直播邊緣在播，所以只有最新那一段值得播，下一塊內容只能等伺服器生成。**

可我們根本不貼著邊緣——每輪段間隙 10.3 秒，一段內容才 5.96 秒，我們比直播**越落越遠**。窗口裡 4 段沒播過的現成內容就這麼躺在那兒，我們一邊空等、一邊把剛播過的那一段再播一遍。

「重播上一段」這個兜底當初是為了**畫面別黑**（見第 15 篇），但它在源刷新慢時會變成「畫面原地循環」。日誌裡 3/3 輪都是 `命中=0`。

順帶一個意外發現：**瀘縣源當天凌晨的末段號 Num15825010 在兩輪共 15 分鐘裡紋絲不動**，源已經停止刷新了。這既解釋了為什麼怎麼測都是 15fps，也說明「拿一個源測到底」這件事本身有風險。

## 三、修法：窗口內順序推進

思路很直白——**別只盯最後一條，在窗口裡找到上次播的那一段，播它的下一段**。

```c
/* 列表全量解析进 g_segs[](不再只留 best) */
int at = -1;
for (int i = 0; i < g_segs_n; i++)
    if (!strcmp(g_segs[i], g_last_seg)) { at = i; break; }

if (at >= 0 && at + 1 < g_segs_n) {
    /* 窗口内还有下一段: 立刻前进, 零等待 */
    snprintf(full, sizeof full, "%s", g_segs[at + 1]);
} else if (at >= 0) {
    /* 已经播到窗口末尾: 只有末尾真的更新了才前进, 否则返回 0 等新段 */
    if (strcmp(g_segs[g_segs_n - 1], g_last_seg))
        snprintf(full, sizeof full, "%s", g_segs[g_segs_n - 1]);
    else { r = 0; goto done; }
} else {
    /* 首播 或 g_last_seg 已滑出窗口: 从倒数第 (1+HLSBUF) 段起播, 主动建缓冲 */
    int off = 1 + hlsbuf(); if (off > g_segs_n) off = g_segs_n;
    snprintf(full, sizeof full, "%s", g_segs[g_segs_n - off]);
}
```

三個分支對應三種處境：窗口內有存量 → 白拿；真到邊緣 → 才等；首播/滑出 → 主動往回退幾段**建緩衝**。

最後這個分支是關鍵。`NETTV_HLSBUF`（預設 3）讓首次取段從「倒數第 4 段」開始，等於一上來就攢了 3 段約 18 秒的餘量。之後每播完一段就往前挪一格，只要伺服器按段時長出貨，就永遠有下一段可播——**等待從常態變成例外**。

## 四、實測

修復後瀘縣源（窗口裡那 4 段存量）：

```
[hls] 选段 总=2311ms 拉列表=2311ms/1次 段数=5 命中=1 位=-1   ← 首播, 建缓冲
[hls] 选段 总= 225ms 拉列表= 225ms/1次 段数=5 命中=1 位=1
[hls] 选段 总= 202ms 拉列表= 202ms/1次 段数=5 命中=1 位=2
[hls] 选段 总= 225ms 拉列表= 225ms/1次 段数=5 命中=1 位=3
```

選段從 **4981ms → 225ms（-95%）**，「重播上一段」在存量耗盡前一次都沒觸發。對應的段間隙：

```
[供数] 段2: 段间隙=6029ms  成分: 选段=250ms   预取=5557ms 音频=5009ms
[供数] 段3: 段间隙=6431ms  成分: 选段=481ms   预取=11541ms 音频=10987ms
[供数] 段4: 段间隙=6234ms  成分: 选段=705ms   预取=17333ms 音频=16774ms
```

段間隙 **10309ms → 6029~6431ms（-40%）**。剩下的 5 秒清一色是 `音频`——那是上一篇定位的 `audio_feed()` 物理排空，屬於下一刀。

為了拿到真穩態（瀘縣源已停刷），換到仍在刷新的松潘源跑 120 秒：

```
[hls] 选段 总=304ms 命中=1 段数=3      ← 11 段全部命中, 无一次重播
[hls] 选段 总=322ms 命中=1 段数=3
[hls] 选段 总=331ms 命中=1 段数=3
...
[STAT] frames=5125 real=2439 elapsed=111993ms fps_x10=217
signal=11 = 0
```

**21.7fps，零崩潰**，選段穩定在 310ms 上下。段間隙仍顯示 11.2 秒，但那是因為松潘一段內容本來就約 10 秒、且 `音频` 一項佔了 8.6 秒——**選段已經不是瓶頸**。

不過只報修復後的數字是沒有說服力的，所以補了一組同二進位族對照（v23 = 修復前的選段邏輯），同樣是松潘源、同樣 120 秒：

| | fps | 段間隙 EMA | 選段 | rb 深度 | 命中率 |
|---|---|---|---|---|---|
| v23（舊選段） | **14.2** | 19029ms | ~310ms | 296 → 146（被抽乾） | — |
| v28（新選段） | **21.7** | 11400ms | 304~338ms | 377 → 489（持續漲） | 11/11 |

有意思的是：**松潘源上舊邏輯其實也不空等**——這個源刷新夠快，拉列表時總有新段，選段同樣只要 310ms。差距不來自 sleep，而來自**緩衝深度**：舊邏輯貼著直播邊緣跑，rb 一路被抽乾到 146（worker 等米下鍋）；新邏輯首播就建了 2~3 段餘量，rb 一路漲到 489。所以幀率差 53% 的真實原因是**供數不再斷頓**，而不是省下了那幾次 `sleep(1)`。

換句話說：這個修法在源刷新快時靠「建緩衝」，在源刷新慢時靠「吃窗口存量」，兩種處境都能兜住。

## 五、代價與取捨

天下沒有免費的幀率。這個修法把「延遲低但卡頓」換成了「流暢但延遲高」：起播時主動往回退 `HLSBUF` 段，預設 3 段約 18 秒延遲。

對電視直播來說我認為這筆交易划算：18 秒延遲用戶基本無感，而「每 10 秒卡一下 + 畫面原地循環」是肉眼可見的糟。真要貼直播邊緣，`NETTV_HLSBUF=0` 就能退回舊行為。

另外提醒一句：**這套邏輯依賴 `g_last_seg` 能在列表裡精確匹配到**。如果源在 URL 上掛了會變的 query 參數（鑑權串、`?m=` 時間戳之類），匹配會失敗並退化成「每輪都跳回建緩衝」。實測的源段名是穩定路徑，沒踩到，但換源時值得先看一眼 `[hls] 拉列表 ... 位=` 這一列——**正常應該是 -1 之後遞增，如果一直是 -1，就是匹配壞了**。

## 六、下一刀

段間隙的帳單現在長這樣：

| 項 | 修復前 | 現在 |
|---|---|---|
| 選段 | 4918ms | **~320ms** |
| 音頻排空 | 5231ms | **5231ms（未動）** |
| 下載 + 入池 | ~220ms | ~220ms |

77% 的黑洞已經集中在 `audio_feed()` 一家身上。第 27 篇做好的**非同步音頻泵**（`NETTV_AUDIO_ASYNC=1`，把整段 `rename` 給子行程慢餵）單獨測過能把音頻從 5231ms 壓到 1ms、幀率 +30%。兩刀疊加後，段週期會短於段內容時長，瓶頸將正式交給 worker 側（渲染 23.2ms）——那時候才是真的打硬仗。

## 附：本次踩到的兩個坑

1. **日誌被重生截斷**：`child_log_bound()` 用 `O_TRUNC` 打開 `/tmp/nettv_child.log`，monitor 每重啟一次子行程，前面的 `[STAT]`/`[供数]` 全沒了。95 秒跑出 973 幀，日誌裡卻只剩 1 條 `[供数]`——差點誤判成「一開局就崩」。已改成 `O_APPEND` + 每次重生打分隔標記。
2. **別拿一個源測到底**：瀘縣源凌晨停刷，同一份程式碼測出來是 15fps；換松潘源是 21.7fps。**偏離結論的往往不是程式碼，是源的狀態**。判源活沒活，隔 9 秒拉兩次 m3u8 比末段號就夠了。
