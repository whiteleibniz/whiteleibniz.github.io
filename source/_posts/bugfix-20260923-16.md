# bugfix 16 — GBA「改完游戏都进不去了」：把「超时补刀」放进收尸线程 = 给游戏设了 600ms 寿命

- **日期**：2026-09-23
- **影响范围**：`lv_pages/gba_game_page.c`（GBA 游戏应用，进游戏 100% 失败）
- **严重级别**：P0（功能完全不可用，且是我自己上一轮改动引入的回归）
- **关联**：bugfix 09~15（同一退出链路的连续迭代）
- **回滚点**：`lv_pages/gba_game_page.c.bak_exit2`（第 14 篇状态：能进游戏、偶发卡画面）

---

## 1. 现象

用户反馈：**「改完游戏都进不去了」**。按确认键选中 ROM 后，游戏画面「闪一下」就回到列表（有时连列表也一起退回桌面），看起来像"根本进不去"。

注意与上一篇（bugfix 15）的区别：

| | bugfix 15 | bugfix 16（本篇） |
|---|---|---|
| 现象 | 能进游戏、能玩，**退出时偶发卡在游戏画面** | **进游戏就秒退**，根本没得玩 |
| 玩家感受 | "偶尔不正常" | "完全不能用" |

**这是我在修 15 的过程中引入的新回归**——"越改越乱"的来源。

---

## 2. 取证（决定性日志）

`/tmp/lvgl_demo.log` 中一次"进游戏"的完整序列：

```
[HW Key] code=115 value=1 -> ENTER          ← 用户按确认键
[gba] 封面: .../Advance Wars (USA) (Rev 1).png
[system] LVGL draw paused                    ← 进入游戏
[Key Thread] 临时按键拦截器已启用。
[Key Thread] EVIOCGRAB 请求释放
[Key Thread] EVIOCGRAB 已释放(交给外部进程)
[Key Thread] EVIOCGRAB 请求恢复独占           ← ★ 紧接着就恢复了
[gba] fb 兜底翻回第0页(前端退出时停在第 1 页)   ← ★ 前端已经死了
[system] LVGL draw resumed[nav] key=27
[pm] 页面 'gba_game' 离场
```

**两个决定性事实**：

1. `EVIOCGRAB 已释放` 与 `EVIOCGRAB 请求恢复独占` 之间**没有 `[miniretro]` 的任何启动日志**——而正常进游戏这一段必然有 12 行（映射 fb、打开 5 个 evdev、加载 core、加载 ROM…）。
2. 顺序上"恢复独占 + 兜底翻页"紧跟在"释放独占"之后，说明**子进程已经退出**，且退得极快。

→ **前端不是自己退的，是被父进程杀掉的。**

---

## 3. 根因

上一轮（bugfix 15）我把收尸逻辑从「阻塞 `waitpid`」改成了：

```c
/* ★ 错误写法（bugfix 15 引入） */
bool reaped = false;
for(int i = 0; i < 60; i++) {            /* 最多 600ms */
    pid_t r = waitpid(pid, &status, WNOHANG);
    if(r == pid) { reaped = true; break; }
    usleep(10 * 1000);
}
if(!reaped) {
    if(kill(pid, 0) == 0) kill(pid, SIGKILL);   /* ★ 把还在正常跑的游戏杀了 */
    waitpid(pid, &status, 0);
}
```

**当时的动机是好的**：想给"前端挂死"留一个硬保证，同时不占用按键线程。注释里甚至写着"绝不设跑满 N 秒就算退出的上限"——

**但这段代码本身就是那个上限。** 判据从「子进程真的消失」偷偷变成了「600ms 到了」，于是：

> 用户按确认 → 前端启动 → 渲染第一帧 → **600ms 到了 → 父进程补 SIGKILL → 游戏"闪一下就没了"**。

而且这解释了为什么"第一次进有时能看到一帧画面"——前端启动 + 渲染第一帧大约就在 600ms 上下，运气好能出一帧。

**这条坑在项目记忆里被记过**（"六条已被证伪的路"第 ① 条：给等待循环设"跑满 N 秒就算退出"的上限），我明知故犯。

---

## 4. 修复

**原则：回到"判据只有一个硬事件——子进程真的消失"，把"等待"和"补刀"从收尸路径上彻底剥离出去。**

| # | 位置 | 改动 |
|---|---|---|
| A | 新增 `gba_kill_later()` | **专职补刀线程**：唯一持有"睡 600ms 再补 SIGKILL"的地方。与 wait 线程持同一把锁、用 `kill(pid,0)` + `child_pid` 一致性校验，避免误伤复用 pid |
| B | `gba_wait_thread()` | 删除 600ms 轮询超时，**恢复为阻塞 `waitpid`（无上限）**——与 FC 页 `fc_wait_thread` 逐行相同 |
| C | `gba_exit_to_list()` | 不在按键线程 `sleep`（会漏键把本页弹掉），改为 `kill(SIGTERM)` + 起补刀线程后**立即返回**去吞键 |
| D | `gba_on_destroy()` | 不变（主线程罕见路径，`SIGTERM` + 300ms 轮询保护 `.sav` 落盘） |

前端 `miniretro_gba.c` 本次**未改动**。

**补刀线程的关键实现**：

```c
static void *gba_kill_later(void *arg)
{
    pid_t pid = (pid_t)(intptr_t)arg;
    usleep(GBA_KILL_TIMEOUT_MS * 1000);

    pthread_mutex_lock(&s_gba.lock);
    bool alive = (s_gba.child_pid == pid);      /* wait 线程收尸后会置 -1 */
    if(alive && kill(pid, 0) == 0) {
        printf("[gba] 前端 %dms 未退出, 补 SIGKILL pid=%d\n", GBA_KILL_TIMEOUT_MS, (int)pid);
        kill(pid, SIGKILL);
    }
    pthread_mutex_unlock(&s_gba.lock);
    return NULL;
}
```

**为什么锁必须包住判断与补刀**：wait 线程把 `child_pid` 置 `-1` 也在同一把锁内。若 wait 已收尸（`child_pid != pid`），补刀线程直接跳过 → 不会对已回收、可能被复用的 pid 下手；若还能取到 `child_pid == pid`，说明进程确实还没被收尸、确实活着 → 补刀正当。

## 5. 自测（本次由 AI 实测通过）

**方法**：设备上注入 uinput 按键导航（`LEFT×2 → DOWN×3 → ENTER×2`，走 `usb_map` 路径）进入《Advance Wars》，然后检查前端存活。

**结果**：

| 检查项 | 结果 |
|---|---|
| 前端进程 | `miniretro_gba` pid=1780 **仍在运行**（距进入游戏已 1 分钟以上） |
| fb 前台页 | `yoffset=1280`（页 1）→ **前端在正常翻页渲染** |
| 日志误杀痕迹 | `grep -c '未退出, 补 SIGKILL'` = **0** |
| 游戏启动日志 | `[miniretro] 游戏已加载 240x160, 59.73 fps` 完整 |
| 画面 | 截图拿到《Advance Wars》实际游戏地图 ✓ |

**结论**：600ms 误杀已消除，游戏可正常进入并持续运行。

> 注：注入键走 `usb_map`，测不出"按买单键退出"（物理码 116 不经过 `gba_key_intercept`），退出路径仍需用户实机手按确认。

## 6. 「FC 为什么流畅、GBA 为什么不行」——差异表

这是用户反复问的核心问题，也是这条链路反复出错的根源。

| 维度 | FC（fceumm） | GBA（mgba） | 后果 |
|---|---|---|---|
| **fb 多缓冲页翻转** | **不翻页**，固定写第 0 页 | **每帧 `FBIOPAN_DISPLAY` 在 0/1 页间切** | GBA 退出必须**把页翻回 0**，否则 LVGL（只画页 0）画的界面看不见 → 屏幕定格游戏画面 |
| **退出时落盘量** | `.sav` 小，收尾快 | `.sav` 可达 32~128KB，真写 SD 卡可能数百 ms | GBA 需要更长的"等它收尾"时间 |
| **等待放哪儿** | 按键线程里 `usleep(120ms)` 就够（前端 ~30ms 就退） | 若同样睡在按键线程，**600ms 期间没人读 event0** → 堆着的事件漏给 LVGL 变成"返回"键 → 本页被弹掉 | GBA 必须把等待挪出按键线程 |
| **收尸判据** | 阻塞 `waitpid`，从来没有超时 | 曾被我加上 600ms 超时 → 变成"给游戏设寿命" | **这就是本篇的 P0** |
| **前端是否碰 fb 残留** | 不碰 | 翻页 + （曾）整页 memcpy 定格 | 决定"退出后画面由谁负责" |

**一句话**：FC 的前端**不碰 framebuffer 的结构**（不翻页、不拷页），所以它的退出只需要"杀进程 + 等收尸"；GBA 的前端**改了 framebuffer 的显示状态**（前台页），所以退出时**必须有人负责把它改回去**——多出来的这一份责任，如果图省事塞进"收尸线程"或"按键线程"，就会分别炸出"游戏进不去"和"退出卡画面"。

## 7. 教训 / 反模式

**新增反模式（已写入 `child-exit-hang-diagnosis` skill）：**

> **把「超时补刀」写进收尸线程 = 变相给子进程设寿命。**
> 看起来是"给挂死留硬保证"，实际把判据从「子进程真的消失」偷偷换成了「N 毫秒到了」。
> 症状很有迷惑性：**游戏/程序"闪一下就没了"、"进不去"**，而日志里收尸线程一切正常。
> 正解：**补刀必须挂在一个"只在收到退出请求后才存在"的专职线程上**，收尸路径永远只有一句
> 无上限的阻塞 `waitpid`。

**其他：**

1. **"判据只有一个硬事件"这条铁律必须落到代码上，不能只写在注释里。** 本次我的注释写着"绝不设上限"，代码却在设上限。
2. **回归的代价高于不修。** bugfix 15 为了解决"偶发卡画面"（低概率、可容忍），引入了"完全进不去"（100%、不可用）。**修概率性问题时，改动必须比问题本身更保守。**
3. **`EVIOCGRAB 请求释放` 到 `请求恢复独占` 之间的距离**是一个很好用的诊断量：太短 = 子进程被杀了（而不是自己退的）；太正常 = 前端正常在跑。**建议把这条写进排查清单。**
4. 静态校验比日志更快：`grep -c 'i < 60'`、`grep -c 'bool reaped'` 归零就能确认"超时逻辑已彻底删除"。
