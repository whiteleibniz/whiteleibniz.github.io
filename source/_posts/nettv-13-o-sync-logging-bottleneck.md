上一篇把「卡」从 0.08fps 抬到 6.3fps（**约 80 倍）之后，我一度以为剩下的就是硬解本身的极限——日志里白纸黑字写着「VSP 单帧解码 43ms，硬件上限 ≈23fps」，监控采样**也说 fb_render 要 33ms。按这个账算，25fps 天花板碰不动了。

但那是对照安卓的表现后不甘心又回头算的一笔账：**43ms 的「解码」里，厂商库自己报硬件只花了 14ms**。剩下 29ms 是什么？顺着这个问题往下挖，最后挖出来的东西完全不在解码器里——是**我自己一行一行加上去的取证日志**。

这篇记这个「日志吃帧率」的完整定位过程：每帧 140ms 的构成表、O_SYNC 的实测代价、以及一个反直觉的结论——**为了抓挂死而加的 trace，让每次解码都慢了 3 倍**。

## 一、先有账本，再开刀：每帧 140ms 拆成五段

不改代码，先从上一轮的完整日志里抠时间。日志里本来就有足够的埋点（AU 头、DRIVE 返回、9c 等待退出、上屏时间戳），写个 30 行的 awk 把它们按 AU 对齐：

| 段                 | 耗时         | 内容                                     |
| ----------------- | ---------- | -------------------------------------- |
| DRIVE（empty 同步投递） | **43ms**   | 厂商库自报：**硬件解码 14ms**                    |
| snap_state + 诊断打印 | ~37ms      | 状态快照 4 行 + pa_of 查询                    |
| 读帧 + 渲染           | ~62ms      | memcpy 3MB 暂存 + 签名扫描 + fb_render（33ms） |
| 尾部                | ~21ms      | fill(out)×2 + REFILL kick + 状态行        |
| **合计**            | **~140ms** | ≈7fps（监控 [STAT] 真值 13.2fps，多帧批处理拉回来的）  |

两个数字当场就对不上：**厂商库日志明写 `decRet: 0, 14ms`**，DRIVE 却花了 43ms；监控已有采样说 fb_render 33ms，但「读帧+渲染」整段 62ms。多出来的时间都在哪？

## 二、第一个凶手：15ms 一次的 O_SYNC

先测闪存写入的底价。设备 /tmp 在 eMMC 上，用 dd 循环各写 60 次 128 字节：

```
fsync  60×128B: 1110ms   ← 每次约 18.5ms
普通写 60×128B:  200ms   ← 每次约 3.3ms（含 fork/exec）
```

然后数一下热循环里到底有多少次同步写。这个项目为了「挂死时 stdout 全丢、相位日志必须活」，有两套日志都带 `O_SYNC`：

- `tr_line`：每次 DRIVE 前后各写一行 vsp_trace.log——**每次投递 2 次，每帧 6 次以上，而且默认是开的**。它是 10-19 为抓「第二个 IDR 挂死」加的，寄存器 MMIO 读（那次内核崩的真凶）后来已经默认关了，但**写文件这件事忘了关**。
- `phx`：REFILL_OUT 每路 2 行，加上每 AU 必触发的 kick 补队列，每帧 3~5 次。
- `ph`：段头一行。

**每帧约 11 次 O_SYNC**。按 15ms 算就是 165ms——比一整帧的时间还多；就算 eMMC 对小写入有合并、实际按 3~~5ms 算，也是每帧 30~~55ms。这把「解码 43ms」直接腰斩再腰斩。

最讽刺的点：`tr_line` 的注释里写着它是为了定位「挂在哪个 DRIVE」而加的。但它自己就是那个让 DRIVE 变慢的东西——**取证手段改变了被取证的系统**。这个项目里这已经是第三次了：调试代码打乱 VSP 状态机导致内核崩、ptsync 为治卡而加的限速器变成卡的放大器、O_SYNC trace 为抓挂死而拖慢每一帧。套路完全一样。

## 三、动手：一个变量——「诊断默认关」

按项目铁律一次只改一个变量，这轮的改动就只有一句话：**热循环诊断全部默认关，env 可恢复**。

```c
/* tr_line: 默认从「开」翻成「关」，NETTV_TRACE=1 才开 */
if (!(e && e[0] == '1')) { g_tr_off = 1; return; }

/* phx / snap_state / [r%04d] / AU头 / DRIVE返回 / [9c等] 统一走 kdiag_on() */
static int kdiag_on(void) {
    if (g_kdiag < 0) {
        const char *e = getenv("NETTV_KDIAG");
        g_kdiag = (e && *e && *e != '0') ? 1 : 0;
    }
    return g_kdiag || vlog_on();
}
```

同时补了一套**零 I/O 开销的分段聚合计时器**（每 200 AU 打一次均值）：墙钟、段循环、snap、读帧、渲染。诊断关了，账不能也跟着关——不然下一轮又要重新考古。

```c
{ long _pw = sys_time_ms();
  if (p_au_prev) { g_t_wall += _pw - p_au_prev; g_t_n++;
      if (g_t_n % 200 == 0)
          P("  [perf] AU#%d 均值: 墙钟=%.1f 段循环=%.1f snap=%.1f 读帧=%.1f 渲染=%.1f (ms)\n", ...);
  }
  p_au_prev = _pw; }
```

新二进制 128256 字节（旧版 128028 备份 .bak_1020），构建部署走既有脚本。

## 四、验证卡在一次「资源冲突」上

A/B 脚本早就写好了（A=新默认，B=`NETTV_STAGE=0` 直读 ION 省掉 3MB memcpy），两轮却都在 20 秒内崩成 `_exit(12)` 重启循环。查进程才发现：**用户桌面上正在放 TV**，VSP/ION 那口约 7MB 的池子被占着，我的第二个实例一路退避重试都抢不到输出 buffer。

两次都是同一个退出码 12（代码里写死的「自管 ION 仍 0 路，拒绝把 IOMMU handle 交给 VSP」），结合「改动只碰日志和计时器、昨天同时段无其他播放器时正常」两点，可以排除回归。这给项目记忆又补了一条：**帧率实验和用户播放互斥**，ION 池是独占资源，起实验前先确认没有活着的播放会话。

所以定论分两半：

- **已确凿**：O_SYNC 每帧 11 次、15ms/次的底价、43ms 里只有 14ms 是硬件（都有日志实测支撑）。
- **待量化**：关掉之后端到端到底多少 fps、直读 ION 能不能省掉那 20ms memcpy——脚本 `/tmp/v16_ab.sh` 已经放在设备上，用户停播后一条命令的事。

按账本估：关诊断约省 30~55ms，加直读 ION 再省 ~20ms，140ms → ~65ms ≈ **15fps**；再往上的 25fps 要动 fb_render 的 33ms（NEON 化或用 VSP 缩放——已确认解码端不支持，只能 CPU 侧做）和 DRIVE 里那 29ms 的厂商侧开销（我们的 Get_phy_addr hook 每帧重查 ion ioctl，fd→PA 可以做缓存）。

## 五、三条可带走的经验

1. **日志不是免费的，同步日志尤其不是。** 普通写 3ms、O_SYNC 15ms 的闪存上，一行 trace 就是半帧解码的时间。凡是挂在热循环里的日志，先按帧数乘一下再留。
2. **「硬件上限」要先问是不是。** 厂商库自己报的 14ms 和 DRIVE 外的 43ms 差了 3 倍，差的部分全在库外——mbinfo 回调、phys ioctl、bind/unbind、双份 FilledDone。性能定位要尊重厂商自己的计时，那是唯一不带我们滤镜的尺子。
3. **取证代码要有「保质期」。** 为抓一个 bug 加的 trace，bug 修完那天就是它的退休日。更好的做法是加的时候就定好默认值和关闭开关，别让临时代码变成默认路径——这个项目已经用三次内核崩和一次帧率惨案交了学费。
