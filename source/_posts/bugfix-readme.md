# Bug 修复归档

本目录归档**每一次 bug 修复的说明文档**。规则：每修复一个 bug，就在本目录新增一份
`bugfix_<日期>_<序号>_简述.md`，写清「现象 → 根因 → 定位过程 → 解决办法 → 验证」。

## 隐私红线（强制）

与 `AI工作流/README.md` 一致：**文档、git 备注、归档文件中禁止出现真实 SSH 密码、账号、真实 IP**。
一律使用占位符：`<设备IP>` / `<密码>`。

## 命名规范

```
bugfix/
├── README.md                              # 本文件（约定说明 + 索引）
├── bugfix_20260922_01_mplayer视频红蓝通道错乱.md
├── bugfix_20260922_02_xxx.md
└── ...
```

- 文件名格式：`bugfix_<日期>_<序号>_简述.md`
  - **日期**：修复完成日，`YYYYMMDD` 八位（如 `20260922`）。
  - **序号**：**当日**两位递增编号，从 `01` 起（如 `01`、`02`）。
  - **简述**：中文，不加空格。
  - 示例：`bugfix_20260922_01_mplayer视频红蓝通道错乱.md`
  这样文件名天然按时间排序，一眼看出修复先后，且不依赖 git 提交 SHA
  （文件名会改变提交自身的 SHA，存在先有鸡还是先有蛋的循环依赖，故不采用）。
- 序号一经分配不复用、不重排；修复被回退也保留文档，在正文标注「已回退」。
- 新增后**必须**在本文件末尾的「索引」表里补一行。
- 若该项目有 git 仓库，**建议**在文档头部「关联提交」一行填写修复该 bug 的提交短 SHA
  （提交后再回填，不影响文件名）。

## 文档结构（每篇必含）

| 章节 | 内容要求 |
|---|---|
| **现象** | 用户/测试看到的外部表现。只写看得见的事实，不写猜测 |
| **影响范围** | 哪些功能/页面/进程受影响；哪些**不受**影响（避免误伤无辜） |
| **根因** | 机制层面讲清"为什么会这样"。要能回答"为什么偏偏是这个字节/这一步" |
| **定位过程** | 怎么一步步逼近真相的：**关键实验**、排除掉的错误方向、以及**为什么先前判断是错的** |
| **解决办法** | 具体改了哪些文件、哪几行、为什么这样改。附代码片段 |
| **验证** | 可复现的验证步骤 + 实际结果。**颜色/显示类问题必须有人眼确认** |
| **经验教训** | 可迁移的方法论或踩过的坑（这一节最容易被省略，但最有复用价值） |

## 写作纪律（承自本项目既有教训）

1. **区分"假设"与"实测"**：只把人眼/日志/探针实测的结论写成事实；推理一律标注为推理。
2. **自证循环不算验证**：抓数据→按假设解码→"看起来对"不是证据。显示类问题必须人眼闭环。
3. **记录失败的方向**：把走错的路也写下来，否则后来者会重走一遍。
4. **命令可复现**：定位/验证命令要能直接粘贴执行（注意替换占位符）。
5. **不写"已修复"了事**：必须写清验证条件与结果，未完全验证的明确标出。
