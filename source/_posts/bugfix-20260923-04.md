# bugfix_20260923_04 — GBA 改用 miniretro 后仍然黑屏（video_cb 硬编码分辨率丢帧）

> **现象**：GBA 启动方式改成 `miniretro + mgba_libretro.so` 后，核心能加载、进程在跑，但**屏幕全黑**。
> **根因层**：`miniretro` 前端帧回调 `video_cb`（渲染管线）。
> **修复工作量**：`extern/miniretro/miniretro.c`（本项与「条纹」修复合计 +81/-13，见 `bugfix_20260923_05`）。
> **文件名**：`bugfix_20260923_04_GBA改用miniretro后仍黑屏.md`
> **关联提交**：（待提交后回填）
> **日期**：2026-09-23

## 现象

1. GBA 启动已改为 `miniretro extern/miniretro/mgba_libretro.so <rom> ...`（见 `bugfix_20260923_03`）。
2. 冒烟测试显示核心加载正常：`core: mGBA 0.11.0`、`游戏已加载 240x160, 59.73 fps`。
3. 但真实进入游戏时**全屏黑**，进程存活、无崩溃日志。
4. 对照：同一个 `miniretro` 跑 FC（`fceumm_libretro.so`，256×240）**画面完全正常**。

线索：**核心加载成功却黑屏 → 帧数据在渲染环节被丢掉了**，且只发生在 GBA 这一路。

## 影响范围

- **受影响**：所有 240×160 的核心（GBA / mGBA）。
- **不受影响**：FC（256×240）——仍走原路径，行为不变。
  （本次改动对 FC 透明，共用的 `miniretro` 可安全改。）

## 根因

`miniretro.c` 的帧回调 `video_cb` 把分辨率**硬编码**成 FC 的尺寸：

```c
#define FC_W 256
#define FC_H 240
...
static void video_cb(const void *data, unsigned width, unsigned height, size_t pitch)
{
    ...
    if(width != FC_W || height != FC_H) return;   /* 非 256x240 直接丢弃整帧 */
```

mGBA 输出的是 **240×160**（日志实锤：`游戏已加载 240x160`）。
`240 != 256` → 条件成立 → `return`，**每一帧都在进入绘制前被丢弃**，`fb_buf` 从不刷新 → 黑屏。

此外，同函数下面的 `scale_rotate90()` 还写死了源尺寸 `FC_W/FC_H`，即便放行也会用错尺寸。

## 定位过程

1. **确认链路**：冒烟测试证明 `core 加载正常`、ROM 正确、fb0 已 mmap、输入设备已打开 → 排除"没启动/没加载"。
2. **找到客观指标**：用"fb0 非黑像素占比"量化——黑屏时应 ≈ 0。
3. **读源码**：在 `miniretro.c` 里 `grep` 分辨率相关符号，`if(width != FC_W || height != FC_H) return;` 一眼可见。
4. **弯路（错方向）**：一开始怀疑"核心没加载 / 像素格式不对"，但日志已证核心加载成功；
   真正的原因是**尺寸守卫**，而不是格式。
5. **验证**：放行 240×160 后重编，受控自测 fb0 非黑像素占比从 ≈0 变为 **0.559** → 画面确实出来了。

## 解决办法

`extern/miniretro/miniretro.c`：

1. 放行 GBA 分辨率：

   ```c
   /* 放行 FC(256x240) 与 GBA(240x160) 两种分辨率; 其它异常尺寸拒绝 */
   if((width != FC_W || height != FC_H) && (width != 240 || height != 160)) return;
   ```

2. `scale_rotate90()` 改用**传入的**动态宽高（`out_h = out_w * rot_canvas_h / rot_canvas_w`），
   不再引用 `FC_W/FC_H`。
3. 补 **0RGB1555** 兜底分支（核心未主动声明像素格式时的默认值；mGBA 实际用 RGB565，分支 2）。
4. 重编：`cd extern/miniretro && sh build.sh`（该目录无 Makefile，用 `build.sh`）。

## 验证

- 受控自测（设备端单独跑 `miniretro mgba_libretro.so <rom>`）：
  `fb0 非黑像素 = 515088 / 921600，占比 0.559`，日志 `core 输出像素格式 = 2`（RGB565）。
  → **画面确实渲染出来了**（此前黑屏时应 ≈0）。
- **用户实机确认**："有图像了" —— 但仍描述为"撕裂状"，转入 `bugfix_20260923_05`。

## 经验教训

1. **复用别平台的前端时，硬编码的分辨率/尺寸守卫是头号杀手。**
   不同 libretro 核心的输出分辨率不同（fceumm 256×240、mGBA 240×160），
   前端任何"== 某尺寸才处理"的写法都会静默丢帧。
2. **"核心加载成功"不等于"有画面"**：加载日志只证明 `retro_load_game` 成功，
   帧要经过 `video_cb` 才能上屏，中间任何一次"静默 return"都会黑屏且不报错。
3. **量化指标（非黑像素占比）很好用，但只能证明"有画面"，证明不了"画面正确"**——
   它能抓出黑屏，抓不出错位/条纹。判"画面对不对"必须人眼看图。
