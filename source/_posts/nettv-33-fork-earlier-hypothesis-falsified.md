> 系列第 33 篇。上一篇把并行渲染池做成了成绩单（20fps → 28fps），但那次 10 分钟回归里藏着一个没解决的污点：**worker 每跑 ~150 秒就被 SIGSEGV 杀一次，10 分钟 3 次**。这一篇是"我以为我知道原因，结果不是"的完整记录——以及一条比结论更值钱的线索。

## 1. 起因：成绩单背后那个污点

回归数据很好看：28.2fps、池渲染 13~14ms、ION 泄漏 0、进程残留 0。但 stdout 里躺着三行：

```
*** monitor: 子进程自退 st=0xb ***
*** monitor: 重启 (子进程 @4215 帧)
```

每代 worker 都老老实实跑了四五千帧才死，不是启动期问题。而且死法很怪：**SIGSEGV，但处理器一句话都没留下**——没有 `/tmp/nettv_segv.log`，stdout 里也没有任何崩溃转储。

## 2. 假设：fork 的时机比 fork 本身更危险

我们的并行渲染池是"常驻子进程"：启动时 fork N 个，之后靠管道收发任务。原来的 fork 点是**第一帧**——那时 OMX 组件已经 init、VSP 已经打开并且正在解码。

于是很自然的一个假设：**在 VSP 正在工作的时候 fork，子进程会复制一份 VSP 的用户态状态**（buffer 队列、寄存器影子、厂商堆里的上下文），父子都认为自己持有这块硬件，状态迟早打架，最后父进程踩到野地址。

这个假设还有一个旁证：项目里早就定过一条铁律——`fork` 出来的子进程必须把 SEGV/BUS/ILL 复位成 `SIG_DFL`，因为父进程的 handler 末尾是 `siglongjmp(g_jb)`，而 `g_jb` 在**父进程栈**上；子进程一旦触发信号，就会 longjmp 进父进程的栈，凭空变成"第二个解码进程"去抢同一个 VSP。既然"子进程继承父进程的执行上下文"这条路上已经栽过一次，那"继承 VSP 状态"很可能就是第二次。

## 3. 方案 A：把池子挪到 VSP 之前

改动本身不复杂，难的是**三件必须先做好的配套**：

| 配套 | 为什么必须先做 |
|---|---|
| `render_cfg_init()` | 渲染配置（带高 / NEON / LUT）靠 fork 继承传给子进程，子进程内不碰 `getenv` |
| `stage_ensure()` | staging 必须 `mmap MAP_SHARED` 且**先于 fork 存在**，否则子进程拿到的是冻结副本（画面错且不报错） |
| `fb_init()` | 子进程写的是 fb 映射出来的地址，映射必须先存在 |

第一项还好，它是一个已有的函数，只是从"第一帧 lazy 调用"改成"提前显式调用"。第二项要动结构：原来 staging 是解码循环里一个 `static` 局部变量，第一帧才创建——只要它在那儿，池子就只能后 fork。所以把它提成文件作用域的 `g_stage` + `stage_ensure()`，行为不变（同样只创建一次），只是时机提前。

第三项是本机的老坑：池子 fork 得早了，之后 `exec` 出来的 mplayer、异步音频泵都会继承管道写端。万一池子进程真死了，父进程的 `read()` 因为别的进程还捏着写端而**永远收不到 EOF**——整帧卡死，而不是应有的"回退串行"。所以四条管道全部 `FD_CLOEXEC`（只在 `exec` 时生效，对靠继承拿 fd 的池子进程无影响）。

## 4. 先把"临终留言"翻案

翻 child.log 时，每次崩溃前最后一行都是同一句：

```
Parent process disappeared, exiting cache process.
```

第一反应是"mplayer 崩了，把我们也带走了"。但顺着进程树推一遍就发现因果是反的：

```
worker 死（SIGSEGV）
  → dl 被 PDEATHSIG 杀
    → mplayer 被杀（它的 PDEATHSIG 也是这么设的）
      → mplayer 的 cache 子进程发现父进程没了，打印这句并退出
```

这句**是结果不是原因**，而且它出现在我们的日志里只是因为 stdout 是继承的。差点被它带沟里——如果当时直接去查 mplayer，这一晚就白干了。

顺带记一条通用经验：**排查崩溃时，先问"这条日志是死因还是死后现象"**。死后现象的特征是它由**别人的子进程**打印，且和你的进程树是同一条死亡链的下游。

## 5. 结果：假设被证伪

同一台板子、同一个源、同样的三个 env（`NETTV_RPOOL=2` + `NETTV_AUDIO_ASYNC=1` + `NETTV_HLSBUF=1`），跑 5 分钟：

| 指标 | v32（基线，10 分钟） | v33（方案 A，5 分钟） |
|---|---|---|
| monitor 重启 | 3 次 | **1 次** |
| fps_x10 | 265~282 | 282 |
| 池渲染墙钟 | 14ms | 13~14ms |
| 首帧自检 | 通过 | 通过 |
| ION clients / 残留 | 0 / 0 | 0 / 0 |
| 音频丢段比 | 0.29 | 0 |

归一化一下：**基线是 1.5 次 / 5 分钟，v33 是 1 次 / 5 分钟**。在只有个位数样本的崩溃统计上，这叫"没有变化"。方案 A 被证伪——fork 时机不是这个崩溃的原因。

（另：这一轮里设备还发生过一次内核复位，时间点是上一轮 v33 跑到第 2 分钟时；第二次 5 分钟跑没有复现。没有足够样本判定它和 v33 有关，只作为疑点记录在笔记里，不作为结论。）

**v33 不部署。** 它没解决问题，就不该动现网——这条原则比"新版一定更好"重要。

## 6. 真值钱的线索：处理器一次都没跑

方案 A 里我塞了一个纯取证的改动：`sigaltstack` 备一块 64KB 替身栈 + `SA_ONSTACK`。动机是——三次 SIGSEGV 处理器零输出，最可能的解释是**栈溢出**：处理器没有栈可跑，内核直接按默认动作杀进程，现场全丢。

结果这条路也被堵死了：**加了 altstack，依旧零输出**；child.log 里 `SIGSEGV` 关键字出现 **0 次**。

处理器没跑，只剩几种可能：

1. 栈溢出（已被 altstack 排除大部分情况）；
2. handler 自己又崩了（但它第一行就是纯计算，然后才 `write`，没机会）；
3. **信号被屏蔽**——故障线程把 SIGSEGV 屏蔽了，内核找不到能投递的线程，直接按默认动作杀整个进程。

第 3 条不是空想，这个项目里就有先例：当年裸 `clone` 出来的渲染子线程会调 `rp_block_sig()` 屏蔽 SIGSEGV，它一崩就是"处理器零输出 + `/tmp/nettv_segv.log` 不存在"，和现在一模一样。那次因此定下了"渲染侧一律 fork、禁用裸 clone"的铁律。

现在的区别是：我们自己的两个会屏蔽信号的线程（vsync 翻页线程、档 2 渲染子进程）默认都是关的。所以嫌疑落到了**厂商库自己创建的线程**（`libstagefright` 的 ALooper / 解码线程）——那是我们改不到、也挡不住的地方。

## 7. 下一步：把黑匣子做在共享内存里

既然处理器帮不上忙，就别指望崩溃瞬间能取到什么，改成**平时一直在记**：

- worker 每帧把"当前环节 id / 帧号 / 段号"写进已有的 `g_cnt_shm`（`mmap MAP_SHARED`，monitor 手里也有一份）；
- 子进程一死，monitor 直接把 shm 里最后一组值打出来。

这套的关键指标是**零 I/O 开销**——写共享内存是几条指令，不像 `ph()` 那样每次 O_SYNC 落盘 15ms。代价是粒度粗（只到"环节"级），但足以区分"崩在厂商 DRIVE 里"还是"崩在读帧/渲染里"。

另一条并行的二分线：用 `NETTV_RPOOL=0 + AF=1` 和 `RPOOL=2 + AF=0` 各跑 5 分钟，把"渲染池"和"异步音频泵"这两个新加入的组件分别排除掉。

## 8. 这一晚的三条方法论

1. **证伪也要写进笔记**。假设被推翻但没留记录，下一轮会从头再推一遍——这次的"fork 时机"假设，推理链完整、旁证充分，照样是错的。记下来，下次直接跳过。
2. **先分清"死因"和"死后现象"**。`Parent process disappeared` 看起来像 mplayer 的锅，其实是死亡链的最下游。
3. **零成本的取证升级优先做**。`sigaltstack` 十行代码，把"栈溢出"这个假设直接判死，比任何推理都便宜。
