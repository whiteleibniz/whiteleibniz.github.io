# bugfix_20260922_03 — FM daemon 无故消失，收音机页永远显示"芯片 0000"

> **关联提交**：221fa7d

## 现象
`fm_user_daemon` 运行一段时间后**无声无息地消失**（`ps` 里找不到，socket 文件
`/tmp/fm_ctl.sock` 还在但 `connect()` 返回 `Connection refused`）。
收音机页因此永远显示 `芯片 0000`、`RDS 不可用`、`已关闭`，所有按钮点了没反应。
日志的最后几行只有正常的 `cmd='state'` / `cmd='rssi'`，**完全没有崩溃信息**。

## 影响范围
- 只影响 FM 收音机功能（页面 ↔ daemon 链路全断）。
- 不影响 lvgl_demo 主体：`lvgl_demo` 有自己的 `/root/lvgl_watchdog.sh` 保活，一直正常。
- 影响所有依赖 `/dev/fm` 常开 fd 的功能：daemon 一死，`/dev/fm` 被 close 触发
  `fm_release`（发 `at+fm=12` 并阻塞约 4s），FM 状态丢失。

## 根因
**对端已关闭的 socket 上做普通 `write()` 会触发 `SIGPIPE`，其默认动作是终止进程。**

daemon 的回写函数原本是：
```c
static void reply(int cfd, const char *fmt, ...)
{
    ...
    if (write(cfd, buf, (size_t)n) < 0)     /* ← 没有 MSG_NOSIGNAL */
        logf_("[fm] 回写失败: %s", strerror(errno));
}
```
且 `main()` 里**没有** `signal(SIGPIPE, SIG_IGN)`。

而客户端（lvgl_demo 收音机页）在"回复写出之前"断开是**常态**：
- 页面 `onDestroy`/应用被 `killall` 时连接被关；
- 页面的 IO 工作线程对 `rssi` 命令设 6s 超时，但内核 `GETRSSI` 要 ~4s；
  页面还会在超时后重连 → 旧连接被丢弃。

一旦发生，daemon 被 SIGPIPE 打死，**没有任何日志**（信号默认动作，不产生用户态输出）。

## 定位过程
1. 先确认进程真的没了、socket 是陈旧的（`pidof` 空、`Connection refused`）。
2. 看 daemon 源码的退出路径：`main()` 里 setup 之后的 `for(;;) accept(...)` 是死循环，
   **没有任何主动 `exit()`**；各命令分支也没有。→ 排除"逻辑自己退出"。
3. 于是只剩"被信号杀死 / 段错误"。grep 信号与写操作：
   ```
   grep -n "write(|send(|MSG_NOSIGNAL|SIGPIPE|signal(" fm_user_daemon.c
   → 112: write(fd, m,...)         （wcnd socket）
   → 252: write(cfd, buf, n)       （客户端 socket，无 MSG_NOSIGNAL）
   没有任何 signal(...)
   ```
4. 时间线吻合：每次"daemon 消失"都发生在**我重启 lvgl_demo 应用**之后。
5. **做对照实验**证明机制（`ssh_tools/sigpipe_ctrl.c`）：fork 两个子进程，各自
   `socketpair()` 后关掉对端，A 组用裸 `write()`、B 组用 `send(..., MSG_NOSIGNAL)`：
   ```
   B(MSG_NOSIGNAL)   : 活着, n=-1 errno=Broken pipe  <- 期望如此
   对照实验结束：A 组若没有输出即表示它已被 SIGPIPE 终止。
   ```
   **A 组完全没有输出 → 确实被 SIGPIPE 终止。** 机制在本机得到证实。

## 解决办法
两处修改（`ssh_tools/fm_user_daemon.c`）：

1. 统一 socket 写函数，永不产生 SIGPIPE：
```c
static int sock_send_raw(int fd, const char *buf, size_t n)
{
#ifdef MSG_NOSIGNAL
    return (int)send(fd, buf, n, MSG_NOSIGNAL);
#else
    return (int)write(fd, buf, n);
#endif
}
```
   - `reply()` 改用它；
   - `wcnd_fm_open()` 里向 `@wcnd` 写 `"wcn FM-OPEN"` 也改用它（同样是对端可能已断的 socket）。
2. `main()` 开头加兜底：
```c
signal(SIGPIPE, SIG_IGN);
```

另加**保活看门狗** `/root/fm_watchdog.sh`（每 5 秒 `pidof fm_user_daemon`，不在就拉起，
模式与既有 `/root/lvgl_watchdog.sh` 一致），防御 OOM/SIGKILL 等其它死法。

## 验证
- **回归测试**（设备端 `python3 /root/fm_sigpipe_test.py`）：6 轮"连上 → 发 `rssi`
  （内核要 ~4s 才回）→ 0.15s 后立刻 `close()`"，正是原本必死的最坏时序。
  结果：**6 轮全部存活，daemon pid 始终 6408 不变 → PASSED**。
- **对照实验**（上节 `sigpipe_ctrl`）：A 组静默死亡 / B 组存活 → 反证修复必要且有效。
- 重启应用后重进收音机页，页面恢复显示 `RDS 可用 · 芯片 2341 · 收听中`。
- 设备自行重启后，`/etc/local.d/zz_fm.start` 自动把 daemon 拉起（日志
  `[fm] wcn FM-OPEN -> WCNBTWIFI-CMD OK`、`chipid=0x2341 rds=1`、`就绪，监听 /tmp/fm_ctl.sock`）。

## 经验教训
1. **写 socket 一律用 `send(..., MSG_NOSIGNAL)`，并在长驻进程开头 `signal(SIGPIPE, SIG_IGN)`。**
   SIGPIPE 是"静默杀手"：不产生任何日志，现象是"进程莫名消失"，
   极易被误判为 OOM 或"自己退出了"。
2. **"没有 exit() 但进程没了" → 优先怀疑信号。** 排查顺序：
   代码退出路径 → 信号（SIGPIPE/SIGSEGV）→ 外部 SIGKILL/OOM。
3. **长驻 ipc daemon 必须考虑"客户端随时可能在回复前断开"**，
   这在 UI 进程会被重启的嵌入式场景里是高频事件，不是边缘情况。
4. 机制类结论要有**对照实验**：光"改完好了"不算证明，要能展示"改之前必坏、改之后必好"。
5. 每个长驻进程都应配保活看门狗；本项目已有 `lvgl_watchdog.sh` 的先例可照抄。
