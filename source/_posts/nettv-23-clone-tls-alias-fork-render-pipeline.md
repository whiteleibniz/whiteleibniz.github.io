上一篇把"治拖影"的翻页线程钉死之后（默认关掉，21.9fps 保平安），自然的问题就是：**帧率还有提升空间吗？** 账本摆在那儿——每帧 41.3ms = 厂商同步解码 14.1ms（硬底线）+ 读帧 2.7ms + 渲染 23.9ms。解码侧已经拆无可拆，唯一的便宜是把**渲染搬到第二个执行单元上和解码流水线化**：worker 侧只要 16.8ms，渲染侧 24.1ms，稳态帧率 = max(两者) ≈ 24ms ≈ 理论上限 41fps。这篇讲这个"档 2"方案的第一版实现——**又是必崩**，以及这次挖出来的、能一口气解释三次历史悬案的病根。

## 一、账本与目标

10-21/22 定稿的帧率账（泸县 1080p 源，60s 采样）：

| 阶段 | 耗时 | 性质 |
|---|---|---|
| bsOnMsg（厂商同步解码） | 14.1 ms | 硬底线，828 次采样全是 14ms，拆不掉 |
| 读帧（ION cached memcpy） | 2.7 ms | 已优化过（44.3→2.6） |
| 渲染（yuv2rgb + 几何合成 + 落 fb） | 23.9 ms | 剖析过：访存 10 / 算术 13 / 散写≈0 / 拷贝 2，无便宜变量 |
| **合计** | **41.3 ms → 21.9 fps** | |

渲染那 24ms 是纯 CPU 活（NEON 已经吃满），但它跟解码**没有数据依赖之外的顺序依赖**——解出第 n 帧再渲染第 n 帧，和第 n-1 帧的渲染完全可以同时进行。所以档 2 的形态很明确：**双缓冲 + 生产者/消费者**，worker 解出帧 memcpy 进 staging 就发布，渲染侧慢慢渲。

## 二、第一版：裸 clone 起渲染线程——必崩

最初实现就是最直觉的那种：`clone()` 起一个渲染线程，双缓冲 + 原子序号握手。逻辑跑通了，一上真机：

```
*** monitor: 子进程自退 st=0xb ***        （SIGSEGV，无限重启，0 帧）
```

phase.log（`O_APPEND|O_SYNC`，崩溃不丢）显示每一代死法完全一样：

```
t=... DRIVE empty(in) 喂 IDR+SPS+PPS (Annex-B 全序列, nFlags=0)
t=... mon-child-signal=11 st=0xb        （60~300ms 后）
```

**每一代 worker 都在"喂 IDR"之后猝死**——跟上一篇翻页线程的现象一模一样，连死亡相位都一致。

## 三、病根：clone 不传 CLONE_SETTLS，父子共用一个 TLS

`clone()` 的 flags 里没有 `CLONE_SETTLS`，会发生一件很隐蔽的事：**子线程的 TPIDRURO 寄存器原样继承父线程的值**——也就是父子两个线程**共用同一块 TLS（线程本地存储）**。

在裸 bionic（`nostdlib`）环境里这意味着：

1. 子线程调任何一个**失败的系统调用**，glibc/bionic 的 `__errno_location()` 会去写 errno——而 errno 就藏在 TLS 里的固定偏移；
2. 这一写，**父线程的 errno 被顺手改掉了**；
3. 父线程紧接着的"喂 IDR"逻辑依赖 errno 做分支判断 → 逻辑走错 → 拿着错的状态继续跑 → 野指针 SIGSEGV。

崩溃地址 `0x747474` = ASCII `"ttt"`，也符合"某块串数据被当指针解引用"的特征。

### 一口气解释三次悬案

把历史笔记翻出来对表，全中：

| 历史悬案 | 当时的归因 | 真相 |
|---|---|---|
| 10-15「第二个 IDR 必崩」 | ION 池干 → 次生崩溃 | clone 线程踩坏父线程 errno |
| 10-22「vsync 翻页线程治拖影必崩」 | 未定论（已默认关） | 同一个病 |
| 本次 v16h/v16i 渲染线程必崩 | —— | 同一个病 |

项目记忆里其实早就写了一条"**禁裸 clone 子线程内用 libc**（TLS 踩坏）"——但一直停留在"子线程自己别调 libc"的层面，**没有把"errno 别名会反杀父线程"和崩溃现象连起来**，所以前两次都去 ION 池里找答案了。这就是笔记的代价：规则写得太窄，下次换个姿势踩进来还是不认识。

## 四、方案：fork 替代 clone

既然病根是"共享地址空间导致互相踩"，解法就干脆做绝：**渲染侧改用 `fork()` 子进程**。

```
worker(父进程)                        渲染子进程
─────────────                        ─────────────
DRIVE 解一帧
memcpy → g_st[wn & 1]   (MAP_SHARED)
g_ps->wn++  ───────────发布────────▶  看到 wn > rn
                                      取 g_st[rn & 1]
                                      fb_render()（判重已在父进程做过）
                                      g_ps->rn++
```

结构上的好处：

- **子进程有独立地址空间**（私有 TLS、堆、栈），它爱怎么出错都出不到父进程头上，父子只共享**显式**的 MAP_SHARED 区域：一个 4KB 握手区（`wn/rn/rstop/rexited` 四个 volatile 字段）+ 两块 3MB 双 staging；
- 子进程把 SIGSEGV/SIGBUS/SIGILL **复位成默认动作**——真出了野指针，死自己一个，父进程 `waitpid(WNOHANG)` 发现后置 `g_pipe_on=0`，**自动回退单线程**，播放不中断；
- 子进程设 `PR_SET_PDEATHSIG(SIGKILL)`，父进程猝死不会留下孤儿渲染进程抱着 fb 不放。

## 五、三个值得记的实现细节

**1. 判重必须留在父进程。** 去重判据 `g_filled`（厂商每解出真帧回调递增）是**父进程地址空间里的量**；fork 之后子进程拿到的是 fork 那一刻的冻结副本，在子进程里判重会永远判"这是旧帧"，结果一帧都不渲。所以发布门放在父进程：`g_filled != filled_seen_p` 才 memcpy + `wn++`。

**2. 帧实宽 1920×1088×3/2 = 0x2FC400，staging 必须 ≥ 0x300000。** 旧代码按"宽×高×1.5 取整到 0x1000"算成 0x2FC000，memcpy 也只拷 0x2FC000——渲染侧读 chroma 平面时**越界 12KB**。malloc 后面有堆兜底所以从来不崩，但这是"画面左缘色带"的高度嫌疑；换成 mmap 定尺会直接 SIGBUS。修成 `ST_SIZE=0x300000` + 全帧拷贝。

**3. 收尾排空比 Kill 重要。** 退出时先 `rstop=1` 通知子进程"渲完手里这帧就退"，等 ≤3s 看 `rexited`；超时才对渲染子进程 `SIGKILL`——**这是全项目唯一允许 KILL 的场景**，因为此时 VSP DMA 早已在 worker 侧排空（`usleep(800ms)`），纯 CPU 渲染过程被杀没有任何硬件状态风险。反过来，解码进行中 KILL 播放器是会内核崩的（旧教训，两次实证）。

## 六、A/B 实测：fork 赢了稳定性，输了帧率

v17 构建部署后（`NETTV_PIPE=1` 开启、默认关），冒烟 45s：**signal=11 = 0**，`流水线: fork渲染子进程(v17)` + `已 fork(pid=19839, 双staging=MAP_SHARED 0x300000)` 确认生效。然后 ABBA 四组（泸县 1080p，各 60s，唯一变量 NETTV_PIPE）：

| 组 | env | signal=11 | 真帧 | fps | worker 墙钟构成 |
|---|---|---|---|---|---|
| A1 | 默认（单线程） | 0 | 1154 | **21.8** | 41.5 = bsOnMsg 14.2 + 读帧 2.6 + 渲染 24.2 |
| B1 | `NETTV_PIPE=1` | 0 | 929 | 17.5 | 36.6 = bsOnMsg 10.1 + 读帧 3.1 + 10.2 + ~13ms 等 render |
| B2 | `NETTV_PIPE=1` | 0 | 918 | 17.4 | 同 B1 |
| A2 | 默认（单线程） | 0 | 1130 | **21.8** | 41.6 = 14.2 + 2.7 + 24.0 |

稳定性目标满分（**fork 后 0 崩溃，渲染侧线程必崩的病根真被拔掉了**），但帧率 **-20%**。查根因一句话就够了：

```sh
cat /sys/devices/system/cpu/cpu1/online    # 1
cat /sys/devices/system/cpu/cpu2/online    # 0  ← 四个核 offline 了两个
```

**在线 CPU 只有 2 个。** 流水线的前提是"渲染与解码在两个执行单元上真并行"，在只有 2 个在线核、还要分给 monitor/dl/mplayer 的机器上，worker 和渲染子进程大部分时间在**分时复用同一个核**，外加每帧 3MB 的 staging 在两核间来回搬（L1 每核私有，cache line 通过 L2 迁移），内存总线和调度开销全部变成净损失。worker 墙钟确实从 41.5 降到 36.6ms，但总吞吐是 57ms/帧——**并行没有发生**。

所以定案：**`NETTV_PIPE` 默认关保持不动**，v17 的单线程路径零退化（A1/A2 与历史基线逐项一致）。但这个方向并没有被证伪到底——留了两个便宜的后续：

- **taskset 亲和性**：把渲染子进程钉在 cpu1、worker 留在 cpu0，排除调度分散因素再测一次；
- **online cpu2/cpu3**：四个核都在线的话，流水线的账本就真的能算了（写 `/sys` 热插拔节点属于改全局配置，要按项目铁律先确认再动）。

## 七、真正的红利：拖影有救了

回头盘点，v17 最大的价值不是帧率，是**把"渲染侧起线程"这个能力洗白了**。10-22 凌晨因为 clone 线程必崩而默认关掉的 vsync 翻页线程（治拖影），当时的嫌疑方向是"ioctl 和 VSP 并发踩 fb 锁"——**错了，真凶是 TLS 别名**。翻页线程本身只做 `WAITFORVSYNC` + `PAN_DRAW` + 等一小块共享状态，用 fork 子进程实现结构上不可能踩父进程，病根没了，功能可以回来了。这是下一篇的事。

## 八、经验

1. **`clone` 起线程在没有 `CLONE_SETTLS` 时是父子 TLS 别名，不是"轻量进程"。** 凡是要跑 libc（尤其是碰 errno）的工作线程，要么规规矩矩传 TLS，要么直接 fork——fork 的隔离性是结构保证，不依赖"记得传哪个 flag"。
2. **"子线程自己出事"和"子线程把父线程搞死"是两回事。** 后者防不住，因为犯罪现场不在自己身上；隔离边界要画在地址空间上，不是画在"我觉得它不会碰"上。
3. **状态判断要放在状态的所有者那一侧。** 判重放在子进程看着挺自然（"谁消费谁判断"），但状态量在父进程——跨了 fork，判断就必须留在父进程。
4. **尺寸常量要按"实宽"算，不要按"取整到好看"算。** 0x2FC000 和 0x2FC400 只差 1KB，换来 12KB 的越界读；这种 bug 靠 malloc 兜底一辈子不暴露，换 allocator 就炸。
5. **并行化之前先数核。** 这次档 2 的整份账本（"渲染 24ms 和解码 16.8ms 流水线化 ⇒ 上限 41fps"）在单核上是个笑话，在两核上也是个惨案——`cat /sys/devices/system/cpu/cpu*/online` 只要三秒钟，应该在写第一行流水线代码之前就看。顺带记住：**"理论上限"四个字，前提是执行单元真实存在**。
