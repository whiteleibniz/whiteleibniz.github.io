# bugfix_20260924_01 — 视频播放卡顿（先做 CPU 预算表，改一处参数 + 重编码片源）

> 日期：2026-09-24　设备：展讯 SC9832A（Alpine / 内核 3.10.65 / 720x1280 竖屏 fb）
> 关联提交：2341fad
> 结果：**解码从来不是瓶颈**；改一处播放参数 + 重编码片源后，实时倍率 **0.75× → 1.08×**
> 性质：性能问题，不是功能故障

---

## 1. 现象与诉求

用户反馈「视频画面和游戏画面卡顿」，并提出在设置里加一个 VSP/GSP 硬件加速开关，
希望打开后视频和游戏都走硬件。

**本轮没有急着写代码，而是先问「卡的到底是哪一步」。** 因为答案决定接下来是做
「视频硬解」（工期以周计、依赖逆向私有 ioctl）还是「硬件缩放」（工期以天计）——
选错方向就是白干几个星期。

## 2. 定位：做一张 CPU 预算表

方法：用同一个播放器跑同一份数据，**两次只差一个开关**，用耗时差量出某一环节的开销。

```sh
cd /home/lvgl_demo/lvgl_demo/sdcard/video
MP=/home/lvgl_demo/lvgl_demo/libs/mplayer/mplayer
$MP -benchmark -vo null -nosound -endpos 15 原子弹.mp4             # 纯解码
$MP -benchmark -vo null -nosound -endpos 15 -vf scale=720:1280 …   # 解码+缩放
$MP -benchmark -vo null -nosound -endpos 15 -vf rotate=1 …         # 解码+旋转
```

全程 `-vo null`（不写 framebuffer），**不会打扰正在使用这台设备的人**。

片源：H.264 1280x720 **60fps** 2821 kbps（竖屏机播横向片源）

| 跑法 | 解码 VC | 后处理 VO | 合计 | 相对实时 |
|---|---|---|---|---|
| 纯解码 | 10.23s | 0.003s | 10.42s | **1.47×** |
| `-vf scale=720:1280`（当时的写法） | 10.32s | **21.47s** | 31.98s | 0.47× |
| `-vf rotate=1` | 10.19s | 9.63s | 20.02s | 0.75× |
| `scale` + `-sws 0` | 10.20s | 11.25s | 21.64s | 0.69× |
| `scale` + `skiploopfilter` + `-sws 0` | 9.18s | 11.25s | 20.62s | 0.73× |

## 3. 根因（三条）

1. **解码从来不是瓶颈**：任何跑法里 VC 都稳定在 1.47× 实时。
   ⇒ 一开始最被看好的「VSP 视频硬解」对这个问题**收益有限**（把 VC 归零也只是从
   0.75× 抬到 1.56×，并不比后面两条便宜）。
2. **缩放是当时最贵的一步**（21.5s，占 2/3）。但更根本的是 —— **这一步本来就不需要存在**：
   片源 1280x720 是**横屏**，屏幕 720x1280 是**竖屏**，**旋转 90° 后尺寸正好相等**。
   旋转是纯像素重排，比插值缩放便宜一倍。
3. **片源 60fps 超出了这台机器的总 CPU 预算**：2×Cortex-A7，实测常驻 768MHz。
   即使把软件优化开到顶（最快缩放 + 跳环路滤波）也只有 0.73×，够不着实时。

## 4. 修复

### 4.1 App 侧：后处理从「缩放」改成「旋转」

`lv_pages/video_player_page.c`，两处 `execlp`（蓝牙出声 / 静音两条分支）+ 一处说明注释：

```c
-  "-vf", "scale=720:-2,expand=720:1280",
+  "-vf", "rotate=1,expand=720:1280",
```

保留 `expand=720:1280` 是为了兼容 **960x720** 这类片源 —— 它旋转后是 720x960，
高度不足才需要补黑边居中；1280x720 旋转后正好铺满，expand 不产生额外开销。

**附带收益**：画面从「屏幕中间一条小图（约 720x405）」变成**整屏**。

### 4.2 片源侧：重编码为 30fps Constrained Baseline

设备无 ffmpeg/mencoder 且无外网，所以在本机用 `imageio-ffmpeg` 转完再传回：

```sh
ffmpeg -y -i in.mp4 -vf fps=30 -c:v libx264 -profile:v baseline -level 3.0 \
       -preset slow -crf 25 -pix_fmt yuv420p -movflags +faststart -c:a copy out.mp4
```

| 文件 | 原 | 新 |
|---|---|---|
| 原子弹.mp4 | 3691 KB / High / 60fps | 591 KB / Constrained Baseline / 30fps |
| 海公牛.mp4 | 942 KB | 249 KB |
| 疼疼疼.mp4 | 3509 KB | 1129 KB |

Baseline 无 B 帧、无 CABAC，软解比 High profile 省力。原片备份在 `sdcard/video/_orig60fps/`。

## 5. 验证

改后同样方法复测：

| 跑法 | VC | VO | 合计 | 相对实时 |
|---|---|---|---|---|
| 新片源 + `rotate=1` | 4.305s | 4.841s | 9.237s | **1.08×** |
| 新片源 + App 实际参数 `rotate=1,expand=720:1280` | 4.278s | 4.803s | 9.170s | **1.09×** |

**0.75× → 1.08×，跨过实时线。** 编译 `MAKE_RC=0 / ERR=0`，lvgl_demo 单实例运行。

回滚点：设备 `lv_pages/video_player_page.c.bak_rotate`；原片 `video/_orig60fps/`。

## 6. 经验：反模式记录（已并入 skill）

- **反模式：没做预算表就承诺要上哪块硬件。** 本轮差点直接去做「VSP 硬解」（工期数周、
  依赖逆向私有 ioctl），而实测显示解码根本不是瓶颈。
- **反模式：只想着把某一步优化得更快，却不问这一步要不要存在。** 第一版结论是
  「缩放太贵，想办法让它更快」（`-sws 0`）；如果先问「能不能不缩放」，答案就是**旋转** ——
  直接省一半，而且画面更好看。
- **反模式：拿单次 `nproc` 下结论。** 这台设备有 `[sprd_hotplug]` 内核线程做动态调核，
  `nproc` 随负载在 1~4 之间变化。我曾一度以为是自己写 `online` 把核搞掉线了，
  查 `dmesg` 看到系统自己的 `plugin`/`unplug` 日志才排除。

## 7. 遗留

- **写 framebuffer 的开销仍未测**：本轮预算表全部基于 `-vo null`，不含真正写屏
  （720×1280×4B ≈ 3.7MB/帧）。需要在屏幕上放 15 秒测一次 `-vo fbdev` 才能补齐。
  **1.08× 的余量不算宽裕，实际观感以现场播放为准。**
- 游戏（GBA/FC）的卡顿来自 **CPU 模拟 + 缩放上屏**，与本轮无关。要治得走 GSP 硬件缩放 ——
  那才是用户最初想要的「硬件加速开关」的正解。
- VSP/GSP 可用性已勘察清楚（详见 MEMORY.md §10）：VSP 驱动完整，用户态入口是
  `/dev/sprd_vsp` + `/dev/sprd_vpp`，可参考 `libomx_avcdec_hw_sprd.so` /
  `hwcomposer.sc8830.so` 反汇编；但**全盘没有任何 vsp/gsp 头文件**，结构体布局只能靠猜。
