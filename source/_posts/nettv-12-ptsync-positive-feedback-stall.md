前面十篇一直在跟「崩」死磕：内核崩、挂死、绿屏、黑屏。等这些都解决了，能连续播 4800 帧之后，剩下的最后一个字是——**卡**。240 秒只上屏 19 帧，约 0.08fps，画面基本是幻灯片。

这篇讲怎么把这个数字抬到 6.3fps（约 80 倍），以及中间怎样用一次诊断实验**否证了追了三天的错误假设**。

## 一、先证伪：不是 IDR 的锅

之前一直有个假设：**「喂第二个 IDR 必挂死」**。日志里每代进程都止于 GOP#2 的 IDR 附近，三种流一致，看起来铁证如山。

要区分两种可能：

- **A**：流式状态下解码器见到任何第二个 IDR 就挂 → 修法是 GOP 边界软复位
- **B**：前面 36 轮累积了漂移/泄漏 → 修法是查资源泄漏

这两条修法完全不同，猜错就是白干一周。所以 10-19 在播放器里埋了个诊断开关 `NETTV_IDRREPLAY=K`：捕获第一个 IDR 之后，**连投 K 次同一份 IDR**（零累积，排掉所有漂移因素）。

10-20 凌晨第一次真正跑起来（上一轮脚本上传时变成 0 字节，白等了一天——这条后面单独说）：

```
[diag] NETTV_IDRREPLAY=3 (首 IDR 连投次数)
[diag] 捕获首 IDR 106336B(t=5), 之后连投 3 次
[diag] AU[4] 重投首 IDR 106336B(t=24), 剩 2 次
[diag] AU[5] 重投首 IDR 106336B(t=24), 剩 1 次
[diag] AU[6] 重投首 IDR 106336B(t=24), 剩 0 次
★ 帧#20 已上屏 @4887ms
★ 帧#21 已上屏 @5028ms
```

**连投三次，一次没挂，帧还在继续出。**

假设 A 直接出局。IDR 本身无罪，"第二个 IDR 必挂"这个说法从根上就是错的——它只是**表象**，真正的问题是 IDR 到达前后那段时间里发生的另一件事。

## 二、真凶：一个只会减速的 A-V 同步

同一份日志往下翻，有一行反复刷：

```
[ptsync] 视频落后, 暂缓解码 (累计 960)
```

240 秒里出现了 138 次（每 16 次丢帧打一行），换算下来丢了两千多次帧。

对应的代码长这样：

```c
/* 返回 1=要等(视频超前), -1=要丢(视频落后太多), 0=正常 */
static int pts_should_skip_or_wait(void)
{
    ...
    long long diff = (long long)vp - (long long)target;
    if (diff < -(long long)thresh) return -1;   /* 落后太多 → 丢帧 */
    return 0;
}
```

注意函数签名承诺了两件事：「超前就等」和「落后就丢」。但** `return 1` 这个分支从来没被实现过**——整个函数只有两种结局：丢帧，或者什么都不做。

于是逻辑变成了单向的：

1. 视频落后 → 丢帧
2. 丢帧 = 消费得更慢（代码里是 `rb_take` 扔掉一个 NAL 然后 `continue`）
3. 更慢 = 更落后
4. 回到第 1 步

**这是个正反馈。** 触发之后只会越来越卡，永远不会收敛。更要命的是触发条件极易满足：直播流的 `video_pts_ms` 每 6 秒（一个 TS 段）才更新一次，而墙钟 `target` 每毫秒都在涨，中间那 6 秒里 `diff` 一路走负，只要超过阈值（当时已放宽到 5000ms）就必然触发。

顺便说，拿它当 A-V 同步基准本身也不成立：音频走的是独立的 mplayer + `bt_audio.fifo`，跟视频根本不是一个时钟源。

## 三、A/B：一个 env 的差距

不改代码，只加一个环境变量，同一份二进制、同一个源（泸县 1080p）、同样 240 秒：

| 轮次 | NETTV_PTSSYNC | 上屏帧数 | AU 推进 | ptsync 丢帧 |
|------|---------------|---------|---------|------------|
| v13  | 默认开 | 19 | AU[27] 后停滞 | 累计 960 |
| v14  | `=0` 关 | 1191（63.6s 就跑满 400 帧上限） | AU[441] | 0 |

**约 80 倍。** 而且关掉之后 AU 一路推到 441，之前"止于 AU[36]"的现象也一并消失了——那同样是丢帧风暴造成的假象，不是解码器崩了。

## 四、修复

结论既然是"这条逻辑在当前架构下有害无益"，修复就是把已验证的 env 行为固化成默认值，代码和开关都留着：

```c
g_ptssync = (e && e[0] == '1') ? 1 : 0;   /* 10-20: 默认关 */
```

并在注释里写清楚为什么。整轮改动只有这一个字符级别的差异，构建产物大小完全没变（还是 128028 字节）——**这也说明这次不能靠二进制大小判版本，得看时间戳和行为**。

## 五、四条教训

**1. 单向的反馈环比没有反馈更危险。**
有减速没加速的控制器，一旦进入负向区间就是单程票。写"A-V 同步"这类闭环逻辑时，先确认两个方向都真的实现了，别让函数签名骗了自己。

**2. 表象会伪装成根因，而且伪装得很像。**
"第二个 IDR 必挂"追了三天，真相是 IDR 到达前后恰好触发了丢帧风暴。**先设计能一刀切开两种假设的实验（IDRREPLAY），再动手修。**

**3. 上传完一定要 md5。**
上一轮 /tmp/r26.sh 是 0 字节却显示 PUSHED，导致"实验跑过、结论没拿到"被误记成"实验失败"。这次改掉了流程，每一步都 `md5sum` 对照。

**4. 卡和崩要用同一套严谨度对待。**
崩有 backtrace，卡什么都没有，很容易靠猜。但卡的定位其实更便宜——一个 env 开关，四分钟就有答案。
