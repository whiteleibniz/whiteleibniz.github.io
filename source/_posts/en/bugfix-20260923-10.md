# bugfix_20260923_10 — GBA freezes completely on exit (rolling back the SIGUSR1 "picture hand-back" handshake scheme)

| Item | Content |
| --- | --- |
| Discovery time | 2026-09-23 |
| Fix time | 2026-09-23 |
| Module | `extern/miniretro/miniretro.c`, `lv_pages/gba_game_page.c` |
| Versions involved | Rolling back all changes from bugfix_20260923_09 |
| Severity level | High (the exit function is completely unusable and it also spreads to the previously normal FC page) |

## 1. Problem symptoms

The user reported two things on the real machine:

1. **GBA games freeze completely on exit** (previously it was "an occasional stutter", still usable);
2. **FC games also froze, even though they were fine before**.

This is a typical **regression**, and item 2 shows the problem is not in the GBA page itself — FC and GBA share the same `extern/miniretro/miniretro` front-end, so the culprit must be in that change on the miniretro side.

## 2. Scope of impact

- All entry points that launch miniretro from an LVGL page: the FC game page and the GBA game page;
- Since `setenv` is **main-process level**, the pollution persists across pages until `lvgl_demo` is restarted — that is, "after leaving GBA, FC also breaks", exactly matching the user's description.

## 3. Root cause analysis

bugfix_09 introduced two mechanisms to "save the ~340ms the kernel spends reclaiming `/dev/input/eventX`", and both are wrong:

### 3.1 `_exit(0)` cannot save the kernel's time; it only makes the process disappear later

It was assumed that `_exit(0)` skipping user-space `close()` calls would make the process disappear immediately. The measurement shows the opposite:

- `_exit(0)` only skips user-space `close()` calls one by one; the kernel's `exit_files()` **still** has to reclaim these fds, and it does so **uninterruptibly on the process exit path**;
- As a result, the child process disappears **later** after `_exit` than with a normal `return`.

The device log is ironclad evidence (same process, with receipt of SIGTERM as time zero):

```
[miniretro][timing] fb_restore 完成          t=   33.8 ms
[miniretro][timing] 收尾完成(快退出)         t=   39.9 ms
[gba] 子进程 17830 未按时退出, SIGKILL 兜底        ← 5 秒后才出现这一行
```

All cleanup finished in `39.9ms`, yet the process was not reclaimed for 5s — all the time was consumed in the kernel's exit path.

### 3.2 Putting the "wait for reaping" timeout loop inside a mutex → UI recovery is dragged out to a full 5 seconds

The structure of `gba_wait_thread` on the GBA page is:

```
阶段① 等 SIGUSR1 / 子进程退出（≤500ms）
pthread_mutex_lock(&s_gba.lock);
阶段② 等收尸，最多 1000 × 5ms = 5s          ← 在锁内
pthread_mutex_unlock(&s_gba.lock);
hardware_keys_set_grab(true);
app_runtime_set_lvgl_paused(false);        ← UI 恢复在锁外，必须等阶段② 结束
```

The child process does not disappear for a long time → phase ② runs the full 5s → **the UI recovers only after a full 5 seconds** = "freezes completely on exit".

The FC page, meanwhile, is blocked on the same non-disappearing child process via `waitpid(pid, NULL, 0)` **with no timeout**,
and likewise hangs — this is the reason "FC was fine before but is stuck now".

### 3.3 Incidental defect: the handshake gate polluted the main process's environment

`gba_launch()` calls `setenv("MINIRETRO_UI_RELEASE_SIGNAL", "1", 1)` before `fork()`.
`setenv` modifies the **current process's** (`lvgl_demo`'s) environment block, which is retained permanently once set:

- Child processes forked later by the FC page also inherit the variable, and thus also send `SIGUSR1` to the parent process;
- The default action of `SIGUSR1` is to **terminate the process** — once the gate fails (for example, the page-side handler is changed back), the parent process is killed by the child process it launched itself.

Conclusion: **do not race against the kernel.** The speed of the exit path is decided by the kernel; the only thing user space can do is "not wait for it to finish on its own".

## 4. Fix

**Completely roll back bugfix_09 and switch to the FC page's exit strategy, which has long been verified on the real machine.**

### miniretro side (child process)

- Delete `notify_parent_ui_released()` and its call, as well as the environment variable gate;
- `_exit(0)` → restore to a normal `return 0` (leave the cleanup to glibc/the kernel as before);
- Keep `on_quit_signal` (SIGTERM → `quit=1` for graceful cleanup) and `fb_restore()` (flip back to page 0 + clear the screen, preventing picture residue) — these two are the correct fixes from bugfix_07 and are not in the rollback scope;
- Keep the `td()` staged timing logs, which are still needed for locating similar problems in the future.

### Page side (`lv_pages/gba_game_page.c`)

- Delete `s_gba_ui_released`, `gba_ui_release_handler`, `setenv`, and `signal(SIGUSR1,…)`;
- `gba_exit_to_list()` is restored to the FC version:

  ```c
  kill(pid, SIGTERM);            /* 让它优雅收尾: 翻页+清屏, 实测 ~40ms */
  usleep(120 * 1000);            /* 足够它把 fb 交还 */
  if(kill(pid, 0) == 0) kill(pid, SIGKILL);   /* 不等它在内核里慢慢收 fd */
  ```

- `gba_wait_thread()` changes reaping to **WNOHANG polling with a 3s cap, never blocking indefinitely**;
  only on timeout does it `SIGKILL` and hand off to the `gba_reap_bg()` background thread for a clean reap (no zombies).
  The only difference from FC is an extra cap as insurance; the normal path returns within 200ms and never triggers it.

## 5. Verification method and results

One-shot measurement on the device (replicating the new page-side logic: SIGTERM → 120ms → SIGKILL → poll for reaping):

```bash
python3 /tmp/gba_exit_verify.py
```

| Metric | Result |
| --- | --- |
| Whether the child process is still alive at 120ms | `True` (normal, it is finishing up in the kernel) |
| Time SIGKILL is sent | 120.4 ms |
| **From SIGTERM to reaping complete** | **455.0 ms** (original scheme >5000 ms) |
| Time `fb_restore` completes | 33.8 ms (the picture has been handed back before this) |
| Exit code | 0 |
| New zombies | None |
| Processes after recovery | `lvgl_demo` ×1, `lvgl_watchdog` ×1 (single instance) |

Compilation side: miniretro's `gcc` returned 0, with 0 errors / 0 warnings; `lvgl_demo`'s `make -j2` returned 0, with 0 errors.
Deployment uses "compile to `*.tmp` then `mv -f` atomic replacement", avoiding exec into a half-overwritten binary while the user is playing.

## 6. Regression risks

- **Exiting still has about 0.45s of waiting**: 120ms of it is our deliberate wait for it to reset the picture, and the latter ~335ms is the kernel's inherent overhead for reclaiming fds, which happens after "the picture has gone black" and is subjectively "a flash of black screen" rather than "a freeze".
  This matches the FC page's behavior and is an acceptable cost.
- If it still feels slow in the future, the correct direction is **"recover the UI as soon as the picture is handed back, and fully background the reaping"**,
  rather than shortening the child process's lifetime — note not to use a main-process-level switch like `setenv` as a gate again.
- The page destruction path (`onDestroy`) already does `SIGKILL` first and then `waitpid`, and is unaffected.
- This change did not touch rendering (double buffering/pitch/240×160) or the audio chain, so the color and sound quality should not change.
