# bugfix_20260923_04 — GBA still shows a black screen after switching to miniretro (hard-coded resolution in video_cb drops frames)

> **Symptoms**: After changing the GBA launch method to `miniretro + mgba_libretro.so`, the core can load and the process is running, but **the whole screen is black**.
> **Root cause layer**: The `miniretro` front-end's frame callback `video_cb` (rendering pipeline).
> **Fix effort**: `extern/miniretro/miniretro.c` (this item and the "stripes" fix total +81/-13 together; see `bugfix_20260923_05`).
> **File name**: `bugfix_20260923_04_GBA改用miniretro后仍黑屏.md`
> **Related commit**: (to be backfilled after commit)
> **Date**: 2026-09-23

## Symptoms

1. The GBA launch method has been changed to `miniretro extern/miniretro/mgba_libretro.so <rom> ...` (see `bugfix_20260923_03`).
2. The smoke test shows the core loads normally: `core: mGBA 0.11.0`, `游戏已加载 240x160, 59.73 fps`.
3. But when actually entering the game, **the whole screen is black**, with the process alive and no crash log.
4. Comparison: the same `miniretro` running FC (`fceumm_libretro.so`, 256×240) **renders the picture completely normally**.

Clue: **the core loads successfully yet the screen is black → the frame data is being dropped in the rendering stage**, and it happens only on the GBA path.

## Scope of impact

- **Affected**: All 240×160 cores (GBA / mGBA).
- **Not affected**: FC (256×240) — it still goes through the original path with unchanged behavior.
  (This change is transparent to FC; the shared `miniretro` can be safely modified.)

## Root cause

The frame callback `video_cb` in `miniretro.c` **hard-codes** the resolution to FC's size:

```c
#define FC_W 256
#define FC_H 240
...
static void video_cb(const void *data, unsigned width, unsigned height, size_t pitch)
{
    ...
    if(width != FC_W || height != FC_H) return;   /* 非 256x240 直接丢弃整帧 */
```

mGBA outputs **240×160** (hard evidence from the log: `游戏已加载 240x160`).
`240 != 256` → the condition holds → `return`, so **every frame is discarded before drawing**, `fb_buf` is never refreshed → black screen.

In addition, `scale_rotate90()` further down in the same function also hard-codes the source size `FC_W/FC_H`; even if frames were let through, the wrong size would be used.

## Diagnosis process

1. **Confirm the chain**: the smoke test proves the `core loads normally`, the ROM is correct, fb0 is mmapped, and the input device is open → rule out "it did not start / did not load".
2. **Find an objective metric**: quantify it with "the proportion of non-black pixels on fb0" — during a black screen it should be ≈ 0.
3. **Read the source code**: `grep` resolution-related symbols in `miniretro.c`, and `if(width != FC_W || height != FC_H) return;` is visible at a glance.
4. **Detour (wrong direction)**: initially suspected "the core did not load / the pixel format is wrong", but the log had already proven the core loaded successfully; the real cause was the **size guard**, not the format.
5. **Verify**: after letting 240×160 through and recompiling, the controlled self-test's proportion of non-black pixels on fb0 changed from ≈0 to **0.559** → the picture really did come out.

## Solution

`extern/miniretro/miniretro.c`:

1. Let the GBA resolution through:

   ```c
   /* 放行 FC(256x240) 与 GBA(240x160) 两种分辨率; 其它异常尺寸拒绝 */
   if((width != FC_W || height != FC_H) && (width != 240 || height != 160)) return;
   ```

2. `scale_rotate90()` is changed to use the **passed-in** dynamic width and height (`out_h = out_w * rot_canvas_h / rot_canvas_w`), no longer referencing `FC_W/FC_H`.
3. Add a **0RGB1555** fallback branch (the default when the core does not actively declare a pixel format; mGBA actually uses RGB565, branch 2).
4. Recompile: `cd extern/miniretro && sh build.sh` (this directory has no Makefile; it uses `build.sh`).

## Verification

- Controlled self-test (running `miniretro mgba_libretro.so <rom>` standalone on the device):
  `fb0 非黑像素 = 515088 / 921600，占比 0.559`, and the log shows `core 输出像素格式 = 2` (RGB565).
  → **The picture really is rendered** (it should have been ≈0 during the previous black screen).
- **User confirmation on the real machine**: "there is a picture now" — but it is still described as "tearing-like", moving on to `bugfix_20260923_05`.

## Lessons learned

1. **When reusing a front-end from another platform, a hard-coded resolution/size guard is the number-one killer.**
   Different libretro cores output different resolutions (fceumm 256×240, mGBA 240×160), and any "== a certain size is processed" pattern in the front-end silently drops frames.
2. **"The core loaded successfully" does not mean "there is a picture"**: the load log only proves that `retro_load_game` succeeded; frames must go through `video_cb` to reach the screen, and any single "silent return" in between causes a black screen with no error reported.
3. **Quantitative metrics (proportion of non-black pixels) are very useful, but they can only prove "there is a picture", not "the picture is correct"** — it can catch a black screen, but not misalignment/stripes. Judging "whether the picture is correct" requires human eyes on the image.
