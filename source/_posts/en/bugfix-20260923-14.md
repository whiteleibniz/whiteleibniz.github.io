# bugfix_20260923_14 — GBA "hangs" after exit (page-flip residue: the screen stays frozen on the game picture)

- **Date**: 2026-09-23
- **Symptom**: after a GBA game exits, the screen is **not black** (the game picture is still shown), but **the UI never comes back and the keys seem dead**; the only option is to restart the app. The user described it as "no black screen anymore, it just hangs outright". **Intermittent** — sometimes normal, sometimes it always hangs.
- **Affected scope**: `lv_pages/gba_game_page.c`, `extern/miniretro/miniretro_gba.c` (GBA frontend)
- **Does it affect FC**: **No** (FC uses the original `miniretro`, which never flips pages)

---

## 1. Background: the two drivers disagree on what a "page" means

The device framebuffer has 3 virtual pages (`yres_virtual=3840` = 3×1280).

| Who | How it uses fb0 |
|---|---|
| **LVGL** (`lv_linux_fbdev`) | Draws only at the mmap base address = **always writes page 0**; `vinfo.yoffset` is set to 0 at init and never changed afterwards; **zero occurrences of `FBIOPAN_DISPLAY`** in the source |
| **GBA frontend** (`miniretro_gba`) | Uses `FBIOPAN_DISPLAY` double-buffered page flipping to eliminate tearing → the foreground page alternates **between pages 0/1** |

**Key inference**: as long as the foreground page stops on page 1 at exit, **whatever LVGL draws is invisible** — because LVGL always writes to page 0 while the screen displays page 1.

## 2. Root cause

1. The frontend flips a page for every rendered frame, so **whether the foreground page is 0 or 1 depends on "the moment of exit"**. Measured frame captures: after starting the game, `yoffset=1280 → 0 → 1280 → 1280 → 1280` was observed in sequence (within the same game session).
2. On exit the frontend would normally flip back to page 0 in `fb_restore()` (**targeted measurement: 0.4s after SIGTERM `yoffset` changes from 1280 to 0**), but the parent process `gba_exit_to_list()` sends a supplementary SIGKILL just **120ms after SIGTERM**; and the frontend's cleanup includes `core_deinit()` — **which flushes the .sav battery save to the SD card**, and when the card write is slow this far exceeds 120ms.
3. Once interrupted by SIGKILL → **the page flip never happens → the foreground page is permanently stuck on page 1 → the screen stays frozen on the game picture** → "hang".

> This explains **why it is intermittent**: the save is already in the page cache → cleanup <120ms → normal; a real SD card write → killed → hang.

## 3. Evidence

| Evidence | Content |
|---|---|
| Source code | `lv_linux_fbdev.c:174 dsc->vinfo.yoffset = 0;` (never changed afterwards), `grep -n 'PAN'` **zero hits** |
| Frame captures | images `shots/final/01..10`: during runtime `yoffset` alternates between 0/1 |
| Targeted experiment | run `miniretro_gba` alone: `yoffset=1280` during runtime → 0.4s after SIGTERM **→0** (showing the frontend cleanup **can** flip the page; the problem is only "whether it gets the chance to run") |
| Residue forensics | `shots/guard/01`: the "desktop" captured after restarting the app is actually **the previous game's picture stored in page 1** (`yoffset=1280`) — the material form of the hang |
| Exclusions | the frontend exit log is complete (`收尾完成 t=30.8ms`), no zombies, no crash loop, `hardware_keys`'s `EVIOCGRAB` idempotency is normal |

## 4. Fix (three layers of fallback, all "idempotent + only act on the abnormal path")

### 4.1 Frontend `miniretro_gba.c` — `fb_restore()` changed to **unconditionally** flip back to page 0

Remove the "first read `yoffset`, flip only if non-zero" branch: flipping to page 0 is itself an idempotent operation, and the check only adds one more branch that can go wrong (although this driver's read-back was measured to be reliable, there is no need to rely on it). On failure / when the flip cannot be performed, print `★ 翻回第0页失败` to help on-site diagnosis.

### 4.2 GBA page — new `gba_reset_fb_page()`: **the parent process provides its own fallback page flip**

Open `/dev/fb0`, and if `yoffset != 0`, `FBIOPAN_DISPLAY` it to 0. **This holds whether or not the frontend was killed** — this is the layer that fixes the root cause. It is called in **3 places**:

| Call site | Purpose |
|---|---|
| `gba_wait_thread()` recovery section (before `set_lvgl_paused(false)`) | game exit → before restoring the UI, first ensure the visible page is page 0 |
| `gba_on_destroy()` | cover it once more when the page leaves |
| `gba_on_create()` | zero it on page entry (in case the last abnormal exit left page-1 residue) |

### 4.3 Supplementary kill delay 120ms → 600ms

Leave time for "flushing the save + flipping the page". **The supplementary kill must be kept** (when the child process really hangs, without SIGKILL the blocking `waitpid` would never return). This 600ms is only spent in the **key thread** and does not slow down UI restoration.

### 4.4 After the restore redraw, add one `lv_refr_now(NULL)`

With only `invalidate`, the actual output has to wait for the next `lv_timer_handler` round; refresh one frame immediately to eliminate the window where "the flag was consumed but the picture was not drawn back".

## 6. Anti-pattern record (new this round, already merged into the skill)

- **Multi-buffered page flipping must "return home" on exit**: as long as one consumer (LVGL) does not flip pages while another producer (external player/emulator) does, **not settling the foreground page on exit = permanent black screen/freeze**. And the responsibility for returning home cannot be left solely to a child process that can be force-killed — the parent process must be able to provide its own fallback.
- **The SIGKILL deadline for a child process must account for its flush overhead** (saves/screenshots/log flushing), otherwise "you think you are guarding against a hang, but you are actually creating a failure".

## 7. Leftovers

- Exit to UI restoration still takes ~400ms (the inherent overhead of the kernel reclaiming evdev fds), **deliberately kept** (consistent with FC).
- Of the three layers of fallback described in this document, only "the frontend flips pages unconditionally" requires rebuilding the frontend; the other layers are all on the page side.
- If double buffering is ever added to the FC page as well (the current FC frontend does not flip pages and has no such problem), **these three layers of fallback must be moved over together**.
