# bugfix_20260923_01 — Bluetooth shows "Connected" while it is actually not connected

> **Symptoms**: The Bluetooth page shows "Connected: 小爱音箱-1303" while there is no usable connection in reality — the speaker makes no sound, and after about 1 minute the state flips back to "Paired" by itself; repeated reconnection attempts behave the same way.
> **Root cause layer**: The `conn` semantics of the user-space Bluetooth protocol stack `bt_user_daemon` / the LVGL Bluetooth page's criterion.
> **Fix effort**: 1 file, +64/-13 lines (`lv_pages/bluetooth_page.c`).
> **File name**: `bugfix_20260923_01_蓝牙显示已连接实际未连接.md`
> **Related commit**: 221fa7d
> **Date**: 2026-09-23

## Symptoms

The Bluetooth settings page shows **`Connected: 小爱音箱-1303`**, and the right side of the device row also shows a **green "Connected"**, but:

- The speaker (小爱音箱-1303, a Xiaomi Xiao AI Speaker) shows no reaction at all (it plays no prompt tone, and the phone/speaker side does not show that it is connected either);
- After a while (about 1 minute) the state **changes back to "Paired" by itself**;
- Repeatedly clicking the device to reconnect behaves the same way; it is forever "connected yet seemingly not connected".

In other words: **the UI says connected, but there is no usable connection in reality.**

## Scope of impact

| | |
|---|---|
| **Affected** | The connection status display on the Bluetooth page; A2DP audio output (the speaker makes no sound); the user cannot tell whether it is actually connected |
| **Not affected** | The Bluetooth switch, scanning/pairing list reads, the pairing records themselves; FM radio; the desktop and other pages |

## Root cause

**Two layers of causes are superimposed**, and neither can be omitted.

### 3.1 Direct cause: the Bluetooth page treats "the ACL link exists" as "Connected"

The `conn` command of `bt_user_daemon` only means that the **ACL (baseband link) has been established**, not that the upper-layer profile (A2DP) is available. The original criterion in `bluetooth_page.c` was exactly this:

```c
bp_get_conn_mac(conn_mac, sizeof(conn_mac));   /* conn 命令 */
if(conn_mac[0]) snprintf(detail, ..., "已连接: %s", nm);   /* ← 直接当成已连接 */
```

### 3.2 Root cause: the link key stored on this machine has been invalidated by the speaker side, so authentication fails

- The link key is stored in `/tmp/bt_linkkey.conf` (`<MAC> <32-bit hex>`, 16 bytes).
- The speaker side has discarded/regenerated that pairing record → the key on this machine **no longer matches**.
- But when the daemon receives the controller's `Link Key Request`, **it replies positive as long as a key exists locally** (the log's exact words: `[pair] link key req -> positive(已存 key, 免 SSP)`), so **re-pairing never happens**.
- Result: HCI authentication fails —

```
[pair] auth complete status=5        ← 0x05 = Authentication Failure
[pair] done paired=1 auth_ok=1 enc_ok=0 -> A2DP
[auth] auth complete status=5
[auth] auth failed
```

- `enc_ok=0` means that **link encryption was never established**, so A2DP naturally cannot be set up (`AVDTP_START` is never sent).
- But **the ACL link has already been established** (L2CAP works and SDP can be queried), so the daemon's `conn` still replies `OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303` → the UI shows "Connected".
- After about 60 seconds the speaker side gives up and the link drops (`[main] disconnect complete evt`), and only then does the daemon flip back to `IDLE`.

In one sentence: **ACL works, authentication fails, encryption is never established, A2DP never starts, yet the UI only looks at ACL.**

## Diagnosis process

### 4.1 The key truth-teller: whether `/tmp/bt_audio.fifo` has a reader

When the daemon's A2DP media loop starts, it **opens the read end of `/tmp/bt_audio.fifo`**. Therefore, opening the write end in non-blocking mode is enough to tell whether the media loop is running:

```python
import os
try:
    fd = os.open("/tmp/bt_audio.fifo", os.O_WRONLY | os.O_NONBLOCK); os.close(fd)
    print("a2dp=True  (有读者，媒体循环在跑)")
except OSError as e:
    print("a2dp=False (无读者)", e)      # ENXIO(6) = No such device or address
```

This is the **only user-space visible A2DP truth** obtainable on this machine. Measured results:

```
T+00  conn='OK IDLE'                                  a2dp=False
T+02  conn='OK CONN c5:09:... 小爱音箱-1303'          a2dp=False   ← 假连接
...   （持续 60 秒）                                   a2dp=False
T+62  conn='OK IDLE'                                  a2dp=False
RESULT connect -> 'RC 0'        ← connect 还回成功！
```

**`connect` returns `RC 0` and `conn` reports CONN, but the fifo never has a reader** → judged to be a fake connection.

### 4.2 Trial and error, and ruled-out directions

| Attempt | Result |
|---|---|
| Suspect that the UI only queries once and does not refresh | ❌ The page already has a 15s auto-refresh (`BP_AUTO_REFRESH_MS`), ruled out |
| Suspect that the daemon is dead | ❌ `state/paired` is normal and the socket is normal |
| Restart via `/etc/init.d/bt_daemon restart` to clear the old key in memory | ❌ **It did not take effect!** openrc reported `udev failed to start`, and the pid was still 1222 (the process was not replaced) → the old key was still in memory, so the fix was ineffective |
| Restart via `kill -9` + `setsid` following the pattern of `bt_bringup.start` | ✅ pid 1222 → 382, the key was really cleared |
| Use a high-frequency loop of `connect` to hold the "fake connection" window open for screenshots | ⚠️ It filled the daemon's accept queue, and subsequent requests got `errno 11 (EAGAIN)`. **Do not probe the daemon at high frequency** |

### 4.3 The protocol stack's exact words after the fix

```
[auth] auth complete status=0            ← 原来是 5
[auth] auth ok -> Set Encryption (0x0413)
[auth] encryption change status=0 enc=1  ← 加密建立
[l2cap] SDP 断开 + 认证完成 -> 建 AVDTP
[a2dp] avdtp begin: L2CAP conn req PSM=0x0019
[avdtp] DISCOVER_RSP seid=4 tsep=0 media=0
[a2dp] media channel ready, sent AVDTP_START seid=4
[a2dp] media loop start GOLD NF=7 bp=35 fl=83 persamp=128 framedur=2902us nch=2
```

## Solution

### 5.1 On-site remediation (reversible)

```sh
# 0) 备份
cp /tmp/bt_linkkey.conf /tmp/bt_linkkey.good

# 1) 删掉失效的 link key（文件里那一行）
grep -v '^c5:09:5d:3e:bd:3c' /tmp/bt_linkkey.conf > /tmp/lk.tmp && mv /tmp/lk.tmp /tmp/bt_linkkey.conf

# 2) 真重启 daemon（openrc restart 不生效，必须 kill + setsid）
for p in $(pidof bt_user_daemon); do kill -9 $p; done
sleep 2; rm -f /tmp/bt_ctl.sock
setsid /usr/local/bin/bt_user_daemon >/tmp/bt_daemon.log 2>&1 </dev/null &
sleep 10

# 3) 重新连接 -> 这一次会走完整配对(SSP)，并把新 key 写回 /tmp/bt_linkkey.conf
printf 'connect c5:09:5d:3e:bd:3c\n' | nc -U /tmp/bt_ctl.sock   # 或走 fm_ctl 同类客户端
```

### 5.2 Code change: `lv_pages/bluetooth_page.c`

Add a criterion for "whether the audio is really going through", and make all three text strings rely on it:

```c
#include <fcntl.h>
#define BP_A2DP_FIFO "/tmp/bt_audio.fifo"
#define BP_CONN_AUDIO_WAIT_MS 25000

/* ★ 判断 A2DP 音频流是否真的跑起来了
 * daemon 的 conn 只表示 ACL 链路存在；Link Key 失效时认证失败(status=5)，
 * A2DP 建不起来、音箱不出声，但 conn 照样回 OK CONN。
 * 判据: 非阻塞打开 fifo 写端 —— 有读者才说明 media loop 在跑。 */
static bool bp_a2dp_ready(void)
{
    int fd = open(BP_A2DP_FIFO, O_WRONLY | O_NONBLOCK);
    if(fd >= 0) { close(fd); return true; }
    return false;
}
```

1. **Status area text**: write "Connected: xx" only when `conn_mac[0] && bp_a2dp_ready()`; when `conn_mac[0]` is set but the audio is not going through, write **"Link established but audio not connected"**.
2. **Device row label**: link only → orange **"No audio"**; link + audio → green "Connected"; paired only → gray "Paired".
3. **Connection result toast**: after `connect` returns `RC 0`, **do not report success immediately**; instead check `bp_a2dp_ready()` every 300 ms, waiting at most 25 s: only report "Connected xx" if it succeeds, and report "Link established, but audio not connected" only on timeout.

## Verification

### 6.1 Positive case (a real connection)

```
[conn] -> 'OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303'
bt_audio.fifo 有读者: True (OK)          ← 媒体循环真在跑
```
Screenshot `shots/btlive_0.png`: the status area shows "Connected: 小爱音箱-1303" and the right side of the device row shows a **green "Connected"**.
→ This time the UI is telling the truth.

### 6.2 Negative case (deliberately corrupt the link key to reproduce the original fake connection)

Replace the entire key with 16 `0x00` bytes and reconnect after restarting the daemon:

```
connect -> RC 0
T+00 conn='OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303'   a2dp=False
T+02 conn='OK IDLE'                                     a2dp=False
[pair] auth complete status=5 / enc_ok=0 -> ABORT
```
Screenshot `shots/btfake_0.png`: the status area shows **"Link established but audio not connected"** and the right side of the device row shows an **orange "No audio"**.
→ With the same hardware state, the UI no longer falsely reports "Connected".

### 6.3 End to end: the audio path is indeed working

After connecting, continuously feed muted PCM into the fifo (the format was reverse-engineered from the daemon log: 44100Hz / 2ch / S16_LE):

```
fifo 写端已打开，开始灌静音 PCM（50.0s）
写完 8634780 字节 (约 49.0 秒音频)
conn(after) = OK CONN c5:09:5d:3e:bd:3c 小爱音箱-1303
[hci] credit inflight=5/1776   ← 全程在收发
```

**The link holds for 50 s while continuously supplying data**, and the HCI credits keep changing → the SBC frames really are being sent up.

## Lessons learned

1. **"Connected" must be defined by the evidence at the very end.** ACL existing ≠ the profile being available ≠ the stream running. Using an intermediate-layer state as a proxy for the end conclusion will eventually lie. The correct criterion in this case was "whether the fifo has a reader".
2. **Link key failure must be treated as a first-level investigation item for speaker-class devices.** A speaker connecting to a different phone, being reset, or receiving a firmware upgrade can all invalidate the key on this machine; the symptom in that case is "connected yet seemingly not connected", which is easily misdiagnosed as a signal/compatibility problem.
3. **`openrc restart` does not necessarily really restart.** On this machine, the `restart` of `bt_daemon` idles because the `udev` dependency fails and the pid does not change — whenever "a state/cache change must take effect", **you must verify whether the pid really changed**.
4. **Do not write high-frequency probing scripts that hammer your own daemon.** A `connect` once per second fills the accept queue, everything after that gets `errno 11`, and it messes up the scene instead.
5. **The daemon's interface semantics must be documented**: `conn` = ACL, which does not mean the connection is usable. This has been synced to the comment at the top of `lv_pages/bluetooth_page.c` and to the project memory.
6. **"No sound" does not necessarily mean the path is broken.** This machine's A2DP media loop is "alive only when there is data": if no PCM enters the fifo, the speaker actively disconnects due to timeout. To judge "whether the audio link is usable", you must look at **both** whether the fifo has a reader and whether the connection is maintained, not just one of them.
