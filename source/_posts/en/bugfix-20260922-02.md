# bugfix_20260922_02 — All marks on the radio page ruler are crowded to the left

> **Related commit**: 221fa7d

## Symptoms
On the newly added "FM Radio" page (`lv_pages/radio_page.c`), the frequency ruler in area D (covering 88~108 MHz, which should span the full width of the card) has **all tick marks, numeric labels, and favorite squares crowded within roughly the leftmost 10px of the card**. To the naked eye it looks like a small vertically stacked pile of ghosting; the entire right side is blank.

## Scope of impact
- Only the ruler in `radio_page.c` is affected (`rp_ruler_rebuild()` / `rp_ruler_pointer_update()`).
- All other sections on the same page (title bar, current frequency, signal bar, control buttons, favorites list, volume bar) are **unaffected** — their coordinates are hard-coded constants that do not depend on a runtime width query.
- No other page is affected.

## Root cause
**In LVGL 9, `lv_obj_get_width()` returns the cached coordinate area `obj->coords`, not the value just passed to `lv_obj_set_size()`.**

Evidence (device-side source code):
```c
/* lvgl/src/core/lv_obj_pos.c:587 */
int32_t lv_obj_get_width(const lv_obj_t * obj)
{
    LV_CHECK_OBJ(obj, MY_CLASS, return 0);
    return lv_area_get_width(&obj->coords);   /* ← 读的是 coords！ */
}
```
`coords` is only refreshed during a layout cycle (`lv_obj_update_layout` / refresh). However, `rp_ruler_rebuild()` is called in `onCreate()` **immediately after** `lv_obj_set_size(marks, w, 78)`. At that moment the layout has not run yet, so `coords` is still all zeros → `lv_obj_get_width()` returns **0**.

The code also contains a "fallback" that hides the problem even deeper:
```c
w = lv_obj_get_width(marks);
if (w < 10) w = 10;          /* 0 -> 10，于是所有 x = (f-min)*(10-1)/span ≈ 0~9 */
```
As a result, all 21 tick marks + 6 labels + 5 favorite squares land at x=0~9, which visually appears as a pile on the left.

## Diagnosis process
1. First look at the full-page screenshot: all other sections are correct and only the ruler collapsed → first suspect that the container layout (flex) took over the child object coordinates.
2. Add a temporary probe inside `rp_ruler_rebuild()` to print the runtime geometry directly:
   ```c
   fprintf(stderr, "[ruler-DBG] marks=%p get_width=%d kids=%u\n", (void*)marks, (int)w, n);
   fprintf(stderr, "[ruler-DBG] mhz=%d x=%d\n", mhz, (int)x);
   fprintf(stderr, "[ruler-DBG] kid0 x=%d y=%d w=%d h=%d\n", ...);
   ```
   Measured output:
   ```
   [ruler-DBG] mhz=88  x=0
   [ruler-DBG] mhz=98  x=4
   [ruler-DBG] mhz=108 x=9
   [ruler-DBG] marks=0xb70963dc get_width=10 kids=32
   [ruler-DBG] kid0 x=0 y=20 w=2 h=20
   ```
   → **`get_width=10` instead of the expected 652** (=720-24-44). The coordinates themselves are fine; only the width value is wrong.
3. `grep lv_obj_get_width` in the source code and confirm that it reads `coords`, which locks in the root cause.
4. Ruled-out wrong directions:
   - Suspected that `lv_obj_set_layout(marks, LV_LAYOUT_NONE)` did not take effect and flex took over → No, `set_pos` itself did take effect;
   - Suspected "label x-12 out of bounds" → That is **another** real but secondary problem (see the "Note" below).

## Solution
**Cache the width that was explicitly set at creation time** and stop relying on a runtime width query (`remote_src/radio_page.c`):

```c
/* 状态里加字段 */
lv_coord_t ruler_w;       /* 【必须缓存】lv_obj_get_width() 读的是缓存 coords，
                           * onCreate 阶段尚未布局 → 返回 0 */

static lv_coord_t rp_ruler_width(void)
{
    lv_coord_t w = s_rp.ruler_w;
    if (w < 100) w = RP_RULER_FALLBACK_W;   /* 600 */
    return w;
}

/* onCreate */
s_rp.ruler_w = full_w - 44;
lv_obj_set_size(s_rp.ruler_marks, s_rp.ruler_w, 78);
```
The three pieces of code that use the width (tick x, favorite square x, pointer x) are all switched to `rp_ruler_width()`.

**A second bug in the same function is fixed at the same time**: the pointer used to be a child object of `marks`, and the first thing `rp_ruler_rebuild()` does is `lv_obj_clean(marks)` — **which deletes the pointer along with everything else**, turning `s_rp.ruler_pointer` into a dangling pointer. This is now fixed by recreating the pointer **after** the `clean` and immediately calling `rp_ruler_pointer_update()`.

**Note (a third issue fixed in passing)**: the tick x values were originally mapped across the full width `[0, w]` with center-aligned labels, which caused the rightmost "108" to be clipped by the card edge (the measured screenshot only showed "10"). After adding left/right padding `RP_RULER_PAD 14`, the labels at both ends are fully visible.

## Lessons learned
1. **In LVGL 9, the `lv_obj_get_*()` family (width/height/x/y) all read the cached `coords`, not "the value just set".** For any scenario of "create an object → immediately compute child object coordinates from its size", you **must cache that size yourself**, or first call `lv_obj_update_layout(obj)` explicitly. This is a pitfall that fails silently (it returns 0).
2. **A "fallback" if can turn a bug from "crash / obvious anomaly" into "a wrong value that looks like it runs"**: `if (w < 10) w = 10;` turned 0 into 10, and the symptom changed from "nothing at all" to "everything crowded on the left", costing one extra round of diagnosis. A fallback value should either be of the same order of magnitude as the normal value, or the code should simply report an error.
3. **`lv_obj_clean(parent)` deletes all child objects of parent**. A persistent handle must not be attached to a container that will be `clean`ed; otherwise it must be explicitly recreated after the clean.
4. **Before setting coordinates for container children, first confirm that the container's layout is NONE** (the other cards on this page happened not to be taken over by flex).
5. The most cost-effective means of debugging UI geometry issues: **add one fprintf line inside the function to print the runtime numbers** — this is an order of magnitude faster than guessing against screenshots.
