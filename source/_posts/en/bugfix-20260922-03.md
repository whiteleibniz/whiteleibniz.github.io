# bugfix_20260922_03 — FM daemon disappears for no reason; the radio page always shows "芯片 0000"

> **Related commit**: 221fa7d

## Symptoms
After running for a while, `fm_user_daemon` **disappears without a sound** (it cannot be found in `ps`; the socket file `/tmp/fm_ctl.sock` still exists, but `connect()` returns `Connection refused`).
As a result, the radio page always shows `芯片 0000`, `RDS 不可用`, and `已关闭`, and all buttons are unresponsive.
The last few lines of the log contain only the normal `cmd='state'` / `cmd='rssi'` entries, with **no crash information at all**.

## Scope of impact
- Only the FM radio function is affected (the page ↔ daemon link is completely broken).
- The main `lvgl_demo` program is not affected: `lvgl_demo` has its own `/root/lvgl_watchdog.sh` keep-alive and has always run normally.
- All functions that depend on a permanently open fd for `/dev/fm` are affected: once the daemon dies, `/dev/fm` is closed, which triggers `fm_release` (it sends `at+fm=12` and blocks for about 4s), and the FM state is lost.

## Root cause
**A plain `write()` on a socket whose peer has already closed triggers `SIGPIPE`, whose default action is to terminate the process.**

The daemon's reply function used to be:
```c
static void reply(int cfd, const char *fmt, ...)
{
    ...
    if (write(cfd, buf, (size_t)n) < 0)     /* ← 没有 MSG_NOSIGNAL */
        logf_("[fm] 回写失败: %s", strerror(errno));
}
```
and `main()` does **not** call `signal(SIGPIPE, SIG_IGN)`.

Meanwhile, it is **normal** for the client (the lvgl_demo radio page) to disconnect "before the reply is written out":
- The connection is closed when the page runs `onDestroy` or the application is killed with `killall`;
- The page's IO worker thread sets a 6s timeout for the `rssi` command, but the kernel `GETRSSI` takes ~4s; the page also reconnects after the timeout → the old connection is discarded.

Once this happens, the daemon is killed by SIGPIPE, **with no log whatsoever** (the default signal action produces no user-space output).

## Diagnosis process
1. First confirm that the process is really gone and that the socket is stale (`pidof` is empty, `Connection refused`).
2. Look at the daemon source code's exit paths: the `for(;;) accept(...)` loop in `main()` after setup is an infinite loop with **no explicit `exit()` at all**; none of the command branches has one either. → Rule out "the logic exited by itself".
3. That leaves only "killed by a signal / segfault". Grep for signals and write operations:
   ```
   grep -n "write(|send(|MSG_NOSIGNAL|SIGPIPE|signal(" fm_user_daemon.c
   → 112: write(fd, m,...)         （wcnd socket）
   → 252: write(cfd, buf, n)       （客户端 socket，无 MSG_NOSIGNAL）
   没有任何 signal(...)
   ```
4. The timeline matches: every "daemon disappearance" happened **after I restarted the lvgl_demo application**.
5. **Run a control experiment** to prove the mechanism (`ssh_tools/sigpipe_ctrl.c`): fork two child processes, each of which calls `socketpair()` and then closes the peer; group A uses a bare `write()` and group B uses `send(..., MSG_NOSIGNAL)`:
   ```
   B(MSG_NOSIGNAL)   : 活着, n=-1 errno=Broken pipe  <- 期望如此
   对照实验结束：A 组若没有输出即表示它已被 SIGPIPE 终止。
   ```
   **Group A produced no output at all → it was indeed terminated by SIGPIPE.** The mechanism is confirmed on this machine.

## Solution
Two changes (`ssh_tools/fm_user_daemon.c`):

1. Unify the socket write function so that it never produces SIGPIPE:
```c
static int sock_send_raw(int fd, const char *buf, size_t n)
{
#ifdef MSG_NOSIGNAL
    return (int)send(fd, buf, n, MSG_NOSIGNAL);
#else
    return (int)write(fd, buf, n);
#endif
}
```
   - `reply()` is switched to use it;
   - Writing `"wcn FM-OPEN"` to `@wcnd` inside `wcnd_fm_open()` is also switched to it (it is likewise a socket whose peer may already be disconnected).
2. Add a fallback at the beginning of `main()`:
```c
signal(SIGPIPE, SIG_IGN);
```

Also add a **keep-alive watchdog** `/root/fm_watchdog.sh` (every 5 seconds it runs `pidof fm_user_daemon` and restarts the daemon if it is absent, following the same pattern as the existing `/root/lvgl_watchdog.sh`), defending against other causes of death such as OOM/SIGKILL.

## Verification
- **Regression test** (device-side `python3 /root/fm_sigpipe_test.py`): 6 rounds of "connect → send `rssi` (the kernel takes ~4s to reply) → `close()` immediately after 0.15s", exactly the worst-case timing that used to be guaranteed to kill it.
  Result: **all 6 rounds survived, and the daemon pid stayed at 6408 throughout → PASSED**.
- **Control experiment** (the `sigpipe_ctrl` from the previous section): group A died silently / group B survived → counter-proof that the fix is necessary and effective.
- After restarting the application and re-entering the radio page, the page again shows `RDS 可用 · 芯片 2341 · 收听中`.
- After the device rebooted on its own, `/etc/local.d/zz_fm.start` automatically brought the daemon up (log entries `[fm] wcn FM-OPEN -> WCNBTWIFI-CMD OK`, `chipid=0x2341 rds=1`, `就绪，监听 /tmp/fm_ctl.sock`).

## Lessons learned
1. **Always use `send(..., MSG_NOSIGNAL)` when writing to sockets, and call `signal(SIGPIPE, SIG_IGN)` at the beginning of long-running processes.**
   SIGPIPE is a "silent killer": it produces no log at all, and the symptom is "the process mysteriously disappeared", which is very easily misdiagnosed as OOM or "it exited by itself".
2. **"No exit() but the process is gone" → suspect signals first.** Order of investigation: code exit paths → signals (SIGPIPE/SIGSEGV) → external SIGKILL/OOM.
3. **A long-running IPC daemon must account for "the client may disconnect at any time before the reply"**; this is a high-frequency event, not an edge case, in embedded scenarios where the UI process gets restarted.
4. Mechanism-level conclusions need a **control experiment**: merely "it works after the change" does not count as proof; you must be able to show "it always failed before and always works after".
5. Every long-running process should have a keep-alive watchdog; this project already has the precedent of `lvgl_watchdog.sh` that can be copied.
