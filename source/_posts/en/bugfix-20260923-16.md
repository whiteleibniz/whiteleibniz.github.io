# bugfix 16 — GBA "after the changes no game can be entered": putting the "timeout supplementary kill" in the reaping thread = giving the game a 600ms lifespan

- **Date**: 2026-09-23
- **Scope of impact**: `lv_pages/gba_game_page.c` (GBA game app; entering a game fails 100%)
- **Severity**: P0 (functionality completely unusable, and it is a regression introduced by my own previous round of changes)
- **Related**: bugfix 09~15 (consecutive iterations on the same exit chain)
- **Rollback point**: `lv_pages/gba_game_page.c.bak_exit2` (state of document 14: games can be entered, intermittent picture freeze)

---

## 1. Symptom

User feedback: **"after the changes no game can be entered"**. After pressing the confirm key to select a ROM, the game picture "flashes once" and returns to the list (sometimes the desktop as well), looking like "it simply cannot be entered".

Note the difference from the previous article (bugfix 15):

| | bugfix 15 | bugfix 16 (this article) |
|---|---|---|
| Symptom | games can be entered and played, **exit intermittently hangs on the game picture** | **entering a game exits instantly**, no way to play at all |
| Player's feeling | "occasionally abnormal" | "completely unusable" |

**This is a new regression I introduced while fixing 15** — the source of "the more I fix, the more of a mess it gets".

---

## 2. Forensics (decisive log)

The complete sequence of one "enter game" event in `/tmp/lvgl_demo.log`:

```
[HW Key] code=115 value=1 -> ENTER          ← 用户按确认键
[gba] 封面: .../Advance Wars (USA) (Rev 1).png
[system] LVGL draw paused                    ← 进入游戏
[Key Thread] 临时按键拦截器已启用。
[Key Thread] EVIOCGRAB 请求释放
[Key Thread] EVIOCGRAB 已释放(交给外部进程)
[Key Thread] EVIOCGRAB 请求恢复独占           ← ★ 紧接着就恢复了
[gba] fb 兜底翻回第0页(前端退出时停在第 1 页)   ← ★ 前端已经死了
[system] LVGL draw resumed[nav] key=27
[pm] 页面 'gba_game' 离场
```

**Two decisive facts**:

1. Between `EVIOCGRAB 已释放` and `EVIOCGRAB 请求恢复独占` there is **no `[miniretro]` startup log of any kind** — while in a normal game entry this section must have 12 lines (mapping fb, opening 5 evdev devices, loading the core, loading the ROM…).
2. In the ordering, "restore exclusive grab + fallback page flip" immediately follows "release exclusive grab", showing the **child process has already exited**, and exited extremely fast.

→ **The frontend did not exit on its own; it was killed by the parent process.**

---

## 3. Root cause

In the previous round (bugfix 15) I changed the reaping logic from "blocking `waitpid`" to:

```c
/* ★ 错误写法（bugfix 15 引入） */
bool reaped = false;
for(int i = 0; i < 60; i++) {            /* 最多 600ms */
    pid_t r = waitpid(pid, &status, WNOHANG);
    if(r == pid) { reaped = true; break; }
    usleep(10 * 1000);
}
if(!reaped) {
    if(kill(pid, 0) == 0) kill(pid, SIGKILL);   /* ★ 把还在正常跑的游戏杀了 */
    waitpid(pid, &status, 0);
}
```

**The motivation at the time was good**: to leave a hard guarantee for "the frontend hangs" while not occupying the key thread. The comment even said "never set an upper limit of running for N seconds counts as exit" —

**but this code itself is that upper limit.** The criterion secretly changed from "the child process really disappears" to "600ms is up", so:

> The user presses confirm → the frontend starts → renders the first frame → **600ms is up → the parent process sends the supplementary SIGKILL → the game "flashes once and is gone"**.

This also explains why "the first entry sometimes shows one frame" — the frontend start + rendering the first frame is right around 600ms, and with luck one frame makes it out.

**This pit was recorded in the project memory** ("six already falsified paths", item ①: setting an upper limit of "running for N seconds counts as exit" for a wait loop), and I violated it knowingly.

---

## 4. Fix

**Principle: return to "the criterion is a single hard event — the child process really disappears", and strip "waiting" and "the supplementary kill" out of the reaping path entirely.**

| # | Location | Change |
|---|---|---|
| A | New `gba_kill_later()` | **a dedicated supplementary-kill thread**: the only place that holds "sleep 600ms then send the supplementary SIGKILL". It shares the same lock as the wait thread and uses `kill(pid,0)` + `child_pid` consistency verification to avoid mistakenly harming a reused pid |
| B | `gba_wait_thread()` | removed the 600ms polling timeout, **restored to a blocking `waitpid` (no upper limit)** — identical line by line to the FC page's `fc_wait_thread` |
| C | `gba_exit_to_list()` | no `sleep` in the key thread (it would leak keys and pop this page away); changed to `kill(SIGTERM)` + start the supplementary-kill thread and then **return immediately** to swallow keys |
| D | `gba_on_destroy()` | unchanged (a rare main-thread path; SIGTERM + 300ms polling to protect .sav flushing) |

The frontend `miniretro_gba.c` was **unchanged** this round.

**Key implementation of the supplementary-kill thread**:

```c
static void *gba_kill_later(void *arg)
{
    pid_t pid = (pid_t)(intptr_t)arg;
    usleep(GBA_KILL_TIMEOUT_MS * 1000);

    pthread_mutex_lock(&s_gba.lock);
    bool alive = (s_gba.child_pid == pid);      /* wait 线程收尸后会置 -1 */
    if(alive && kill(pid, 0) == 0) {
        printf("[gba] 前端 %dms 未退出, 补 SIGKILL pid=%d\n", GBA_KILL_TIMEOUT_MS, (int)pid);
        kill(pid, SIGKILL);
    }
    pthread_mutex_unlock(&s_gba.lock);
    return NULL;
}
```

**Why the lock must cover both the check and the supplementary kill**: the wait thread also sets `child_pid` to `-1` within the same lock. If reaping has already completed (`child_pid != pid`), the supplementary-kill thread skips directly → it will not act on an already-reclaimed, possibly-reused pid; if `child_pid == pid` can still be obtained, the process really has not been reaped and really is alive → the supplementary kill is legitimate.

## 6. "Why is FC smooth and GBA not" — difference table

This is the core question the user keeps asking, and also the root cause of the repeated failures on this chain.

| Dimension | FC (fceumm) | GBA (mgba) | Consequence |
|---|---|---|---|
| **fb multi-buffered page flipping** | **no page flipping**, always writes page 0 | **`FBIOPAN_DISPLAY` every frame, alternating between pages 0/1** | GBA exit must **flip the page back to 0**, otherwise the UI drawn by LVGL (which only draws page 0) is invisible → the screen stays frozen on the game picture |
| **Amount of flushing on exit** | small .sav, fast cleanup | .sav can reach 32~128KB; a real SD card write can take hundreds of ms | GBA needs a longer "wait for its cleanup" time |
| **Where to wait** | `usleep(120ms)` in the key thread is enough (the frontend exits in ~30ms) | if sleeping in the key thread likewise, **during those 600ms nobody reads event0** → the piled-up events leak to LVGL and become the "back" key → this page is popped | GBA must move the wait out of the key thread |
| **Reaping criterion** | blocking `waitpid`, never had a timeout | I once added a 600ms timeout → it became "setting a lifespan for the game" | **this is this article's P0** |
| **Whether the frontend touches fb residue** | no | page flipping + (once) full-page memcpy freeze | determines "who is responsible for the picture after exit" |

**In one sentence**: the FC frontend **does not touch the framebuffer's structure** (no page flipping, no page copying), so its exit only needs "kill the process + wait for reaping"; the GBA frontend **changes the framebuffer's display state** (foreground page), so on exit **someone must be responsible for changing it back** — this extra responsibility, if crammed into the "reaping thread" or the "key thread" for convenience, blows up as "the game cannot be entered" and "the exit hangs on the picture" respectively.

## 7. Lessons / anti-patterns

**New anti-pattern (already written into the `child-exit-hang-diagnosis` skill):**

> **Putting the "timeout supplementary kill" in the reaping thread = covertly setting a lifespan for the child process.**
> It looks like "leaving a hard guarantee for hangs", but it actually covertly swaps the criterion from "the child process really disappears" to "N milliseconds is up".
> The symptom is very misleading: **the game/program "flashes once and is gone", "cannot be entered"**, while everything looks normal in the reaping thread's log.
> The correct approach: **the supplementary kill must hang on a dedicated thread that "only exists after an exit request is received"**, and the reaping path always has only one unbounded blocking `waitpid`.

**Others:**

1. **The iron rule of "the criterion is a single hard event" must be enforced in code, not just written in comments.** This round my comment said "never set an upper limit", yet the code was setting one.
2. **The cost of a regression is higher than not fixing.** bugfix 15, in order to solve "intermittent picture freeze" (low probability, tolerable), introduced "completely cannot enter" (100%, unusable). **When fixing a probabilistic problem, the change must be more conservative than the problem itself.**
3. **The distance between `EVIOCGRAB 请求释放` and `请求恢复独占`** is a very useful diagnostic quantity: too short = the child process was killed (rather than exiting on its own); normal = the frontend is running normally. **It is recommended to add this to the troubleshooting checklist.**
4. Static verification is faster than logs: `grep -c 'i < 60'`, `grep -c 'bool reaped'` returning to zero confirms "the timeout logic has been completely removed".
