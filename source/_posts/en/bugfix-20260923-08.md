# bugfix_20260923_08 — GBA picture has red and blue swapped (color regression)

- Date: 2026-09-23
- Module: GBA game page / `scale_rotate90()` in `miniretro.c`
- Impact: The colors of all GBA game pictures (FC games share the same function and are likewise affected)

## 1. Problem symptoms

The game displays normally, with no stripes or tearing, but the **overall colors have red and blue swapped**:
the orange-gold Dragon Ball turns blue and the "DRAGON BALL" title turns blue. This is a color regression introduced by this round of changes.

## 2. Scope of impact

- All GBA / FC game pictures
- Does not affect the LVGL desktop and list page (that is a separate drawing path)

## 3. Root cause analysis

This machine's framebuffer has a **real byte order of `[R, G, B, X]`**,
while the pixels packed internally by LVGL/miniretro are `0xAARRGGBB` (stored little-endian as `[B, G, R, A]`),
so before writing to fb, **one and only one swap of the R/B two bytes is required**.

To improve the frame rate, this round rewrote `scale_rotate90()` into two steps:

1. First rotate the source image by 90° into the small canvas `rot_buf` (also moving the R/B swap over from the second step to reduce hot-loop overhead);
2. Then scale-copy `rot_buf` into the framebuffer.

**When making the change, the swap was added only at the new position, and the original swap in the second step's hot loop was forgotten to be deleted** → the swap executed twice →
R/B is swapped back, equivalent to no swap → red and blue are reversed overall.

## 4. Fix

Delete the R/B swap in the second step's scaling loop, keeping the R/B swap **done only once in the small-canvas step**
(that step has only `src_w × src_h` pixels, 38400 for GBA; putting it in the scaling loop would be 780,000 times).
Add a comment at that position explaining "the first step has already swapped; swapping here would swap it back", to prevent stepping on the pitfall again.

## 5. Verification method and results

After decoding captured frames into PNG on the device (`os.pread` dump + decoding as PNG by `[R,G,B,X]`), confirm visually:

| Version | Dragon Ball color | Verdict |
|---|---|---|
| Swapped twice (regression version) | Blue | ✗ Red and blue swapped |
| Swapped once (after fix) | **Orange-gold** | ✅ Correct |

## 6. Regression risks

- Color correctness **can only be confirmed visually / via frame capture**; it cannot be replaced by metrics like "proportion of non-black pixels" (which is exactly what fooled us this time).
- If the `scale_rotate90()` structure is changed again in the future, ensure that the R/B swap is done **exactly once in total** across the whole chain.
