# bugfix_20260924_01 — Video playback stuttering (first build a CPU budget table, then change one parameter + re-encode the source)

> Date: 2026-09-24　Device: Spreadtrum SC9832A (Alpine / kernel 3.10.65 / 720x1280 portrait fb)
> Related commit: 2341fad
> Result: **decoding was never the bottleneck**; after changing one playback parameter + re-encoding the source, the real-time ratio went from **0.75× → 1.08×**
> Nature: a performance issue, not a functional failure

---

## 1. Symptom and requirement

User feedback: "the video picture and the game picture stutter", together with a request to add a VSP/GSP hardware acceleration switch in the settings, hoping that with it enabled both video and games would go through hardware.

**This round did not rush to write code, but first asked "which step is actually stuttering".** Because the answer decides whether the next step is "video hardware decoding" (schedule measured in weeks, depends on reverse-engineering private ioctls) or "hardware scaling" (schedule measured in days) — picking the wrong direction means several wasted weeks.

## 2. Localization: build a CPU budget table

Method: run the same data with the same player, **two runs differing in only one switch**, and use the time difference to measure the cost of a given stage.

```sh
cd /home/lvgl_demo/lvgl_demo/sdcard/video
MP=/home/lvgl_demo/lvgl_demo/libs/mplayer/mplayer
$MP -benchmark -vo null -nosound -endpos 15 原子弹.mp4             # 纯解码
$MP -benchmark -vo null -nosound -endpos 15 -vf scale=720:1280 …   # 解码+缩放
$MP -benchmark -vo null -nosound -endpos 15 -vf rotate=1 …         # 解码+旋转
```

The whole run uses `-vo null` (no framebuffer writes), so it **will not disturb the person currently using this device**.

Source: H.264 1280x720 **60fps** 2821 kbps (a landscape source on a portrait device)

| Run | Decode VC | Post-process VO | Total | Relative to real time |
|---|---|---|---|---|
| Pure decode | 10.23s | 0.003s | 10.42s | **1.47×** |
| `-vf scale=720:1280` (the form used at the time) | 10.32s | **21.47s** | 31.98s | 0.47× |
| `-vf rotate=1` | 10.19s | 9.63s | 20.02s | 0.75× |
| `scale` + `-sws 0` | 10.20s | 11.25s | 21.64s | 0.69× |
| `scale` + `skiploopfilter` + `-sws 0` | 9.18s | 11.25s | 20.62s | 0.73× |

## 3. Root cause (three points)

1. **Decoding was never the bottleneck**: in any run, VC stays steadily at 1.47× real time.
   ⇒ The initially most favored "VSP video hardware decoding" has **limited benefit** for this problem (zeroing out VC only raises 0.75× to 1.56×, which is not cheaper than the next two points).
2. **Scaling was the most expensive step at the time** (21.5s, accounting for 2/3). But more fundamentally — **this step should not exist in the first place**: the source is 1280x720, which is **landscape**, while the screen is 720x1280, which is **portrait**; **after a 90° rotation the dimensions match exactly**. Rotation is a pure pixel rearrangement, half the cost of interpolated scaling.
3. **The source's 60fps exceeds this machine's total CPU budget**: 2×Cortex-A7, measured steady 768MHz. Even with software optimization maxed out (fastest scaling + skipping the loop filter) it is only 0.73×, short of real time.

## 4. Fix

### 4.1 App side: post-processing changed from "scale" to "rotate"

`lv_pages/video_player_page.c`, two `execlp` sites (the Bluetooth audio / muted branches) + one explanatory comment:

```c
-  "-vf", "scale=720:-2,expand=720:1280",
+  "-vf", "rotate=1,expand=720:1280",
```

`expand=720:1280` is kept for compatibility with sources like **960x720** — after rotation it becomes 720x960, and black bars are needed for centering only when the height is insufficient; 1280x720 after rotation fills the screen exactly, and expand incurs no extra cost.

**Side benefit**: the picture changed from "a small image in the middle of the screen (about 720x405)" to **full screen**.

### 4.2 Source side: re-encode to 30fps Constrained Baseline

The device has no ffmpeg/mencoder and no external network, so it was converted locally with `imageio-ffmpeg` and transferred back:

```sh
ffmpeg -y -i in.mp4 -vf fps=30 -c:v libx264 -profile:v baseline -level 3.0 \
       -preset slow -crf 25 -pix_fmt yuv420p -movflags +faststart -c:a copy out.mp4
```

| File | Original | New |
|---|---|---|
| 原子弹.mp4 | 3691 KB / High / 60fps | 591 KB / Constrained Baseline / 30fps |
| 海公牛.mp4 | 942 KB | 249 KB |
| 疼疼疼.mp4 | 3509 KB | 1129 KB |

Baseline has no B-frames and no CABAC, making software decoding easier than High profile. The original files are backed up in `sdcard/video/_orig60fps/`.

## 5. Verification

Retest with the same method after the change:

| Run | VC | VO | Total | Relative to real time |
|---|---|---|---|---|
| New source + `rotate=1` | 4.305s | 4.841s | 9.237s | **1.08×** |
| New source + App's actual parameters `rotate=1,expand=720:1280` | 4.278s | 4.803s | 9.170s | **1.09×** |

**0.75× → 1.08×, crossing the real-time line.** Build `MAKE_RC=0 / ERR=0`, lvgl_demo running as a single instance.

Rollback point: device `lv_pages/video_player_page.c.bak_rotate`; original files `video/_orig60fps/`.

## 6. Lessons: anti-pattern record (already merged into the skill)

- **Anti-pattern: promising a piece of hardware before making a budget table.** This round almost went straight to "VSP hardware decoding" (schedule of weeks, depends on reverse-engineering private ioctls), while measurements showed decoding was never the bottleneck.
- **Anti-pattern: only thinking about making a step faster, without asking whether the step should exist.** The first version's conclusion was "scaling is too expensive, find a way to make it faster" (`-sws 0`); if we had first asked "can we avoid scaling", the answer would be **rotation** — directly halving the cost, and the picture looks better too.
- **Anti-pattern: drawing conclusions from a single `nproc`.** This device has the `[sprd_hotplug]` kernel thread doing dynamic core tuning, and `nproc` varies with load between 1~4. I once thought I had knocked cores offline by writing `online` myself, and only ruled it out after checking `dmesg` and seeing the system's own `plugin`/`unplug` logs.

## 7. Leftovers

- **The cost of writing the framebuffer is still unmeasured**: this round's budget table is entirely based on `-vo null` and does not include actually writing to the screen (720×1280×4B ≈ 3.7MB per frame). A `-vo fbdev` run of 15 seconds on the screen is needed to complete the picture. **The margin at 1.08× is not generous; the actual experience is subject to on-site playback.**
- The stuttering in games (GBA/FC) comes from **CPU emulation + scaling to screen**, unrelated to this round. Treating it requires GSP hardware scaling — that is the correct answer to the user's original "hardware acceleration switch".
- The VSP/GSP availability has been fully surveyed (see MEMORY.md §10 for details): the VSP driver is complete, the user-space entry points are `/dev/sprd_vsp` + `/dev/sprd_vpp`, and `libomx_avcdec_hw_sprd.so` / `hwcomposer.sc8830.so` can be referenced for disassembly; but **there are no vsp/gsp header files anywhere**, so struct layouts can only be guessed.
