# bugfix_20260922_01 Red/Blue Channel Swap in mplayer Video Playback

> **Symptom**: after the desktop icon and FC game colors were corrected, the colors are still wrong when playing mp4 on the "Video" page (red and blue swapped).
> **Root cause layer**: framebuffer color metadata × external player (mplayer `-vo fbdev`).
> **Fix effort**: 2 source files +54/-2 and +50/-2, plus a miniretro rebuild.
> **File name**: `bugfix_20260922_01_mplayer视频红蓝通道错乱.md`
> **Related commit**: `5113a12`
> **Date**: 2026-09-22

---

## 1. Symptom

On the same screen, different functions show **inconsistent** colors:

| Function | Color behavior |
|---|---|
| Desktop icons, text, background | normal (previously corrected) |
| FC games (miniretro) | normal |
| **mp4 played on the "Video" page** | **red and blue swapped** (red objects display as blue) |

Key point: **only the video player is wrong**. This itself shows the problem is not in "the screen's entire color scheme",
but in "the video player's independent path".

## 2. Scope of Impact

- **Affected**: all videos played by the external mplayer process used by `lv_pages/video_player_page.c`.
- **Not affected**: the LVGL self-drawing parts (desktop/various pages) and miniretro (FC games) —
  each has its own independent fb write path and its own local R/B swap, so no changes are needed.

## 3. Root Cause

### 3.1 Prerequisite: the machine's real screen byte order is opposite to what the driver reports

`FBIOGET_VSCREENINFO` reports `r16:8 g8:8 b0:8` (semantics `[B,G,R,X]`),
but writing solid colors to fb + visual confirmation shows the **real byte order is `[R,G,B,X]`**:

| Memory bytes written to fb | What the screen actually displays |
|---|---|
| `[00,00,FF,FF]` | **Blue** |
| `[FF,00,00,FF]` | **Red** |

→ `offset0 = red`, `offset2 = blue`, **exactly opposite to what the driver reports**.

### 3.2 Core mechanism: the external player **reads** this metadata and writes pixels accordingly

The `fbdev` output driver of `libs/mplayer/mplayer` (MPlayer 1.4-13) reads
`FBIOGET_VSCREENINFO` at initialization, **decides which byte to write each color to based on the read offsets**,
and prints its chosen layout in the log:

```
var = r16:8 g8:8 b0:8   ->  VO: [fbdev] 720x1280 => 720x1280 BGRA
var = r0:8  g8:8 b16:8  ->  VO: [fbdev] 720x1280 => 720x1280 RGBA
```

- `BGRA` = blue at byte 0 → but this panel wants red at byte 0 → red and blue are swapped on screen ✗
- `RGBA` = red at byte 0 → matches the panel ✓

**So mplayer's code is not wrong; it just obediently follows the parameters the driver falsely reports.**

### 3.3 Why this cannot be solved by changing code here

| Consumer | How it gets colors | Can code be changed? |
|---|---|---|
| LVGL (`main.c` `fb_flush_cb`) | packs pixels itself, writes memory directly | ✅ already changed (swap R/B) |
| miniretro (`scale_rotate90`) | packs pixels itself, writes memory directly | ✅ already changed (swap R/B) |
| **mplayer (`-vo fbdev`)** | **reads fb metadata and writes accordingly** | ❌ third-party precompiled binary, no source code |

mplayer is a 13.7 MB precompiled ELF (`libs/mplayer/mplayer`), and there is **no source code** on the device,
so its code cannot be changed — only the **parameters it reads** can be changed.

## 4. Localization Process

### 4.1 Detours Taken (recorded to avoid walking them again)

| Wrong direction | Why it is wrong |
|---|---|
| Looking for mplayer in the system paths (`/usr/bin`, `/usr/local/bin`) | none exist → at one point misjudged as "no player on the device". It is actually at `libs/mplayer/mplayer`, hit by the relative-path candidates of `video_find_mplayer()` |
| Trying `-vf format=bgr32` / `format=rgb32` / `format=bgra` | **all ineffective**. The fbdev vo overrides the format filter's choice; the four output byte groups are **exactly identical** |
| Trying `-vo fbdev2` | behaves the same as `fbdev`, still BGRA |
| Wanting to modify the custom `lvfb` driver | the lvfb ("LVGL-style framebuffer output") driver does exist in this mplayer, but it **rejects** this machine's format: `[lvfb] unsupported framebuffer format: 720x1280 32bpp r16:8 g8:8 b0:8` (it **still rejects** after correction to `r0:8 b16:8`). There is no lvfb source code on the device, so it cannot be modified |
| Using `ffmpeg -f lavfi` to create solid-color test videos | the device has **no ffmpeg**; this route is blocked. Instead, compare directly with existing mp4 files |

### 4.2 Decisive experiment: change only the fb var and see whether the output bytes change

**Controlled variable**: the same command, the same mp4, with the **only change being the fb var**.

```sh
# A) 出厂 var（r16 g8 b0）
./mplayer -vo fbdev:/dev/fb0 -nodouble -bpp 32 \
          -vf scale=720:-2,expand=720:1280 -ao null -frames 1 <video.mp4>

# B) 校正 var（r0 g8 b16）后，跑完全相同的命令
```

Results (sampled at the screen center):

| Case | `VO:` log line | Screen center bytes |
|---|---|---|
| A factory var | `VO: [fbdev] ... BGRA` | `[e5 d7 cc ff]` |
| B corrected var | `VO: [fbdev] ... RGBA` | `[cc d7 e5 ff]` |

**Only the R/B two bytes are swapped; everything else is exactly the same** — cleanly pointing to the fb var as the single variable.

### 4.3 Key elimination experiment: does changing var affect the controller's actual color sampling?

This is the watershed between "stacked correction" and "replacement correction".

**Approach**: after correcting var to `r0:8 b16:8`, write the **same** `[FF 00 00 FF]` to fb,
and have the user visually report the color.

**Result**: the user answered "red" — **exactly the same** as the color seen **before** changing var.

**Conclusion**: `red/green/blue.offset` is **just metadata for software to read; the controller ignores it**.
Changing var does not affect hardware scan sampling; it only affects "software that reads this metadata" (i.e., mplayer).

→ Therefore the fix is **additive**: var must be corrected (to fix mplayer),
while the R/B swap in LVGL/miniretro themselves **must be kept** (deleting it would double-swap and revert to wrong).

## 5. Solution

### 5.1 Add an idempotent var correction function

Call it once in `fb_init()` (immediately after opening fb) to correct var to `r0:8 g8:8 b16:8`:

```c
/* 校正 fb 参数, 让读取该元数据的外部播放器(mplayer)自动取对字节序。
   实测: 改 var 不影响控制器取色, 只影响读元数据的软件。 */
static void fb_fix_color_spec(int fd)
{
    struct fb_var_screeninfo v;
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) < 0) { perror("[fb] fix: FBIOGET"); return; }
    if(v.red.offset == 0 && v.blue.offset == 16 &&
       v.red.length == 8 && v.green.length == 8 && v.blue.length == 8)
        return;                                    /* 已是目标布局, 幂等 */
    v.red.offset   = 0;  v.red.length   = 8;
    v.green.offset = 8;  v.green.length = 8;
    v.blue.offset  = 16; v.blue.length  = 8;
    if(ioctl(fd, FBIOPUT_VSCREENINFO, &v) < 0) {
        fprintf(stderr, "[fb] fix: FBIOPUT failed: %s\n", strerror(errno));
        return;
    }
    if(ioctl(fd, FBIOGET_VSCREENINFO, &v) == 0)
        fprintf(stderr, "[fb] color spec -> r%u:%u g%u:%u b%u:%u\n",
                v.red.offset, v.red.length, v.green.offset, v.green.length,
                v.blue.offset, v.blue.length);
}
```

### 5.2 Call it at both `fb_init()` sites

| File | Location | Effect |
|---|---|---|
| `main.c` | after `fb_init()` opens `g_fb_fd` | mplayer is a **child process** of lvgl_demo, so it naturally inherits the correct state |
| `extern/miniretro/miniretro.c` | after `fb_init()` opens `fb_fd` | when running games standalone, separated from the main program, the fb state is also correct |

### 5.3 Parts that **remain unchanged** (important)

- `main.c`'s `fb_flush_cb`: **keep** the R/B swap
- `extern/miniretro/miniretro.c`'s `scale_rotate90`: **keep** the R/B swap

These two write memory directly and do not read metadata; deleting the swap would double-swap and revert to wrong.

## 6. Verification

### 6.1 Automated verification (whether var self-heals + whether the mplayer layout changes)

```sh

<工具> restore           # 得到 r16:8 g8:8 b0:8

# 2) 重启主程序, 观察它是否自动校正

# 3) 看 mplayer 的布局选择
```

**Live result**: var automatically changed from `r16:8 g8:8 b0:8` to `r0:8 g8:8 b16:8`,
the log printed `[fb] color spec -> r0:8 g8:8 b16:8`, and the mplayer layout changed from `BGRA` to `RGBA`. ✓

### 6.2 Visual verification (**required**)

The user opens "Video" on the device → plays mp4 → visually confirms the picture colors.

**User confirmation result**: "The colors are correct now". ✓

### 6.3 Regression verification (confirm nothing already fixed was broken)

## 7. Lessons Learned

1. **"On the same screen, different processes are fixed differently"** — this was the biggest cognitive leap this time.
   Consumers that write fb fall into three categories:
   - **Self-drawing programs** (LVGL, miniretro) → change the **code**, swapping at their own write points
   - **External programs that read metadata** (mplayer `-vo fbdev`) → change the **parameters** (correct the fb var)
   - **Kernel/controller** → usually not modifiable, and measured to **ignore** var

   Fixing only one category leaves "some function's colors still wrong". **The first step in troubleshooting color problems should be to enumerate all processes that write fb.**

2. **Look at the choice the external program prints itself first**. mplayer's `VO: [fbdev] ... BGRA` line
   directly shows the basis of its judgment, faster than any reasoning. When there are logs, do not guess.

3. **A controlled-variable A/B experiment beats "change a bunch and try again"**. Same command + same material + changing only one variable
   (fb var) yielded the clean conclusion "only the R/B two bytes swapped", locking in the causality directly.

4. **Distinguish "metadata" from "hardware behavior"**. Before changing `var.red.offset`, ask first:
   "Is it used by hardware, or only read by software?" — this can be answered by "write the same bytes before and after the change and see whether the screen changes".
   This judgment determines whether the fix is additive or replacement, and **getting it wrong causes a double swap**.

5. **Verify command-line options before giving up on them**. `-vf format=...` and `-vo fbdev2` look reasonable,
   but live testing shows they are all ineffective. Spending a few minutes to disprove them beats recompiling the player on intuition.

6. **Do not use `pkill -f <pattern>` to kill daemons**. `pkill -9 -f lvgl_watchdog` matches
   **the shell itself carrying the command** (its command line contains that string) → kills your own SSH session,
   manifesting as `RC: -1` with truncated output, looking like "the command did not execute at all". **Kill by PID**:
   ```sh
   for p in $(ps -o pid,args | grep lvgl_watchdog.sh | grep -v grep | awk '{print $1}'); do kill -9 $p; done
   ```

7. **After patching a remote machine, review with `git diff --ignore-cr-at-eol`**.
   `git diff` once displayed a 54-line real change as 1618 lines of "whole-file rewrite" —
   that was just CRLF/LF triggering git's line-ending heuristic, not a broken change.
