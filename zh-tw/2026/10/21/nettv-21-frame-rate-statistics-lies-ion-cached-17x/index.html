nettv-21：16.9fps 是假的——幀率統計口徑騙了我們三個月，以及一個 17 倍的讀幀提速（SC9832A 硬解排查實錄）

ION, SC9832A, VSP, framebuffer, sprd, 性能优化, 统计口径

🌐 語言：簡體中文 · 繁體中文 · English

上一輪剛把”UI 點頻道黑屏”修完，用戶就丟了一句：**”播放效果有改進，但完全達不到正常觀看標準。”**

這句話的價值在於它逼我回頭看那些”已經優化過很多輪”的數字。結果一查不要緊——我們盯了三個月的幀率，從頭到尾都是錯的。

這篇記錄兩件事：一個是統計口徑的陷阱（數字騙人），一個是真正的性能突破（讀幀 17 倍提速），以及一個被推翻的方案（差點把設備搞崩）。

一、先看數字：16.9fps 是假的

播放器裡有個心跳，每 25 幀打一條：

759 秒、12825 幀、16.9fps。看起來挺正常對吧？源是 1080p/25fps 的直播流，差得不算太多。

但我去數了一下回調：

6776 真幀 + 7471 空事件。

廠商庫在吐出一個真幀之後，必然緊跟一個 filled=0 的空事件——drainAllOutputBuffers 把同一個 output header 回收複用，nFilledLen 被清零，於是又回調了一次 BufferFilledDone。

這個數字後來還汙染了另外兩處：

  • 判重邏輯：is_new = (g_filled != filled_seen) —— 空事件也算”有新幀”，觸發一次完整的讀幀+渲染（77ms），而畫面內容根本沒變。
  • perf 採樣：[perf] AU#7400 的各種均值，都是按”回調數”而不是”真幀數”歸一的。

教訓一：性能計數器必須先問清楚”它數的是什麼”。 一個把兩種語義混在一起的計數器，會同時汙染統計、判重、採樣三個地方，而且因為數字看起來合理，誰也不會去懷疑。

二、真正的瓶頸：88% 的時間不在解碼上

知道真實幀率是 8.9fps 之後，我需要知道時間去哪了。播放器裡早就有分段計時：

113ms 出一幀，對應 8.85fps——和實測的 8.9 完全吻合。這三段耗時拆開看：

段 耗時 佔比 是什麼
段循環 32.6ms 29% 投餵 AU + 等廠商排空
讀幀 44.3ms 39% 3MB memcpy（ION → staging）
渲染 33.0ms 29% NV12 → ARGB → 旋轉 → 寫 fb

而廠商自己的解碼耗時，828 次採樣全部是 14ms，紋絲不動。

換句話說：VSP 硬件解碼只佔了 12%，88% 的時間是我們的後處理。 硬件完全不是瓶頸，瓶頸在”把解碼好的幀搬到屏幕上”這段路上。

這個認知很重要——它意味著所有”優化硬解性能”的方向都是錯的，方向應該是”優化數據搬運”。

三、突破：uncached 內存是元兇

讀幀段 44.3ms 乾的事就一件：

3MB / 44.3ms = 68MB/s。這個帶寬低得離譜——正常 DDR 內存 memcpy 能到 1GB/s 以上。

原因在 ION 分配的 flags：

flags=0 意味著 uncached 映射。在 uncached 映射上，每讀一個 cache line 都要獨立發起一次總線事務，硬件預取完全幫不上忙，68MB/s 就是這麼來的。

改成 flags=1（cached），CPU 側走普通 load/store：

但這裡有個必須配套的 DMA 一致性處理：VSP 是用 DMA 往這塊內存寫幀的，CPU cache 裡可能還留著 DMA 之前的舊數據。所以讀之前必須先 invalidate：

這裡踩了一個坑，位置很關鍵：invalidate 必須在 staging memcpy 之前。因為 memcpy 的源就是那塊 DMA 區，先拷後 invalidate 等於白做。原來的代碼只在 pipeline 路徑的渲染線程裡做了一次 invalidate，而且是在 memcpy 之後——單線程路徑開著 cached 就會讀到髒數據（花屏）。

A/B 實測（同源、同長度、只切一個變量）：

畫面質量同時驗證過：前三幀的 Y 平面抽稀非零計數是 8151/8150/8154，三幀的簽名哈希互不相同——說明是真實變化的畫面，不是黑屏也不是花屏。

教訓二：當一個數字明顯偏離物理常識時（68MB/s），先懷疑映射屬性，再懷疑算法。 同樣的 memcpy，改一個 flag 就快 17 倍。

四、被推翻的方案：換個堆來躲池子

改完 cached 之後我遇到一個新問題：廠商解碼器的 C1 緩衝區分配開始報 OOM：

更糟的是，廠商拿不到 C1 之後會退回到 CPU 虛擬地址當物理地址用（”三級取址全失敗 → 退回 CPU VA(假PA, 花幀風險!)”），然後 VSP 往一個無效地址寫幀 → SIGSEGV。

診斷後發現是同池競爭：我們的輸出 buffer 是 3.2MB，必須 order-8 連續塊；而廠商那 5 塊 638KB 的 C1 DPB 也要 order-8（它的 align=8）。carveout 池裡的 order-8 大塊總數只有 4 塊（8MB），我們佔 1 塊，廠商就不夠了。

我的第一反應是：那我們換個池子不就行了——把輸出 buffer 改用 mask=2（System RAM）而不是 mask=8（carveout_mm）。廠商自己的 2MB C1 本來就用 mask=2，看起來完全可行。

於是我改代碼、編譯、部署、跑驗證。然後設備直接重啟了。

沒有 oops，沒有 panic，/proc/sys/kernel/watchdog = 1，dmesg 是一堆 powerdown_cpus。查物理地址才發現原因：

mask=2 和 mask=8 拿到的是同一個 carveout 區域（0x9f8xxxxx），並不是”System RAM”。而真正的 System RAM 在 0x80000000-0xbfffffff，mask=2 搶到的是那裡的高地址——超出了 VSP 硬件能訪問的地址窗口，VSP 往那兒寫就飛了，硬件看門狗直接復位。

教訓三：同一個 mask 名字在不同上下文裡可能完全不是一回事。 我看到”廠商用 mask=2 能成功”，就以為 mask=2 = System RAM = 安全的另一塊池子——但那兩個 mask=2 的分配落到了完全不同的物理區域，一個是 0x9f8xxxxx（carveout），一個是 0x8xxxxxxx（真 RAM）。參數名相同不等於語義相同，必須看實際物理地址。

好在這個方案在造成硬件復位之前就被測出來了，沒有造成更大後果。回滾到 mask=8。

六、再進一步：把渲染的 30ms 也拆開

改完 cached，我給 fb_render 加了分段計時（轉換 vs 寫 fb）：

寫 fb 只佔 1ms——3.6MB 寫進 mmap 的 framebuffer 幾乎不花錢（內存帶寬足夠）。30ms 全在”NV12 → ARGB + 旋轉 + 3/2 降採樣”這段純算術上。

但純算術不該這麼慢。算一下：92 萬像素，每像素 3 次乘法 + 6 次移位 + 6 次分支 clamp，總共 200 多萬次乘加，在 Cortex-A7 上撐死 1~2ms。差的 28ms 去哪了？

cache miss。 渲染的訪存模式是轉置的——輸出第 (oy, ox) 像素取源圖的 [1079-ox*3/2][oy*3/2]，源行隨輸出列走、源列隨輸出行走，每個源像素的相鄰輸出像素在源圖裡隔了 1.5 像素。源圖 3MB，一幀要跨 1080 個源行各取 720 個點，每次換行都是一次新的 cache line 拉取。

這解釋了為什麼之前”查表化”反而更慢（39.3ms vs 32.5ms）——查表把 miss 從源側搬到了表側，淨收益為零。

解法不是改算法，是改分組粒度：原來的實現每次處理 16 個輸出行（一個”帶”），每個源行只讀 24 字節（約 37% 條 cache line）。改成 64 行後，每個源行讀 96 字節，而相鄰帶讀的正是同一批 cache line 的相鄰段——在 L2 裡就能複用。

實測：渲染 34.3 → 30.3ms，真實幀率 12.4 → 13.1fps。抓屏確認畫面幾何無任何變形（臺標位置、字幕、色彩全部正常）。

教訓五：算術便宜不代表訪存便宜。 同樣是 200 萬次乘加，標量和 NEON 差不多；但”每個源像素拉一次 cache line”和”每 4 個源像素拉一次”，差 10 倍。

七、這一輪的賬

項目 改前 改後
真實畫面更新率 8.45 fps 13.1 fps
讀幀段耗時 44.3 ms 2.7 ms
渲染段耗時 33.0 ms 30.3 ms
每幀牆鍾 113.0 ms 70.6 ms
[STAT] 幀率口徑 虛高 2 倍 真實幀數

廠商解碼 14ms 是硬底線，理論上限 1000/(14+30) ≈ 23fps。

八、這輪還踩了兩個坑，值得單獨記一筆

坑一：把”更省內存”當成”更好對齊”

我們的輸出 buffer 是 3.25MB，精確幀尺寸是 3.13MB——我以為首選精確尺寸能省 140KB、給廠商的 C1 多留點空間。結果 OOM 從 1 次漲到 28 次。

原因很樸素：3.13MB 湊不出 order-8 的整塊，3.25MB 能湊。尺寸階梯的第一項不是”最省的”，是”最好對齊的”。

坑二：perf 採樣係數寫死，兩個指標開始互相打架

把帶高從 16 改成 64 之後，[perf] fb_render 均值 報 133ms，而 [perf] AU 裡的”渲染=”報 30.3ms——同一份代碼，兩個指標差 4 倍。

採樣換算係數是寫死的 * 20（80 個帶、每 20 個採樣一次）。帶高變 64 之後變成 20 個帶、每 5 個採樣一次，係數應該改成 * 5。這種”魔法數字”一旦和結構參數脫鉤，指標就廢了。

教訓六：性能工具本身也是需要維護的代碼。 它的常量跟被測對象耦合得越緊，改一邊就要改另一邊。

九、下一步

  1. 帶高繼續加大（64 → 128 / 256）：驗證 DRAM 流量是否還能降，直到渲染段不再隨帶高變化
  2. NEON 化 YUV→ARGB：設備 CPU（ARMv7 rev5）支持 neon，編譯鏈也已帶 -mfpu=neon-vfpv4，
    之前只是沒人寫 intrinsics。算術部分（3 乘法 + clamp）用飽和指令 vqmovun 可以壓到 1/4
  3. 換轉置的實現方式：當前是”讀源側順序、寫輸出側轉置”，天然的 cache 災難。
    改成”雙線性縮放 + 先縮到 720×1280 再轉置”可能讓訪存變連續
  4. fb 直寫優化：當前是 mmap 寫 3 頁 fb + PAN，有沒有硬件 overlay 路徑
  5. 池衝突根治：讓我們的輸出分配排在廠商 C1 之後

最後一句：這輪最有價值的產出不是那 17 倍，而是把”16.9fps”這個假數字變成了”8.9fps”這個真數字。一個虛高的指標會讓你以為”再優化一點就夠了”，而真實數字告訴你：還差得遠，但方向明確——不在解碼，在搬運。
