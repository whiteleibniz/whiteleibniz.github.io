展訊 SC9832A 網絡電視攻堅（二十四）：6 分鐘連續播放不崩不漏，以及 sysfs 騙我說"只有 1 個核"

前面二十幾篇基本都在跟”崩潰”和”幀率”纏鬥，而且絕大多數結論只跑過 60 秒。60 秒能證明”能出幀”，證明不了”能一直看”。這次把窗口拉到 6 分鐘，拿一批以前沒量過的東西：ION 有沒有緩慢洩漏、幀率會不會隨時間衰減、熱不熱、以及一個意外翻案——這臺機器到底有幾個核在幹活。

一、先看結論

指標 結果
連續播放時長 386 s（SIGTERM 主動收尾，非崩潰）
回調數 / 真幀數 11700 / 5571
穩態幀率 14.4 fps（fps_x10 全程 143~150，無衰減）
SIGSEGV 0
ION 客戶端 播放中恆為 3，退出後歸 0（無洩漏）
溫度 / 主頻 27.7 ℃ / 1.3 GHz（無熱降頻）
桌面 / framebuffer 桌面存活，收尾後 fb 恢復正常

長時間穩定性這項目前是達標的。 剩下的真問題是：為什麼長時間穩態只有 14.4fps，而 10-22 單段 60s 測試是 21.8fps。

二、翻案：sysfs 的 online 文件在騙人

10-22 我給”檔 2（fork 渲染流水線）判負”找的根因是”在線 CPU 只有 2 核”。這次複查，讀到的是更極端的東西：

照這個讀數，機器是單核。但順手寫了個固定工作量的並行基準（每個進程 1.5 億次整數乘加，用 CLOCK_MONOTONIC 自計時），結果完全對不上：

併發路數 各路耗時
1 路 2080 ms
2 路 2080 / 2080 ms
3 路 2080 / 2087 / 2110 ms
4 路 2085 / 2095 / 2098 / 2135 ms

四路同時跑，每路耗時和單路幾乎一樣——這是教科書級的”真·多核”曲線。單核上四路並行應該各花 8 秒左右。而且基準跑完再讀 online，值變成了 [0-3]。

所以：

  • sysfs 的 online/offline 和 /proc/cpuinfo 在這臺機器上都不可信，它們是 hotplug 記賬，不等於”有沒有核在跑”。
  • 判核數的可靠辦法是吞吐反推，不是讀文件。
  • 順帶推翻 10-22 的定案：檔 2 判負不是因為核不夠，那個 -20% 得重新找原因（大概率是 3MB 幀在跨進程共享內存裡來回搬 + 握手粒度）。

另外順手試了熱插拔寫入，echo 1 > cpu1/online 返回失敗、但狀態確實在動——這個內核的 hotplug sysfs 行為很怪，別拿它當實驗變量。

三、新賬本：62.6ms 裡有 21.6ms 不在任何計時器裡

長時間穩態的 perf 行長這樣：

把已剖析項加起來：14.1 + 2.5 + 23.8 = 40.4ms。牆鍾 62.6ms，差 21.6ms 沒人認領。對比單段文件模式（10-22）：牆鍾 41.5ms ≈ 剖析和 41.3ms，一毫秒都不差。

差額只在”邊下邊播”的直播模式下出現，方向很明確：卡在等數據上。看 rb_take：

環形緩衝一空就 2ms 一睡地輪詢，這段等待沒有落到 g_t_slp/g_t_read/g_t_ren 任何一項裡，於是就成了”牆鍾裡憑空多出來的 21.6ms”。它佔掉整幀時間的三分之一還多。

這也解釋了穩態 14.4fps 的來源：供給側（下載 + 解複用 + 寫環）跟不上消費側，消費者有三分之一的時間在空轉等米下鍋。這時候再去優化渲染那 23.8ms，性價比已經不高了——先讓米下鍋。

四、可以立刻做的三件事（按性價比）

  1. 給 rb_take 的空轉加計時（新增 g_t_wait，10 行以內）。現在 21.6ms 是”推算”出來的，必須變成”量”出來的，否則後面所有優化都是在猜。
  2. 量化 dl 側供數能力：單次 curl 拿一段的平均耗時、段間隙多長、rb 深度曲線。如果段間隙是大頭，就把”提前拉下一段”做成默認（雙槽預取的邏輯在，但沒驗過它在真實 CDN 上的效果）。
  3. 把 usleep(2000) 的粒度降下來（200~500us，或換成 futex/條件變量）。2ms 粒度意味著平均每次白白多睡 1ms，一幀裡若空轉十次就是 10ms。

五、方法論沉澱

  • “穩定”必須單獨測：60 秒的 A/B 和 6 分鐘的連續播放是兩件事。這次如果不是拉長窗口，就看不到”牆鍾 55ms → 63ms”的爬升，也看不到 ION 恆 3 不漲這種好消息。
  • 剖析項加不滿牆鍾，本身就是最大的線索。賬對不上時，先找”沒被計時的路徑”（阻塞讀、輪詢睡、隱式同步），別急著懷疑硬件。
  • 不要用 sysfs//proc 的記賬值當硬件事實。能反推就反推：固定工作量 + 不同併發度，看耗時拐點。
  • 收尾繼續用 SIGTERM + usleep(800ms) 排空 DMA，全程沒碰過 SIGKILL，設備零重啟。

六、下一步

先把 g_t_wait 計時加上重建一版，把 21.6ms 坐實；然後看它是不是真的大頭——是的話，提幀的主戰場就從”渲染”換到”供數”，目標 14.4 → 20fps 以上。
