nettv 播放器無畫面與按鍵阻塞故障修復

一、故障現象

用戶在桌面點擊「網絡電視」的頻道後：

  • 後臺能看到 nettv_player 進程在跑，甚至同時存在多個歷史殘留進程；
  • 前端沒有任何畫面；
  • 導航按鍵全部失靈（只能按買單鍵，界面像卡死）。

二、根因鏈（三層，一層比一層深）

1. 直接原因：頻道源全部失效

設備實測頻道表 8 個源，curl 全部返回 000（連接超時）。公開直播源（voc、各地 P2P 流）平均存活期只有幾周，失效是常態。

2. 深層原因：播放器對「源不可達」的處理是無限重啟

nettv_player（sprd_msg 基線）的結構是「監控父進程 + 解碼子進程」：

  • 子進程拉不到 m3u8 → load_chunk 失敗 → _exit(10)；
  • 監控父進程不看退出碼，150ms 後重新 fork → 再次失敗 → 再次重啟……

於是進程永遠不退出、永遠解不出幀。這直接造成兩個用戶可見症狀：

  • 無畫面：沒有任何幀被解碼出來；
  • 按鍵阻塞：UI 頁（nettv_page.c）在啟動播放器時暫停了 LVGL 主循環並安裝按鍵攔截器，由一個等待線程 waitpid 阻塞收屍——播放器不退出，等待線程就永不返回，界面和按鍵就一直不恢復。

3. 最深的坑：修「源不可達退出」時連續踩了三個時序競爭

第一版補丁很直觀——連續 3 次拉不到播放列表就判死刑、退出碼 98、監控見到 98 就不重啟。但實測完全不生效，日誌裡依舊是無限重啟。逐層拆解後發現是三個競爭：

  1. 停滯看門狗誤殺取源階段：看門狗的邏輯是「啟動寬限 8s + 之後 5s 無新幀就殺掉重啟」。可 VSP 組件 init 本身就要數秒，3 次 curl 重試又要 15~25s——看門狗在子進程走到「拉列表」之前就把它斃了，退出碼 98 根本沒機會產生。
  2. 兩次拉取之間的空窗：即使加了「拉列表中」共享旗標，旗標只在 hls_pick() 內置位，段間 sleep(1) 和 curl fork 的空窗裡旗標是 0，看門狗照樣開火。
  3. 啟動期與播放期的寬限混為一談：從未出過幀（啟動期）和出過幀後掛起（VSP 掛死）用的是同一個 8s 寬限，而啟動期合法耗時（組件 init + 取源 + 下載 25s）本就該長得多。

三、修復方案

播放器側（sprd_msg_np.c，4 處）

  1. hls_pick() 返回值語義化：1=拿到新段，0=直播還沒刷新，-1=播放列表都拉不到（源不可達）；
  2. load_chunk()：連續 3 次 -1 判死刑，置 g_src_dead 並通過共享內存旗標 shm[1]=98 立刻通知監控（不用等退出碼，0.4s 內響應）；
  3. 監控父進程：見到旗標 98 → 殺掉子進程 → _exit(98)，絕不重啟；同時保留退出碼 98 的第二道判定；
  4. 停滯看門狗按語義分檔：prev>0（出過幀，VSP 掛死）維持 8s+5s 快速重啟；prev==0（從未出幀=啟動期）寬限 90s。取源階段（含 sleep/curl 空窗）全程置 shm[2]=1 免看門狗，連續拉列表超 60s 仍兜底。

UI 頁側（nettv_page.c）

等待線程收屍後按退出碼分流：WEXITSTATUS(status)==98 時通過 lv_async_call 在主線程把狀態欄改成「頻道源不可達, 已自動返回 (換臺或編輯頻道表)」。LVGL 對象只能主線程碰，跨線程提示必須走 lv_async_call。

頻道表

8 個源全死後，設備實測替換為 4 個存活源（錢江都市/上虞/松潘/瀘縣，均返回有效 m3u8），舊錶備份為 stations.m3u.bak_20261012。

四、驗證結果

場景 修復前 修復後
點死源頻道 播放器無限重啟、界面永久卡死、只能斷電 約 40s 自動退出（退出碼 98），界面與按鍵恢復，狀態欄提示源不可達
點活源頻道 — 正常解碼出幀（錢江都市實測每輪 4 幀後撞上已知的「第二個 IDR 掛起」，監控重啟循環，屬遺留問題）

五、經驗總結

  1. 「後臺進程在跑」不等於「在工作」：本例中進程在跑恰恰是故障本身——無限重啟循環。判斷健康要看功能真值（出幀數、退出碼），不能看進程存在性。
  2. 看門狗的寬限必須按語義分檔：啟動期（含網絡取源）和運行期掛死的合法耗時差一個量級，混用一個 8s 寬限就會在啟動期誤殺，把「本來會自己退出的流程」打成「無限重啟」。
  3. 修「該退出」類 bug 時，先確認沒有更底層的「提前殺死」機制：退出碼設計得再對，被看門狗搶先 SIGKILL 就永遠傳不出來。父子進程通信優先用共享內存旗標（即時），退出碼只作兜底。
  4. 冪等操作不要加前置判斷，等待條件不要用計時：本例看門狗的退出條件表面是「無新幀」事件，實際混入了「8s 計時」，一混就錯（與「等子進程循環不設時長上限」是同一類錯誤的鏡像）。
  5. UI 阻塞類故障先問「誰在等一個永不到來的事件」：本例是 waitpid 等一個永不退出的播放器。讓子進程保證會退出（退出碼 98 + SIGKILL 兜底），阻塞等待就是安全的。

六、遺留問題

  • 第二個 IDR 掛起（addr=0x747474 段錯誤或永久掛起）：1080p 直播流第一個 GOP 出約 4 幀後喂第二個 IDR 必發，監控重啟只能換來「4 幀一輪」的幻燈模式。這是 nettv 流暢播放的最後障礙，已列入每日定時攻堅任務。
  • 直播源需要定期巡檢替換，頻道表平均幾周失效一輪。
