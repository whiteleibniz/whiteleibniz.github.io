展訊 SC9832A 網絡電視攻堅（九）：一次 SIGKILL 把設備打成重啟——VSP 解碼中斷的代價與兩個連帶坑

前幾篇一直在跟「第二個 IDR 必掛死」死磕，日誌斷層、證據反覆丟失。這次本來只想加一個診斷開關跑 60 秒，結果把設備連著打成兩次重啟。覆盤下來，事故本身就是最有價值的結論：解碼中用 kill -9 打斷 nettv_player，等於讓內核去收拾 VSP 沒排空的 DMA，直接崩。順帶還清掉了兩個長期誤判。

一、事故現場

實驗腳本按老習慣寫的：起播放器，( sleep 75; pkill -9 ... ) & 兜底，timeout -s KILL 90 硬收尾。跑完一查：

不是 sshd 會話耗盡，也不是”卡死”——設備真的重啟了。 ping 一直通（協議棧中斷驅動），SSH 不通（進程調度不起來），和 10-18 晚那次”ping 通但 sshd 無響應”是同一件事，當時判錯了方向。

二、根因：VSP 的 DMA 必須讓它自己排空

播放器的退出路徑裡一直有一句 usleep(800000)，註釋寫著”排空 DMA，防內核崩”。這是 10-09 就踩過的坑：VSP 硬件還在往 ion 連續內存裡寫幀的時候，如果進程被外力掐掉，驅動側沒有機會收回這次 DMA，接下來就是內核崩。

關鍵在於：**SIGKILL 不會走任何用戶態退出路徑**。_exit() 也不會。所以

  • pkill -9 -f nettv_player ✗
  • timeout -s KILL 90 ... ✗
  • SIGKILL 之後那 800ms 排空代碼一行都不會執行 ✓（崩給你看）

正確的停法只有兩種：

  1. 讓它自己退出：播放器第二個參數是「總幀數上限」（g_arg2，0 = 無限），達到就走正常退出流程：
  2. 只發 SIGTERM：播放器裝了 SIGTERM 處理，會先停喂、排空 DMA 再退。SIGKILL 留作 3 秒後的兜底，但正常情況下不該觸發。

改完之後腳本長這樣（outputs/r26.sh）：全程沒有 -9，靠幀數上限自退。

三、連帶坑一：日誌是 4KB 全緩衝，”行緩衝”的註釋騙了自己

排查過程中最迷惑人的一點：進程明明跑了 75 秒，日誌文件永遠停在 4096 字節，grep 什麼都搜不到。

原因很樸素：stdout 重定向到文件後是 4KB 全緩衝，代碼註釋裡寫的”已開行緩衝（setvbuf _IOLBF）”在這條路徑上沒生效。進程被 SIGKILL → 緩衝區永遠不 flush → 你看到的日誌是若干個 4KB 塊，最後一截全丟。

所以：

  • 實驗日誌必須等進程自己正常退出再看，別指望被殺的進程把尾部吐出來；
  • 判定”程序是不是卡住了”，不能只看日誌大小（4KB 一跳），要看 pgrep 和 /proc/<pid>/stat。

四、連帶坑二：OpenRC 服務沒有 start() 會被靜默跳過

實驗一開始報了個很唬人的錯：

查下去發現 /system/lib/*.so 全是懸空符號鏈接——它們指向 /mnt/android_sys/lib/，而 android_sys 分區根本沒掛。

固化腳本 /etc/init.d/00_android_sys 是存在的，rc-update show 也顯示在 default runlevel 裡，但開機就是不執行。原因：OpenRC 的 runscript **必須定義 start()**（或者用 command= / start_stop_daemon），裸的一段 shell 會被靜默跳過。改成標準 runscript 後立刻好了：

rc-service 00_android_sys start → mnt=304，問題解決。以後看到 library "libc.so" not found，先查 ls /mnt/android_sys/lib | wc -l，別去動編譯參數。

五、本次真想做的實驗：給「第二個 IDR 掛死」做二分

事故歸事故，診斷開關已經加進源碼了（outputs/sprd_msg_np_v2.c，環境變量 NETTV_IDRREPLAY，默認 0 關閉）：

思路：現在的現象是每代 worker 都活到 AU[36]（GOP#2 的 IDR）然後 DRIVE 掛死 5~10 秒。這有兩種可能——

  • A. 組件狀態說：流式態下 任何 IDR 都會掛，跟餵了多少輪無關 → 修法是 GOP 邊界做解碼器軟復位（flush + 重建緩衝區），不用重啟進程；
  • B. 累積漂移說：前 35 輪消耗掉了某種資源（ion/CMA、偏移、引用計數），IDR 只是恰好撞在爆點上 → 修法完全不同，得去查 36 輪裡的洩漏。

做法：捕獲第一個 IDR 之後，緊接著連投 K 次同一份 IDR（零累積、組件狀態與 AU[36] 時一致）。如果重投第 1 次就掛死，A 成立；如果連投 3 次全過、仍然要等到 36 輪才掛，B 成立。

判據就兩條：

二進制已經編好部署（nettv_player 118788 字節，舊版備份在 .bak_1019），但實跑數據這次沒拿到——就是被上面兩次重啟攔下來的。

六、下一次開工的三條紀律

  1. 起實驗前先 pgrep 確認沒有別的播放進程；收尾只用 SIGTERM 或幀數上限，任何 -9 都等於讓設備重啟。
  2. 每次跑完先看 uptime，重啟過的數據一律作廢（日誌不全、現場沒了）。
  3. 手動跑播放器前先停桌面（lvgl_demo 佔著 fb，雙寫衝突），否則現象會被汙染。

把這條放最後是因為它最貴：一次重啟，前面半小時的取證全清零。
