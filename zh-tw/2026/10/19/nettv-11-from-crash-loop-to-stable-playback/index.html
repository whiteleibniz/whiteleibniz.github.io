把網絡電視調通：從一天崩三次到連續播 4800 幀

設備：展訊 SC9832A（sc8830 系列），Alpine/armv7l，720×1280 豎屏，LVGL 桌面。
目標：HLS 直播流用 VSP 硬件解碼輸出到 framebuffer，達到安卓官方播放效果。
最終：遼寧衛視《鄉村財富》穩定播出，uptime 36 分鐘零重啟，4808 幀上屏。

起點：每輪必崩

新版代碼每跑必崩，崩在相位樁最後一行：

sigsetjmp 攔不住，dmesg 無 OOM，內存還剩 882 MB。內核態崩潰。

五個根因，五次 A/B

根因 1：調試代碼自己就是崩因

10-18 晚上我加了一套”掛死現場取證”：vrp_hook() hook 廠商的 VSP 寄存器寫函數，
每次調用都從 rb + 0x60901000 / rb + 0x60908000 直接讀 MMIO 寄存器窗口；
tr_line() 更狠，每次 DRIVE 前後各讀一次。

vrp_hook 是每一輪輪詢都會走的高頻路徑。於是 VSP 狀態機被打亂，
崩在緊隨其後的 DRIVE fill(out)#1。

崩潰點不在調試代碼那行，所以棧、日誌、信號處理全都指不到它。
舊版（能跑的）完全沒有這段代碼——這才讓我想到去比。

修法：NETTV_TRACE_MMIO 默認 0，直接 return 不碰 MMIO。
驗證：跑到 AU[1100]+，564 次 fill 全返回，零重啟。

根因 2：NAL 切碎

三次崩潰現場的鐵證——崩點永遠緊跟一個被切成多片的 NAL：

A/B 決定性：NETTV_CHUNK=0 → 1200 幀跑到 AU[1100]+ 零重啟；默認 4096 → 每輪必崩。

機理推斷：廠商庫對”同一 NAL 分多次 nOffset 續投同一 buffer”的處理有缺陷。
（我最初查錯了方向——NETTV_SPLIT 管的是拆 NAL 邊界，切碎由 g_chunk 決定，兩者不同。）

根因 3：虛擬地址當成物理地址 → 一片綠

日誌裡兩行並列就是鐵證（同一個 fd=12）：

廠商 VSP 按 handle->ints[12] 當物理地址寫幀，我填的卻是 mmap 的虛擬地址。
硬件訪問不到用戶態虛擬地址 → 寫不進真顯存 → 屏上一片綠。

修法：新增 g_gh_pa[] 存真 PA，4 處 fh[12] 全部改填 PA，VA 只留給 CPU 讀幀。

根因 4：ION 搶不到 + 不釋放

自管 ION（heap mask=8 carveout_mm，物理連續）搶到時一切正常，搶不到時
ghOut 會退回 gralloc 的真 handle——而 gralloc 走 IOMMU heap，無物理連續 backing，
VSP 拿假 PA 寫幀必崩內核。

兩個改動：重試 6 輪 + 120ms 退避 + 尺寸階梯；仍搶不到就 _exit(12) 讓看門狗重生，
寧可不出畫面也不打飛內核。另外退出前調 ION_IOC_FREE(0xc0044901) 主動釋放。

根因 5：最貴的那個——是我自己

ps | grep -c nettv_player 顯示堆了 12~23 個殭屍進程。

每輪調試我都 nohup 起一個腳本，而 monitor 內部還會自己重生 worker/worker-dl/mplayer，
每輪實驗多留一整套，每個搶 2MB C1 緩衝 → 池被撐爆 → 後續起不來。

pgrep -x nettv_player 只數主進程，看不到這些，所以我一度誤判成”內核洩漏”，
還專門寫了個 ion_release() 去救火。

pkill -f nettv_player 全清後，池立刻回到 total 0，立刻就能正常播。

這一條最值錢：**症狀和真因差了十萬八千里，而唯一的分界線是”多問一句 ps”**。

最後一小時：抓屏騙了我一小時

畫面明明上屏了，我抓屏看到的卻是舊的 WiFi 設置頁，連抓 4 張內容一模一樣。

真因：/sys/class/graphics/fb0/virtual_size = 720,3840 —— fb 有 4 頁，
我的抓屏腳本只讀第 0 頁。而 fb_render() 每幀寫 g_fbpg*720*1280*4 偏移
並 fb_pan() 翻頁，內容在第 1/2 頁。

抓屏看到舊畫面 ≠ 沒上屏。 先查 virtual_size，再下結論。

順手把抓屏腳本改成自動：驅動 pan_offset 恆 0 讀不到當前頁，於是逐頁統計
色彩種類數取最多者（實測 page0=55 色殘留舊頁 vs page1=617 色真實畫面）。
中間試過”採樣求和”，結果選反了——求和反映亮度不反映多樣性。

最終驗證

方法論覆盤

1. 「調試代碼自己就是崩因」是一類獨立故障模式。
它不會崩在自己那行，所以棧和日誌全都指不到它。
只有把能跑的舊版和崩的新版擺在一起，逐字段比對運行時狀態，才看得出”舊版沒有這段”。

2. 崩點模式比”猜假設”有力得多。
根因 2 是靠”崩點永遠緊跟 subN/M”這個模式一眼看出來的，
而不是靠推理。拿到多次崩潰現場，第一件事是找它們的共同模式。

3. 排查期必須有絕對可靠的取證通道。
這個項目 stdout 被自定義 stdio 的 4KB 塊緩衝吞掉，崩潰時緩衝區全丟——
我一度靠空日誌誤判過三次。後來改用 O_SYNC 直寫的相位樁，
每次腳本上傳都 md5sum 校驗（踩過 3 次 0 字節腳本導致誤判”新版不崩”）。

4. 「跑不起來」先 ps 一遍。
真的，這個成本 1 秒，能省掉一小時的錯誤歸因。

5. A/B 是唯一誠實的實驗。
本文五個根因，每一個都是”改一個變量、跑一次、對比”定出來的。
憑推理猜出來的假設，我試了八個，全錯。
