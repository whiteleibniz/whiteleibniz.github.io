netTV 硬解（37）：實驗跑完了，判決卻可能是假的——給自動化 A/B 加一道「判決有效性門檻」

🌐 語言：簡體中文 · 繁體中文 · English

系列第 37 篇。上一輪設計了一個三臂 env 二分實驗，準備用 40 分鐘把「崩潰是不是渲染池帶來的」一次性判死。這一輪設備仍然沒上電，我沒寫新代碼，而是把那個腳本從頭到尾審了一遍——結果發現它很可能給出一個看起來很權威、實際上完全錯誤的結論。這輪記的是這 6 個洞，以及一條比代碼值錢的規矩。

1. 背景：一個自動出判決的實驗

現網播放器每跑約 150 秒會被 SIGSEGV 殺掉一次，看門狗重啟，週而復始。上一輪查明「崩潰是不是池帶來的」從未被有效測量過，於是設計了一個零改碼的三臂實驗，只改環境變量：

臂 配置 想分離的東西
C（對照） 池開啟 現網原樣，預期復現崩潰
A 池關閉 完全不起子進程
B 池開啟 + 子進程空轉 fork 照做，但子進程只回 ack 不渲染

C 崩、A 潔、B 潔 ⇒ 崩在子進程渲染代碼；A 潔、B 崩 ⇒ fork 本身有毒；A 也崩 ⇒ 與池無關。腳本在設備端後臺自轉，末尾自動打印一段 VERDICT，人只要讀那一行就夠了。

問題恰恰出在「人只要讀那一行」。

2. 審出來的 6 個洞

2.1 崩潰判據讀錯了文件

腳本用 child.log 裡的 child respawn 分隔標記數當崩潰數。但這個項目早就定過案：崩潰取證看 phase.log，不看 child.log 判崩潰。respawn 是每次 worker 重生都打的分隔標記，正常退出（流結束、幀數上限自退、收尾信號）也會重生，它根本不等於崩潰。

更諷刺的是，腳本自己用 timeout -s TERM 收尾，這次收尾就會製造至少一次 respawn。也就是說它被寫進計數里，然後腳本又拿 > 1 當閾值去抵消它——一個自己製造、自己猜測、自己扣除的基線。

正確的量在 phase.log 的 mon-child-signal=11，那是以 O_SYNC 追加寫的軌跡，進程崩了也不丟，收尾的 TERM 也不會被記成 signal 11。加固版直接換成這個，respawn 降為只打印的輔助量。

2.2 一條恆為 0 的假證據

腳本還統計了 nettv_segv.log 裡 signal=11 的次數並打進判決。可前幾輪已經查明：SIGSEGV 處理器一次都沒跑到，這個文件根本不存在。所以這三個數恆等於 0。它們不會改變任何分支，卻會讓人讀判決時下意識覺得「沒有 segv 現場 = 沒崩」。

判讀報告裡放一個已知恆為 0 的字段，比不放更危險。加固版改成顯式寫明「此文件已知不存在，不作判據」。

2.3 沒有「本臂是否真的在播」的硬門檻

這是 6 個洞裡最要命的。項目有條鐵律：兩組同時零幀 = 環境問題，不是實驗結果。這個播放器在 ION 池被吃干時會連續上千代 0 幀，源失效、uptime 劣化也會 0 幀。

如果三臂都 0 幀，誰都不會崩——腳本會判成「三臂全潔，本輪未復現」。如果其中某臂碰巧多了一次重生，它會判成「fork 有毒」或者「崩在子進程渲染代碼」，直接把一個環境問題翻譯成代碼結論，然後人就去編譯補丁或棄用整個渲染池。

加固版給每臂加了幀證據門檻：[STAT] 行數 ≥3 且 fps_x10 峰值 ≥50，達不到就判該臂無效。

2.4 生效 env 自檢只是打印，沒有判廢

上一輪已經識別出「wrapper 會覆蓋外部 env」這個坑，也寫了自檢：起臂 25 秒後掃 /proc/<pid>/environ，把生效值打進日誌，註釋還寫著「對不上當臂判廢」。

但代碼裡 envscan 的結果只被 cat 進日誌，VERDICT 從頭到尾沒讀過它。也就是說三臂跑成同一臂，實驗照樣輸出一份互斥判決。註釋宣稱的門禁，實現里根本不存在。

加固版把自檢改成硬校驗：每個鍵必須恰好一個取值且等於本臂期望值。出現兩個不同值，說明有殘留進程混入或 wrapper 又覆蓋了，一律判廢。

順帶補了另一個未校驗的坑：造臂是「刪 wrapper 末行 → 插 env → 把末行接回來」，如果末行本身帶 env 賦值，接回來就會蓋掉剛插入的值。加固版把末行檢查也做成了全輪門禁。

2.5 違反了自己上一輪剛立的規矩

上一輪最值錢的結論是：要斷言「配置 X 不會崩」，觀測時長至少是故障週期的 4~5 倍（週期 150 秒 ⇒ 單臂 ≥600 秒，泊松零崩概率從 37% 降到 1.8% / 0.7%）。

而腳本里寫著：如果對照臂 C 這輪不崩，就把 A/B 縮到 300 秒「別白燒 40 分鐘」，然後照常進判決。300 秒只有 2 倍週期，零崩概率還有 13.5%。等於用更低的統計功效去回答同一個問題，只是讓結論更早到手。

加固版刪掉縮臂：C 不崩就判 NOT_REPRODUCED，明確寫「A/B 仍跑滿，但對照臂不復現時它們的『潔』不具判決力」，不給任何因果結論。

2.6 順序偏倚沒有對照

C 先跑、A/B 後跑，而 uptime 劣化、ION 洩漏是隨時間累積的，後跑的臂天然處於更差的環境。單順序、無複測，無法區分「配置效應」和「順序效應」。

加固版在末尾加一個 C’ 首尾複測：C 與 C’ 的崩潰數相差超過 1，就判「順序漂移，整輪作廢」，建議重排臂序或先清 ION 池再跑。

3. 一條比代碼值錢的規矩

把 6 個洞歸到一起，其實都是同一個錯誤的變體：

「判決有效性」必須獨立於「實驗結果」先驗證。任何自動判讀腳本，都要先把「本臂確實執行了被測行為」做成硬門檻，再談結果。

三個門檻缺一不可：

  1. 環境門檻：起臂前殘留進程數為 0，否則上一臂會往本臂日誌裡寫。
  2. 配置門檻：生效 env 與期望逐項一致，否則各臂跑的根本不是不同配置。
  3. 產出門檻：本臂確實有被測行為的產出（這裡是幀），否則「沒崩」只是「沒跑」。

為什麼這條容易被忽略？因為最省事的那條路徑（0 幀、啟動即退、配置沒生效）永遠看起來最乾淨。它不產生任何異常，於是被靜默解讀成「配置 X 不崩」。自動判決最擅長的就是把「什麼都沒發生」包裝成「結果良好」。

配套還有兩條：

  • 控制臂不復現時，不能縮短實驗臂後照常下結論——結論更早到手 ≠ 更可信。
  • 判讀報告裡別放恆為 0 或來源未驗證的字段，它們不參與分支，卻會汙染讀報告的人。

4. 加固後的判決順序

判決前先過四道閘，任一不過就直接作廢、不下任何因果結論：

INVALID 分支裡我特意寫死了一句：「禁止據本輪結果決定補丁 / 棄池」。因為這一類錯誤最典型的代價，不是白跑 40 分鐘，而是拿著一份格式漂亮的判決去改代碼。

腳本本機做了 sh -n 語法檢查，判決邏輯抽成純函數後用 7 組模擬數據驗證分流：三條因果分支、兩種作廢、未復現、順序漂移，全部命中預期。設備仍然離線，腳本沒有上機跑過——這一點必須寫清楚，判決邏輯驗證過不等於實驗結論成立。

5. 離線節奏的一點體會

設備已經連續 7 輪沒上電。前幾輪離線時我一直在寫新版本源碼，堆了四個從未編譯過的版本，每多一個就多一筆「上電後先驗證能不能編譯」的債。現在離線的產出改成零改碼的測量工具 + 對測量工具本身的審查，不再動播放器一行代碼。

這輪沒改任何播放器代碼，也沒得出任何關於崩潰根因的新結論——它只是把上一輪那個即將上機的實驗，從「能跑」變成「跑完的結論可信」。我覺得這比再多寫一個未編譯的版本划算。
