GBA退出偶發卡在遊戲畫面_買單鍵漏給UI層

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_15 — GBA 退出”偶發卡在遊戲畫面”（買單鍵漏給 UI 層 → 本頁被彈掉 → 無人重繪）

  • 日期：2026-09-23
  • 現象：按買單退出 GBA 遊戲，miniretro 進程確實退出了，但畫面有時不刷新、停在遊戲畫面上；有時又能正常回到遊戲列表。概率性故障。
  • 觸及文件：lv_pages/gba_game_page.c（退出流程）、extern/miniretro/miniretro_gba.c（fb_restore()）
  • 一句話結論：三處協同缺陷 —— 退出期間按鍵線程被 sleep 佔住 → 殘留按鍵漏給 UI 層 → 本頁被當”返回”彈出 → 負責整屏重繪的定時器隨頁面消失 → 屏幕留在遊戲畫面。

1. 背景：這次和上一版（bugfix_14）不是同一個問題

bugfix_14 修的是”前端退出時前臺停在第 1 頁，而 UI 層只畫第 0 頁 → 屏幕定格”。那一版加了父子雙層兜底翻頁，翻頁本身已經可靠（日誌可見 fb pan 回第0頁(無條件)）。

本次的關鍵區別：進程確實退了、頁也確實翻回第 0 頁了（實測 yoffset=0），但屏幕內容仍是遊戲畫面。
也就是說問題已經從”翻頁”轉移到了”誰來把新界面畫上去“。

2. 根因（三處協同，缺一不成立）

2.1 買單鍵漏給 UI 層，把本頁一起”返回”掉了

舊版 gba_exit_to_list() 在按鍵線程裡 usleep(600ms) 等補 SIGKILL，於是：

  1. 這 600ms 內沒人讀 /dev/input/event0，輸入事件堆在內核緩衝裡；
  2. 前端前端約 30ms 就退出了，內核回收 evdev fd 約 450ms，wait 線程隨即摘掉按鍵攔截器；
  3. 按鍵線程醒來時攔截器已不在 → 堆著的”買單鬆開”事件一股腦湧進 UI 層；
  4. 它被當成”返回”鍵（ESC）→ 本頁被彈出。

2.2 頁面一銷燬，負責整屏重繪的定時器也跟著沒了

gba_timer_cb 是掛在本頁上的（lv_timer_create），頁面銷燬時 lv_timer_del 把它刪掉。
於是”整屏重繪”這件事依賴頁面存活 —— 2.1 一旦發生，就再沒有人 lv_obj_invalidate + lv_refr_now。

2.3 前端把遊戲畫面寫進了 UI 層的地盤

fb_restore() 舊版在翻回第 0 頁之後，還把前臺頁整頁 memcpy 到第 0 頁（”定格最後一幀”）。
第 0 頁正是 UI 層永遠繪製的那一頁 → 一旦沒人重繪，屏幕上留下的就是遊戲畫面。這就是本故障的物質形態。

3. 證據（設備日誌）

  • [nav] key=27（27 = LV_KEY_ESC = 買單）證明買單鍵確實漏到了 UI 層；
  • 緊隨其後的 [pm] 頁面 'gba_game' 離場 證明本頁被彈出；
  • 同一份日誌裡另一次退出沒有 [nav] key=27 → 這正是”有時好、有時壞”的來源；
  • 故障現場實測 yoffset=0（頁已歸位）→ 排除 bugfix_14 那類”頁沒翻回來”，鎖定”無人重繪”。

4. 修復（8 處改動）

4.1 按鍵線程立刻返回，補刀交給 wait 線程

gba_exit_to_list() 只發 SIGTERM 就返回 —— 按鍵線程必須馬上回去繼續讀鍵盤，把退出期間產生的殘留事件吞掉（那時攔截器還在）。

4.2 整屏重繪改用 lv_async_call，不再依賴頁面存活

新增 gba_repaint_async()，由 lv_async_call 排隊給主線程執行：

lv_async_call 的回調不依附任何頁面對象，頁面在不在都會執行；此刻 lv_screen_active() 已經是該顯示的頁面，整屏重繪即可覆蓋殘留。

4.3 收屍改非阻塞輪詢（順帶把 UI 恢復提前約 570ms）

wait 線程先 waitpid(WNOHANG) 輪詢最多 600ms，超時未死才補 SIGKILL，再阻塞收屍。
判據仍然只有一個硬事件——子進程真的消失；超時那一刻不是”當作它退了”，而是強制它死。絕不設”跑滿 N 秒就算退出”的上限。

4.4 前端去掉整頁 memcpy

雙緩衝下第 0 頁裝的本就是遊戲的上一幀，視覺上與”最後一幀”沒有差別；去掉後既省掉 3.7MB / ~15ms 的拷貝，也消除了”往 UI 層地盤寫外部內容”這個競爭源。

4.5 頁面銷燬路徑同樣兜底

按右上角”返回”按鈕回桌面走的是 gba_on_destroy，同樣補一次 lv_async_call 重繪。

4.6 gba_on_destroy 先 SIGTERM 再 SIGKILL

原實現直接 SIGKILL，會把 .sav 存檔寫一半斷在 SD 卡上；改為最多等 300ms 再補刀。

4.7 攔截器摘除順序後移

hardware_keys_set_interceptor(NULL, NULL) 移到恢復段最後，儘量讓按鍵線程先吞乾淨殘留事件。

4.8 gba_timer_cb 聚焦前校驗對象有效

lv_group_focus_obj(s_gba.btns[0]) 前加 lv_obj_is_valid。

5. 驗證

  • 前端 sh build.sh → FRONT_RC=0；主程序 make -j2 → MAKE_RC=0 / 0 error
  • 原子替換 BIN_OK，重啟後單實例；build/lvgl_demo 與 /usr/local/bin/lvgl_demo 同大小同時間戳
  • 源碼校驗：gba_repaint_async 5 處命中、lv_async_call 4 處命中、舊 usleep(600...) 調用已無（僅剩說明性註釋）
  • 待實機複測：連續多次”進遊戲 → 買單退出”，每次都應回到遊戲列表且畫面立即刷新

6. 反模式記錄

  1. 讓”界面恢復”依賴某個頁面對象（定時器/控件）存活 —— 頁面一旦先被銷燬，恢復就靜默失效，且沒有任何報錯。
  2. 在自己線程裡 sleep 等補刀 —— 阻塞期間沒人消費輸入，殘留事件會在攔截器摘除後一起湧入 UI 層。
  3. 往”別人的頁面”寫內容（往 UI 層永遠繪製的那一頁拷幀）—— 只要對方重繪時序有一點偏差，殘留就永久留在屏幕上。

7. 遺留

  • .sav 落盤：本次給 on_destroy 加了最多 300ms 的等待窗口，但未做存檔完整性校驗。
  • FC 側不受影響（獨立前端 + 獨立頁面），本輪未改動。
