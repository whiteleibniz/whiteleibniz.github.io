bugfix_20260923_09 — GBA 退出遊戲返回列表卡頓（內核回收輸入設備 fd 極慢）

  • 日期：2026-09-23
  • 模塊：GBA 遊戲頁退出路徑 / extern/miniretro/miniretro.c / 內核輸入子系統
  • 影響：GBA 退出返回列表的響應速度（FC 頁共用 miniretro，同理但本次未改）；另含一次”兜底強殺後未收屍”的殭屍進程問題

與 bugfix_07 的區別：07 修的是”退出後畫面僵住/殘留“（fb 停在翻轉頁）。
本次修的是 07 之後仍然存在的”畫面回得慢“——按買單鍵要等約 0.35~0.4 秒才回到列表。

1. 問題現象

按”買單”鍵（116）退出遊戲，畫面已經不再是遊戲畫面，但要過約 0.35~0.4 秒列表才出現，體感是”卡一下”。用戶反饋：”退出遊戲返回到列表還是卡頓”。

2. 影響範圍

  • GBA 遊戲退出返回列表（本次修復）
  • FC 遊戲退出（共用同一份 miniretro，理論同樣慢；FC 頁未改，行為不變）
  • 附帶修掉：一次 SIGKILL 兜底後未收屍 → 子進程變殭屍掛在 lvgl_demo 名下

3. 根因分析

用 2ms 粒度採樣 + 在 miniretro 退出路徑里加分段計時（ssh_tools/gba_exit_latency.py）實測：

逐個設備復現（不需要 miniretro，單獨 open/close 就能復現）：

設備 節點 驅動 close 耗時
物理四鍵 /dev/input/event0 sprd-gpio-keys 39 ~ 215 ms
另一組按鍵 /dev/input/event1 sprd-eic-keys ~80 ms
耳機鍵 /dev/input/event2 headset-keyboard ~80 ms

結論：

  1. 子進程內部收尾不是瓶頸（deinit/pan/清屏合計約 30ms）。
  2. 本機內核關閉 sprd 輸入設備固定要幾十~幾百毫秒。進程退出時內核必然要關這些 fd，用戶態怎麼改都躲不掉 —— 所以”子進程真正消失”至少要 ~340ms。
  3. 父進程側還有兩段白等：
    • gba_exit_to_list() 裡 usleep(250ms) 死等；
    • gba_wait_thread() 用阻塞式 waitpid 等子進程”真正消失”（= 內核那 340ms 之後）才恢復 LVGL。
  4. 兩段疊加 → 約 0.35~0.4s。卡頓不是渲染問題，是”等一個不必要的事件”。

4. 修復方案

核心思路：UI 恢復不再等子進程死亡，改由子進程在”畫面已交還”的那一刻主動通知父進程。

miniretro 側（子進程）

  • cleanup 順序固定為：core_deinit()（必須保留，mGBA 要在這裡落盤電池存檔 .sav）→ fb_restore()（翻回第 0 頁 + 清屏，約 35ms）→ notify_parent_ui_released() → _exit(0)。
  • notify_parent_ui_released()：給父進程發 SIGUSR1。
    必須由父進程用環境變量 MINIRETRO_UI_RELEASE_SIGNAL 顯式開啟才發 —— SIGUSR1 默認動作是終止進程，沒裝處理函數的調用方（如 FC 頁）一旦收到就會被打死。
  • _exit(0) 之後不再逐個 close(fd)/munmap：反正內核退出時都要做，而那 340ms 丟到後臺去，不阻塞 UI。

頁面側（lv_pages/gba_game_page.c）

  • gba_launch()：fork 之前裝 signal(SIGUSR1, gba_ui_release_handler) + setenv("MINIRETRO_UI_RELEASE_SIGNAL","1",1)（必須早於 fork，否則信號可能先到 → 默認動作殺進程）。
  • gba_exit_to_list()：只 kill(pid, SIGTERM)，一行都不等。
  • gba_wait_thread() 兩階段：
    • 階段① 5ms 粒度等”收到 SIGUSR1 或 子進程真退出”（≤500ms 兜底），一滿足就 hardware_keys_set_grab(true) → 摘攔截器 → app_runtime_set_lvgl_paused(false)；
    • 階段② 後臺收屍：5s 超時後 SIGKILL 並同步 waitpid 收屍。
  • 保留分秒計時 [miniretro][timing] 日誌，方便下次迴歸直接看數字。

5. 驗證方法與結果

① 退出耗時對比（受控測量）

指標 修復前 修復後
子進程內部收尾 385 ms 37 ms
父進程收到”畫面已交還” — 40.6 ms
子進程真正消失（內核回收） 394 ms 337 ms（已與 UI 無關）

② 握手協議驗證（ssh_tools/gba_ui_release_test.py，python 偽父進程，無需按物理鍵）

③ 恢復是否”瞬時”：lv_tick_inc() 在主循環裡無條件執行（main.c:635），暫停期間 LVGL 時間照走，所以恢復後 100ms 定時器早已過期，第一次 lv_timer_handler() 就觸發整屏重繪；主循環 10ms 一跳。即恢復路徑沒有額外等待。

預期觀感：按買單 → 40ms 交還畫面 → 立即重繪列表（原 0.350.4s）。

6. 迴歸風險

  • 子進程既不通知也不退出：階段① 500ms 後仍會恢復 UI，退化為舊行為，不會卡死；階段② 5s 後強殺收屍。
  • 子進程退出期間（0.30.4s）仍持有 fb0/evdev 的 fd（內核正在回收），但它已不再繪製，不影響 LVGL（LVGL 自己持有 fb0；yoffset 是設備級狀態）。
  • FC 頁未改：退出仍等子進程消失（~340ms）。若要一併提速，把上述頁面側三處改動搬到 fc_game_page.c 即可（miniretro 側已就緒，且默認不開信號門禁）。
  • 部署紀律（本次踩坑）：extern/miniretro/build.sh 是 gcc ... -o miniretro，直接寫目標文件。用戶正在玩時重編，恰有啟動動作 exec 到半覆蓋的二進制 → 子進程卡在 exec 裡、啟動失敗、2.5s 後被兜底強殺且未收屍（殭屍）。
    現統一要求：二進制一律”編到 *.tmp → mv -f 原子替換”，部署走 ssh_tools/gba_redeploy.py。
