bugfix_20260923_02 — 頁面離場不清焦點組，導致桌面焦點環消失

現象：進過任意頁面再返回桌面後，按方向鍵粉色焦點框憑空消失、且走不到目標圖標；
重啟應用即恢復。觸摸點擊不受影響。
根因層：LVGL 頁面框架的焦點組生命週期（lv_pm/lv_page_manager.cc）/ 桌面自定義導航（main.c）。
修復工作量：2 個文件（lv_pm/lv_page_manager.cc +49、main.c +7/-1）。
文件名：bugfix_20260923_02_頁面離場不清焦點組導致桌面焦點環消失.md
關聯提交：221fa7d
日期：2026-09-23

現象

在任何非桌面頁面裡返回桌面之後，桌面按方向鍵會出現：

  1. 粉色焦點框憑空消失 —— 按了鍵，界面上看不出當前選中了哪個圖標；
  2. 繼續按方向鍵走不到想去的圖標（比如想回到「收音機」，卻卡在別處或原地不動）；
  3. 反覆按也沒有規律，重啟應用（不是重啟設備）後恢復正常，一進頁面再返回又壞。

即在”進過頁面 → 返回桌面”這條路徑上，桌面導航會被汙染。

這是排查「藍牙顯示已連接實際未連接」過程中連帶發現的 bug：
為了給藍牙頁做按鍵驗證（進頁面 → 返回 → 走到藍牙圖標），發現根本走不到，
一查才知道桌面焦點早就壞了。

影響範圍
受影響 桌面（launcher）的按鍵導航；所有”進過頁面再返回”的場景；間接觸發了本會話另一處「收音機頁進不去」的誤判
不受影響 觸摸點擊（不走焦點組）；頁面內部自身的導航；頁面渲染；FM 收音機、藍牙等業務邏輯

觸摸能點、按鍵不能走，是本 bug 最典型的表現。

根因

兩處獨立缺陷疊加，各自都能讓導航失靈。

3.1 頁面離場時，不把自己的控件從”公共焦點組”裡摘掉

LVGL 的默認焦點組是全局共享的。各頁面在 onCreate 裡調用
lv_group_add_obj(lv_group_get_default(), obj) 把自己的控件掛進去，
但離開時幾乎沒有人調用 lv_group_remove_obj() ——
全倉只有 3 個文件做了這一對操作，其餘頁面全是”只加不減”。

於是每進一次頁面，就有一批已經隨頁面一起被刪除、或已不可見的控件
殘留在組裡，變成”幽靈焦點”。實測計數（lv_group_get_obj_count）：

group_find_neighbor 在這些幽靈裡挑鄰居，於是：

  • 選中一個沒有 user_data 的控件 → 桌面畫焦點框的代碼拿不到格子信息 → 框消失；
  • 方向鍵的”鄰居關係”被幽靈攪亂 → 走不到目標圖標。

3.2 group_find_neighbor 只看控件自己的 HIDDEN，不看祖先

main.c 的自定義導航裡，原判定是：

而 LVGL 裡隱藏一個面板，隱藏的是外層容器，裡面的子控件自己並不帶
LV_OBJ_FLAG_HIDDEN。結果：狀態欄那個收起狀態的音量浮層滑塊
（父面板 340×42，滑塊自己 252×14）被當成合法候選選中了。

定位到它靠的是”打印幽靈對象的形狀再反查”（見 §4.2）：

選中它同樣沒有可用 user_data → 焦點框畫不出來。

一句話：① 組裡有幽靈；② 判定可見性只看了自己，沒看祖先。

定位過程

4.1 先確認”焦點到底落在誰身上”

在桌面渲染焦點框的那段代碼里加了一行 stderr 打點（printf 會因塊緩衝延遲，
**必須用 fprintf(stderr, ...)**）：

  • 故障時（頁面管理器清理已上、祖先感知未上的中間狀態）：
    [fc] focus idx=17/18 cell=0x... content=(nil) box=(nil)
    → content/box 為 空指針 = 當前焦點對象沒有 user_data，
    桌面拿不到”這個焦點屬於哪個圖標格”的信息，    框自然畫不出來    。
    idx=17/18 也印證了：桌面只往組裡加了 17 個格子，第 17 個（0 基）根本不是桌面的。
  • 修復後：[fc] focus idx=7/18 cell=0xb70881d4 content=0xb7088374 box=0xb7088444
    → 三個指針都有值 = 焦點框能正常畫出來。

idx 的分母（組內對象總數）本身就是線索：把每個頁面進/出時的組計數打出來，
會看到數字只漲不跌（見 §3.1 與 §6.1）—— 這正是”幽靈在累積”的直接證據。

只加焦點打點不夠，還需要知道幽靈長什麼樣。臨時在頁面管理器里加了一段 dump：

經驗教訓

  1. 全局共享的容器，進和出要成對。 焦點組是全局單例，頁面只 add 不 remove，
    等於把垃圾倒進了公共區域 —— 而且症狀出現在受害者（桌面）身上，不在肇事者（頁面）身上，
    極難從現象反推。凡是”全局註冊表”，就該由框架層統一託管生命週期，別指望每個頁面自覺。
  2. 生命週期要分兩層看：對象被刪 ≠ 從組裡摘掉。 頁面銷燬得乾乾淨淨（[pm] destroy 正常），
    控件照樣賴在組裡。查這類問題時，打印”容器裡現有多少元素”比打印”我刪了什​麼”有效得多。
  3. 可見性判定必須祖先感知。 LV_OBJ_FLAG_HIDDEN 只描述對象自己；
    “這個控件現在用戶能不能看見”是一個沿父鏈的問題。LVGL 裡凡是”隱藏容器”的寫法，
    都會踩這個坑。
  4. “重啟應用就好”是強烈的”外部汙染”信號。 它說明故障不是算法本身錯，
    而是運行期狀態被別處改髒了 —— 排查方向應立刻從”算得對不對”轉向”誰動過共享狀態”。
  5. 診斷打點用 fprintf(stderr, ...)。 printf 寫文件是塊緩衝，日誌會滯後很久，
    容易誤判成”代碼沒執行”（排查 FM 頁面時也踩過同一個坑）。
  6. 把”規範”下沉到框架層，而不是寫進文檔。 本例最初只是在文檔裡寫”記得 remove”，
    結果沒人執行；搬進 pm_page_destroy 後，新舊頁面一次性合規。
    能被代碼強制的約定，不要靠自覺。
