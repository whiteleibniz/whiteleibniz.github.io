GBA音畫延遲1到2秒_音箱端緩衝定位

wlb
2026-09-23
bugfix, 模拟器

bugfix_20260923_17 · GBA 音畫延遲 1~2 秒：定位到音箱端緩衝，設備側無可修點

  • 日期：2026-09-23
  • 設備：展訊 SC9832A / Alpine Linux / 720x1280 fb
  • 應用：GBA 遊戲（miniretro_gba + mgba_libretro.so）→ 藍牙 A2DP（小愛音箱）
  • 分類：音頻鏈路 / 延遲預算定位
  • 結論：設備側全鏈路延遲 ≤0.25s，與用戶實測 12s 差 48 倍；超出部分在藍牙音箱端的應用層緩衝，設備側既不可觀測也不可控 → 本輪不做代碼改動

1. 現象

用戶反饋：GBA 遊戲「聲音比遊戲畫面落後」，量級 1~2 秒，且固定（一進遊戲就落後那麼多，長時間玩也沒有明顯變化）。

“固定”這一條是決定性的：它排除了”設備側積壓”這一類原因（積壓會隨時間累積、越玩越久），指向鏈路中某一段的固定緩衝。

2. 定位方法：鏈路分段量化（延遲預算表）

把「遊戲音頻生成 → 出聲」拆成 5 段，逐段量化出延遲，找出量級對不上的那一段：

# 段 延遲 依據（可復現）
1 mGBA core 內部音頻緩衝 ~33ms libretro.c：internalAudioBufferSize = audioSamplesPerFrame * 2（上限 0x4000）；GBA 每幀 ~1097 樣本 → 約 2 幀；且 retro_run 每幀 mAudioBufferRead(buffer, ..., audioSamplesPerFrameAvg) 一次取走，不累積
2 前端 miniretro_gba 0 fifo_write() 是收到就寫、非阻塞（EAGAIN 直接丟）；重採樣為無狀態丟樣（s_out_acc 累加器 + 直接複製樣本），無內部隊列、無攢批
3 /tmp/bt_audio.fifo 積壓 80ms 水位閉環後實測 back ≈ 14000B（原始 0.21s 已壓到 ~0.08s）
4 daemon 在途包 ≤122ms A2DP_MEDIA_INFLIGHT_MAX=6 × 20.3ms/包；實測 inflight=0/1776、credit busy=0
5 藍牙空口 + 音箱應用層緩衝 不可觀測 見 §3
— 設備側小計 ≤0.25s

對照用戶實測的 1~2 秒：差額全部落在第 5 段。

3. 為什麼判定在音箱端（以及為什麼設備側測不到）

判定依據：設備側四段都有硬實測、加起來 ≤0.25s；「固定」的性質又排除了累積型原因。剩下的量級只能來自音箱。

為什麼設備側觀測不到音箱緩衝（這三條是本節的重點，別再白費力氣找）：

  1. ACL 層的 Number-Completed(0x13) 不等於應用層消費確認 —— 它由藍牙控制器回，只表示”空口傳完了”，音箱把包放進自己緩衝後並不會因此額外通知。
  2. A2DP 媒體通道走 L2CAP basic mode，沒有 credit 流控 —— sink 不會告訴 source”我手裡還壓著多少”。
  3. daemon 的發送節奏是設備側絕對時鐘（每 20.3ms 一包），與音箱的消費節奏完全解耦；設備側只能知道”我發了多少”，無法知道”它播到哪”。

旁證：daemon 源碼註釋（v48R22 那次修復）自述「sink 緩衝約 2s」。那次是異常態（缺 START 直接推流）下觀察到的，但側面印證該音箱的緩衝深度就在秒級。

4. 本輪結論與決策

  • 不做設備側代碼改動。理由：設備側剩下可壓的只有約 90ms（fifo 水位 60→30ms、在途窗口 6→3），相對 1~2s 是 5% 量級，收益可忽略；且收緊藍牙發送窗口有歷史「CP 復位」風險，風險收益比不划算。
  • 上一輪已落地的fifo 水位閉環（把積壓從 0.21s 壓到 0.08s）保留，它是有效的、無副作用的改進。
  • 可行的改善方向只在音箱端：音箱 App / 音箱本體的「低延遲 / 遊戲模式」開關；或換一臺延遲更小的藍牙音箱/耳機做對照。

5. 驗證

  • 用戶已確認：固定落後、量級 1~2 秒 → 與”音箱固定緩衝”模型完全吻合。
  • 對照實驗（推薦用戶做，一步定論）：把設備連到另一個藍牙耳機/音箱，若延遲顯著改變 → 100% 確認是音箱端；若換誰都一樣 1~2 秒 → 再回頭查鏈路。

6. 反模式與踩坑

  • ★ 別用”設備側的緩衝指標”去解釋”秒級”延遲 —— 先做延遲預算表，看哪個量級對不上，再深挖那一段。憑直覺猜”肯定是緩衝”會一直在設備側空轉。
  • ★ Number-Completed ≠ 應用層消費確認（見 §3.1），拿它估音箱緩衝是錯的。
  • ★ 測量時注意計數方式：全文件計數做差分才有意義；用”固定前綴計數”做差分必然為 0（自己給自己挖的坑，本輪真踩了）；日誌輪轉也會汙染差值。
  • ★ FIONREAD 量 fifo 積壓是可信的：它返回管道內可讀字節數，與讀端數量無關；只讀 FIONREAD、不 read，就不會搶走消費者的數據。
  • ★ 前端”把音頻拉伸到實時”的設計是正確的：核心產出隨實際幀率變化，前端按 s_fpc × s_fps_meas 歸一後恆以 44100 幀/秒輸出，音畫內容速率保持同步（代價是音調隨幀率下降）。別再懷疑這裡。
