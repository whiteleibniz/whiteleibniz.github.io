bugfix_20260923_13 — GBA 退出”卡黑屏”：真兇是前端退出時自己清屏（不是 fork 形式的問題）

  • 日期：2026-09-23
  • 設備：展訊 SC9832A / armv7l / Alpine / 720×1280 fb0（yres_virtual=3840，3 頁）/ 4 物理鍵
  • 涉及文件：
    • 設備 extern/miniretro/miniretro.c（GBA 專用前端，編譯產物 miniretro_gba）
    • 本地 ssh_tools/_tmp/miniretro.c（同源）
    • 本地 ssh_tools/gba_redeploy.py（部署腳本，本次修掉一處會誤傷 FC 的隱患）
  • 證據腳本：ssh_tools/gba_black_probe.py、ssh_tools/gba_black_run.py、ssh_tools/ssh_run.py

1. 問題現象

用戶反饋：GBA 遊戲退出時”卡黑屏”；而 FC 遊戲用同樣的退出方式（同樣是 fork + 獨立前端進程）一直很流暢。

用戶提出的疑問是：”GBA 這個前端不是 fork 這種形式嗎？” ——
是。GBA 與 FC 走的是完全相同的 fork + execl 形式（父進程 = lvgl_demo，子進程 = extern/miniretro/miniretro_gba 或 miniretro，前端直接寫 /dev/fb0）。
正因為形式相同，”為什麼一個流暢一個卡”只能到屏幕內容上去找，而不是在進程模型上找。

2. 影響範圍

  • 僅 GBA 頁退出路徑（lv_pages/gba_game_page.c → miniretro_gba）。
  • FC 頁未受影響：它的前端 extern/miniretro/miniretro 是 git 倉庫原版、不捕獲 SIGTERM，本次一行未動（md5 校驗見 §5）。

3. 根因分析

3.1 實測：兩個前端收到 SIGTERM 後，屏幕到底發生什麼

停掉 lvgl_demo/watchdog，直接拉起兩個前端跑 3s，然後發 SIGTERM，按時間點採樣屏幕中心區域
（”非黑比例 / 平均亮度”，fb0 有 3 個虛擬頁，採樣按當前 yoffset 取當前顯示頁）：

3.2 結論

差別只有一個：退出時前端要不要清屏。

  • miniretro（FC）不捕獲 SIGTERM、不做任何 fb 操作 → 被內核直接殺掉，屏幕停在遊戲最後一幀。
  • miniretro_gba（GBA）捕獲 SIGTERM 走優雅收尾，其中 fb_restore() 裡有一句 memset(fb_buf, 0, fb_total_bytes)，
    在第 20 ms 就把整塊虛擬顯存清黑 → 屏幕立刻變黑。

而兩個前端的子進程”真正消失”都要 ~1020 ms（內核 exit_files() 逐個回收繼承來的 5 個 /dev/input/eventX 與 fb0 映射的固有開銷，與前端寫不寫 fb 無關）。
父進程（GBA 頁）當前用的是阻塞 waitpid，要等收屍完成才恢復 UI（這是 12 號文檔按用戶要求對齊 FC 的做法）。

於是兩條時間線是：

  • FC：0~1020 ms 屏幕定格在遊戲最後一幀 → 恢復 UI 重繪。用戶看到的是”畫面定了一下，很流暢”。
  • GBA（修前）：20~1020 ms 屏幕是純黑 → 恢復 UI。用戶看到的就是”卡黑屏“。

一句話：**”卡”是兩個前端共有的（~1s 的內核回收開銷，FC 也一樣）；”黑”才是 GBA 獨有的、由自己清屏造成的。**

3.3 為什麼當初會寫上 memset 清屏

原本的擔心是”殘留遊戲畫面”：LVGL 恢復後只刷髒區，殘留會糊在屏幕上。
但 GBA 頁恢復時本來就做了 lv_obj_invalidate(lv_screen_active()) 整屏重繪，這個擔心不成立 ——
清屏是多餘動作，代價卻是整整 1 秒的純黑屏。

4. 修復方案

4.1 fb_restore()：清屏 → 跨頁定格拷貝（核心修復）

  • 翻回第 0 頁的動作保留（yoffset 不歸零 = LVGL 畫在不可見頁 = 永久黑屏，這個是必須的）。
  • 不再清屏；若退出瞬間前臺是第 1 頁，則把第 1 頁整頁拷到第 0 頁，保證”屏幕內容與退出前逐像素一致”（定格，不閃黑、不跳幀）。
  • 頁偏移用既有變量 fb_page_bytes（= 一屏字節），與渲染側 fb_dst = fb_buf + target * fb_page_bytes 完全一致，不存在越界。

4.2 部署腳本 gba_redeploy.py：修掉一處會誤傷 FC 的隱患

--mini 分支原本寫死 gcc ... -o miniretro.tmp ... mv -f miniretro ——
即把 GBA 源碼編成 FC 的二進制名，會把上一輪辛苦還原的 FC 原版覆蓋掉。
本次改為只產出 miniretro_gba，並加了保護：編前備份 + 編後 cmp 校驗，一旦 FC 前端 md5 變化就報錯。

教訓：同一目錄下兩個”同名家族”的產物，構建腳本必須用不同的目標名，並在腳本頭寫死約束。

5.2 實機驗證（AI 自測，已按要求執行）

驗證一：退出時屏幕是否還黑（兩個前端各跑 3s → SIGTERM → 採樣到子進程消失）

  • FC：全程 非黑 0.954 / 亮度 227.4，與退出前完全一致（定格）。
  • GBA（修後）：全程 非黑 1.000 / 亮度 248.0，與退出前完全一致（定格）。
  • 黑屏窗口從 ~1s 降為 0。

驗證二：拷貝分支是否真的被執行到（雙緩衝下前臺頁在 0/1 間切換）

  • 採樣 4 次運行中 yoffset 均為 0（詳見 §6 遺留項 3），但退出日誌顯示 fb pan 回第0頁 17.8ms
    → fb 定格最後一幀(不清屏) 33.0ms，耗時 15 ms —— 正是整頁 3.7 MB 的拷貝用時，證明拷貝分支已執行。
  • 無任何 pan 失敗 告警。

驗證三：收尾狀態

  • lvgl_demo ×1、lvgl_watchdog ×1（測試期間產生的重複 watchdog 已清理為單實例）。
  • FC 前端 md5 = a95d9171d8d8b82a52c12ac84e68aaa2，與編前備份一致。

6. 遺留與觀察（未處理，供後續參考）

  1. 退出後回列表仍要等約 1 秒：這是阻塞 waitpid 等收屍 + 內核回收 fd 的固有開銷，FC 完全一樣（1015ms）。
    若將來要做到”畫面一交還就恢復 UI”，需要重新引入”提前放行”機制 ——
    但那正是 09/10 兩輪翻車的方向（當時的錯誤是：_exit(0) + 超時循環放在互斥鎖內 + setenv 跨頁汙染）。
    本次按用戶要求”與 FC 逐行一致”，不做該優化。
  2. 內核回收 fd 需 ~1020 ms，比早先實測的 ~455 ms 更長（可能受當時系統負載影響）。屬內核固有行為，前端無法影響。
  3. 驅動回讀 yoffset 不可靠：即使 pan 實際生效（拷貝分支被觸發，說明 g_front=1），FBIOGET_VSCREENINFO 回讀仍是 0。
    因此 fb_restore() 裡那段”yoffset 回讀校驗”不會誤報，但也發現不了 pan 失敗 —— 不宜把它當作 pan 是否成功的判據（早先的記憶記載需相應修正）。
  4. 設備在本輪測試期間自行重啟過一次（uptime 45 min），與本 bug 無關。
