bugfix_20260923_18 — GBA 退出後偶發殘留遊戲畫面（強制翻頁）

  • 日期：2026-09-23
  • 現象：退出 GBA 遊戲後，屏幕有時仍顯示”退出那一刻的遊戲畫面”，界面沒回來；
    不是必然發生 —— 同樣的操作，有時正常回到遊戲列表，有時就定格在遊戲畫面上。
  • 影響面：lv_pages/gba_game_page.c（只改這一個文件，前端不動）
  • 是否影響 FC：不影響（FC 前端不翻頁，無頁概念）
  • 與第 14 篇的關係：14 篇治的是”退出後必卡“（加 gba_reset_fb_page() 兜底），
    本次 18 篇治的是那個兜底自己帶來的偶發性 —— 它帶了一個不該有的前置判斷。

1. 背景：誰在畫哪一頁

設備 framebuffer 有 3 個虛擬頁（yres_virtual = 3840 = 3 × 1280）。

誰 怎麼用 fb0
LVGL（lv_linux_fbdev） 只用 mmap 基址繪製 = 永遠寫第 0 頁；yoffset 初始化後不再改，源碼裡 FBIOPAN_DISPLAY 零命中
GBA 前端（miniretro_gba） 用 FBIOPAN_DISPLAY 雙緩衝頁翻轉消撕裂 → 前臺在第 0/1 頁之間來回切

推論：退出時若前臺停在第 1 頁，LVGL 畫什麼都看不見 → 屏幕定格遊戲畫面。
第 14 篇就是靠這個推論定位的，父進程側加了 gba_reset_fb_page() 兜底。

2. 根因：兜底裡那個”看起來無害”的前置判斷

第 14 篇加的兜底實現是帶條件的：

當時的判斷依據是”實測這個驅動的 yoffset 回讀是可靠的”。這次的問題是：這句話即使成立，
也不足以支撐這個判斷 —— 因為它還隱含假設了：

「回讀 yoffset == 0」等價於「掃描輸出正在讀第 0 頁」

yoffset 只是驅動內部的記賬值（下一次 pan 的請求參數），它不保證等於掃描輸出
（scanner / LCDC）當前正在讀的那一頁。兩者一旦不一致：

  • 屏幕實際顯示第 1 頁（遊戲畫面）；
  • 回讀 yoffset 卻是 0；
  • 判斷為假 → 整段翻頁被跳過 → 殘留。

而”兩者是否一致”取決於退出那一刻驅動內部狀態（上一幀提交方式、SIGKILL 落在哪一拍），
與代碼路徑無關 —— 這正好解釋了用戶說的”不是必然發生“。

換句話說：第 14 篇的兜底，把”一定會卡”變成了”偶爾會卡”。
它只在”回讀恰好不可信”時失效，所以看起來像隨機。

第二處隱患：翻頁與整屏重繪分處兩個執行流（前者在收屍線程、後者被
lv_async_call 排給主線程）。這是同一個視覺事務的兩半，中間任何打斷
（回調被吞、頁面先被銷燬、主循環那一拍沒跑到）都會留下”翻回去了但沒重繪”
或”重繪了但前臺還在第 1 頁”的中間態，單獨看都表現為畫面沒回來。

3. 修復（一個文件，4 處改動）

全部在 lv_pages/gba_game_page.c。

3.1 gba_reset_fb_page() — 去掉判斷，無條件翻頁（核心）

關鍵差別：GET 只用一次——為了拿到一份完整合法的 fb_var_screeninfo 當底稿；
它絕不參與”要不要翻頁”的決策。翻頁請求每次都發。

3.2 gba_repaint_async() — 翻頁與重繪同拍

兩件事放進同一個主線程回調、中間不插任何操作 → 必然同拍完成，不留中間態。

3.3 gba_timer_cb() — 主線程側雙保險

主線程恢復路徑（finished 標誌那條）在重繪前同樣補一次翻頁。與 3.2 誰先跑到都行，
翻頁冪等。

3.4 前端 miniretro_gba.c — 不動

它的 fb_restore() 早在第 14 篇就已經是”無條件翻回第 0 頁”，
本次要修的正是頁面側漏掉的那半邊對稱性。

共 5 個調用點（grep -c 'gba_reset_fb_page();' = 5）：
gba_repaint_async / gba_wait_thread / gba_timer_cb / gba_on_create / gba_on_destroy。

為什麼”無條件”是安全的

所有調用點都在子進程已經消失之後（或頁面剛創建、根本沒有子進程時），
不存在併發寫 fb0 的對手；FBIOPAN_DISPLAY 本身冪等，已經在第 0 頁時多發一次零副作用。

項 結果

靜態：舊條件判斷殘留 0 處（FBIOGET_VSCREENINFO,&v) == 0 && v.yoffset != 0）✓
靜態：無條件翻頁調用點 5 處 ✓
靜態：讀回重試代碼 1 處 ✓

5. 反模式記錄（已併入 skill）

  • ★ 「冪等操作 + 前置判斷」是自找分支。判斷所依賴的那個值（這裡是驅動回讀）
    只要存在”與真實狀態不一致”的可能，判斷就會把零成本的冪等操作變成
    “偶發不執行“，而症狀看起來像隨機故障。對冪等且成本可忽略的操作：直接做，不要問。
  • ★ 同一個視覺事務的兩半不要分處兩個執行流。”讓前臺頁歸位”和”把新畫面畫上去”
    是同一件事，拆到兩個線程/兩個回調就會留下人人都看不懂的中間態。
  • ★ 「實測 X 可靠」這類結論必須帶上它支撐的推論範圍。
    “回讀可靠”≠”回讀值等於掃描輸出”，後者才是代碼真正依賴的假設。
  • **偶發故障的第一偵查方向是”判斷條件”而不是”時序”**：先問”這段代碼有沒有可能
    在正確輸入下選擇不做” —— 收益遠高於先懷疑競態。

6. 遺留

  • 用戶實機連續複測：多次”進遊戲 → 買單退出”，每次都應立即回到遊戲列表。
  • 回滾點：設備上 lv_pages/gba_game_page.c.bak_fbpan = 本次改動前。
  • 若將來把這條退出邏輯複製到別的”外部程序接管 fb”的應用（如視頻播放頁），
    必須連”無條件翻頁”一起搬，不要只搬 gba_reset_fb_page() 的名字。
