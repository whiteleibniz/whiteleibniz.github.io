GBA退出邏輯對齊FC

bugfix_20260923_12 — GBA 退出邏輯改為與 FC 逐行一致（取消 GBA 專屬分支）

項目 內容
發現時間 2026-09-23
修復時間 2026-09-23
模塊 lv_pages/gba_game_page.c
涉及版本 承接 bugfix_20260923_11 之後的現場（前端已分離）
現象等級 中（無新故障，屬”消除結構分歧”的收斂性修復）
觸發方式 用戶明確要求：「你把 GBA 的改成 FC 的退出邏輯吧」

1. 問題現象

前端分離（bugfix_20260923_11）之後，GBA 與 FC 雖然各用一個二進制，但退出邏輯仍不是同一套：
GBA 頁保留了一條 FC 頁沒有的”提前放行”路徑（exiting 標誌 + 後臺收屍線程 + 畫面連刷 3 幀）。

這條路徑是 09→10→11 三輪故障中反覆出問題的地方。用戶據此判斷”兩邊邏輯混在一起、退出莫名其妙”，
要求直接把 GBA 的退出邏輯改成 FC 那一套。

用戶的判斷是對的：FC 那套是唯一被實機長期驗證過的退出路徑，任何”改進版”目前都沒有可信的驗證基礎。

2. 影響範圍

  • lv_pages/gba_game_page.c：退出路徑（gba_wait_thread / gba_exit_to_list / gba_timer_cb / 狀態結構體）。
  • 不涉及 miniretro_gba（前端二進制不動），不涉及 FC 頁（FC 頁保持原樣，一行未改）。
  • 結構層面：消除”同構組件之間的人為差異”——差異本身就是後續故障的藏身處。

3. 根因分析

3.1 修復前的四處差異（GBA 相對 FC 的額外複雜度）

# 差異點 FC 頁 GBA 頁（修復前）
1 等待判據 阻塞 waitpid，只認”子進程真的消失” 5ms 輪詢，認 exiting 標誌 或 子進程消失
2 退出函數副作用 只 SIGTERM → 120ms → SIGKILL 追加 s_gba.exiting = true
3 收屍兜底 無（阻塞必然拿到屍） gba_reap_bg() 獨立後臺線程
4 畫面恢復 lv_obj_invalidate() ×1 invalidate() + for(3) lv_refr_now()

3.2 為什麼這四處差異是風險

  • 第 1 處是 09/10/11 三輪卡死/卡黑屏的同一個病灶。只要等待判據裡出現”標誌位”或”時間上限”這類
    非硬事件，就存在”把仍在運行的遊戲判成已退出”的可能，後果固定為兩條：
    ① hardware_keys_set_interceptor(NULL) 摘掉按鍵攔截器 → 退出鍵失效，再也退不出遊戲；
    ② app_runtime_set_lvgl_paused(false) 讓 LVGL 搶回 fb0 → 與仍在運行的遊戲互相覆蓋。
    歷史兩版的差別只是”誤判的觸發條件不同”（時間上限 / 標誌位被讀到），本質同源。
  • 第 3、4 處是為第 1 處的時序問題打的補丁。提前放行意味著”標誌已消費但子進程仍在碰 fb0”，
    於是不得不連刷 3 幀來搶畫面、不得不另開線程收屍。改回硬事件判據後，這兩個補丁不再有存在理由，
    留著反而是多餘的失敗面。
  • 結構性理由：FC 頁這套邏輯經過長期實機驗證；GBA 頁卻帶著一條”只此一處”的路徑。
    同一份設計意圖在兩處寫法不同，未來任何一次修改都容易只改一邊 —— 這正是 11 號文檔裡
    “共用二進制被改壞”那類問題的翻版，只是從”共享產物”變成了”共享語義、各自實現”。

3.3 代價的取捨（明確接受）

FC 那套的唯一代價是：恢復 UI 要等內核回收 evdev fd，實測發信號→收屍完成約 455ms
（其中子進程內部收尾 ~34ms，其餘是內核固有開銷）。09/10 兩輪就是試圖”省掉這幾百毫秒”才出的故障。

本次明確選擇承擔這 ~400ms，換取”GBA 與 FC 行為逐行一致”。理由：

  • 455ms 的黑屏一閃在用戶感受上屬於”退出有一下停頓”，可接受；
  • 相比”偶發卡死、退出鍵失效、只能重啟”，這個代價小得多；
  • 一致性帶來的可驗證性 > 幾百毫秒的性能收益。

4. 修復方案

原則：GBA 頁退出路徑照抄 FC 頁，不給任何專屬分支。

4.1 gba_wait_thread() 改為阻塞 waitpid

安全性依據：上游 gba_exit_to_list() 保證 SIGTERM 後 120ms 必然補上 SIGKILL，
而 SIGKILL 不可捕獲 ⇒ 子進程必然結束 ⇒ 阻塞的 waitpid 必然返回，不存在死等。

4.2 gba_exit_to_list() 去掉提前放行

4.3 刪除 gba_reap_bg() 後臺收屍線程

阻塞 waitpid 必然拿到屍，兜底線程沒有存在意義。刪除後同時消除”兩處代碼都去 child_pid
賦值”的競態空間。

4.4 狀態結構體去掉 exiting 字段

gba_state_t 的 exiting 及 gba_launch() 裡對它的復位一併刪除，字段佈局回到與 fc_state_t 對齊。

4.5 gba_timer_cb() 畫面恢復回到單次 invalidate

4.6 文件頭註釋重寫

把”我們比 FC 更快”的敘述改成”刻意與 FC 完全一致，並說明為什麼不再追求更快“，
同時把兩輪失敗方案（SIGUSR1 握手 / 時間上限）作為反例留在註釋裡，防止後來者再走一遍。

5. 驗證方法與結果

5.1 代碼一致性核對（本地）

  • grep -n "exiting\|reaped\|reap_bg\|lv_refr_now\|SIGUSR1\|RELEASE_SIGNAL" →
    僅命中註釋內容，無任何代碼殘留；
  • gba_wait_thread() 與 fc_wait_thread() 逐行對照 → 結構、判據、恢復順序、順序註釋全部相同，
    僅 s_gba / s_fc 前綴與縮進不同。

5.2 構建與部署（設備端）

ssh_tools/gba_redeploy.py（不帶 --mini，只部署頁面 + 編譯 + 重啟）：

檢查項 結果
make -j2 MAKE_RC=0，error: 計數 = 0
二進制替換 ATOMIC_OK（編到 .tmp 再 mv -f，原子）
部署前在跑的遊戲 無
重啟後進程 lvgl_demo ×1 + lvgl_watchdog ×1，單實例，無殭屍

5.3 實機功能驗證（交由用戶）

  1. 桌面 → GBA 遊戲 → 選 ROM → 確認，進入遊戲；
  2. 按買單鍵退出 → 預期約半秒黑屏一閃後回到遊戲列表，退出鍵全程有效；
  3. 進入遊戲後停留 5 秒以上再退出（重點：驗證不再有”跑滿 N 秒被誤判”）→ 表現應與第 2 步相同；
  4. 再進一次並正常玩一段 → 退出，確認無殘留黑屏、列表可繼續操作；
  5. 對照 FC 遊戲：進入 → 退出，行為應與 GBA 表現一致（同為”半秒黑屏一閃”）。

6. 迴歸風險

風險 評估
退出比上一版慢約 400ms 已明確接受，這是與 FC 對齊的必然代價，也是唯一被驗證過的時序
單次 invalidate 是否夠用 FC 頁同樣只 invalidate 一次且長期正常；恢復時機現已與 FC 相同，判斷為足夠。若實機出現”退出後殘留遊戲畫面”，則說明 GBA 側 fb 清理與 FC 有差異，需從 miniretro_gba 的 fb_restore() 查，而不是再加連刷
阻塞 waitpid 會不會死等 不會：SIGKILL 不可捕獲，上游必然發出
pthread_create 失敗的極端分支 該分支（gba_launch 內）裡是 waitpid(pid, NULL, 0) 且未先 kill，理論上會阻塞到遊戲自行結束。FC 頁存在完全相同寫法，為保持逐行一致本次未改；屬極低概率路徑，如要修應兩側同時修
FC 頁 本次一行未改

7. 相關文件

文件 說明
lv_pages/gba_game_page.c 本次改動全部集中於此（退出路徑 + 結構體 + 文件頭註釋）
lv_pages/fc_game_page.c 參照基準，未改動
extern/miniretro/miniretro_gba GBA 專用前端，未改動
ssh_tools/gba_redeploy.py 部署腳本；本次順帶修正取 PID 方式（見下）
bugfix_20260923_11 上一環：前端分離、卡黑屏根因

附：部署腳本的一處修正

gba_redeploy.py 原先用 ps -o pid,args | grep 'lvgl_demo' 取 PID 再 kill -9。
該命令經由 sh -c 執行，承載它的 shell 自身命令行裡就含 lvgl_demo 字樣 →
被 grep 匹配 → 殺掉自己 → SSH 連接被重置（上一輪部署時就斷在這裡）。
現改為 ps -o pid,comm | awk '$2=="lvgl_demo"{print $1}'：comm 是進程名（不含參數），
承載 shell 的 comm 是 sh，不會自匹配。miniretro 系列改用 $2 ~ /^miniretro/ 前綴匹配。
