FM_daemon因SIGPIPE靜默退出

wlb
2026-09-22
bugfix, 收音机

bugfix_20260922_03 — FM daemon 無故消失，收音機頁永遠顯示”芯片 0000”

關聯提交：221fa7d

現象

fm_user_daemon 運行一段時間後無聲無息地消失（ps 裡找不到，socket 文件
/tmp/fm_ctl.sock 還在但 connect() 返回 Connection refused）。
收音機頁因此永遠顯示 芯片 0000、RDS 不可用、已關閉，所有按鈕點了沒反應。
日誌的最後幾行只有正常的 cmd='state' / cmd='rssi'，完全沒有崩潰信息。

影響範圍

  • 隻影響 FM 收音機功能（頁面 ↔ daemon 鏈路全斷）。
  • 不影響 lvgl_demo 主體：lvgl_demo 有自己的 /root/lvgl_watchdog.sh 保活，一直正常。
  • 影響所有依賴 /dev/fm 常開 fd 的功能：daemon 一死，/dev/fm 被 close 觸發
    fm_release（發 at+fm=12 並阻塞約 4s），FM 狀態丟失。

根因

對端已關閉的 socket 上做普通 write() 會觸發 SIGPIPE，其默認動作是終止進程。

daemon 的回寫函數原本是：

且 main() 裡沒有 signal(SIGPIPE, SIG_IGN)。

而客戶端（lvgl_demo 收音機頁）在”回覆寫出之前”斷開是常態：

  • 頁面 onDestroy/應用被 killall 時連接被關；
  • 頁面的 IO 工作線程對 rssi 命令設 6s 超時，但內核 GETRSSI 要 ~4s；
    頁面還會在超時後重連 → 舊連接被丟棄。

一旦發生，daemon 被 SIGPIPE 打死，沒有任何日誌（信號默認動作，不產生用戶態輸出）。

定位過程

  1. 先確認進程真的沒了、socket 是陳舊的（pidof 空、Connection refused）。
  2. 看 daemon 源碼的退出路徑：main() 裡 setup 之後的 for(;;) accept(...) 是死循環，
    **沒有任何主動 exit()**；各命令分支也沒有。→ 排除”邏輯自己退出”。
  3. 於是只剩”被信號殺死 / 段錯誤”。grep 信號與寫操作：
  4. 時間線吻合：每次”daemon 消失”都發生在我重啟 lvgl_demo 應用之後。
  5. 做對照實驗證明機制（ssh_tools/sigpipe_ctrl.c）：fork 兩個子進程，各自
    socketpair() 後關掉對端，A 組用裸 write()、B 組用 send(..., MSG_NOSIGNAL)： A 組完全沒有輸出 → 確實被 SIGPIPE 終止。 機制在本機得到證實。

解決辦法

兩處修改（ssh_tools/fm_user_daemon.c）：

  1. 統一 socket 寫函數，永不產生 SIGPIPE：
    • reply() 改用它；
    • wcnd_fm_open() 裡向 @wcnd 寫 "wcn FM-OPEN" 也改用它（同樣是對端可能已斷的 socket）。

另加保活看門狗 /root/fm_watchdog.sh（每 5 秒 pidof fm_user_daemon，不在就拉起，
模式與既有 /root/lvgl_watchdog.sh 一致），防禦 OOM/SIGKILL 等其它死法。

驗證

  • 迴歸測試（設備端 python3 /root/fm_sigpipe_test.py）：6 輪”連上 → 發 rssi
    （內核要 ~4s 才回）→ 0.15s 後立刻 close()“，正是原本必死的最壞時序。
    結果：6 輪全部存活，daemon pid 始終 6408 不變 → PASSED。
  • 對照實驗（上節 sigpipe_ctrl）：A 組靜默死亡 / B 組存活 → 反證修復必要且有效。
  • 重啟應用後重進收音機頁，頁面恢復顯示 RDS 可用 · 芯片 2341 · 收聽中。
  • 設備自行重啟後，/etc/local.d/zz_fm.start 自動把 daemon 拉起（日誌
    [fm] wcn FM-OPEN -> WCNBTWIFI-CMD OK、chipid=0x2341 rds=1、就緒，監聽 /tmp/fm_ctl.sock）。

經驗教訓

  1. 寫 socket 一律用 send(..., MSG_NOSIGNAL)，並在長駐進程開頭 signal(SIGPIPE, SIG_IGN)。
    SIGPIPE 是”靜默殺手”：不產生任何日誌，現象是”進程莫名消失”，
    極易被誤判為 OOM 或”自己退出了”。
  2. “沒有 exit() 但進程沒了” → 優先懷疑信號。 排查順序：
    代碼退出路徑 → 信號（SIGPIPE/SIGSEGV）→ 外部 SIGKILL/OOM。
  3. **長駐 ipc daemon 必須考慮”客戶端隨時可能在回覆前斷開”**，
    這在 UI 進程會被重啟的嵌入式場景裡是高頻事件，不是邊緣情況。
  4. 機制類結論要有對照實驗：光”改完好了”不算證明，要能展示”改之前必壞、改之後必好”。
  5. 每個長駐進程都應配保活看門狗；本項目已有 lvgl_watchdog.sh 的先例可照抄。
