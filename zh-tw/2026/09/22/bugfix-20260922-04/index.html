bugfix_20260922_04 — 桌面「FM 收音機」圖標渲染成空心方框

關聯提交：221fa7d

現象

在桌面新增「收音機」應用入口後，圖標位置、底色（暖磚紅 0xe6614f）、文字「收音機」
都正確，但圖標本身是一個空心方框（tofu），不是任何有意義的圖形。

影響範圍

  • 隻影響桌面「收音機」入口的圖標。
  • 其它已有應用圖標全部正常（它們用的都是字體裡確實存在的字形）。
  • 不影響收音機頁內部的功能與佈局。

根因

launcher_page.c 裡為 FM 選的圖標碼位在 lv_font_cn_16 中根本沒有對應字形：

LVGL 渲染時 lv_font_get_glyph_dsc() 返回 not-found，就畫成方框。
U+F519 屬於 FontAwesome 5.x 才加入的圖標，而本機中文字體
lv_font/font_cn.c（lv_font_cn_16）只覆蓋 FontAwesome 4.x 的老子集。

定位過程

  1. 項目規範 §3.4 明確要求：圖標可用性必須驗證字形存在，不能用”碼位區間覆蓋”或
    “看著像”來推斷    。桌面截圖裡 U+F519 是方框，與規範警告一致。
  2. 第一版探針 glyph_probe.c 只用了我記憶裡的碼位表，結果標籤對應關係是錯的
    （把 0xF050 當成 LV_SYMBOL_PREV、0xF0C9 當成 LV_SYMBOL_LIST）。
    → 教訓：不要用人工映射的碼位表去查字形。
  3. 重寫 glyph_probe2.c：直接用 LV_SYMBOL_* 宏本身做輸入，
    自己解 UTF-8 首字符得到碼位，徹底消除人工映射錯誤。實測 52 項裡
    有字形 46 / 缺 6，缺的正是 F519 / F2CE / F7C0 / F8CE / F130 / F09E。
  4. 再寫 glyph_sweep.c 掃 U+F000..U+F8FF 全區間，得到權威清單：共 60 個圖標。
    其中沒有任何”電臺 / 天線 / 電波”形狀 —— 所以不能靠”換一個更像的碼位”解決。
  5. 編譯 glyph_probe* 時踩到的坑：lv_font_cn_16 定義在應用源碼
    lv_font/font_cn.c 裡（不屬於 liblvgl.a），且靜態庫 liblvgl_thorvg.a
    含 C++ 目標文件 → **必須用 g++ 鏈接並直接帶上 app 已編好的
    build/lv_font/font_cn.o**： （用 gcc 會報 undefined reference to lv_font_cn_16 與一堆 std:: 未定義。）

解決辦法

從實測有字形的 60 個圖標裡，選語義最貼近”只能聽聲音的廣播設備”、且未被現有
應用佔用的 LV_SYMBOL_VOLUME_MAX（U+F028，喇叭帶聲波，18x16）：

（同時排查了現有 16 個應用的圖標占用，避免撞車：DIRECTORY/EDIT/AUDIO/VIDEO/KEYBOARD/
SETTINGS/WIFI/BLUETOOTH/IMAGE/LIST/HOME/REFRESH/POWER/TINT/FILE 均已佔用。）

驗證

  • 重新編譯部署後取桌面截圖：「收音機」圖標位置出現完整的喇叭圖形（有人眼在物理屏確認），
    不再是方框；焦點框也正確落在該格上。
  • 留檔圖：shots/radio_icon_fix_rgb.png（正確字節序）。

經驗教訓

  1. 圖標可用性只能靠 lv_font_get_glyph_dsc() 實證，不能靠碼位表或”FontAwesome 區間覆蓋”推斷。
    本項目已因此踩過一次（U+F519）和一次探針自擺烏龍（人工碼位映射錯）。
  2. 寫探針時要用”權威來源”本身做輸入（這裡是 LV_SYMBOL_* 宏），
    而不是自己轉錄一份映射表 —— 轉錄錯誤會讓探針本身失去可信度。
  3. 先確認”到底有沒有解法”再動手：掃描全區間後才知道這個字體根本沒有電臺形狀，
    否則會一直在”換哪個碼位”上浪費時間。
  4. 在這個項目裡編譯小探針要複用的是**應用已編好的 font_cn.o + g++**，
    不要試圖重新編譯 27MB 的 font_cn.c，也不要指望 liblvgl.a 裡有 CJK 字體。
