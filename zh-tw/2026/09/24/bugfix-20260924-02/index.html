bugfix_20260924_02 — 「切換桌面」橫屏菜單白屏卡死（transform 渲染路徑不可用）

關聯提交：2341fad

⚠️ 本文結論已被 bugfix_20260924_03 推翻：transform 在本機一直可用（fc_game_page.c 就是同一套用法）；
白屏真因是 **transform_pivot 未顯式設為 50%**（默認是對象左上角 → 1280x720 畫布繞左上角旋轉後整體轉出可視區）。
請以 03 為準；本文保留僅作“一次錯誤定性”的過程記錄。

  • 日期：2026-09-24
  • 影響範圍：lv_pages/launcher_page.c（新功能「切換桌面」→ 橫屏放大菜單）
  • 結論一句話：這個 LVGL 構建裡 transform（旋轉/縮放）渲染路徑不可用 —— 任何帶 transform 的對象整個不繪製；
    改為純 set_size 動畫後功能正常。

1. 現象與訴求

用戶反饋：在桌面點「切換桌面」後 白屏卡死。

只讀現場取證（ssh_tools/_tmp/dbg_white.sh）：

檢查項 結果
進程 lvgl_demo 存活，PPID=1，STAT=S
CPU 0%（top 顯示進程空閒）
日誌尾部 大量 [HW Key] code=115/116 與 [nav] key=19/20/27，無 segfault / assert / fatal
結論 不是崩潰、不是死循環 —— 是界面沒畫出來（渲染層問題）

2. 定位：先把設備救回來，再用「最小實驗」縮小變量

  1. 先回滾：lv_pages/launcher_page.c.bak_cover 還原 → make -j2 → 原子替換 → 重啟。
    日誌立即出現 [fb] flush ... px0=ffdff3ff/ffe0f3ff（桌面漸變底色），設備恢復可用。
  2. 再做最小實驗：臨時在 onCreate 末尾插入 launcher_set_cover(true)（自動進入菜單），
    這樣不必依賴按鍵就能穩定復現，並用 grab_screen.py 抓幀逐層判斷”誰沒畫出來”。

三次抓幀的結論遞進：

版本 抓幀結果 推斷
方案 A：容器 1280x720 + transform_rotation=900 整屏只剩父容器底色，容器和卡片全部不見 大容器旋轉被整體丟棄
方案 B 首版：容器不旋轉，卡片仍用 transform_scale 容器背景 + 頂部提示文字正常畫出，所有卡片消失 transform 與對象大小無關，只要帶 transform 就不畫
方案 B 修正版：零 transform，改 set_size 動畫 卡片、圖標、中文標題全部正常 根因確認

關鍵對照：同一個容器裡，”沒有 transform 的提示 label”畫得出來，”有 transform 的卡片”畫不出來 ——
變量被縮到只剩 transform 一項。

3. 根因

該 LVGL 構建（/root/lvgl_install 預編譯 liblvgl.a）的 transform 渲染路徑在運行期不可用。

  • 早先我用靜態符號法判斷”支持”：nm liblvgl.a 裡 lv_draw_sw_transform 在 T 段、
    lv_obj_set_style_transform_rotation / scale_x / scale_y 都在 → 結論”能鏈接、應該能畫”。
    這個判斷只證明符號存在，不證明運行正確。
  • 最強旁證其實一直襬在源碼裡：launcher_page.c 的 launcher_start_zoom() 開頭是
    (void)target; return; /* transform disabled */。git log -S 顯示它是 v1.0 初始提交就帶的 ——
    當時被解讀為”上游自己關掉了按下縮放效果”，實際含義是”這臺機器上 transform 畫不出來，所以關掉”。
    註釋裡的 “disabled” 是    證據    ，不是噪音。

4. 修復

lv_pages/launcher_page.c（補丁腳本 ssh_tools/_tmp/patch_cover3.py + patch_cover4.py + patch_cover5.py）：

  1. 棄用整屏旋轉方案（改為豎屏內橫向放大帶）：屏幕 720×1280，卡片橫向排列，
    選中項 1.5×、左右各 1.0×；參數 CARD=200 / GAP=250 / SEL=384 / SIDE=256，
    在 720 寬內正好 200 + 250 + 250 = 700 鋪滿，不重疊。
  2. cover_geom() 徹底不用 transform，改成尺寸動畫： cover_anim_cb 仍由一個 lv_anim 統一插值所有卡片的 cx 與 scale（320ms，ease_out）。
  3. 刪除 cell 上已無用的 transform_pivot_*。
  4. 進入菜單時**補一次”隱藏 root 其它子對象”**（ch2 != s_cover_root）：
    網格是用 tileview 在 onCreate 後段創建的，只在進入時隱藏一次不夠穩。

5. 驗證

  • 抓幀三連（outputs/cover_check4~6.png）：容器背景、頂部提示、中間放大卡片、兩側正常卡片、
    白色圖標、中文標題（任務管理 / 切換桌面 / 相機）全部正常。
  • 左右鍵導航：[cover] built n=19 cx=360 cy=576 後，按右鍵 11 次，選中項按預期逐個居中放大（截圖 cover_check5.png）。
  • 最終版（去掉臨時的自動進入）部署後，桌面漸變底色正常、無崩潰。

6. 經驗（反模式記錄）

  1. “符號存在 ≠ 能力可用”：nm 只能證明鏈接得過。涉及渲染/驅動能力時，必須抓一幀實際畫面，
    或者在最小對象上做一次實驗 —— 不要把靜態符號當成能力驗證的終點。
  2. 上游註釋要當證據讀：/* transform disabled */ 若早點當真，就能省掉一整輪白屏事故。
    遇到 “disabled / not supported / FIXME” 先問”他們為什麼關”。
  3. 排查要給變量做減法：本輪靠”臨時自動進入 + 抓幀”，把”按鍵路徑 / 焦點組 / 佈局 / 渲染”四條線
    縮到”transform 有 vs 無”一條，才定住根因。
  4. 故障先回滾：改動一多，第一動作是恢復到可用基線（源文件 .bak_* + 原子替換），
    再在安全前提下做實驗，避免用戶長時間面對壞畫面。
  5. USB 注入鍵驗證不了物理鍵路徑：/root/vhwkey2 走 usb_map，與物理鍵語義不同；
    Enter/ESC 的實際手感必須由人手驗（詳見 §7）。

7. 遺留

  • 進入菜單後按物理福利鍵（Enter）選中「切換桌面」應返回、按物理買單鍵（ESC）應返回 ——
    這兩條由用戶實機確認（USB 注入的 ENTER/ESC 在本輪測試中未產生預期效果，但注入語義與物理鍵不同，
    不能用它下結論）。
  • 卡片放大的只是色塊與整體尺寸，圖標符號字號不隨縮放變化（無更大字號的圖標字體，僅有 montserrat_24）；
    若需要”圖標也變大”，需再引入一檔大字號字體。
  • 每次進入菜單會打印一行 [cover] built n=.. cx=.. cy=..（診斷用，保留便於以後排查）。
